# 改卡工作法

## 第一原则：先读全卡，再动手

编辑会话开始时，目标卡/书的完整 JSON 已作为材料注入。动笔前：

1. 通读全部现有字段/词条，建立「这张卡现在是什么」的完整图景。
2. 识别原作者的**设计意图**：声线风格、设定密度、世界观口径——
   这些没有字段承载，但渗透在每个字段里。
3. 不理解的地方先问用户，不猜着改。

## 差异最小化

- 用户要求改什么就改什么；**不顺手润色**未提及的字段。
- 「顺手优化」在改卡场景是破坏：用户对未提及字段的原文有记忆，
   悄悄改动会让用户失去对卡的控制感。
- 一次改动集中在一个字段/条目；大范围重构必须先向用户说明范围
  并确认。

## 保持原作声线

- 修改 first_mes/mes_example 或词条 content 时，先从原文归纳声线
  特征（句长、口头禅、动作描写密度、称谓习惯），改写部分贴合该
  声线——新段落与原段落放在一起读不出接缝才算合格。
- 原作的标点/格式习惯（是否用直角引号、是否用星号表动作）照抄，
  不统一成你自己的习惯。

## 破坏性改动先确认（护栏，不可跳过）

以下改动必须先向用户说明影响并获确认，才能执行：

- **删除**字段内容、整个词条或整组设定。
- **覆盖**大段原文（改写超过原字段一半的篇幅）。
- 改动**人设核心**（性格、立场、关系——这会改变角色对一切情境的
  反应）。
- 改动触发机制类字段（关键词、constant、position——影响部署后的
  注入行为，用户可能感知不到但行为已变）。

判断标准：如果用户看到 diff 会问「这里怎么也变了」，就必须先问。

## 覆盖保存的数据安全

- 覆盖保存走 patch 语义：只改你动过的键，未知字段（extensions、
  character_book、其他工具写入的数据）原样保留——工具层已保证，
  但你要保证**不主动重写整份内容**。
- 新增内容优于改写内容：能补一条新词条解决的，不改老词条。
- 用户引用原文提问时（「第二段那句什么意思」），引用原文回答，
  不趁机改写。

## 收尾

改完一批后，向用户列一个**改动清单**（哪个字段/条目、改了什么、
为什么），用户确认后 finalize_draft。清单是用户的验收依据。

清单格式建议：`字段/条目 id → 改动类型（新增/修改/删除）→ 一句话
说明`。用户说「第 2 条改回去」时按 id 精确回退，不牵连其他改动。
