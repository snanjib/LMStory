> - LMStory-DOC-06B：中级模式视觉规范
>
> **v0.2.2 架构调整**（2026-07-30）：故事模式生成流程从原"四步生成（generating → extracting → retrieving → reviewing → summarizing；v0.2.2 阶段名重命名：drafting→generating、revising→reviewing）"调整为"检索前置生成 + 可选审查"。核心变化：
> - **检索前置**：extracting 阶段从 generating 之后移到 generating 之前，输入改为"用户当前消息（优先）+ 最近 n 轮对话"，关键词分类从 2 类扩展到 5 类（characters/items/locations/actions/plots，与记忆库结构对齐）
> - **generating 注入记忆**：生成阶段注入【世界设定】+【相关往事】，LLM 在掌握"规则"后再落笔
> - **审查可选**：`intermediate.reviewEnabled` 默认 false（生成即最终，3 次 LLM 调用；v0.2.2 重命名：`reviseEnabled`→`reviewEnabled`），用户可手动开启（4 次 LLM 调用，审查修正）
> - **CompactionPoint 引入**：达到 `contextBudget.compactionTriggerRatio`(0.5) 触发压缩，压缩摘要兼任宏摘要（废弃独立宏摘要阶段），作为稳定前缀提升 LLM 缓存命中
> - **检索扩容**：topK 3→12，新增 absolute_threshold(0.5)/relative_threshold(0.65)/key_entity_importance_threshold(4)/key_entity_max_inject(3) 四个检索参数
> - **会话级覆盖**：`chat_sessions` 新增 3 列（revise_enabled_override/recent_min_ratio_override/retrieval_ratio_override；DB 列名保留不变，Dart 字段名 `reviewEnabledOverride`）
>
> **本文档 §6 数据库设计已同步调整**：v0.2 仅新建 experiential_memories / memories_fts 两表；factual_memories 推迟到 v0.3；旧记忆表（working_memories 等）在 v0.2 不删除（项目未发布，dev 数据 disposable，v0.3 启动时再清理）。原计划的 memory_vectors 向量虚拟表因 sqlite-vec pub 包损坏废弃而移除，v0.2 向量检索改用纯 Dart 暴力检索。

### 1.2 依赖规则

| 规则 | 说明 | 示例 |
|------|------|------|

### 1.3 目标架构 vs 现有实现的偏差

> 以下偏差对应概要设计文档 AC-01 ~ AC-07，此处仅标注位置，详细迁移方案见各子系统设计文档。

| 偏差编号 | 位置 | 目标 | 现状 |
|---------|------|------|------|
| AC-01 | `HudRepository` 接口 | Domain 层 `hud/domain/repositories/` | Data 层 `hud/data/repositories/hud_repository_impl.dart` |
| AC-02 | `ToolExecutor` | Domain 层 UseCase | Presentation 层 `hud/presentation/tool_executor.dart` |
| AC-03 | `EmbeddingQueue` | Domain/Data 层 | Presentation 层 `tool_executor.dart` 内 |
| AC-04 | 双写协议 | 独立 UseCase 编排 | `HudRepositoryImpl.applyPatch` 内耦合 |
| AC-05 | `ChatControllerBase` | 拆分为编排层 + 子管理器 | 单类承担全部职责 |
| AC-07 | 记忆架构 | 事实类/经历类（HUD 为事实类记忆的只读视图） | 短期/长期/工作记忆 |
| AC-08 | 导航结构 | 侧边栏+主区域布局（MainLayout）+ HomePage 主界面 + 导航栈 | 2-Tab 底部导航（HomePage）— **v0.1 实际实现已修正** |

> **v0.1 实际实现差异（AC-08）**：原始设计使用 2-Tab 底部导航（HomePage：会话 Tab + 设置 Tab）。v0.1 实际实现采用「侧边栏 + 主内容区 + 导航栈」布局（MainLayout）：桌面端 240dp 侧边栏在左 + 主内容区；移动端侧边栏为 Drawer（75% 宽度），AppBar 含汉堡菜单按钮。侧边栏包含 logo、会话列表、新建会话按钮、返回主界面按钮、设置按钮。主内容区采用导航栈模型 `List<ChatSession?>`：栈顶为 null 时渲染 HomePage 主界面（含 App 标题/Logo、新建对话大按钮、最近会话列表、设置入口、高级模式预留开关），栈顶为 ChatSession 时渲染 ChatModePage。新建对话创建草稿会话（`__draft_` 前缀，不入库），首条消息发送时才入库。移动端返回键依次回退导航栈至主界面，主界面两次返回退出 app。

### 3.2 接口设计约束

| 约束 | 说明 |
|------|------|
| **接口定义在 Domain 层** | 所有 Repository 抽象接口定义在 `features/{name}/domain/repositories/`，实现在 Data 层 |
| **接口不依赖 Flutter** | Domain 层接口仅使用 Dart 核心类型，不导入 Flutter |
| **接口不暴露实现细节** | Repository 接口不暴露 drift 表类型、Dio 响应类型等 Data 层细节 |
| **异步优先** | 所有涉及 IO 的方法返回 `Future` 或 `Stream`，同步方法仅用于纯计算 |
| **错误不吞没** | 接口实现应将底层异常转换为 Domain 异常向上传播，禁止静默吞没 |

### 4.1 Simple 模式数据流（v0.1）

> **v0.1 实际实现差异**：原始设计中 SSE 流通过 `ChatRepository.streamChat()` 发起。
> v0.1 实际实现中 SSE 流由 Controller 直接通过 `HttpClient.streamPost()` + `SseParser.parse()` 管理。

```
┌──────────┐    ┌──────────────────┐    ┌──────────────────┐
│ 用户输入  │ →  │ ChatMode       │ →  │ HttpClient       │
│ ChatInput │    │ Controller       │    │ .streamPost()    │
└──────────┘    └────────┬─────────┘    └────────┬─────────┘
                         │                       │
                         │                       ↓
                         │              ┌──────────────────┐
                         │              │ SseParser        │
                         │              │ .parse(stream)   │
                         │              └────────┬─────────┘
                         │                       │
                ┌────────┴───────────┐           │
                │                    │           │
                ↓                    ↓           ↓
        ┌──────────────┐   ┌──────────────┐  ┌──────────────┐
        │ 流式文本更新  │   │ 消息持久化    │  │ SSE 事件流    │
        │ (State)      │   │ ChatRepo     │  │ TextDelta     │
        └──────────────┘   │ .addMessage()│  │ StreamEnd     │
                           └──────────────┘  │ StreamError   │
                                              └──────────────┘
```

**Simple 模式核心流程（v0.1 实际实现）**：

1. 用户输入 → `sendMessage` 入口 → `_compactionService.shouldCompact()` 预检阈值 → `_compressHistoryCore()` 流式压缩（占位摘要 → SSE 流式打字 → 落库，对标 ChatBox，在用户消息插入前触发）
2. 压缩完成（如需）→ Controller 创建 `ChatMessage`，持久化到 DB，更新状态
3. `_resolveSettings()` 解析运行时配置（内联方法，非独立 SettingsResolver）
4. `_httpClient.streamPost()` 发起 SSE 请求 → `_sseParser.parse()` 逐行解析
5. `_handleSseEvent()` 处理 SSE 事件 → `_handleTextDelta()` 更新消息列表
6. 流结束 → `_persistAssistantMessage()` 持久化助手消息

> 注：压缩时机对标 ChatBox 的阻塞式压缩——在 `sendMessage` 开头触发，确保上下文顺序为「摘要 → 用户消息 → AI 回复」。`contextWindow` 未知（null）时不触发自动压缩；LMStory 中 `contextWindow` 未知时使用默认值 96000（对标 ChatBox `DEFAULT_CONTEXT_WINDOW`）。

> **v0.2 多协议适配层接入（DOC-12 v1.1）**：步骤 4 的 SSE 请求构造与解析现由 `LlmRemoteDataSource` 委托给 `LlmAdapterFactory.getAdapter({protocol, baseUrl, modelId})` 完成：
> - 调用方（Controller）零感知：`LlmService` 接口不变
> - 适配器负责构造 URL/Header/Body（按协议差异，如 Anthropic 的 `x-api-key` + `system` 顶层字段、Gemini 的 `contents` + `generationConfig` 包裹）
> - 适配器负责解析 SSE 流（OpenAI `choices[0].delta` / Anthropic 6 事件状态机 / Gemini `candidates[0].content.parts`）
> - 底层 `RawSseChunkParser` 共享双换行切分逻辑，各协议 SSE 解析器在其之上实现协议特有事件状态机
> - **DeepSeek 端点自动路由（2026-07-28 新增）**：`openaiCompatible` 协议下，若 `DeepSeekAdapter.isDeepSeekEndpoint(baseUrl, modelId)` 判定为 DeepSeek 端点，自动路由到 `DeepSeekAdapter`（处理思考模式下 `tool_choice:"required"` 不支持 + 不支持 `parallel_tool_calls` 两项兼容性差异，详见 DOC-12 §5.4.2）
> - DeepSeek V4 `reasoning_content` 字段跨轮回传：助手消息持久化时写入 `chat_messages.reasoning_content` 列（schemaVersion=25 新增，DOC-12 §5.4.2），下一轮请求由 `OpenAiAdapter._convertMessage` 还原（`DeepSeekAdapter` 继承自 `OpenAiAdapter`，复用此还原逻辑）
> 详见 DOC-12 §2.1、§5.1、§5.3。

### 4.3 工作上下文组装协议（v0.2）

提供两种组装策略，通过 `prompt_assembly.strategy` 配置切换：

**缓存优先模式**（默认，`cache_first`）：稳定内容在前，对话原文在位置3（半稳定，部分缓存命中），状态面板在经历类记忆之前（先建立正确状态认知）。

```
[1] system: System Prompt
[2] system: 事实类记忆（世界书）
    ─── 缓存命中区 ───
[3] user/assistant × N: 最近 N 轮对话原文
    ─── 半稳定区 ───
[4] system: 当前状态面板（标签"绝对真理"）
[5] system: 检索到的经历类记忆（含冲突警告）
[6] user: 当前用户输入
    ─── 变动区域 ───
```

**语义优先模式**（`semantic_first`）：按信息权威性排列，状态面板紧跟事实类记忆。

```
[1] system: System Prompt
[2] system: 事实类记忆（世界书）
    ─── 缓存命中区 ───
[3] system: 当前状态面板（标签"绝对真理"）
[4] system: 检索到的经历类记忆（含冲突警告）
[5] user/assistant × N: 最近 N 轮对话原文
[6] user: 当前用户输入
    ─── 变动区域 ───
```

**冲突消解规则**：在经历类记忆中附加提示——"若其中的状态信息与当前面板冲突，必须以当前面板为准。"

## 5. 双模式架构设计

### 5.1 模式独立性原则

Simple 与 Advanced 是**独立模块**，不是同一模块的两种配置：

| 维度 | Simple 模式 | Advanced 模式 |
|------|------------|---------------|
| **产品定位** | 可自由配置的 AI 对话工具 | 角色扮演叙事引擎 |
| **Controller** | `ChatModeController` | `AdvancedChatController` |
| **Page** | `ChatModePage` | `AdvancedChatPage` |
| **会话卡片** | `SimpleSessionCard` | `AdvancedSessionCard` |
| **依赖模块** | Core + Settings + Templates | Core + Settings + Templates + Memory + HUD |
| **上下文组装** | 直接从 DB 加载最近 N 条 | PromptAssembler 四层协议 |
| **Tool Call** | 不支持 | 支持 `update_world` |
| **分支行为** | 重发覆盖（默认）/ 派生新分支 | 派生新分支 |

### 5.2 共享基类设计

> **v0.1 实际实现差异**：原始设计定义 `ChatControllerBase` 抽象基类，`ChatModeController` 和 `AdvancedChatController` 继承之。
> v0.1 实际实现中 `ChatModeController` 为直接 `StateNotifier<ChatModeState>`，不继承 `ChatControllerBase`。
> 以下为原始设计，标记为已废弃，保留供 v0.2 重构参考。

**向量检索方案**（纯 Dart 暴力检索，v0.2 定案）

> **方案变更**：原计划使用 `sqlite-vec` 扩展提供的 `memory_vectors` 虚拟表做 KNN 检索，但 pub 包 `sqlite_vec 0.1.7-alpha.3` 损坏废弃（`src/` 缺失 `sqlite-vec.c`，CMake 全平台构建失败）。v0.2 主方案改为**纯 Dart 暴力检索**：向量仅存 `experiential_memories.embedding` BLOB 单一数据源，检索时由 ExperienceRepositoryImpl 加载该 session 全部 `has_embedding=1` 的向量到内存，调用 `VectorEngine.batchSearch`（Core 层 Isolate 内余弦相似度）返回 topK。详见 DOC-08 §5.3、DOC-05-8 §9.12、DOC-09A-1 §3.4。

- **不再建 `memory_vectors` 表**：无独立向量索引表，无跨表同步开销，无事务一致性负担
- **性能**：1536 维 × 1000 条 ≈ 5-15ms（ARM64 Isolate），满足 Q-02 ≤50ms 目标；100% 召回率
- **维度**：embedding 维度取决于用户配置的 embedding 模型（384/768/1536），存为 BLOB（Float32List 小端字节序）
- **v0.3 升级路径**：待 vec1（SQLite 官方向量扩展，2026 年新出，IVFADC+OPQ 真 ANN）出现 Dart 绑定后，重新评估 SQL KNN 方案

### 6.5 数据库迁移策略

#### 设计原则

**v0.1 Schema 一次到位**：项目尚未发布，无用户数据需要保留。v0.1 的表结构直接采用设计文档定义的最终 Schema，避免后续破坏性迁移。当前代码中的旧 Schema（如 `parent_user_msg_id` 为 INTEGER、缺少 `message_id` 等）需在 v0.1 发布前修正。

#### onUpgrade 策略（2026-07-25 修订：增量迁移，不丢数据）

> **重要变更**（2026-07-25）：原 dev 阶段 onUpgrade 采用"覆盖式重建"策略（DROP 所有业务表后整体重建），但实际使用中用户反馈升级后已有数据全部丢失（会话、API Key、记忆等），这违背了用户的核心要求——**升级不丢数据，只扩展表结构**。
>
> **新策略**：任何 `from < schemaVersion` 升级时，onUpgrade 调用 [`repairSchema()`](#修复表结构功能2026-07-24-新增2026-07-25-更新至-schemaversion26) 做纯增量迁移：
> 1. `CREATE TABLE IF NOT EXISTS`：创建缺失的表
> 2. `ALTER TABLE ADD COLUMN`：补齐已存在表缺失的列（SQLite 限制：自动移除 NOT NULL 无 DEFAULT、UNIQUE、PRIMARY KEY 约束）
> 3. `CREATE INDEX IF NOT EXISTS`：重建索引
> 4. 重建 FTS5 虚拟表（如果不存在）
> 5. `PRAGMA user_version`：更新 schemaVersion 到最新
>
> **核心保证**：不修改已有列的类型/约束，不删除任何数据。所有用户数据（会话、消息、API 配置、记忆等）在升级后完整保留。
>
> **历史教训**：
> - 2026-07-21 前：逐版本 addColumn 策略，v21 因表不存在崩溃（SqliteException code 1: no such table）
> - 2026-07-21：改为"覆盖式重建"（DROP + CREATE），解决了崩溃但导致数据丢失
> - 2026-07-25：改为"增量迁移"（调用 `repairSchema()`），既不崩溃也不丢数据
>
> **代码位置**：`lib/features/chat/data/database/app_database.dart` `MigrationStrategy.onUpgrade`。
>
> 下方各版本的"dev 模式策略"说明保留作历史记录，实际 onUpgrade 行为以本节"增量迁移"策略为准。

#### 修复表结构功能（2026-07-24 新增，2026-07-25 更新至 schemaVersion=26）

**背景**：dev 阶段 schemaVersion 不断升级（v15→v26），用户需要在**不丢数据**的情况下修复表结构差异。2026-07-25 起，onUpgrade 也改为调用 `repairSchema()`，因此"修复表结构"功能与 onUpgrade 行为完全一致——都是纯增量迁移，不丢数据。

**双重入口**：
- **自动触发**：schemaVersion 升级时，drift 的 `onUpgrade` 回调自动调用 `repairSchema()`
- **手动触发**：设置 → 数据管理 → "修复表结构"卡片，用户可主动调用 `repairSchema()` 修复任何表结构差异

**功能入口**：设置 → 数据管理 → "修复表结构"卡片（位于"数据恢复"和"清除会话和消息"之间）

**技术实现**（`AppDatabase.repairSchema()`）：

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | `CREATE TABLE` | 创建缺失的表（用 `Migrator.createTable`，表已存在会跳过） |
| 2 | `ALTER TABLE ADD COLUMN` | 补齐已存在表缺失的列（用 `GenerationContext` + `writeColumnDefinition` 生成列定义） |
| 3 | `CREATE INDEX IF NOT EXISTS` | 重建索引（已存在会跳过） |
| 4 | 重建 FTS5 虚拟表 | `_createV16Tables()`（已存在会跳过） |
| 5 | `PRAGMA user_version` | 更新 schemaVersion 到最新 |

**SQLite ALTER TABLE ADD COLUMN 限制处理**：
- NOT NULL 无 DEFAULT → 移除 NOT NULL（降级为 nullable）
- NOT NULL 有 DEFAULT → 保留（SQLite 允许）
- UNIQUE → 移除
- PRIMARY KEY → 移除

**纯增量策略**：不修改已有列的类型/约束，不删除任何数据。

**UI 交互**：
- 二次确认对话框（提示用户先导出全量备份）
- 修复完成后展示详细报告（新建表列表 + 新增列列表 + schemaVersion）
- 无变更时提示"数据库表结构已是最新，无需修复"

**与 `recreateConversationTables()` 的区别**：

| 方法 | 策略 | 数据丢失 | 适用场景 |
|------|------|---------|---------|
| `recreateConversationTables()` | DROP + CREATE | **会丢数据** | 清除所有会话和消息 |
| `repairSchema()` | ALTER TABLE ADD COLUMN | **不丢数据** | 修复表结构差异 |

**代码位置**：
- `lib/features/chat/data/database/app_database.dart` - `repairSchema()` + 辅助方法
- `lib/features/chat/domain/repositories/chat_repository.dart` - 接口定义
- `lib/features/chat/data/repositories/chat_repository_impl.dart` - 实现
- `lib/features/settings/domain/services/data_management_service.dart` - `repairDatabaseSchema()`
- `lib/features/settings/presentation/pages/data_management_page.dart` - UI 卡片 + 确认对话框 + 结果展示
- `lib/features/settings/domain/entities/data_management_models.dart` - `SchemaRepairResult` 数据类

> **文件行数说明**：`app_database.dart` 在添加 `repairSchema()` 后达到 505 行，略超 500 行阈值。考虑到 `repairSchema()` 及其辅助方法（`_tableExists`、`_getTableColumns`、`_safeColumnDefForAlterTable`）共约 130 行，是一个完整的数据库维护功能模块，与 `AppDatabase` 类紧密耦合（需要访问 `allTables`、`createMigrator`、`customStatement`、`transaction` 等），拆分到 extension 会增加复杂度但不显著改善可读性。暂不拆分，如后续 `app_database.dart` 继续增长再考虑。

### 6.6 Web 平台存储方案（v0.2 dev-0.2-web 分支）

#### 背景

为参赛评委公网体验，新增 Web 平台支持。Web 平台无文件系统访问，原 `NativeDatabase`（基于 `dart:ffi` + `sqlite3_flutter_libs`）无法在浏览器运行，需切换为 `WasmDatabase`（基于 sqlite3.wasm + IndexedDB）。

#### 平台检测与存储分流

通过 Dart **条件导入**（conditional imports）实现平台分流，编译期决定加载哪个实现，无运行时开销：

```dart
// database_connection.dart（原生）
import 'dart:io';
import 'package:drift/native.dart';
import 'package:path_provider/path_provider.dart';
import 'package:path/path.dart' as p;

Future<QueryExecutor> createDatabaseExecutor() async {
  final dbFolder = await getApplicationDocumentsDirectory();
  final file = File(p.join(dbFolder.path, 'lmstory.db'));
  return NativeDatabase.createInBackground(file);
}

// database_connection_web.dart（Web）
import 'package:drift/wasm.dart';

Future<QueryExecutor> createDatabaseExecutor() async {
  final result = await WasmDatabase.open(
    databaseName: 'lmstory',
    sqlite3Uri: Uri.parse('sqlite3.wasm'),
    driftWorkerUri: Uri.parse('drift_worker.js'),
  );
  return result.resolvedExecutor;
}

// app_database.dart
import 'database_connection.dart'
    if (dart.library.html) 'database_connection_web.dart';
```

#### Web 资源文件

| 文件 | 位置 | 来源 | 说明 |
|------|------|------|------|
| `sqlite3.wasm` | `web/sqlite3.wasm` | drift pub 包内置 | SQLite 编译为 WebAssembly（706 KB） |
| `drift_worker.js` | `web/drift_worker.js` | `dart compile js` 编译 | drift Web Worker 脚本，运行数据库操作（354 KB） |

> 版本对齐：`sqlite3.wasm` 与 `drift_worker.js` 必须与 `pubspec.yaml` 中的 `drift` 版本一致（当前 2.28.2）。升级 drift 后需重新编译 worker。

#### 平台能力差异矩阵

| 能力 | 原生（Android/iOS/桌面） | Web |
|------|------------------------|-----|
| 数据库引擎 | `NativeDatabase`（FFI + SQLite） | `WasmDatabase`（WASM + IndexedDB） |
| API Key 存储 | `flutter_secure_storage`（Keychain/Keystore） | `flutter_secure_storage`（WebCrypto + IndexedDB，非硬件级） |
| 文件日志 | 写入 `getApplicationDocumentsDirectory()` | 跳过（仅加载日志级别配置） |
| 模型注册表缓存 | 文件缓存（7 天过期） | 仅内存缓存（刷新页面后失效） |
| 数据库文件大小查询 | `File.length()` | 返回 0（无法访问 IndexedDB 大小） |

#### 6.6.6 CORS 代理（第三方 API 跨域转发）

**问题背景**：浏览器环境下，直接调用 NVIDIA、OpenAI 等第三方 API 时，目标服务器不返回 `Access-Control-Allow-Origin` 头，浏览器拦截请求（CORS 策略），导致模型列表拉取、对话、embedding 等功能全部失败。

**解决方案**：通过同源代理转发请求。Web 平台时，所有外部 API 请求由部署服务器上的 `/api-proxy` 端点转发到目标 URL，服务器间通信不受 CORS 限制。

**前端注入点**：`ApiUrlResolver.resolve()` 是所有 API 请求 URL 的统一出口（模型列表、流式/非流式对话、embedding、模型测试均经过此方法）。Web 平台时，`_wrapWithProxyIfNeeded()` 自动将完整目标 URL 包装为 `/api-proxy?url=<编码后的URL>`。原生平台（Android/iOS/桌面）不经过代理，直接请求目标 URL。

**代理实现**：`tool/serve_web.py` 中的 `CoopProxyHandler` 同时处理静态文件服务和 CORS 代理转发。代理逻辑：
- 请求头白名单透传：仅 `Authorization`、`Content-Type`、`Accept`、`User-Agent`
- 响应头白名单透传：仅 `Content-Type`、`Content-Length`、`Cache-Control`、`ETag`
- 所有代理响应添加 `Access-Control-Allow-Origin: *`
- 支持 GET/POST/PUT/DELETE/OPTIONS 方法
- 错误处理：HTTPError 透传状态码、URLError 返回 502、其他异常返回 500

**SSE 流式说明**：代理使用 `Transfer-Encoding: chunked` 分块编码，分块读取上游响应（`resp.read(4096)`）并立即写入客户端连接（`wfile.flush()`），实现真正的流式转发。SSE 流式数据（如 LLM 打字效果）能实时到达浏览器，不会缓冲在代理内存中。多线程服务器（`ThreadingMixIn`）确保 SSE 长连接不会阻塞其他请求。

**Web 平台客户端流式实现**：仅服务器端流式转发不够——`package:http` 的 `BrowserClient` 基于 XMLHttpRequest（XHR），Chromium 浏览器会缓冲整个响应体，Dart 代码要等到响应完全接收才能拿到数据，导致 SSE 打字效果失效（表现为"一直转圈直到超时"）。为此，SSE 流式 HTTP 客户端采用条件导入平台分流：
- `lib/core/network/http_client.dart`：条件导入入口，导出 `HttpClient` 类和共享类型（`CancellationToken`、`CancelledException`）
- `lib/core/network/http_client_types.dart`：共享类型定义（跨平台复用）
- `lib/core/network/stream_post_native.dart`：原生平台实现，使用 `package:http`（dart:io HttpClient，真流式）
- `lib/core/network/stream_post_web.dart`：Web 平台实现，使用 `dart:html` 的 `HttpRequest` + `onProgress` 事件，每次进度回调时读取 `responseText` 的增量部分转发给 `StreamController`，规避 XHR 的响应缓冲

条件导入语法：`import 'stream_post_native.dart' if (dart.library.html) 'stream_post_web.dart'`，编译期 tree-shaking 确保各平台只编译对应实现。

**Web 平台后台中断判定**：Web 平台浏览器切标签页/最小化窗口不会真正暂停网络（SSE 流通常仍在工作），与移动端 App 被系统暂停不同。`MainLayout.didChangeAppLifecycleState` 在 Web 平台延迟 60 秒才检查卡死状态，避免切窗口误触发"后台生成已中断"提示。原生平台（Android/iOS）仍保持立即检查。

**Web 平台 Isolate 兼容**：`TokenCounter`（tiktoken 编码）和 `VectorEngine.batchSearch`（向量余弦相似度）在原生平台通过 `Isolate.run` 在后台线程执行以避免阻塞 UI。但**浏览器不支持 `dart:isolate`**，Web 平台调用 `Isolate.run` 会永久挂起（Future 永不完成），导致中级模式 generating 阶段（`buildGeneratingMessagesV2` 同步等待 token 计数；v0.2.2 重命名：drafting→generating、`buildDraftMessagesV2`→`buildGeneratingMessagesV2`）和 retrieving 阶段（向量检索）卡死。两处均通过 `kIsWeb` 判断平台分流：Web 平台直接在主线程同步计算（tiktoken 短文本 <1ms，向量检索 <1000 条时纯数学计算不会明显阻塞），原生平台继续走 Isolate。`TokenCounter` 在 Web 平台额外缓存 encoding 实例避免重复加载 BPE 表。

**安全说明**：代理仅允许 `http://` 和 `https://` 协议的 URL，防止 SSRF 攻击。API Key 通过 `Authorization` 头透传，代理不记录也不存储。

/// ChatSessionSettings（单一已解析类，所有字段非空）
class ChatSessionSettings {
  final String modelId;
  final String presetId;
  final String systemPrompt;
  final double temperature;
  final double topP;
  final int maxTokens;
  final bool autoCompaction;
  final double compactionThreshold;  // 百分比（0.4-0.9，默认 0.6），对标 ChatBox
  final bool streamEnabled;
}

/// 解析逻辑在 ConfigurationResolver.resolveSettings() 中完成（v0.1.1 重构后从 Controller 抽离）
/// 解析顺序：会话级设置 → 激活预设 → 第一个可用 preset → 用户覆盖 → 配置文件默认
Future<ChatSessionSettings> _resolveSettings() async {
  final session = state.session;
  final config = await _configLoader.load();
  final chatConfig = config.broadcastChat;

  // 1. 确定 presetId：会话级 > 激活预设 > 第一个可用 preset
  var presetId = session.presetId ?? '';
  if (presetId.isEmpty) {
    final activePresetId = await _presetRepository.getActivePresetId();
    if (activePresetId != null) presetId = activePresetId;
    else { /* fallback to first available preset */ }
  }

  // 2. 获取 API key（缓存到 _cachedApiKey）
  // 3. 确定 modelId：会话级 > 用户覆盖默认模型 > 配置文件默认
  // 4. 确定 autoCompaction：会话级 > 用户覆盖 > 配置文件默认

  return ChatSessionSettings(
    modelId: modelId,
    presetId: presetId,
    systemPrompt: session.systemPromptOverride ?? '',
    temperature: session.temperature ?? chatConfig.temperature,
    topP: session.topP ?? chatConfig.topP,
    maxTokens: session.maxTokens ?? chatConfig.maxTokens,
    autoCompaction: autoCompaction,
    compactionThreshold: (session.compactionThreshold ?? chatConfig.compactionThreshold).toDouble(),
    streamEnabled: session.streamEnabled ?? chatConfig.streamEnabled,
  );
}

| 故事模式·关键实体门槛 | `intermediate.retrieval.key_entity_importance_threshold` | 4 | v0.2.2 新增。importance >= 此值的实体无论检索分数都强制注入 |
| 故事模式·关键实体上限 | `intermediate.retrieval.key_entity_max_inject` | 3 | v0.2.2 新增。关键实体强制注入的最大数量 |

> **故事模式检索参数变更说明**（v0.2.2 架构调整）：原 `intermediate.retrieval.top_k` 为 3（v0.2，每条记忆信息密度高，3 条足够）。v0.2.2 调整为 12 的理由：12 条记忆约 1800-2400 token，加事实层约 3000-4000 token，在 128K 上下文下可承受；不直接拉到 15 是因为 LLM 对中间 system 消息的注意力有限，注入过多会稀释每条记忆的注意力权重。调高质量阈值到 0.5/0.65 抵消注意力稀释；关键实体强制注入（importance>=4 最多 3 个）避免关键角色因检索分数低被漏掉。

> **压缩阈值公式（对标 ChatBox `compaction-detector.ts`）**：
> ```
> availableWindow = max(contextWindow - 32000, floor(contextWindow × 0.5))
> thresholdTokens  = floor(availableWindow × compactionThreshold)
> isOverflow       = (currentTokens > thresholdTokens)
> ```
> - `compactionThreshold` 为百分比（0.4-0.9，默认 0.6），非绝对 token 数。
> - `contextWindow` 来源：模型缓存的 `contextWindow` 字段；未知（null）时不触发自动压缩。
> - LMStory 中 `contextWindow` 未知时使用默认值 96000（对标 ChatBox `DEFAULT_CONTEXT_WINDOW`）。
> - `BroadcastChatConfig.compactionThreshold` 类型为 `double`，默认值 0.6。

## 8. 安全设计

### 8.1 敏感信息保护

| 资产 | 保护措施 | 存储位置 |
|------|---------|---------|
| API Key | `flutter_secure_storage` 加密存储 | 平台 Keychain / Keystore |
| 用户对话 | SQLite 本地存储，无网络传输 | 应用沙箱 |
| 配置信息 | SharedPreferences 明文（不含敏感数据） | 应用沙箱 |

### 8.2 网络安全

| 措施 | 说明 |
|------|------|
| HTTPS 强制 | 所有 API 请求强制 HTTPS |
| API Key 不入日志 | 日志中禁止记录 API Key |
| Auth Interceptor | 请求拦截器注入 `Authorization: Bearer {key}`，Key 从安全存储动态读取 |
| 请求超时 | 默认 30s，可配置，防止无限等待 |

### 8.3 降级策略

| 场景 | 降级方案 |
|------|---------|
| SSE 连接中断 | 显示已接收内容 + 错误提示，支持重发 |
| API Key 无效 | 引导用户检查设置 |
| 网络不可用 | 提示离线状态，本地数据仍可浏览 |
| Embedding API 超时（v0.2） | 仅使用 FTS5 检索 |
| 记忆折叠 LLM 失败（v0.2） | 保留原事件不折叠，下次重试 |

## 9. 错误处理体系

### 9.1 异常分类

```
LMStoryException (abstract)
├── NetworkException
│   ├── TimeoutException
│   ├── ConnectionException
│   └── ApiException (statusCode + message)
├── DatabaseException
│   ├── QueryException
│   └── MigrationException
├── BusinessException
│   ├── SessionNotFoundException
│   ├── InvalidConfigurationException
│   └── ToolCallParseException
└── AuthException
    └── InvalidApiKeyException
```

### 9.2 错误传播规则

| 层 | 处理方式 |
|----|---------|
| **Core** | 抛出原始异常（NetworkException / DatabaseException） |
| **Data** | 捕获 Core 异常，转换为 Domain 异常，附加上下文信息 |
| **Domain** | UseCase 不捕获异常，向上传播 |
| **Presentation** | Controller 捕获异常，转换为用户友好提示，更新 State.error |
