## 1. 概述

### 1.1 文档背景

本文档定义 v0.2 交付的"中级模式"完整设计。

### 1.2 三档架构定位

LMStory 采用三档架构，覆盖不同质量/延迟/成本需求的用户：

| 维度 | Simple（v0.1） | 中级（v0.2） | Advanced（v0.3） |
|------|---------------|-------------|------------------|
| 核心机制 | 单次生成 | 检索前置+可选审查+经历检索 | Agent Loop |
| 经历层（事件日志） | ❌ | ✅ 语义检索 | ✅ 主动检索 |
| 事实层（当前状态） | ❌ | ❌ | ✅ 主动管理 |
| 状态冲突解决 | ❌ | ❌ | ✅ |
| 长期伏笔呼应 | ❌ | ⚠️ 靠经历检索 | ✅ 靠事实层 |
| 延迟 | 5-15s | 20-35s | 30-60s |
| 成本 | 1x | 3-4x | 3-10x |
| 产品定位 | 普通聊天 | "有记忆的聊天" | "严格状态管理的角色扮演" |

### 1.3 v0.2 交付范围

v0.2 **只交付中级模式**。Advanced 模式（Agent Loop、事实层、HUD、update_world）推迟到 v0.3。

中级模式的核心价值：让 AI 能"记住"之前发生过的事件，通过语义检索在后续对话中呼应历史。

### 1.4 与现有设计文档的关系

`doc/design/02_系统设计.md` 和 `03_子系统设计.md` 原有的 v0.2 设计内容（事实层 factual_memories、HUD 状态面板、update_world 工具、混合检索权重 0.5/0.3/0.2、PromptAssembler 预组装策略等）现归属于 **v0.3 Advanced 模式**。本文档定义的 v0.2 中级模式是独立子集，仅包含经历层 + 四步生成 + 语义检索。

v0.3 启动时，需基于本文档的解耦接口（第 7 节）扩展 Advanced 模式，并对 02/03 文档进行同步修订。

## 2. 核心流程

> 详细状态机、数据流、流式输出方案见 **DOC-09A-1 §1**。

### 2.1 每轮对话的高层流程（v0.2.2 检索前置 + 可选审查）

v0.2.2 架构调整后，每轮对话为 **7 步事务**（含 2 个可选阶段），核心改动是**检索前置**——extracting 前置到 generating 之前，generating 阶段直接注入【世界设定】+【相关往事】生成正文，避免"生成已偏离记忆后 reviewing 只能打补丁"的锚定效应。reviewing 改为可选（默认关闭），生成即最终。

```
用户发送消息
    │
    ▼
[可选·条件触发] compacting：CompactionPoint 压缩
    │   触发条件：总占用（基础上下文+检索区+历史）> contextWindow × compactionTriggerRatio（默认 0.5）
    │   压缩摘要兼任宏摘要，作为稳定前缀注入后续阶段（提升 LLM 缓存命中率）
    │   未触发则跳过，对用户透明
    ▼
请求1 extracting：提取 5 类检索关键词（结构化：工具调用/JSON）
    │   输入：用户当前消息（优先）+ 最近 5 轮对话（按距离递减）
    │   输出：{characters:[], items:[], locations:[], actions:[], plots:[]}
    ▼
本地 retrieving：5 路并行混合检索
    │   FTS5 3 路：characters/items/locations 精确匹配
    │   Vector 2 路：actions/plots 语义匹配
    │   关键实体强制注入：importance>=4 的实体无论检索分数都注入
    ▼
请求2 generating：生成正文，注入记忆 ★核心改造
    │   输入：角色提示词 + 压缩摘要（可选）+ 历史 + 【世界设定】+ 【相关往事】+ 用户消息
    │   输出：生成正文（已按记忆生成，纯文本）
    ▼
[可选·默认关闭] 请求3 reviewing：审查修正
    │   reviewEnabled=false（默认）→ 生成即最终，跳过 reviewing
    │   reviewEnabled=true → 复用 retrieving 结果，轻量修正（去 AI 味+事实矛盾检查）
    ▼
请求4 summarizing：提取事件摘要 + 事实 deltas（结构化：工具调用/JSON）
    │   输入：用户消息 + 回复正文（生成正文或审查后正文）+ 已知实体块
    │   输出：EventSummary（5W1E）+ FactsDelta
    ▼
本地 persisting（drift transaction 原子写入）
    - reply 写入 chat_messages
    - eventSummary 追加 experiential_memories（含 embedding BLOB 字段）
    - FactsDelta 写入 factual_entities + factual_attributes
    - 若本轮触发了压缩：压缩摘要写入 experiential_memories（memory_level=macro）+ compaction_points
    - FTS5 索引同步 memories_fts
```

| 步骤 | LLM 请求 | 输入 | 输出 | 输出形式 |
|------|---------|------|------|---------|
| 0 compacting（可选） | ✅ 条件触发 | 原文区对话历史 | 压缩摘要（剧情宏观骨架） | 纯文本（流式） |
| 1 extracting | ✅ | 用户当前消息 + 最近 5 轮对话 | `{characters:[], items:[], locations:[], actions:[], plots:[]}` | 结构化（工具调用/JSON） |
| 2 retrieving | ❌ 本地 | 5 类关键词（分路：characters/items/locations→FTS5，actions/plots→Vector） | topK=12 相关记忆列表 + 事实层实体快照 | — |
| 3 generating | ✅ | 角色提示词 + 压缩摘要（可选）+ 历史 + 【世界设定】+ 【相关往事】+ 用户消息 | 生成正文（已注入记忆） | 纯文本 |
| 4 reviewing（可选） | ✅ 默认关闭 | generating 同前缀 + 生成正文全文 + 审查后缀 | 回复正文 | 纯文本 |
| 5 summarizing | ✅ | 用户消息 + 回复正文 + 已知实体块 | `{what, when?, where?, who?, significance?, extra?, summary?, tags, importance, event_ended}`（5W1E，）+ FactsDelta | 结构化（工具调用/JSON） |
| 6 persisting | ❌ 本地 | 回复 + 事件摘要 + FactsDelta + 压缩摘要（可选） | DB 写入 | — |

> 步骤编号 0-6 对应状态机的 7 个阶段（compacting/extracting/retrieving/generating/reviewing/summarizing/persisting），其中 compacting/reviewing 为可选阶段。LLM 请求数：默认 3 次（extracting/generating/summarizing）；开启 reviewing 时 4 次；触发压缩时额外 +1 次。

**v0.2.2 核心改动总结**：

| 项 | v0.2.1 旧方案 | v0.2.2 新方案 |
|----|------|--------|
| 检索时机 | generating 之后 | **generating 之前** |
| 生成正文是否注入记忆 | 否 | **是** |
| 审查阶段 | 强制执行 | **可选，默认关闭** |
| extracting 输入 | 用户消息 + 生成正文 | **用户消息 + 最近 5 轮对话** |
| 关键词分类 | 2 类（entities/events） | **5 类**（characters/items/locations/actions/plots） |
| 关键词上限 | 总 5 个 | **每类 10 个，共 50 个** |
| 检索 topK | 3 | **12** |
| LLM 请求数（默认） | 4 次 | **3 次** |
| 压缩机制 | 无 | **CompactionPoint**（压缩摘要兼任宏摘要） |

**~~compact 降级~~**（2026-07-16 起已移除）：~~retrieving 结果为空或低质量（`skipReviseWhenEmptyRetrieval=true`）→ 跳过 revising，草稿即终稿 → 仍走 summarizing 生成摘要 → persisting。~~ v0.2.2 进一步修订：reviewing 改为可选（`reviewEnabled` 默认 false），与检索结果质量无关——生成已注入记忆，质量本身有保障。注入前质量过滤在 retrieving 阶段由 controller 完成（双阈值取严格：`finalScore >= absoluteThreshold(0.5) && finalScore >= maxScore × relativeThreshold(0.65)`）。详见 §6.1 与 DOC-09B §8.7。

**结构化输出降级链**（extracting/summarizing 专用）：工具调用 → JSON 模式 → 提示词约束+容错解析。文本步骤（compacting/generating/reviewing）输出纯文本无需结构化。详见 §4.2 与 DOC-09A-2 §6。

### 2.2 关键参数

- **请求次数**（v0.2.2 修订）：默认 3 次 LLM 调用（extracting/generating/summarizing）+ 1 次程序检索 + 1 次 embedding API（事件摘要向量化）。**开启 reviewing 时 +1 次 LLM 调用**（4 次）；**触发压缩时再 +1 次 LLM 调用 + 1 次 embedding API**（压缩摘要向量化，仅当总占用超 `contextWindow × compactionTriggerRatio` 时触发，多数轮次不会触发）。**宏摘要独立阶段已废弃**（v0.2.2：压缩摘要兼任宏摘要，不再有独立的 macroSummarizing 阶段）
- **延迟**：约 15-25 秒（默认 3 次 LLM 调用）；开启 reviewing 时 20-35 秒（4 次）；触发压缩时再增加约 5-8 秒
- **成本**：约 2-3x（默认 3 次调用，相对于 Simple）；开启 reviewing 时 3-4x
- **分步骤模型**（2026-07-12 新增；**2026-07-21 配置架构重构**修订；**2026-07-30 v0.2.2 修订**）：v0.2.2 流程的每个步骤可独立配置模型/供应商（`phase_models` 配置组）。简单任务（extracting 关键词提取、summarizing 摘要生成）可配置小模型降低成本，复杂任务（generating 生成正文）保留大模型保证叙事质量，reviewing（可选）配置与 generating 相同或更大模型。**故事模式不再有单一"默认模型"中间层**——配置优先级链简化为两层：**会话级 phase > 全局 phase**（都没配置时直接报错 E010（generating 阶段），其他阶段可降级复用 generating 阶段的 NamingConfig，不再回退到 Simple/broadcastChat）。仅拆分模型，不拆分 temperature/maxTokens 等参数。详见 DOC-09B §10.1 phase_models 组、§10.2 分步骤模型优先级链。
- **标题生成模型**（**2026-07-21 配置架构重构**新增）：新增 `common.title_model` 跨模式共享配置节点（preset_id + model_id 两字段），用于 Simple/Intermediate 模式的会话标题生成，独立于故事模式业务模型。`ConfigurationResolver.resolveTitleNamingConfig()`（无参数）从 `common.title_model` 全局配置读取；未配置时返回 null，调用方使用 `SessionTitleGenerator.fallbackTitle`（取用户首条消息前 20 字符）。详见 DOC-09B §10.1 common.title_model 配置组。
- **模型思考能力适配**（**2026-07-27 v2.12 新增；2026-07-30 v0.2.2 修订**）：故事模式 4 阶段独立判断模型是否支持 reasoning（`RoundContext` 拆分为 `generateSupportsReasoning` / `extractSupportsReasoning` / `reviewSupportsReasoning` / `summarizeSupportsReasoning` 4 字段），由 `ConfigurationResolver.resolvePhaseSupportsReasoning(session, phase)` 按各阶段实际模型查询 capabilities + `ModelCapabilityInferrer` 兜底推断。思考参数统一由 `ThinkingParamBuilder` 适配 6 套厂商原生格式（OpenAI/DeepSeek/Qwen3/GLM/Kimi/OpenRouter），Simple 模式和故事模式共用。**修复前**：单一 `supportsReasoning` 字段查的是 Simple 模式默认模型，故事模式 4 阶段模型脱节导致 `reasoningEffort` 永远为 null，思考参数完全不发送——尤其影响 reviewing 阶段"去 AI 味"+"审查生成"功能（§4.2 v2.6 审查机制依赖 reasoning 能力）。详见 DOC-12 §5.6。**v0.2.2 阶段 2-G 明确作用范围**：思考预算（reasoningEffort）仅作用于 generating（生成）和 reviewing（审查）阶段；extracting/summarizing/macroSummarizing 等结构化任务阶段强制禁用（`ReasoningEffort.disabled`），不消耗思考预算。
- **reviewing 可选化**（v0.2.2 新增）：`reviewEnabled` 默认 false（生成即最终），优先级链：会话级 `reviewEnabledOverride` > 全局 `reviewEnabled`（DB 列名保持 `revise_enabled_override`，Dart 字段名为 `reviewEnabledOverride`）。开启时复用 retrieving 阶段已检索到的【世界设定】+【相关往事】结果，不重新检索——检索 query 来自 extracting 阶段（基于用户消息 + 历史对话），与生成内容无关。详见 §4.2、DOC-09B §10.1。
- **上下文预算分配**（v0.2.2 新增）：`contextBudget` 配置组——`compactionTriggerRatio`（压缩触发线，固定 0.5，总占用达此线触发压缩）、`recentMinRatio`（原文区下限，null=动态计算：`max(0.10, 32000 / contextWindow)`）、`retrievalRatio`（检索区比例，固定 0.15）、`recentMinTokenTarget`（下限动态计算目标 token，默认 32000）。`outputReserve` / `dialogueBudgetRatio` 已废弃（@Deprecated），统一用 `maxTokens`。会话级覆盖 3 列：`revise_enabled_override` / `recent_min_ratio_override` / `retrieval_ratio_override`（DB 列名保持不变，Dart 字段对应 `reviewEnabledOverride` / `recentMinRatioOverride` / `retrievalRatioOverride`）。详见 §4.5、DOC-09B §10.1、DOC-13。

## 3. 检索策略

> 检索算法实现、查询构造、归一化、合并排序、边界条件、embedding 同步生成见 **DOC-09A-1 §3**。

### 3.1 FTS5+Vector 5 路并行混合检索（v0.2.2 修订）

中级模式采用 FTS5（全文检索）+ Vector（向量检索）**5 路并行**混合检索（v0.2.2 从原 2 路扩展为 5 路，与 5 类关键词分类对齐）：

| 通道 | 关键词类 | 检索方式 | 用途 |
|------|---------|---------|------|
| FTS5 通道 1 | characters | 精确匹配 | 角色名（含主角） |
| FTS5 通道 2 | items | 精确匹配 | 关键物品/道具名 |
| FTS5 通道 3 | locations | 精确匹配 | 出现场景/地点名 |
| Vector 通道 1 | actions | 语义匹配 | 角色动作/行为 |
| Vector 通道 2 | plots | 语义匹配 | 剧情事件/情节要点 |

- **5 路并行**：`Future.wait` 并发执行 5 路检索，任一通道失败自动降级（不影响其他通道）
- **合并**：对每个唯一 memoryId，按 `finalScore = fts5Score × 0.5 + vectorScore × 0.5` 加权排序，取 topK=12
- **关键实体强制注入**：`importance >= keyEntityImportanceThreshold`（默认 4）的实体无论检索分数都注入，最多 `keyEntityMaxInject`（默认 3）个，避免关键角色因检索分数低被漏掉
- **质量过滤**：双阈值取严格——`finalScore >= absoluteThreshold(0.5) && finalScore >= maxScore × relativeThreshold(0.65)`，全部不满足则【相关往事】区块省略

### 3.2 权重设计

中级模式权重简化为 **0.5/0.5**（FTS5 与 Vector 不分主次），避免过度设计。v0.3 高级模式在此基础上扩展 Temporal 维度，权重细化为 0.5/0.3/0.2。

### 3.3 关键事件加权（2026-07-16 起默认不生效）

原设计：importance ≥ 4 的关键事件，finalScore × 1.5（boost 倍数可配置）。

2026-07-16 修订后默认值不生效：`keyEventThreshold` 默认 999（实际无记忆可达此重要性阈值）、`keyEventBoost` 默认 1.0（不放大），与 `importanceWeight` 功能重叠故统一由 importance 加权承担。用户仍可通过配置恢复关键事件加权（设 `keyEventThreshold=4` + `keyEventBoost=1.5`）。详见 DOC-09A-1 §3.6 与 DOC-09B §10.1 retrieval 组。

> **v0.2.2 新增**：`keyEntityImportanceThreshold`（默认 4）+ `keyEntityMaxInject`（默认 3）——事实层关键实体强制注入机制，与上述经历层关键事件加权不同：关键实体是事实层（factual_entities）的二元判定（注入或不注入），关键事件是经历层（experiential_memories）的分数加权。详见 §3.6、DOC-09A-1 §3.11。

### 3.4 Embedding 方案

- **v0.2**：纯 API 方案，用户配置 OpenAI 兼容 embedding endpoint（`/v1/embeddings`）
- **v0.3+**：追加本地向量化作为可选项（ONNX Runtime + 量化小模型）

理由：API 成本极低（每轮约 $0.00001-0.00005）、质量高、Flutter 本地推理生态不成熟。

embedding 同步阻塞生成（extracting 阶段流结束后立即调用 actions/plots 关键词向量化供 retrieving 使用；summarizing 阶段流结束后立即调用事件摘要向量化供 persisting 使用），失败降级 `has_embedding=false`，详见 DOC-09A-1 §3.9。

**向量化对象**（v0.2，2026-07-19；v0.2.2 修订）：从原 `summary` 单字段改为 5W1E 6 字段拼接文本（带中文标签前缀），如 `"时间:修炼第三天·清晨 地点:青云山后山 人物:林川 事件:悟得青云功第一层 意义:修为突破的关键节点 额外:无"`。6 字段拼接后语义更丰富，向量化质量更高，FTS5 与 Vector 两路召回对齐。宏摘要（v0.2.2：压缩摘要兼任）仍按 `summary` 单字段向量化（5W1E 6 字段为空字符串，拼接后等于空文本兜底），不采用 5W1E 拆分以保留多轮聚合语义。详见 DOC-09C §1、DOC-09A-1 §3.9。

> **v0.2.2 retrieving 阶段查询向量化**：原方案对 events 类关键词整体向量化为单一 queryVector；v0.2.2 改为对 actions/plots 两类关键词分别向量化，产生 2 个 queryVector 走 Vector 通道 1/2，与 5 路并行检索对齐。

### 3.5 多粒度记忆检索（DOC-10 v1.1，schemaVersion=19 启用；v0.2.2 修订；v0.2.3 宏摘要重构）

> **设计动机**：原检索仅有"每轮一条微摘要"单一粒度，长对话中相邻轮次的微摘要常呈碎片化、信息空洞。多粒度记忆在 micro 层之上引入 macro 层（对若干相邻 micro 的聚合总结），让检索能优先召回"完整事件级"的高密度摘要。

> **v0.2.2 修订**：废弃独立 macroSummarizing 阶段，改为压缩摘要兼任宏摘要。

> **v0.2.3 重大修订**（2026-08-04，宏摘要重构）：压缩摘要与宏摘要**职责分离**。压缩时除生成累积式压缩摘要（-> 上下文注入）外，**并行生成分段宏摘要**（-> 记忆检索 + 记忆查看器）。分段宏摘要仅覆盖本次压缩新增轮次（非累积），importance=3，参与语义检索（正常权重，不额外加权）。宏摘要与微摘要**共存**（不再"保留 macro 丢弃 micro"去重）。检索输出中宏摘要标注为"段落摘要"，微摘要标注为"事件记忆"。首次压缩时压缩摘要兼作宏摘要（仅生成一个摘要）。详见 §4.5。

#### 双层结构（v0.2.3 修订）

| 层级 | 写入时机 | 内容 | importance | 检索参与 |
|------|---------|------|-----------|---------|
| micro（微摘要） | 每轮 summarizing 步骤产出一条 | 单轮事件摘要，append-only | LLM 输出（1-5） | 参与语义检索，finalScore × 1.0（基线），标注"事件记忆" |
| macro（分段宏摘要） | compacting 阶段触发压缩时写入 | 分段宏摘要（仅覆盖本次压缩新增轮次，非累积） | 3（v0.2.3 固定） | 参与语义检索，正常权重（不额外加权），标注"段落摘要" |

#### ~~双触发机制~~（v0.2.2 已废弃）

~~宏摘要生成在以下两种条件任一命中时触发~~（v0.2.2 废弃，改由 compacting 阶段触发）：

1. ~~**LLM 事件结束判断**（`event_end`）：extracting 步骤 LLM 输出 `event_ended=true`，标记当前事件结束 → 触发宏摘要生成~~
2. ~~**固定轮次兜底**（`round_limit`）：累计 `macroIntervalRounds`（默认 5）轮未生成宏摘要 → 强制触发，避免长期无宏摘要~~

**v0.2.3 触发机制**：分段宏摘要由 compacting 阶段触发--总占用（基础上下文+检索区+历史）> `contextWindow × compactionTriggerRatio`（默认 0.5）时触发 CompactionPoint 压缩，压缩时并行生成压缩摘要（累积式，-> 上下文注入）和分段宏摘要（分段式，-> 记忆检索 + 记忆查看器）。首次压缩时压缩摘要兼作分段宏摘要（仅生成一个摘要）。分段宏摘要写入 `experiential_memories`（`memory_level=macro`，`importance=3`）。

#### 宏摘要检索参与（v0.2.3 修订）

~~宏摘要优先召回（macroBoost）~~（v0.2.3 已移除）：原设计对 macro 记忆的 `finalScore` 乘以 `(1 + macroBoost)` 加权，v0.2.3 移除该加权机制。

**v0.2.3 新方案**：分段宏摘要参与语义检索，**正常权重**（不额外加权）。分段宏摘要 importance=3，与微摘要（importance 1-5）在同一 finalScore 排序中竞争，不享受 boost 加权。分段宏摘要在检索输出中标注为"段落摘要"，微摘要标注为"事件记忆"，让 LLM 区分两类记忆的粒度。

> **设计理由**：分段宏摘要覆盖本次压缩新增轮次的剧情段落，与微摘要（单轮事件）粒度不同但互补。两者共存于检索结果中，LLM 可同时获得"段落级"和"事件级"的参考信息。不再额外加权，让 finalScore 自然排序--分段宏摘要的信息密度优势通过 importance 加权（importance=3 贡献 `3/5 × importanceWeight`）自然体现，无需单独 boost。

#### 多粒度共存（v0.2.3 修订，原"多粒度去重"）

~~多粒度去重（DOC-10 §5.3）~~（v0.2.3 已移除）：原设计在同一事件的 macro 和 micro 都被召回时**保留 macro、丢弃 micro**，通过 `parentEventIds` 字段关联去重。v0.2.3 移除去重逻辑。

**v0.2.3 新方案**：宏摘要与微摘要**共存**--分段宏摘要和微摘要各自独立注入检索结果，不做去重。分段宏摘要标注为"段落摘要"，微摘要标注为"事件记忆"，两者粒度不同但互补，LLM 可同时获得段落级和事件级的参考信息。

#### 配置项（v0.2.3 修订）

**v0.2.3 配置变更**：`macro_summary` 配置组（含 `macroBoostEnabled` / `macroBoost` / `macroIntervalRounds` / `macroSummaryEnabled`）已移除。分段宏摘要由 compacting 阶段触发，不再需要独立配置组。`microVectorizeThreshold` 从原 `MacroSummaryConfig` 移至 `RetrievalConfig`（详见 DOC-09B §10.1 retrieval 组）。分段宏摘要 importance 固定为 3，`importanceWeight` 加权正常生效（`3/5 × importanceWeight`）。

#### 检索注入格式（v0.2，2026-07-19）

注入 reviewing 步骤的【相关往事】区块格式从单行 summary 改为**多行结构化 5W1E 字段**，由 `IntermediateContextBuilder._formatMemories` + `_formatSingleMemory` 渲染。每条记忆独立成块，按字段非空情况展开为多行：

```
【相关往事】
[3轮前·重要性4]
· 何事：勇者斩杀了巨龙
· 何时：战斗结束时
· 何地：火山口
· 何人：勇者与巨龙
· 为何重要：获得了关键道具
· 补充：巨龙临死前留下一句预言
```

**设计原则**：每条记忆独立成块用空行分隔（提升 LLM 注意力分配）；仅展示非空字段（避免空行污染）；字段标签用中文（与提示词字段说明一致）；所有 5W1E 字段都为空时（旧数据兼容）回退使用 `summary` 或 `displayText` 单行展示。

**多行结构化的理由**：单行 summary 在剧情密集场景下信息密度不足，5W1E 多行结构让 LLM 更易识别时间/地点/人物等关键要素的对应关系，提升 reviewing 阶段的引用准确度。

> 注入前质量过滤（双阈值取严格：`finalScore >= 0.4 && finalScore >= maxScore × 0.6`）在 `_formatMemories` 中完成（见 §6.1、DOC-09A-1 §3.2/§3.6）。当全部记忆都不满足阈值时，【相关往事】区块省略，reviewing 只做润色。v0.2.3：多粒度去重已移除，分段宏摘要与微摘要共存于检索结果。

### 3.6 事实层检索与注入（DOC-11 中间方案，schemaVersion=22 启用）

> **设计动机**：长对话后 LLM 写错角色品种、性别、年龄，多实例串台（两只狗的 skills 归属混乱），用户明确改名后 LLM 仍用旧名。根本原因：设定信息从未被结构化提取，LLM 每轮只能从对话历史"临时记忆"。

> **方案定位**：v0.2 中级模式提前落地事实层子集——实体+属性双表 + FactsDelta 协议 + 三重防护 + 5 层健康度防护，但不含 v0.3 的 Agent Loop / HUD / state_snapshots / update_world。详见 `doc/design/11_事实层中间方案设计.md`。

#### 数据结构（实体+属性双表）

| 表 | 用途 | schemaVersion |
|----|------|---------------|
| `factual_entities` | 实体表（角色/宠物/NPC/地点/物品），每实体一条记录 | 22 新增 |
| `factual_attributes` | 属性表，每属性一条记录（用 entityId 隔离同名属性，杜绝串台） | 22 新增 |
| `factual_memory_history` | 审计日志（CREATE/UPDATE/APPEND/REMOVE/ARCHIVE 全量记录） | 22 新增 |

#### 检索流程（retrieving 阶段，纯本地无 LLM）

`FactContextBuilder.buildFactBlock` 在 retrieving 阶段执行：
1. 加载关键实体（`importance >= keyEntityImportanceThreshold`，强制注入）
2. 按 `keywords.entities` 匹配相关实体（`primaryName` 精确匹配 OR `aliases` 数组包含）
3. 合并去重，最多 `injectionMaxEntities` 个（关键实体优先，关键词命中次之）
4. 批量加载这些实体的所有属性
5. 按实体类型分组（角色/宠物/NPC/地点/物品）格式化文本

> **与经历层检索的差异**：经历层用 FTS5+Vector 混合检索（基于 score 排序）；事实层用名字匹配+重要性筛选（二元判定：注入或不注入，无 score）。理由：事实层是"当前世界状态"快照，全部注入即可。

#### 注入位置（reviewing 阶段）

`IntermediateContextBuilder.buildReviewMessagesV2` 采用方案C：前缀与 generating 完全一致（角色提示词 + 压缩摘要 + 历史 + 【世界设定】 + 【相关往事】 + 当前用户消息），末尾追加一条 user 消息（含审查后缀 + 生成正文全文，用 `--审查提示词--` / `--生成内容--` 标记分隔）。详见 DOC-13 §7.1。

#### 写入流程（summarizing 阶段，双工具并行调用）

`SummarizePhaseHandler` 在 summarizing 阶段并行调用 `extract_event_summary` + `extract_facts` 两个工具，由 LLM 一次性产出事件摘要 + 事实变更 deltas。`FactApplier.applyDeltas` 在 persisting 事务内应用 deltas（与经历层 persisting 同事务，DOC-11 §8.2 原子性保证）。

> **DeepSeek 端点的兜底补调（2026-07-28 新增）**：DeepSeek 官方 API 不支持 `parallel_tool_calls`（仅支持串行调用），`DeepSeekAdapter` 会跳过 `parallel_tool_calls` 字段，导致 LLM 在单次响应中只调用一个工具（如只调 `extract_event_summary` 跳过 `extract_facts`）。为此 `SummarizePhaseHandler._runSingleToolCall` 实现兜底补调逻辑：检测 LLM 响应中只调用了一个工具时，自动追加调用缺失的另一个工具，保证两个工具都被执行。其他端点（OpenAI/OpenRouter 等）走 `parallel_tool_calls:true` 路径，由 LLM 在单次响应内并行调用两个工具，无需兜底。详见 DOC-12 §5.4.2。

**三重防护**（DOC-11 §7.1）：
1. 提示词约束（在 `kExtractFactsToolPrompt` 中明确"经历≠事实"+ 示例对比）
2. 冲突检测（key 已存在 + 值真的不同才允许修改）
3. 重要性阈值（importance>=4 的关键属性需 confidence>=4 才允许修改）

**5 层健康度防护**（DOC-11 §7.4）：
1. 属性 schema 白名单（每种实体类型预定义 attrKey 集合）
2. 提示词约束（临时状态≠事实）
3. 系统级去重（精确+语义相似度 Levenshtein + 包含关系检测）
4. 更新频率限制（3 轮 2 次）
5. 属性值长度上限（200 字）

#### 失败降级

事实层失败不阻塞对话：`FactContextBuilder.buildFactBlock` 异常时返回空结果；`FactApplier.applyDeltas` 异常时由外层事务回滚整轮 persisting（DOC-11 §8.3，绝不牺牲一致性）。详见 DOC-09A-2 失败处理、DOC-09C §1 时序。

#### 配置项（详见 DOC-09D）

> **命名规范**（2026-07-20 修正）：JSON 配置文件用下划线命名（`injection_max_entities`），Dart 代码用驼峰命名（`injectionMaxEntities`）。下列示例与 `assets/configs/default_config.json` 保持一致。

```json

    "factual": {
      "enabled": true,
      "key_entity_importance_threshold": 4,
      "injection_max_entities": 20,
      "modify_confidence_threshold": 4,

    }
  }
```

## 4. 上下文组装

> n 值定义、token 预算控制、多级缩减策略、两套 prompt 完整结构见 **DOC-09A-2 §4**。

### 4.1 n 值（最近几轮对话）

复用 Simple 模式的 `maxContextMessages` 配置项。NULL = 无限制，由 token 预算控制兜底。本质与 Simple 模式相同——上下文可计算，只是拼接内容不同。

> **v0.2.2 阶段 2-F 更新**：故事模式引入 CompactionPoint 压缩机制后，原文区由 `recentMinRatio` + `compactionTriggerRatio` 动态控制，不再需要"最近 n 轮原文"的硬性消息数截断。`IntermediateContextBuilder` 和控制器不再读取 `maxContextMessages`，本节 n 值机制仅在 Simple 模式生效。`ChatSession` 实体字段保留（Simple 模式仍使用）。

### 4.2 四步 System Prompt

四步生成后，每个 LLM 请求只做一件事，需要四套差异后缀（共享同一角色设定前缀）：

**generating（生成版）**：
- 角色设定 + 创作指引（共享前缀）
- 任务说明：生成正文
- 输出格式：纯文本（无 JSON/标记）

**extracting（关键词提取版）**：
- 任务说明：从生成正文提取检索关键词
- 输出格式：`{entities:[], events:[]}`（工具调用优先，降级 JSON）

**reviewing（审查版）**：
- 角色设定 + 创作指引（与生成版共享）
- 任务说明：基于检索经历审查修正生成正文
- 输出格式：纯文本（无 JSON/标记）
- **消息结构**（2026-07-13 修订 v2）：生成正文以 `system` 角色注入（加
  `generatedInjectionPrefix` 前缀标注"待审查"），用户输入放在生成正文前，最后一条
  `user` 消息为审查请求（"请基于以上生成正文与相关往事，先审查生成正文的事实一致性、
  叙事质量和AI味，再生成最终回复…"），聚焦模型注意力于审查任务。详见
  DOC-09A-2 §4.6。
- **2026-07-19 修订（v2.15）**：删除原"允许原样输出"暗示（原 user 消息文本 +
  system prompt 同义明文构成三重暗示，导致 LLM 经常原样输出生成正文）。新提示词
  （`kReviewingSuffixPromptV2`）改为两步结构：(1) 在 reasoning tokens 中完成生成正文
  审查（事实一致性 / 叙事质量 / AI 味集群清单 8 项，参考 humanizer-main 项目），
  (2) 基于审查结果生成回复。审查依赖 reasoning 能力，配套硬约束（段落数量守恒 +
  情节要点守恒）与集群原则（防过度修正）。详见 DOC-09A-2 §4.6 v2.15。

**summarizing（摘要版）**：
- 任务说明：生成本轮事件摘要（5W1E 多字段结构，v0.2）
- 输出格式：`{what, when?, where?, who?, significance?, extra?, summary?, tags, importance, event_ended}`（工具调用优先，降级 JSON）
  - `what` 必填（事件，最小可检索单元）
  - `when`/`where`/`who`/`significance`/`extra` 可选（5W1E 其余 5 字段，按场景灵活，缺失字段宁可省略不硬凑）
  - `summary` 降级为可选（向后兼容字段，宏摘要继续使用 summary，单事件优先使用 5W1E 6 字段）
  - `tags`/`importance`/`event_ended` 必填（元数据）
- 提示词常量：`kExtractSummaryToolPrompt` 重写为 5W1E 多字段提取（含 6 字段说明 + 通用性原则 + JSON 输出示例 + 旧 summary 字段向后兼容说明），工具定义 `kExtractSummaryToolDefinition.parameters` 改为 5W1E 多字段（`required = ['what', 'tags', 'importance', 'event_ended']`，`additionalProperties: false` 保持 OpenAI strict 模式兼容）。详见 DOC-09A-2 §6.10.2、DOC-09B §8.3。

> **提示词白盒化**（v2.0 四步重构修订）：原"两步生成"的 9 段可编辑提示词（分隔标记版 + JSON 兜底版）已重构为四步版本。文本步骤（generating/reviewing）输出纯文本无需结构化；结构化步骤（extracting/summarizing）使用工具调用优先 + JSON 降级的同一提示词（兼容两种输出方式）。由 `PromptsConfig`（`core/config/intermediate_config.dart`）承载：
> - `defaultRolePrompt`（共享前缀，会话/全局 systemPrompt 为空时使用）
> - `generatingSuffixV2`（generating 差异后缀：纯文本生成正文）
> - `reviewingSuffixV2`（reviewing 差异后缀：纯文本回复）
> - `extractKeywordsPrompt`（extracting 系统提示：兼容工具调用与 JSON 降级）
> - `extractSummaryPrompt`（summarizing 系统提示：兼容工具调用与 JSON 降级，compact 降级复用）
> - `generatedInjectionPrefix` / `memoriesInjectionTitle`（生成正文/往事注入消息前缀）
>
> 缺省值取自 `intermediate_prompts_v2.dart` 常量。旧两步版提示词（`intermediate_prompts.dart` 的 `draftSuffix`/`reviseSuffix`/`compactReviseSuffix` 及其 Json 变体）标注 `@Deprecated`，保留常量供 `fromJson` 兼容旧配置，将在正式发版时移除。用户可通过「故事模式设置 → 提示词模板」页面逐段查看与编辑（覆盖 key 前缀 `intermediate.prompts.*`）。详见 DOC-09B §10.1 prompts 组、§10.4 提示词编辑 UI。

### 4.3 缓存友好的拼接顺序

**核心原则**：稳定内容前置，变化内容后置。

为提升 prompt 缓存命中率，system_prompt 拆分为"共享前缀"+"差异后缀"：

```
[共享前缀 - generating 和 reviewing 相同]
角色设定 + 创作指引

[generating 差异后缀]
任务：生成正文
输出格式：纯文本

[reviewing 差异后缀]
任务：基于检索经历审查修正生成正文
输出格式：纯文本
```

extracting/summarizing 步骤的输入是上一阶段的固定产出（生成正文/回复正文），作为独立 system 消息注入，system prompt 本身（`extractKeywordsPrompt`/`extractSummaryPrompt`）稳定不变，缓存友好。

**缓存命中率预期**：约 40-60%（低于 Simple 模式的 70-80%，因多了检索经历变量）。

### 4.4 模板系统扩展

现有模板系统需扩展支持：
1. **prompt 分段**：一个模板可定义"共享前缀"+"差异后缀"
2. **变量替换**：`{{character}}`、`{{retrieved_memories}}` 等
3. **拼接顺序控制**：稳定前置，变化后置

### 4.5 压缩机制（v0.2.2 引入 CompactionPoint）

~~中级模式**不使用 CompactionPoint**（与 Simple 模式的核心差异）。经历记忆（experiential_memories）替代长期记忆功能，避免摘要与事件摘要内容重叠。上下文超限时通过 token 预算控制多级缩减处理。~~

**v0.2.2 修订**（2026-07-30）：中级模式**引入 CompactionPoint** 压缩机制，解决长对话滑动窗口导致 prefix caching 完全不命中、计费翻倍问题。

#### 触发条件

总占用（基础上下文 + 检索区 + 历史）> `contextWindow × compactionTriggerRatio`（默认 0.5）时触发压缩。等价于：历史 > `contextWindow × compactionTriggerRatio - 基础上下文 - 检索区`。基于"总占用"而非"纯历史"自动适应固定开销，压缩线永远可达，避免死循环。`outputReserve` 已废弃（@Deprecated），可用窗口统一为 `contextWindow - maxTokens`（仅作辅助参考，不再参与触发判定）。详见 DOC-13 §5.1。

#### 压缩流程

```
原文涨到上限（50%）→ 触发 compacting 阶段 → LLM 流式压缩旧对话为剧情宏观骨架摘要
  → 压缩到下限（动态，约 32K token）→ 继续对话
压缩量 = 上限 - 下限（128K 模型约 16K token，1M 模型约 452K token）
```

#### 压缩摘要与宏摘要职责分离（v0.2.3 修订，原"双重职责"）

~~双重职责~~（v0.2.3 已修订）：原设计压缩摘要兼任宏摘要（一个摘要承担两个职责），v0.2.3 改为**职责分离**--压缩时生成两个独立摘要：

1. **压缩摘要**（累积式）：作为 system 消息注入 generating/reviewing prompt（紧跟角色提示词之后），生成后到下次压缩前完全不变，提升 LLM 缓存命中率（缓存命中区从 ~500 token 扩大到 ~5000 token，扩大 3-6 倍）。累积式--每次压缩在上一次压缩摘要基础上追加新内容。
2. **分段宏摘要**（分段式）：写入 `experiential_memories`（`memory_level=macro`，`importance=3`），参与语义检索，在记忆查看器中展示。分段式--每次压缩仅覆盖本次压缩新增轮次（非累积），独立成段。

**首次压缩的特殊处理**：首次压缩时无历史压缩摘要，压缩摘要兼作分段宏摘要（仅生成一个摘要，同时用于上下文注入和记忆检索）。后续压缩时并行生成两个摘要（两个 LLM 调用或单次调用双输出）。

**并行生成设计**：后续压缩时，压缩摘要和分段宏摘要通过并行 LLM 调用生成（或单次调用同时输出两个摘要），互不依赖。压缩摘要关注"对话流向的宏观骨架"（累积式），分段宏摘要关注"本次压缩新增轮次的剧情段落"（分段式）。

#### 四层信息架构（v0.2.3 修订，原"三层信息架构"）

| 机制 | 定位 | 内容 | 粒度 | 去向 |
|------|------|------|------|------|
| **压缩摘要** | "对话流向"的宏观骨架（累积式） | 主要事件时间线、角色出场、剧情阶段、关键转折 | 粗（骨架） | 上下文注入（稳定前缀） |
| **分段宏摘要** | "本次压缩段落"的剧情总结（分段式） | 本次压缩新增轮次的剧情段落摘要 | 中（段落） | 记忆检索 + 记忆查看器（v0.2.3 新增） |
| **经历检索** | "相关事件"的细节参考 | 5W1E 事件级细节、实体属性快照 | 细（血肉） | 记忆检索（标注"事件记忆"） |
| **最近对话原文** | "氛围语气"的载体 | 具体对话、细节描写、角色心理 | 原文（最细） | 历史区 |

#### generating prompt 结构（v0.2.2 新）

| 顺序 | role | 内容 | 稳定性 | 缓存命中 |
|------|------|------|--------|---------|
| 1 | `system` | 角色提示词 | 稳定 | ✅ |
| 2 | `system` ★ | **压缩摘要**（稳定前缀，v0.2.3：不再兼任宏摘要） | 稳定（下次压缩前不变） | ✅ |
| 3..n | `user/assistant` | 最近对话原文（动态百分比保留） | 半稳定（旧消息不变，新消息追加末尾） | 部分命中（旧部分） |
| n+1 | `system` ★ | 记忆引导语 + 【世界设定】+ 【相关往事】 | 动态 | ❌ |
| n+2 | `user` | 当前用户消息 | 动态 | ❌ |

> **v0.2.2 上下文机制重构**（DOC-13）：记忆块（世界设定 + 相关往事）从历史前移到历史后，旧历史消息能命中缓存（原记忆块在历史前破坏全部缓存）。缓存命中区从"只有角色提示词"扩大到"角色提示词 + 压缩摘要 + 旧历史消息"。

#### 配置项（contextBudget 组）

```json
{
  "intermediate": {
    "contextBudget": {
      "compactionTriggerRatio": 0.5,
      "recentMinRatio": null,
      "retrievalRatio": 0.15,
      "recentMinTokenTarget": 32000
    }
  }
}
```

| 字段 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| `compactionTriggerRatio` | double | 0.5 | 压缩触发线（固定，UI 不允许修改）。总占用达 `contextWindow × compactionTriggerRatio` 触发压缩 |
| `recentMinRatio` | double? | null | 原文区下限百分比。null=动态计算，非 null=用户自定义 |
| `retrievalRatio` | double | 0.15 | 检索区比例 |
| `recentMinTokenTarget` | int | 32000 | 下限动态计算的目标 token 数 |

**下限动态计算逻辑**（当 `recentMinRatio` 为 null 时）：

```dart
double computeRecentMinRatio({
  required int contextWindow,
  required int recentMinTokenTarget,
}) {
  final raw = recentMinTokenTarget / contextWindow;
  return raw.clamp(0.10, 0.45); // 下限保护：最低 10%，最高 45%
}
```

**会话级覆盖**：3 个 nullable 列（`revise_enabled_override` / `recent_min_ratio_override` / `retrieval_ratio_override`）。NULL = 使用全局配置；非 NULL = 使用会话级覆盖值。`compactionTriggerRatio` 固定 0.5，不提供会话级覆盖。

#### 失败处理

压缩失败映射 E018，0 次自动重试，直接进入 `failed` 状态。用户可通过"从中断处继续"重试。**不提供"跳过压缩直接用全部原文"的降级选项**——若原文已超上限，跳过压缩会导致 generating prompt 超长，可能触发 LLM 截断或报错。详见 §6.2、DOC-09A-2 §6。

#### 与 Simple 模式 CompactionPoint 的差异

| 维度 | Simple 模式 | 中级模式（v0.2.2） |
|------|-------------|------------------|
| 触发阈值 | token 阈值 × compactionThreshold（0.6） | 总占用 > contextWindow × compactionTriggerRatio（0.5） |
| 摘要内容 | 自由文本，聚焦"继续对话所需" | 剧情宏观骨架（事件时间线/角色出场/剧情阶段/关键转折） |
| 双重职责 | 仅压缩 | v0.2.3：职责分离--压缩摘要（累积式->上下文注入）+ 分段宏摘要（分段式->记忆检索，importance=3） |
| 缓存优化 | system + 摘要为稳定前缀 | 同左，扩大缓存命中区 3-6 倍 |

详见 DOC-09A-2 §5。

#### 历史过滤（v0.2.2 新增 2026-08-04）

**问题背景**：压缩触发后，`chat_messages` 表中 boundary 之前的旧消息仍然存在（不删除，仅标记压缩点）。若加载历史时不过滤，`shouldCompact` 计算的 `historyTokens` 会持续累积包含已压缩的旧消息，导致每轮都误触发压缩（用户反馈：每次发消息都显示"正在压缩对话历史"，但供应商调用记录显示请求仅 37507 token，远未达 100k 阈值）。

**过滤逻辑**（`IntermediateCompactionService.filterByCompactionPoint`，对标 Simple 模式 `getCompressedMessages`）：

```
输入：allMessages（全量消息，按 createdAt 排序）+ compactionPoints（压缩点列表）
输出：过滤后的消息列表

1. compactionPoints 为空 -> 返回 allMessages（首轮或未触发过压缩）
2. 取最新 CompactionPoint 的 boundaryMessageId + summaryMessageId
3. 在 allMessages 中定位 boundary 索引（找不到 -> 返回 allMessages，异常兜底）
4. 查找 summaryMessage（应在 allMessages 中，持久化时已写入）
5. 返回 [summaryMessage, ...boundary 之后的消息（排除旧 isSummary=true）]
```

**关键约束**：
- **新用户消息位置**：boundary 是"压缩到此为止"的最后一条消息，boundary 之后的消息（含本轮新用户消息和助手回复）保留在 summary 之后，确保新用户消息始终在压缩摘要后边（用户需求 2026-08-04）。
- **旧摘要丢弃**：多次压缩后旧摘要会堆积，每次压缩由新摘要替代旧摘要，旧摘要（isSummary=true）不保留在历史中（其内容已被纳入新摘要）。
- **UI 渲染**：过滤后的列表中 summaryMessage 的 `isSummary=true`，UI 层（`IntermediateChatBody._buildMessage`）识别此标记用 `IntermediateCompactionSummaryCard` 隔断卡片渲染，区别于普通消息气泡（详见 DOC-06B §6.1C）。

**调用点**：
1. `loadHistory`：加载历史消息时过滤，UI 展示 + 后续 `shouldCompact` 计算均基于过滤后列表
2. `_prepareAndRunRound`：准备轮次上下文时过滤，`round.history` 传入 `shouldCompact`/`compact` 时已是过滤后列表

**compactionService 为 null 时**（旧测试环境）：回退到全量加载，保持向后兼容。

#### 压缩提示展示时机（v0.2.2 修复 2026-08-04）

**问题背景**：用户反馈"每轮发送消息都看到『正在压缩对话历史』提示"，但供应商调用记录显示请求 token 远未达压缩触发线（100k）。真实根因有二：

1. **phase 切换缺失**（主要）：`_prepareAndRunRound` 在消息数 ≥ 8 时把 phase 设为 compacting，`_runCompactionPhase` 中 `shouldCompact` 返回 false（未超阈值）时只调用 `_runExtractPhase` 却**不改 phase**，而 `_runExtractPhase` 开头也不设 phase（仅在 extract LLM 调用完成后设 retrieving）。结果 phase 一直停留在 compacting，UI 全程显示"正在压缩对话历史..."直到关键词提取完成（数秒），用户每轮都看到压缩提示。
2. **check 期间初始 phase 即为 compacting**：即使最终 `shouldCompact` 正确返回 false，检查期间（配置加载 + token 计数）UI 仍短暂显示压缩提示。

**修复方案**（`intermediate_chat_controller.dart` + `intermediate_chat_controller_phases.dart`）：

```
_prepareAndRunRound：
  1. phase 统一初始化为 extracting（不再根据消息数预设 compacting）
     - 取消 skipCompaction 的分支判断，消除"检查期间闪现压缩提示"

_runCompactionPhase：
  1. service == null     -> phase 显式置 extracting，再调用 _runExtractPhase
  2. shouldCompact false -> phase 显式置 extracting（修复 phase 停留 bug），再调用 _runExtractPhase
  3. shouldCompact true  -> phase 置 compacting（此时才显示"正在压缩对话历史"），执行 compact
```

**效果**：仅在真正触发压缩时显示"正在压缩对话历史"提示；未超阈值时用户全程看到"提取关键词中"，完全看不到压缩提示。

**设计取舍**：初始 phase 从 compacting 统一改为 extracting，容忍了"真正压缩时 extracting → compacting → extracting"的过渡切换（每段都有明确加载文案，视觉可接受），换取了"不压缩时零压缩提示"的确定性。这与用户核心诉求一致——压缩提示只在压缩时出现。

### 5.2 memories_fts 表（FTS5 虚拟表）

v0.2（schemaVersion=21）重建为 **7 内容字段索引**（原 v19 仅 `summary` 单字段），让所有 5W1E 字段都可被关键词检索召回：

| 字段 | 类型 | 说明 |
|------|------|------|
| summary | TEXT | 全文检索字段（宏摘要主字段；微摘要可选，5W1E 兜底） |
| when_text | TEXT | 5W1E·时间全文检索字段（v21 新增） |
| where_text | TEXT | 5W1E·地点全文检索字段（v21 新增） |
| who_text | TEXT | 5W1E·人物全文检索字段（v21 新增） |
| what_text | TEXT | 5W1E·事件全文检索字段（v21 新增） |
| significance | TEXT | 5W1E·意义全文检索字段（v21 新增） |
| extra | TEXT | 5W1E·额外信息全文检索字段（v21 新增） |
| memory_id | TEXT UNINDEXED | 关联记忆 ID（仅返回字段，不参与索引） |
| memory_type | TEXT UNINDEXED | 记忆类型（experiential，仅返回字段） |
| session_id | TEXT UNINDEXED | 所属会话（用于会话级过滤，仅返回字段） |

**建表 SQL**：`CREATE VIRTUAL TABLE memories_fts USING fts5(summary, when_text, where_text, who_text, what_text, significance, extra, memory_id UNINDEXED, memory_type UNINDEXED, session_id UNINDEXED, tokenize='trigram')`

**分词器**：`tokenize='trigram'`（FTS5 内置 trigram 分词器，UTF-8 字符级 3 字符滑动窗口）。中文每个字符是独立 Unicode 字符，trigram 能正确切分中文连续字符，支持中文全文检索。≥3 字符查询走 trigram MATCH；<3 字符查询自动 fallback 到 LIKE。

**MATCH 召回**：所有 7 内容字段都参与 FTS5 MATCH 召回（关键词可在任一字段命中）。宏摘要 5W1E 6 字段填空字符串（不影响 trigram 分词）。`rank` 是 FTS5 内置 BM25 分数（负值，越小越相关）。详见 DOC-09A-1 §3.3。

**同步方式**：显式插入（非触发器）。写入 experiential_memories 时，同一 drift transaction 内同时写入 memories_fts。

**重要性存储门槛**（2026-07-08）：`importance < importanceStorageThreshold`（默认 3）的低重要性记忆仍写入 `experiential_memories`，但**跳过 FTS5 索引建立和 embedding 生成**（不可被检索）。这些记忆留存原始事件信息，在上下文 token 超阈值时由 `MemoryConsolidator` 异步批量合并为高重要性剧情节点记忆（合并后建索引+embedding，删除原始记忆），详见 DOC-09A-1 §4。

### 5.3 向量检索方案（纯 Dart 暴力检索）

> **方案变更**：原计划使用 sqlite-vec 虚拟表 `memory_vectors` 做 KNN 检索，但 pub 包 `sqlite_vec 0.1.7-alpha.3` 损坏废弃（`src/` 缺失 `sqlite-vec.c`，CMake 全平台构建失败；包 0 likes / 55 周下载 / 5 月无更新，已废弃）。v0.2 主方案改为**纯 Dart 暴力检索**。

**数据存储**：向量数据存储在 `experiential_memories.embedding` BLOB 字段（§5.1 已定义），单一数据源，无独立向量索引表。

**检索流程**：ExperienceRepositoryImpl 从 `experiential_memories` 加载该 session 全部 `has_embedding=true` 的向量到内存 → 调用 `VectorEngine.batchSearch`（Core 层，Isolate 内余弦相似度计算）→ 返回 topK。详见 DOC-05-8 §9.12、DOC-09A-1 §3.4。

**性能**：1536 维 × 1000 条 ≈ 5-15ms（ARM64 Isolate），满足 Q-02 ≤50ms 目标；100% 召回率。v0.2 阶段记忆量小（<1000 条/会话），性能充裕。

**维度**：embedding 维度取决于用户配置的 embedding 模型（384/768/1536）。用户切换 embedding 模型时，已有向量的维度可能与新查询向量不一致——V1 实现采用**维度过滤跳过**策略（`ExperienceRepositoryImpl._vectorSearch` 中 `vec.length != queryVector.length` 的候选直接跳过，非破坏性），偏离原"清空已有向量"方案。理由：非破坏性策略保留历史向量数据，切换模型不丢数据；用户重新生成会逐步用新维度向量替换旧向量。详见 DOC-05-8 `_vectorSearch` 实现。

> **不再建 `memory_vectors` 表**：原 sqlite-vec 虚拟表方案废弃。向量仅存 `experiential_memories.embedding` BLOB 单一数据源，无独立索引表，无同步开销，无跨表事务一致性负担。

> **v0.3 升级路径**：待 vec1（SQLite 官方向量扩展，2026 年新出，IVFADC+OPQ 真 ANN）出现 Dart 绑定后，重新评估 SQL KNN 方案。届时可建 `memory_vectors` 表，VectorEngine 降级为回退。

### 5.7 叙事时间机制（2026-07-25 新增）

> **背景**：v0.2 中级模式原计划仅使用相对时间描述（5W1E 的 `when` 字段，如"次日清晨"），不引入绝对叙事时间锚点。但实际使用中发现：长程对话中相对时间描述容易累积漂移（"次日清晨"反复出现导致 LLM 失去时间推进感），且无法在检索注入时让 LLM 快速判断事件距今多远。因此提前到 v0.2 启用绝对叙事时间机制——LLM 在 summarizing 阶段输出绝对故事内时间（如"来公寓第三天"），作为时间锚点支撑长程叙事连贯性。原计划 v0.3 启用，现提前到 v0.2。

#### 5.7.1 数据流

```
轮次 N summarizing 阶段：
  1. SummarizePhaseHandler._buildRecentTimelineBlock(sessionId)
     ↓ 查询最近 5 轮 experiential_memories.narrative_time（按 turn_number 降序）
     ↓ 格式化为"第N轮：xxx"列表
     ↓ 替换 extractSummaryPrompt 中的 {{recent_timeline}} 占位符
  2. LLM 看到时间线，输出 EventSummary.narrativeTime（如"来公寓第四天"）
  3. 持久化阶段：narrativeTime 写入 experiential_memories.narrative_time 列
  4. persist 成功后：控制器 upsert chat_sessions.current_narrative_time = narrativeTime

轮次 N+1 generating/reviewing 阶段：
  - 可读取 chat_sessions.current_narrative_time 作为当前时间锚点（注入提示词）

轮次 N+1 summarizing 阶段：
  - 回到步骤 1，查询最近 5 轮（含轮次 N）构建时间线
```

#### 5.7.2 字段说明

| 字段 | 位置 | 类型 | 说明 |
|------|------|------|------|
| `narrativeTime` | `EventSummary` 实体 | `String?` | LLM 在 summarizing 阶段输出的绝对叙事时间（如"来公寓第三天"）。null 表示本轮未输出叙事时间，保留原状态 |
| `narrative_time` | `experiential_memories` 表 | `TEXT NULLABLE` | 持久化 `EventSummary.narrativeTime`。v0.2 启用（原 v0.3 启用） |
| `current_narrative_time` | `chat_sessions` 表 | `TEXT NULLABLE` | 会话级当前叙事时间状态。persist 成功后由控制器 upsert 写入（schemaVersion=26 新增） |
| `narrativePeriod` | `experiential_memories` 表 | `TEXT NULLABLE` | 叙事时段（如"来公寓第三天"中的"来公寓第三天"）。**仍为 v0.3 启用**，中级模式恒 NULL |

#### 5.7.3 与 5W1E `when` 字段的区别

| 字段 | 用途 | 示例 | 更新方式 |
|------|------|------|---------|
| `when`（5W1E） | 单条事件的相对时间描述 | "次日清晨"、"三年后"、"战斗结束时" | LLM 每轮自由输出，不参与会话状态 |
| `narrativeTime` | 绝对时间锚点 | "来公寓第三天"、"修炼第七天" | LLM 每轮输出后 upsert 到会话状态 |

两者**共存**：`when` 用于单条事件的时间描述（可空），`narrativeTime` 用于绝对时间锚点（**必填**，不可留空）。

#### 5.7.4 提示词改动

summarizing 阶段 `extractSummaryPrompt` 提示词：
1. 新增 `{{recent_timeline}}` 占位符——由 `SummarizePhaseHandler._buildRecentTimelineBlock` 替换为最近 5 轮的时间线列表（首轮替换为"首轮，暂无历史时间线"）
2. 新增 `narrativeTime` 必填字段——LLM 必须输出绝对叙事时间，不可留空
3. 新增【绝对时间约束】段落--明确判断流程：
   - 参照本轮内容与【最近叙事时间线】中最近一轮的值
   - 若本轮时间未推进：**直接沿用最近一轮的字面值**（保持表述一致，避免同一时间出现不同表述如"搬进公寓第一天"vs"搬进新家第一天"）
   - 若本轮时间推进：基于推进信号输出新的绝对时间
   - 若首轮无历史时间线：根据本轮内容归纳出初始绝对时间
4. **占位符位置优化**（2026-08-04 修订）：`{{recent_timeline}}` 占位符从提示词中部移至末尾，使前方规则文本成为稳定前缀，提升 prompt cache 命中率。`{{known_entities}}` 占位符同理从 `extractFactsPrompt` 中部移至末尾。

#### 5.7.5 检索注入

【相关往事】每条记忆标题行**优先用 `narrativeTime`**（如"[来公寓第三天·重要性4]"），无 `narrativeTime` 时回退用"X轮前"（如"[3轮前·重要性4]"）。详见 DOC-09A-2 §8.1。

#### 5.7.6 v0.3 升级路径

- `narrativePeriod` 仍在 v0.3 启用（中级模式恒 NULL）
- 时序通道评分（temporal channel scoring）仍在 v0.3 启用

### 6.1 原子事务原则

**核心原则**：每轮对话是一个原子事务——草稿→提取关键词→检索→修正→摘要→入库，要么全部成功，要么全部失败。任何环节失败 → **数据层**事务回滚（不写入任何数据）+ **UI 层**保留已显示的中间产物并提示用户重试。

**无降级质量**（失败时）：不用草稿充当回复、不静默跳过检索。

**~~Compact 降级~~**（2026-07-16 起已移除）：~~（非失败，正常流程）：当检索关键词为空、检索结果为空或低质量时（`skipReviseWhenEmptyRetrieval=true`），跳过 revising 步骤，草稿直接作为最终回复，仍走 summarizing 生成 EventSummary。这是质量保留的优化（无检索素材时重写无意义），不是失败恢复——整轮仍正常完成并持久化。~~ 现行行为：revising 始终执行，即使无记忆注入也走 revising 做润色（revising 双重功能：按记忆修正草稿 + 润色文案）。注入前质量过滤在 `IntermediateContextBuilder._formatMemories` 中完成（双阈值取严格：`finalScore >= 0.4 && finalScore >= maxScore × 0.6`），全部不满足时【相关往事】区块省略，revising 只做润色。`skipReviseWhenEmptyRetrieval` 配置项保留但不再生效（向后兼容）。详见 DOC-09B §8.7。

**数据回滚 ≠ UI 清空**：失败时数据层绝不持久化（原子事务不变），但 UI 层**保留**已显示的草稿/检索/半截回复，让用户能看到失败发生在哪一步。

### 6.2 失败处理策略概览

| 失败环节 | 重试次数 | 仍失败后行为 |
|---------|---------|-------------|
| 请求1 generating（生成）失败 | 2 次 | 整轮失败，报错，用户重试 |
| 请求2 extracting（关键词提取）失败 | 2 次 | 整轮失败，报错，用户重试 |
| 检索完全失败（两路都挂） | 1 次 | 整轮失败，报错，用户重试 |
| 检索部分失败（单路挂） | 不重试 | 降级用单路结果继续 |
| 请求3 reviewing（审查）失败 | 2 次 | 整轮失败，报错，用户重试 |
| 请求4 summarizing（摘要）失败 | 2 次 | 整轮失败，报错，用户重试 |
| 结构化输出降级（工具调用→JSON→提示词约束） | 按降级链逐级 | 详见 DOC-09A-2 §6 |
| 流式中断 | 1 次 | 整轮失败，报错，用户重试 |
| Embedding 失败 | 不重试 | 降级 has_embedding=false，事务仍提交 |
| 持久化失败 | 不重试 | 事务回滚，整轮失败 |

> 完整状态机、重试时序、UI 保留策略见 DOC-09A-2 §6.1-6.7。错误码 E010-E018 见 DOC-09B §9。

### 7.1 Repository 拆分

按接口隔离原则（ISP），拆分为两个独立 Repository：

```dart
// 中级模式实现（签名以 DOC-05-5 §4.5 为权威基准）
abstract interface class ExperienceRepository {
  Future<List<ScoredMemory>> searchExperiences({
    required String sessionId,
    required String query,
    required int topK,  // 默认 3（RetrievalConfig.topK，v0.2由 5→3）
    required double fts5Weight,
    required double vectorWeight,
    required int keyEventThreshold,
    required double keyEventBoost,
    required double normalizationEpsilon,
  });
  Future<ExperientialMemory> appendExperience({
    required String sessionId,
    String? summary,  // v0.2 降级为可选（宏摘要使用，单事件优先用 5W1E）
    required int importance,
    required List<String> tags,
    required int turnNumber,
    String? narrativeTime,
    String? narrativePeriod,
    // ─── 5W1E（v0.2，与 memories_fts 7 内容字段对齐）───
    String? when,
    String? where,
    String? who,
    String? what,
    String? significance,
    String? extra,
  });
  Future<List<ExperientialMemory>> getRecentExperiences(
    String sessionId, {required int limit, bool includeArchived = false});
  Future<void> updateEmbedding(String memoryId, Float32List embedding);
  Future<void> insertFtsIndex({
    required String memoryId,
    String? summary,  // v0.2 降级为可选（与 appendExperience 签名保持一致）
    required String sessionId,
    // ─── 5W1E（v0.2，与 memories_fts 7 内容字段对齐）───
    String? when,
    String? where,
    String? who,
    String? what,
    String? significance,
    String? extra,
  });
  Future<void> deleteAllExperiences(String sessionId);
}

// v0.3 高级模式新增
abstract interface class FactRepository {
  Future<List<FactualMemory>> searchFacts(String sessionId, String query);
  Future<void> upsertFacts(String sessionId, Map<String, String> facts);
}
```

> **签名对齐说明**：本接口签名以 DOC-05-5 §4.5 为权威基准。`searchExperiences` 返回 `List<ScoredMemory>`（含 finalScore 供排序），非 `List<ExperientialMemory>`；参数为命名参数（含检索权重/关键事件阈值/boost/归一化ε），非 3 个扁平参数。`appendExperience` 返回 `ExperientialMemory`（含 memoryId），非 void；不引入 `ExperienceEvent` 实体——其字段与 `EventSummary`（09B §8.1）完全重叠，故统一为命名参数。`saveEmbedding` 统一为 `updateEmbedding`。中级模式只实现 ExperienceRepository，无空方法。v0.3 新增 FactRepository 是纯增量。
>
> **v0.2 5W1E 改造**（2026-07-19）：
> - `appendExperience` 签名扩展——`summary` 由 `required String` 降级为可选 `String?`（宏摘要继续使用 summary，单事件优先使用 5W1E 6 字段），新增 6 个 5W1E 命名参数（when/where/who/what/significance/extra，均 `String?`），与 `memories_fts` 表 7 内容字段对齐，支持 FTS5 多字段检索
> - `insertFtsIndex` 签名同步扩展——`summary` 降级为可选 `String?`，新增 6 个 5W1E 命名参数，FTS5 索引内容字段从 1 个（summary）扩展到 7 个（summary + 5W1E 6 字段），null/空字符串字段插入空字符串避免 NULL 影响 BM25 排序
> - `RetrievalConfig.topK` 默认值 5→3（方案二改为 5W1E 多字段结构后，每条记忆信息密度更高、更具体，3 条已足够覆盖相关上下文，同时减少 token 占用和注意力稀释）
> - 调用方（Controller）从 `EventSummary` 提取 5W1E 字段传入 `appendExperience` / `insertFtsIndex`；向后兼容旧调用点（不传新字段时 5W1E 6 字段为 null）

### 7.5 路由分发

中级模式与 Simple 模式共享同一个 `MainLayout` 顶层路由，通过 `ChatSession.mode` 字段分发到不同页面和 Controller：

| session.mode | 页面 | Controller | 草稿前缀 |
|-------------|------|-----------|---------|
| `chat` | ChatModePage | ChatModeController | `__draft_` |
| `intermediate` | IntermediateChatPage | IntermediateChatController | `__draft_intermediate_` |

**首页双卡入口**：HomePage 提供两张卡片——"新建对话"（chat 模式）+ "新建故事"（intermediate 模式），点击后创建对应模式的草稿会话。

**草稿会话机制**（v2.9 修订：快照语义 + 物化触发扩展）：点击新建卡片时创建带前缀的草稿会话（sessionId 不入库），页面以草稿会话挂载。草稿会话在以下任一时机物化为真实会话（入库）：(1) 用户发送首条消息时；(2) 草稿期间首次修改会话配置时（v2.9 新增）。Controller 调用 `createSession(mode: ...)` 或 `_materializeDraftSessionWith()` 物化，并更新 state.session。`MainLayout._refreshCurrentSession` 通过双前缀检测跳过草稿会话的刷新。

> **v2.9 快照语义**（2026-07-22 配置快照语义；v2.16 扩展 2026-08-03）：物化时由 `ConfigurationResolver.snapshotSimpleDefaults()`（chat 模式）/ `snapshotIntermediateDefaults()`（intermediate 模式）读取当前全局配置生成 `GlobalDefaultsSnapshot`（v2.9 时 14 字段；v2.16 扩展至 17 字段，新增 `effectiveContextLimit` / `phaseModels` / `jsonMode` / `contextBudget` 中部分由 v0.2.2 阶段补充，详见 `lib/features/chat/domain/services/configuration_resolver.dart`），控制器将草稿值与快照值合并后写入 `chat_sessions` 表会话级字段。后续全局配置变更不影响已物化的会话——这是"值快照"而非"引用解析"。用户需求："如果使用的是全局设置的值，使用这一刻的值，而不是全局设置那一项的引用"。**v2.16 扩展**（2026-08-03）：`contextBudget.recentMinRatio` / `retrievalRatio` 也纳入快照独立模式（物化时复制全局值到 `recentMinRatioOverride` / `retrievalRatioOverride`，原 v2.12 "保留 NULL" 策略废弃；`reviewEnabledOverride` 仍保留 NULL 语义）。详见 DOC-05-6 §5.1 v1.6、DOC-06B §6.8 v3.9 / v3.16、DOC-09C §草稿会话物化策略 v2.24。

**Provider 注册**：两个模式的 Controller 均以 `StateNotifierProvider.family<*, *, ChatSession>` 注册在各自页面文件底部，按 ChatSession 实例创建。`MainLayout` 的 `ref.listen` 按 `current.mode` 选择监听对应 Provider 的 state 变化（草稿→真实会话转换时刷新侧边栏）。

## 8. 与高级模式的关系

### 8.1 复用率估算

| 层级 | 中级实现工作量 | 高级复用比例 |
|------|---------------|-------------|
| Domain 实体 | 20% | 80%（高级只新增 FactualMemory） |
| Repository 接口 | 30% | 70%（高级新增 FactRepository） |
| Data 层实现 | 40% | 60%（高级新增事实层 SQL） |
| Core 层（Embedding/Vector/SSE） | 100% | 100%（完全共享） |
| Presentation Controller | 0% | 0%（完全分离） |
| Presentation Page | 30% | 50%（共享组件，布局不同） |

**整体复用率约 70-80%**——中级实现的大部分代码成为高级的底座。

### 8.2 v0.3 高级模式的增量工作

基于中级模式的底座，v0.3 需要新增：
- FactualMemory 实体 + FactRepository
- Agent Loop 控制器（AdvancedChatController）
- ToolExecutor + 工具注册框架
- 工具：search_experiences、search_facts、update_world
- HUD Controller + View（factual_memories 只读视图）
- StatePatchParser（状态补丁解析）
- FactualMemoryChangeEvent 领域事件
- factual_memories 表（纯增量迁移）

### 8.3 设计原则的延续

中级模式确立的设计原则在 v0.3 继续：
- 原子事务原则（update_world 两写单事务）
- 缓存友好拼接（Agent Loop 的每次工具调用都遵循稳定前置）
- 流式全过程可见（Agent Loop 的每次工具调用都显示折叠小窗）
- Repository 接口隔离（新增 FactRepository 不影响 ExperienceRepository）
