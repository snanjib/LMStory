## 7. 流式显示交互

### 7.1 IntermediateChatState 字段

中级模式 Controller 状态为独立类（不复用/不继承 ChatModeState），包含会话、消息、阶段、流式产物等全部字段：

```dart
class IntermediateChatState {
  // 注：中级模式无 ForkAnchor（见 DOC-09A-1 §2.2 简化 Fork），不复用 forkAnchors 字段

  /// 当前阶段（枚举，非字符串，避免非法值）
  /// v2.12 流程 15 个值：idle / compacting / extracting / retrieving / generating
  ///       / reviewing / summarizing / persisting / failed
  ///       + compacting_retry / extracting_retry / retrieving_retry
  ///       / generating_retry / reviewing_retry / summarizing_retry
  /// v2.12 修订：新增 compacting 阶段（条件触发）；状态机顺序调整为
  ///       compacting?→extracting→retrieving→generating→reviewing?→summarizing→persisting
  /// v0.2.2 阶段名重命名：drafting→generating、revising→reviewing
  final IntermediatePhase phase;

  /// 已持久化的消息列表（不含流式中的临时内容）
  final List<ChatMessage> messages;

  /// 当前会话（UI 访问 title 等；草稿会话物化后更新为真实会话）
  final ChatSession session;

  /// 请求2生成流式内容（generating 阶段实时更新，reviewing 后折叠）
  /// v0.2.2 重命名：streamingDraft → streamingGenerated
  final String? streamingGenerated;

  /// 请求2 extracting 输出的检索关键词（extracting 完成后填充）
  /// V2：关键词从 generating 迁移到 extracting 步骤产出
  /// 注：字段名 draftKeywords 保留兼容（artifacts 表列名），语义为 extracting 产出
  final List<String>? draftKeywords;

  /// 检索到的经历记忆（retrieving 完成后填充）
  /// 用于：1) 检索小窗显示命中数；2) 请求3 reviewing 上下文注入
  final List<ExperientialMemory>? retrievedMemories;

  /// 请求3回复流式内容（reviewing 阶段实时更新，主区域显示）
  final String? streamingReply;

  /// 请求4 summarizing 输出的事件摘要（summarizing 完成后填充，persisting 阶段使用）
  /// V2：事件摘要从 reviewing 迁移到 summarizing 步骤产出
  final EventSummary? currentEventSummary;

  /// 失败时记录失败阶段 + 失败原因（phase=failed 时非 null）
  final FailureContext? failureContext;

  /// 重试计数（按阶段分别计数：compacting/generating/extracting/retrieving/reviewing/summarizing）
  final Map<IntermediatePhase, int> retryCounts;

  /// 本轮用户输入（重试时复用）
  final String? userInput;

  /// 生成正文全文（reviewing 注入 + UI 折叠展示）
  /// v0.2.2 重命名：draftText → generatedText
  final String? generatedText;

  /// 重新生成/编辑重发"准备中"标识（DB 删除期间 UI 遮罩）
  /// 入口立即置 true，state.messages 截断时置 false，DB 删除失败也置 false。
  /// 详见 DOC-09A-1 §2.4/§2.5
  final bool isPreparingRegenerate;
}
```

> **`isPreparingRegenerate` 加载遮罩**（v2.1，2026-07-13）：`regenerateMessage` / `editAndResend` 入口立即置 true，覆盖 `await deleteRoundAndDownstream` 期间 UI 仍显示待删除下游消息的"残留感"问题。`intermediate_chat_body.dart` Stack 末尾条件渲染遮罩（半透明夜航底色 `bg.withValues(alpha:0.5)` + 居中 `CircularProgressIndicator`（primary 色）+ ink 色文案"正在准备重新生成..." + `AbsorbPointer` 拦截消息列表交互）。DB 删除完成、state.messages 截断时同步置 false，后续由四步生成小窗（GeneratePanel 等）接管 UI 反馈。

**IntermediatePhase 枚举定义**（V2 四步扩展，对齐 DOC-09A-2 §6.1 状态机；v0.2.2 阶段名重命名）：

```dart
enum IntermediatePhase {
  idle,
  generating,        // v0.2.2 重命名：drafting → generating
  generatingRetry,   // v0.2.2 重命名：draftingRetry → generatingRetry
  extracting,        // V2 新增：请求2 关键词提取
  extractingRetry,   // V2 新增
  retrieving,
  retrievingRetry,
  reviewing,         // v0.2.2 重命名：revising → reviewing
  reviewingRetry,    // v0.2.2 重命名：revisingRetry → reviewingRetry
  summarizing,       // V2 新增：请求4 事件摘要
  summarizingRetry,  // V2 新增
  persisting,
  failed,
}
```

> **类型从 String 改为枚举的理由**：String phase 容易写入非法值（如拼写错误 "draftng"），编译期无法捕获；枚举在编译期保证取值集合正确，且 switch 可获得 exhaustiveness check。V2 四步流程 13 个枚举值与 DOC-09A-2 §6.1 状态机的 8 个正常状态（6 主阶段 + idle/failed）+ 5 个重试状态一一对应。

> **V1 历史**（实现偏离，2026-07-01）：V1 阶段仅使用 6 个正常状态，3 个 `*Retry` 状态保留不用。V2 四步重构后扩展为 13 个枚举值（新增 extracting/summarizing 主阶段及其重试状态），全部启用。`retryCounts` 按 5 个可重试阶段（generating/extracting/retrieving/reviewing/summarizing）分别计数。**v2.12 新增** compacting 阶段及其重试状态（compacting/compactingRetry），枚举值扩展为 15 个，可重试阶段扩展为 6 个（新增 compacting）。

### 7.2 多段式流式显示（V2 四步；v2.12 修订：检索前置 + 可选审查 + CompactionPoint）

> **v2.12 修订（2026-07-30）**：状态机顺序由旧称"drafting→extracting→retrieving→revising→summarizing→persisting"调整为"compacting?(可选)→extracting→retrieving→generating→reviewing?(可选)→summarizing→persisting"（v0.2.2 阶段名重命名：drafting→generating、revising→reviewing）。新增 compacting 阶段（条件触发），reviewing 阶段改为可选（默认关闭）。VisualFlowTimeline 节点顺序同步调整。

### 7.3 阶段过渡时序（V2 四步；v2.12 修订：检索前置 + 可选审查）

```
用户发送
  │
  ▼
[条件触发] phase=compacting（总占用达 contextWindow × compactionTriggerRatio 0.5 时）
  │ 压缩小窗显示"正在压缩上下文..."（无流式展示）
  ▼
[提取小窗展开] phase=extracting
  │ 提取小窗显示"提取关键词中"（无流式，结构化步骤）
  ▼
提取完成（解析出 5 类分类关键词：characters/items/locations/actions/plots）
  │ 提取小窗更新为"关键词：N 个"
  │ 保持 1 秒后折叠为单行摘要
  ▼
[检索小窗展开] phase=retrieving
  │ 提取小窗已折叠在上方
  │ 检索小窗显示"正在检索..."（5 路并行：实体类 3 路 FTS5 + 事件类 2 路 Vector）
  ▼
检索完成
  │ 检索小窗更新为"找到 N 条相关经历 + M 个世界设定实体"
  │ 保持 1 秒后折叠为单行摘要
  ▼
[生成小窗展开] phase=generating
  │ 提取/检索小窗已折叠在上方
  │ 生成小窗显示"正在构思生成..." + 流式内容（注入【世界设定】+【相关往事】生成）
  │ 首字到达后展开小窗显示流式内容
  ▼

  │ 生成小窗保持展开 2 秒后自动折叠为单行摘要
  │ 摘要 = "生成已完毕"
  ▼
[审查开关判断]
  │
  ├─ 关闭（默认，reviewEnabled=false）─▶ 生成即最终，直接进入 summarizing
  │   主区域直接显示生成流式内容（复用 GeneratePanel 流式输出，不切换到主区域）
  │
  └─ 开启（reviewEnabled=true）─▶ [主区域开始流式] phase=reviewing

              │ 主区域流式显示审查后正文（runPlainText 纯文本流式，软约束审查）
              ▼
              回复流式完成（纯文本，无事件摘要）
  ▼

  │ 显示"生成摘要中"（无流式，结构化步骤）
  ▼

  │ 摘要小窗更新为"摘要已生成"
  │ 保持 1 秒后折叠为单行摘要
  ▼

  │ drift transaction 原子写入（含压缩摘要，若本轮触发压缩）
  ▼

```

### 7.4 完成后的折叠摘要（V2 四步）

每轮完成后，生成/提取/检索/摘要小窗自动折叠为单行摘要，保留在主回复气泡上方：

```

│ ▸ 生成已完毕                         │  ← 折叠的生成小窗
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│ ▸ 关键词：3 个                       │  ← 折叠的提取小窗（V2 新增）
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│ ▸ 找到 3 条相关经历                  │  ← 折叠的检索小窗
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│ ▸ 摘要已生成                         │  ← 折叠的摘要小窗（V2 新增）
└─────────────────────────────────────┘
┌─────────────────────────────────────┐
│ [主回复气泡]                         │  ← 最终回复
│ ...                                  │
└─────────────────────────────────────┘
```

用户可点击折叠小窗重新展开查看生成全文 / 关键词 / 检索经历详情 / 事件摘要。

#### 7.4.1 自动折叠时序详细机制（2026-07-17 新增）

§7.3 时序图中"保持 X 秒后自动折叠"的详细机制：面板到达完成态后启动 `Timer(foldDelayMs, _doAutoFold)`，但触发折叠前先检测面板是否在屏幕视口可见区域：

- **视口可见性检测**：通过 `context.findRenderObject()` + `localToGlobal(Offset.zero)` 获取面板在屏幕的全局坐标，结合 `MediaQuery.of(context).size.height` 判断面板是否与屏幕可见区域相交。
- **可见时延迟折叠**：若面板可见（说明用户可能正在阅读），延迟折叠一次并重新计时（`_foldRetryCount++`）。
- **最大延迟次数**：最多延迟 2 次（`_maxFoldRetries = 2`），总阅读时间 ≈ `foldDelayMs × 3`（生成小窗：2000ms × 3 = 6 秒；检索/提取/摘要小窗：1000ms × 3 = 3 秒）。避免面板长时间不折叠占用屏幕空间。
- **不可见或达上限后折叠**：面板不在视口（已被滚出屏幕）或达到最大延迟次数后，执行 `setState(() { _expanded = false; _hasAutoFolded = true; })`。
- **用户交互取消定时器**：用户主动点击展开/折叠后，`_autoFoldTimer.cancel()` + `_hasAutoFolded = true`，之后不再自动折叠。

**设计意图**：避免用户正在阅读面板内容（生成全文 / 检索经历摘要 / 事件摘要）时被自动折叠打断阅读节奏。视觉规范见 DOC-06B §5.3。

#### 7.4.2 ListView children 顺序（2026-07-07 修订；V2 四步扩展 2026-07-10；统一组件重构 2026-07-13；v2.22 压缩摘要卡片 2026-08-04）

`IntermediateChatBody` ListView children 顺序：

```
1. state.messages（含历史 artifacts 小窗）
   - 若列表首条为 isSummary=true：渲染 IntermediateCompactionSummaryCard
     隔断卡片（整宽 + surfaceVariant 底 + divider 边框，详见 DOC-06B §6.1C）
   - 每个 assistant 消息前渲染 4 个统一组件（GeneratePanel/ExtractPanel/
     RetrievalPanel/SummarizePanel）的 artifacts 模式
   - 最后一轮 assistant 的小窗在 idle 时跳过内联渲染（避免与末尾重复）
2. pendingUserMessage          ← 临时用户气泡
3. _buildCurrentRoundPanels()  ← 当前轮小窗区域（统一组件 + 数据源切换）
   - 生成中：GeneratePanel -> ExtractPanel -> RetrievalPanel -> streamingReply -> SummarizePanel
   - 完成后（idle）：4 个统一组件的 artifacts 模式（避免"四合二"闪动）
```

**v2.22 新增（2026-08-04）**：`_buildMessage` 在渲染每条消息前检测 `message.isSummary`，若为 true 则用 `IntermediateCompactionSummaryCard` 渲染（隔断卡片），不走普通气泡分支。摘要消息由 `filterByCompactionPoint` 置于列表最前，boundary 之后的消息（含新用户消息）排在摘要之后，确保新用户消息始终在压缩摘要后边（用户需求 2026-08-04）。

**原顺序（已废弃）**：`[pendingUserMessage, ...messages, GeneratePanel, ...]`--pendingUserMessage 在列表顶部。
**问题**：`didUpdateWidget` 在 streamingGenerated 变化时调用 `_scrollToBottom()`，把滚动位置定位到 GeneratePanel（最底部），导致 pendingUserMessage 被滚到顶部不可见。用户感知"消息发送后看不到自己的气泡"。

**新顺序（2026-07-07 修订）**：`[...messages, pendingUserMessage, GeneratePanel, ...]`——pendingUserMessage 紧贴生成小窗。
**效果**：滚到底部时，新发的用户消息 + 生成/检索小窗 + 流式回复都在视窗里。

**统一组件重构（2026-07-13）**：消除完成后"四合二"闪动。原设计在末尾渲染 4 个实时流式小窗（GeneratePanel/ExtractPanel/RetrievalPanel/streamingReply/SummarizePanel），完成后（phase=idle）这些小窗消失，改为在 assistant 消息前渲染 2 个历史小窗（HistoryGeneratePanel/HistoryRetrievalPanel）。这一"4→2"切换造成画面闪动。

新设计：4 个小窗统一接收 `artifacts` 参数（`IntermediateRoundArtifacts?`），非 null 时进入历史态。完成后 phase=idle 切换瞬间，末尾"当前轮"区域的 Widget 实例保留（相同 Key `current-round-*` + 类型），仅切换数据源从 streaming 字段到 artifacts 快照，避免销毁重建。最后一轮 assistant 的小窗在 idle 时仅在末尾渲染（跳过内联），避免重复。历史轮次的 assistant 消息前渲染 4 个统一组件的 artifacts 模式（Key `history-*-turnN`）。

#### 7.4.3 滚动跟随机制（2026-07-17 新增）

`IntermediateChatBody` 的自动滚动到底部逻辑需区分"用户主动上滑阅读历史"与"内容更新需要跟随到底部"两种场景，避免用户上滑阅读时被强制拉回底部打断阅读。

**状态变量**：

- `bool _userScrolledUp = false`：用户已主动上滑，暂停自动跟随。
- `double _lastPixels = 0`：上一次 scroll 位置，用于方向检测。

**`_onScroll` 检测逻辑**：

```
pixels = position.pixels
atBottom = pixels >= maxScrollExtent - threshold

if (pixels < _lastPixels && !atBottom) {
  _userScrolledUp = true;  // 向上滑动且未在底部 → 标记为用户上滑
}
if (atBottom) {
  _userScrolledUp = false;  // 回到底部 → 恢复自动跟随
}
_lastPixels = pixels;
```

**`didUpdateWidget` 中的自动跟随触发条件**：

- **pendingUserMessage 出现**：`_userScrolledUp = false` + `_scrollToBottom()`——用户发送新消息时强制回到底部（新消息本就该可见）。
- **新内容到达（streamingGenerated / streamingReply 更新）**：`hasNewContent && !_userScrolledUp && _isNearBottom()` → `_scrollToBottom()`——仅在用户未主动上滑时跟随。
- **`_jumpToBottom` 手动跳底**：`_userScrolledUp = false`——用户主动点"跳到底部"按钮时重置状态。

**设计意图**：用户上滑阅读历史消息或上方小窗内容时，流式新内容不会强制把视图拉回底部，避免打断阅读；用户回到底部（手动跳底或滚到底）后恢复自动跟随。

**重试按钮组**（v2.12 架构调整：统一三选项，2026-07-30）：

| 按钮 | 回调 | 适用场景 | 行为 |
|------|------|---------|------|
| 整轮取消 | `cancelEntireRound()` | 所有失败 | 丢弃本轮所有中间产物（生成正文/关键词/检索结果/摘要），回到 idle 状态。**用户消息内容回填到消息输入框**，方便用户修改后重新发送（消息气泡从消息列表移除） |
| 从中断处重试 | `continueFromFailed()` | 所有失败 | 保留失败前已成功的阶段输出，仅从失败阶段重新执行 |
| 整轮重试 | `retry()` | 所有失败 | 丢弃本轮所有中间产物，从第 1 步（含压缩，若触发）重新执行 |

> **v2.12 修订**（2026-07-30）：失败处理从原"四按钮"（清空本轮/临时降级/从中断处继续/整轮重试）统一为"三选项"（整轮取消/从中断处重试/整轮重试）。主要变化：
> - **"清空本轮"→"整轮取消"**：原"清空本轮"保留用户消息气泡、用户可重发；新"整轮取消"将用户消息内容**回填到消息输入框**（消息气泡从列表移除），方便用户修改后重新发送。语义更清晰——"取消"表示本轮作废，输入回到编辑态。
> - **移除"临时降级"按钮**：原 E104（embedding 调用失败）时显示的"临时降级继续"按钮（`continueWithFts5Only()`，跳过 embedding 仅用 FTS5）移除。理由：用户决策"统一三选项，不增加新选项"。E104 失败现在走三选项处理，用户可通过"从中断处重试"重试（embedding 服务恢复后自动成功），或"整轮取消"后调整嵌入模型配置。
> - **"从中断处继续"→"从中断处重试"**：文案微调，语义不变，复用现有 `continueFromFailed()` 方法。
> - **"整轮重试"起点变更**：原从 generating 重新开始；v2.12 后从第 1 步（含 compacting，若触发条件仍满足）重新执行。

**`continueFromFailed()` 行为细节**（2026-07-22 新增；v2.12 修订扩展 compacting 阶段）：
- 守卫：`phase == failed && _round != null && failureContext != null`
- 重新解析配置（用户可能通过会话设置修改了模型/温度等），但保留已完成阶段的产出（generatedText/keywords/scoredMemories/retrievedFacts/replyText/thinkingContent/eventSummary/factsDeltas）
- 配置解析失败时用旧配置兜底，不阻塞继续重试
- 根据 `failureContext.failedPhase` 从对应阶段继续（v2.12 新增 compacting）：
  - compacting 失败：无产出可复用（压缩是第 1 步），等价于整轮重试（重新压缩）
  - generating 失败：无产出可复用，等价于整轮重试
  - extracting/retrieving/reviewing/summarizing/persisting 失败：从失败阶段继续
- `_round` 在 `_fail` 时不再清空（2026-07-22 修复），保留供 continueFromFailed 复用

**failed 状态下可修改会话配置**（2026-07-22 新增；2026-07-29 修订 controller 守卫）：
- `IntermediateSessionSettingsSheet` 的 `isGenerating` 判断改为 `phase != idle && phase != failed`
- `IntermediateChatController.updateSession` 守卫同步对齐：仅当 `phase != idle && phase != failed` 时拒绝更新（生成中拒绝），idle 与 failed 状态下均允许写库。2026-07-22 修订 UI 时遗漏了 controller 端守卫同步，导致 failed 状态下用户修改模型后被静默拒绝、配置回退、重试仍用旧模型，已于 2026-07-29 修复
- failed 状态下用户可通过右上角设置入口修改模型/温度等配置
- 修改配置后点击"从中断处重试"或"整轮重试"时，会重新解析配置生效

**重试行为**（v2.12 修订，与 DOC-09A-2 §6.4 一致）：用户点"整轮重试"后，清掉所有已显示的旧内容，从第 1 步（含 compacting，若触发条件仍满足）重新执行。点"整轮取消"则丢弃本轮所有中间产物（生成正文/检索/半截回复），**将用户消息内容回填到消息输入框**（消息气泡从列表移除），phase 回到 idle，用户可修改后重新发送。

> **"整轮取消"语义说明**（v2.12 修订，原 "清空本轮"语义说明）：v2.12 将"清空本轮"改为"整轮取消"，语义从"保留用户消息气泡"改为"**用户消息内容回填到消息输入框**"。理由：(1) "取消"比"清空"语义更清晰——表示本轮作废，输入回到编辑态；(2) 回填到输入框比保留消息气泡更符合用户直觉——用户想重新组织输入时，内容已在输入框等待编辑，无需先找到旧消息再复制；(3) 与事务性原则一致——整轮取消后无任何本轮产物残留（消息气泡也移除），但内容不丢失（回填输入框）。用户消息本就未持久化（事务已回滚），回填的是 `pendingUserMessage` 文本。

**`cancelEntireRound()` 行为细节**（v2.12 新增；v2.13 修订回填机制）：
- 守卫：`phase == failed`（或 `phase != idle && phase != persisting`，即生成中任意时刻用户主动取消）
- 清空 `_round`（generatedText/keywords/scoredMemories/retrievedFacts/replyText/thinkingContent/eventSummary/factsDeltas 全部丢弃）
- 清空 `pendingUserMessage`（消息气泡从列表移除），**保留 `userInput`**（Controller 不直接写输入框）
- `phase` 回到 `idle`，`failureContext` 清空
- 若本轮已触发压缩并生成了压缩摘要（compacting 成功但后续阶段失败），压缩摘要一并回滚（事务性：避免"压缩了但没用上"的孤儿摘要）

> **v2.13 回填机制修订**（2026-08-05）：原描述"Controller 直接将 `pendingUserMessage.text` 回填到 `_inputController.text`"不准确。实际实现采用"Controller 清气泡 + 保留 userInput -> 页面层检测回写"两段式机制：
> 1. **Controller 层**：`cancel()` / `clearRound()` / `recoverIfStuck()` 三个方法行为一致，均调 `state.clearTemporary().copyWith(pendingUserMessage: null)` 清空临时气泡，但保留 `userInput` 字段。Controller 不依赖 UI 层的 `TextEditingController`，不直接写输入框。
> 2. **页面层**（`IntermediateChatPage`）：通过三个检测点监听"pendingUserMessage 从有变无 + userInput 非空 + phase==idle"的状态组合，触发 `_tryRestoreDraft()` 将 `userInput` 回写到输入框，随后调 `controller.clearUserInput()` 清空 `userInput` 避免重复触发：
>    - `initState`：页面首次创建时检查（如异常中断后重新进入会话）
>    - `didUpdateWidget`：切会话时检查新会话是否需要回写草稿
>    - `ref.listen`：实时监听 state 变化，中断后自动回写
> 3. **设计理由**：Controller 与页面解耦--Controller 只管状态语义（清气泡、保留输入内容），不依赖 UI 控件；页面层负责将状态映射到输入框。这样 Controller 可在无页面上下文时（如后台恢复）安全执行，页面重建后自然完成回写。

> **v2.14 响应优化**（2026-08-10）：`cancel()` 改为 fire-and-forget 模式，解决用户点击停止按钮后 UI 不即时响应的问题：
> 1. **`isStopping` 状态字段**：新增 `IntermediateChatState.isStopping`（bool），cancel 时立即置 true，后台清理完成后置 false。UI 据此显示灰色脉冲动画的"正在终止"按钮，禁用发送。
> 2. **fire-and-forget**：`cancel()` 不再 `await _streamRunner.cancel()`，而是同步设置 `isStopping=true` + 清空 state，让 UI 即刻响应。`_streamRunner.cancel()` 的 Future 通过 `unawaited(_waitForCancelCompletion(cancelFuture))` 在后台完成（3 秒超时兜底）。
> 3. **竞态防护**：`StreamRunner.cancel()` 使用 `identical` 检查确保不误清新轮次的 subscription/token；`sendMessage()` 和 `_prepareAndRunRound()` 增加 `isStopping` 守卫，停止期间禁止启动新轮次。
> 4. **非流式阶段检查点**：`_runRetrievePhase` 在 embedding 请求前后、事实层检索前增加 `isCancelled` 检查；`_runPersistPhase` 入口增加检查。减少非流式阶段的停止等待时间。
> 5. **`clearTemporary()` 不清空 `isStopping`**：由 controller 的 `_waitForCancelCompletion` 后台回调管理。`clearRound()` 和 `recoverIfStuck()` 显式置 `isStopping: false`。

**保留用户消息的操作能力**（详见 DOC-09A-2 §6.4.1）：失败后若用户选择"从中断处重试"或"整轮重试"，保留的 `pendingUserMessage` 在 phase ∈ {idle, failed} 时支持完整操作——复制 / 编辑重发（`editPendingUserMessage`）/ 删除（`deletePendingUserMessage`），与持久化消息的操作集合一致。若用户在 pendingUserMessage 存在时发送新消息（非编辑重发），UI 层先弹出"覆盖未发送的消息？"确认对话框，用户确认后才覆盖。**v2.12 修订**：用户选择"整轮取消"后 `pendingUserMessage` 已回填到输入框并从列表移除，此时无 pendingUserMessage 可操作（输入框文本即为原消息内容，用户可直接编辑重发）。

**`onBackgroundInterrupt()` 后台主动中断**（2026-08-10 新增）：

App 切到后台时（`AppLifecycleState.paused`），`MainLayout._handleAppPaused` 遍历导航栈所有会话，调用各 controller 的 `onBackgroundInterrupt()`。

- **中级模式**：设置 `_backgroundInterrupted = true` + fire-and-forget 调用 `_streamRunner.cancel()`
  - `_streamRunner.cancel()` 同步设置 `_isCancelled = true`，使 `_fail()` 的 guard `if (_streamRunner.isCancelled) return;` 直接返回，**不触发 `_scheduleRetry` 自动重试**
  - `token?.cancel()` 同步取消 SSE 底层连接和 readTimer，不等 30s 超时
- **Simple 模式**：设置 `_backgroundInterrupted = true` + `_currentCancelToken?.cancel()`
  - 触发 `CancelledException` -> `_handleStreamError` 走取消分支（不持久化错误、回滚 Fork）

**为什么需要主动中断而非依赖 readTimeout 被动超时**：readTimeout 超时后 `_fail` 会触发 `_scheduleRetry` 自动重试，重试发起的新 SSE 请求让 `recoverIfStuck` 的 `isStreaming` 检测失效（`isStreaming == true`），导致用户回到前台后看到"从中断步骤继续生成"（实际是自动重试），且重试使用可能不完整的 `_round` 上下文（compacting 修改了 history 但 CompactionPoint 未持久化），导致上下文缺失（如生成前文中不存在的人物）。

**`recoverIfStuck()` 后台恢复检测**（v2.13 新增 2026-08-05）：

App 从后台恢复时，可能遇到 OS 暂停网络导致流式请求中断、但 phase 仍停在流式阶段（generating/reviewing/extracting/summarizing 等）的"卡死"状态。`recoverIfStuck()` 由 `MainLayout._handleAppResumed` 在 App 切回前台时调用，检测并恢复此类状态。

- **触发条件**（满足任一）：
  1. `_backgroundInterrupted == true`（`onBackgroundInterrupt` 设置，即使 cancel 的 async 部分尚未完成、`isStreaming` 仍为 true 也能检测到）
  2. phase 在流式阶段（generating/generatingRetry/reviewing/reviewingRetry/extracting/extractingRetry/summarizing/summarizingRetry）且 `_streamRunner.isStreaming` 为 false（流已停止但 phase 未回到 idle）
- **不覆盖的阶段**：persisting（DB 事务，无流式订阅）、retrieving（DB 查询，无流式订阅）--这些阶段通常很快完成，不靠流式状态判断
- **行为**：与 `cancel()` 一致--清空 `pendingUserMessage`（气泡消失）+ 保留 `userInput`（供页面层回写输入框），`_round` 置 null，phase 回到 idle，重置 `_backgroundInterrupted = false`
- **回写机制**：同 §7.5 cancelEntireRound 的两段式机制--Controller 清气泡 + 保留 userInput -> 页面层检测回写
- **用户提示**：返回 true 表示发生了恢复，调用方（`MainLayout`）显示 SnackBar 提示"后台生成已中断"
- **返回 false**：未检测到卡死状态（phase 已是 idle/failed，或流式仍在进行中且无后台中断标志），不做任何操作

### 7.6 阶段过渡动画规范

- 生成小窗 → 检索小窗：生成小窗折叠动画 200ms，检索小窗展开动画 200ms，串行执行
- 检索小窗 → 主区域：检索小窗折叠 200ms，主区域气泡淡入 150ms
- 失败灰显：所有元素 opacity 0.4 + 灰度滤镜，过渡 300ms
- 重试清空：旧内容淡出 150ms + 新生成小窗淡入 200ms

### 7.7 后台生成与返回手势

**设计原则**：Simple/Intermediate 模式统一由 MainLayout 外层 PopScope 处理返回手势，页面层不再包裹内层 PopScope。

**机制**：
- IntermediateChatController 是 non-autoDispose 的 StateNotifierProvider.family（按 ChatSession 隔离）
- 生成中按返回手势 → MainLayout 外层 PopScope（`canPop: false`）拦截 → `_onPopInvoked` → `_popNavigation`（setState 移除导航栈栈顶，非 Navigator.pop）
- 页面 widget unmount，但 controller 仍存活于 ProviderContainer，SSE 流不中断
- 重新进入会话 → sessionId-family provider 命中同一 controller → state 完整保留（phase / streamingGenerated / streamingReply / retrievedMemories 等）
- `loadHistory()` 有 phase 守卫（`if (state.phase != IntermediatePhase.idle) return;`），不会用数据库旧消息覆盖正在生成的 state

**侧边栏呼吸点**：`_trackGeneratingSessions` 遍历整个导航栈，聚合所有正在生成的 sessionId，在侧边栏显示呼吸点提示用户后台生成状态。

**历史决策**：v0.2 早期 IntermediateChatPage 曾有内层 PopScope + "后台继续生成" toast 提示，但因错误调用 `Navigator.of(context).pop()` 弹掉根路由导致黑屏，已移除。返回手势改由外层统一处理，toast 提示一并移除（用户不需要）。

## 8. 事件摘要结构化输出

### 8.1 EventSummary 数据结构

```dart
class EventSummary {
  final String summary;        // 事件摘要文本
  final int importance;        // 重要性 1-5
  final List<String> tags;     // 标签数组
  final int turnNumber;        // 对话轮次序号（程序填充，非 LLM 输出）
}
```

> **turnNumber 来源说明**：`turnNumber` 是程序按当前会话轮次递增填充的，**不是 LLM 输出字段**。LLM 只输出 summary/importance/tags 三项（V2 由 summarizing 步骤的工具调用/JSON 输出，见 §8.4），turnNumber 在 Controller 层写入。这避免 LLM 数错轮次导致记忆时序错乱。

### 8.2 importance 评分标准（1-5）

LLM 在请求4 summarizing 输出时按以下标准评分（V2：从请求2 reviewing 迁移到请求4 summarizing；2026-07-16 细化评分标准）：

| 分值 | 含义 | 示例 |
|------|------|------|
| 1 | 日常闲聊，无情节价值 | "你好"、"今天天气不错"、"再见" |
| 2 | 普通互动，轻微信息 | 角色介绍自己的名字、角色描述日常喜好、简单的寒暄回应 |
| 3 | 重要情节节点 | 角色遭遇困境、做出选择、到达新地点、认识新角色 |
| 4 | 关键转折点 | 角色关系变化、重大事件发生、获得/失去重要物品、战斗胜负 |
| 5 | 核心剧情节点 | 生死攸关、世界观揭示、主线推进、关键角色登场/退场、重大真相揭露 |

**评分原则**（2026-07-16 新增）：
- **默认给 3 分**：不确定时优先给 3 分，避免过度拔高
- **宁可低估也不要高估**：高 importance 会加权检索，误判会污染记忆库信噪比
- **纯对白不自动加分**：只有对白内容揭示剧情节点才加分，纯寒暄/闲聊即使篇幅长也不加分
- **纯战斗不自动加分**：只有战斗结果影响剧情走向才加分，无后果的切磋/训练保持 3 分

**用途**：
- 检索阶段的 importance 加权（`importanceWeight > 0` 时 `(importance/5) × importanceWeight` 加到 finalScore，见 DOC-09A-1 §3.6）
- ~~关键事件加权~~（2026-07-16 起默认不生效：`keyEventThreshold` 默认 999、`keyEventBoost` 默认 1.0，与 importanceWeight 功能重叠故统一）
- UI 层可选的事件重要性标记（v0.2 不展示，v0.3 HUD 可显示）

### 8.3 tags 生成规范

- 数量：0-5 个，由 LLM 根据事件内容自主提取
- 格式：短词组（2-8 字），如 `["角色冲突", "记忆唤醒"]`、`["战斗", "受伤"]`
- 用途：v0.2 仅作为元数据存储，不参与检索；v0.3 可作为 HUD 事件分类标签
- LLM 提取规则：覆盖事件涉及的核心角色、动作、情感、场景

### 8.4 结构化输出格式（V2 四步）

> **V2 四步重构修订**（2026-07-10）：事件摘要的产出从"请求2 reviewing 的分隔标记/JSON 输出"迁移到**请求4 summarizing 独立步骤**。summarizing 采用工具调用 → JSON 模式 → 提示词约束降级链（详见 DOC-09A-2 §6.9.0），不再使用分隔标记。下方"V1 流式分隔标记格式"为历史方案，已废弃。

**V2 summarizing 步骤输出**（请求4，结构化）：
- 工具调用模式：LLM 调用 `extract_event_summary` 工具，输出 `{summary, tags, importance}`
- JSON 模式降级：LLM 直接输出 `{"summary":"...","importance":3,"tags":["..."]}` JSON
- 提示词：`kExtractSummaryToolPrompt`（兼容工具调用与 JSON 两种方式）
- 解析：`SummarizePhaseHandler` 调 `parseEventSummary`，解析失败 → 抛 `SummarizeFailedException` → E017

**V2 extracting 步骤输出**（请求2，结构化；2026-07-16 修订）：
- 工具调用模式：LLM 调用 `extract_keywords` 工具，输出 `{entities, events}`
- JSON 模式降级：LLM 直接输出 `{"entities":["古碑"],"events":["碑文显现"]}` JSON
- 提示词：`kExtractKeywordsToolPrompt` + `kExtractKeywordsToolDefinition`
- 解析：`ExtractPhaseHandler` 调 `parseKeywords`，解析失败 → 抛 `ExtractFailedException` → E013
- **数量硬限制**：entities ≤ 3 个，events ≤ 2 个，合计 ≤ 5 个。提示词加入硬性约束，`kExtractKeywordsToolDefinition` 的 description 同步说明
- **质量要求**：entities 必须是具体名词（人名/地名/物品名），events 必须是具体事件（动宾短语）。禁止条款：禁止概括性短语（如"剧情"、"对话"）、禁止提取所有角色名（只提取与本轮事件相关的）。提示词加入正反例：
  - 正例：entities=["古碑","青云门后山"]，events=["碑文显现"]
  - 反例：entities=["角色","场景"]，events=["发生了事情"]

#### 8.4 V1 流式分隔标记格式（已废弃，2026-07-08）

> **V1 历史方案**：以下分隔标记格式在 V2 四步重构后不再使用（文本步骤纯文本输出，结构化步骤独立请求）。保留供历史参考。旧配置项 `draft_separator` / `event_summary_separator` 标注 `@Deprecated`。

请求2的流式输出采用分隔标记区分 reply 和 eventSummary：

```
{正常回复文本，可能多行}

<<<EVENT_SUMMARY>>>
{"summary":"...","importance":3,"tags":["..."]}
```

**解析逻辑**：
1. 流式过程中，遇到 `<<<EVENT_SUMMARY>>>` 标记前的内容作为 `streamingReply`
2. 遇到标记后，标记之后的内容作为 eventSummary JSON 流式缓冲
3. 流结束后，解析 eventSummary JSON

### 8.5 解析容错

> **V2 修订**（2026-07-10）：解析容错逻辑迁移到 `ExtractPhaseHandler` / `SummarizePhaseHandler`，复用 `stream_marker_parser.dart` 的 `parseKeywords` / `parseEventSummary`（含 markdown 剥离 + JSON 提取容错）。下方表格为 V1 分隔标记模式的容错规则，V2 结构化步骤的容错由降级链处理（详见 DOC-09A-2 §6.9.0）。

| 异常情况 | 处理策略 |
|---------|---------|
| 未找到分隔标记 | 整个输出作为 reply，eventSummary 为空 → 触发重试（带"严格输出格式"提示） |
| eventSummary JSON 解析失败 | 触发重试（带"严格 JSON"提示），重试仍失败 → 整轮失败 |
| importance 超出 1-5 | clamp 到 [1, 5] 范围 |
| tags 不是数组 | 降级为空数组 `[]` |
| summary 为空字符串 | 触发重试，重试仍失败 → 整轮失败 |

### 8.6 结构化输出开关（V2 四步）

> **V2 四步重构修订**（2026-07-10）：V1 的 `json_fallback` / `inject_response_format` 开关在 V2 中标注 `@Deprecated`（不再影响四步流程行为，无任何调用点，仅保留供 fromJson 兼容旧配置，正式发版时移除）。V2 改用 `tool_calling_enabled` 控制结构化输出降级链。会话级覆盖机制已迁移到 `_applyToolCallingOverride`（仅覆盖 `tool_calling_enabled`）。

**V2 配置项** `intermediate.stream.tool_calling_enabled`（默认 `true`）：
- `true`（默认）：extracting/summarizing 优先尝试工具调用（`tools` + `toolChoice=required`），供应商不支持时降级到 JSON 模式
- `false`：跳过工具调用，直接走 JSON 模式（兼容已知不支持的供应商）

降级链详见 DOC-09A-2 §6.9.0。`json_mode_override` 会话级覆盖机制已迁移为仅覆盖 `tool_calling_enabled`（`_applyToolCallingOverride`），不再操作 `@Deprecated` 的 `jsonFallback`/`injectResponseFormat`。

#### 8.6 V1 JSON 兜底开关（已废弃，2026-07-08）

> **V1 历史方案**：以下 `json_fallback` / `inject_response_format` 双开关方案在 V2 四步重构后不再影响流程行为，无任何调用点，仅保留供 fromJson 兼容旧配置。详见上方 V2 修订说明。

配置项 `intermediate.stream.json_fallback`（默认 `true`，用户决策：分隔标记模式在国产模型上不稳定，默认走 JSON 方案）：
- `false`：使用分隔标记格式（性能更好，流式体验更佳）
- `true`（默认）：要求 LLM 输出完整 JSON，流式过程中缓冲全部内容，结束后解析

JSON 兜底开关用于分隔标记格式在某些 LLM 上不稳定时的备选方案。

**`inject_response_format` 配合开关**（新增）：`json_fallback=true` 时，是否真正向 LLM 请求注入 OpenAI `response_format: {type: 'json_object'}` 由 `intermediate.stream.inject_response_format`（默认 `true`）控制。两者关系为：

- `jsonMode = jsonFallback && injectResponseFormat`（两者均开才注入 response_format）
- `jsonFallback=true` + `injectResponseFormat=false`：仅靠提示词约束 LLM 输出 JSON（不注入 response_format），保留对照能力
- `jsonFallback=true` + `injectResponseFormat=true`：提示词约束 + 请求体 response_format 双重强制，稳定性最高
- `jsonFallback=false`：`injectResponseFormat` 无意义（分隔标记模式输出为混合格式，与 response_format 互斥），控制器会告警

> **设计意图**：`injectResponseFormat` 默认 `true`（与 `jsonFallback` 同步），用户决策默认启用 JSON 方案以获得最高稳定性。需要对照分隔标记模式时通过开关关闭。支持 response_format 的 LLM 能显著降低 E011/E015 格式错误率。

**UI 暴露**（v1.10 新增；V2 四步扩展 2026-07-10；会话级覆盖迁移 2026-07-10）：V2 配置项 `tool_calling_enabled` 在两处提供 UI 开关，对非技术用户友好：

| 会话设置面板 `IntermediateJsonModeSelector` | 3 态下拉（使用全局设置 / 启用 / 禁用） | `chat_sessions.json_mode_override`（NULL/true/false，schemaVersion ≥ 17，字段名保留兼容） | 会话级覆盖。`null`=跟随全局；`true`/`false`=强制覆盖 `stream.toolCallingEnabled` |

> **以下为 V1 两步生成历史方案**（已废弃，2026-07-10）：V2 四步重构后，generating/reviewing 改为纯文本输出（无 JSON），extracting/summarizing 改为工具调用降级链。下方的"两步生成 JSON 格式"、E011/E015 错误码映射、分隔标记模式差异均为 V1 历史内容，保留供参考。

**两步生成的 JSON 格式**：

| 请求 | JSON 格式 | 解析函数 |
|------|----------|---------|
| 请求1（生成） | `{"draft":"生成正文","keywords":["关键词1","关键词2"]}` | `parseDraftJsonResult` |
| 请求2（审查） | `{"reply":"回复正文","eventSummary":{"summary":"...","importance":N,"tags":[...]}}` | `parseReviseJsonResult` |

**错误码映射**（jsonFallback=true 时）：
- 生成 JSON 解析失败（非法 JSON / draft 缺失或为空）→ **E011**（生成格式错误）→ 触发 `jsonFormatRetry` 自动重试
- 审查 JSON 解析失败（非法 JSON / reply 缺失 / eventSummary 缺失或字段不全）→ **E015**（审查格式错误）→ 触发 `jsonFormatRetry` 自动重试

**与分隔标记模式的差异**：
- 流式过程中不调用 `onDelta`（不流式显示），全部缓冲到 StringBuffer
- 流结束后一次性解析完整 JSON，提取正文 + 结构化字段
- 解析成功后将完整正文一次性设入 `streamingGenerated` / `streamingReply`（供 persisting 阶段 UI 显示）
- 提示词改用 JSON 兜底版（`kGenerateSuffixPromptJson` / `kReviewSuffixPromptJson`），明确要求"不要输出 JSON 以外的任何内容、禁止 markdown 代码块包裹"
- E011/E015 重试时追加的"严格格式提示"内容随 jsonFallback 切换（要求合法 JSON 而非分隔标记）

> **实现说明**（2026-07-02）：JSON 兜底开关已实现。`StreamConfig.jsonFallback` 字段从"定义但无消费者"转为完整可用：`IntermediateContextBuilder` 按 flag 选提示词、`IntermediateChatController._runStream` 按 flag 切缓冲模式、`stream_marker_parser.dart` 新增 `parseDraftJsonResult` / `parseReviseJsonResult`。E011 在分隔标记模式下不触发（生成缺标记时降级为空关键词），仅在 jsonFallback 模式下作为生成 JSON 解析失败的错误码。

## 9. 错误码定义

中级模式新增错误码 E010-E018，共 9 个（V2 四步重构后 E011/E015 不再产生，E013/E017 语义重新定义）：

| 错误码 | 含义 | 触发场景 | 用户提示 | 处理策略 |
|--------|------|---------|---------|---------|
| E010 | 生成失败 | 请求2 generating 重试用尽 | "生成失败，请重试" | 整轮失败，用户重试 |
| E011 | ~~生成格式错误~~（V2 弃用） | V1: 分隔标记缺失/JSON 解析失败；V2 不再产生（generating 纯文本输出） | "生成格式异常，请重试" | V2 保留映射供向后兼容，实际不触发 |
| E012 | 检索完全失败 | FTS5 + Vector 两路都失败 | "记忆检索失败，请重试" | 整轮失败，用户重试 |
| E013 | 关键词提取失败（V2 重新定义） | 请求1 extracting 工具调用/JSON 解析失败 | "关键词提取失败，请重试" | 自动重试（extractingMaxRetries），用尽→整轮失败 |
| E014 | 审查失败 | 请求3 reviewing 重试用尽 | "审查失败，请重试" | 整轮失败，用户重试 |
| E015 | ~~审查格式错误~~（V2 弃用） | V1: eventSummary JSON 解析失败；V2 不再产生（reviewing 纯文本输出） | "回复格式异常，请重试" | V2 保留映射供向后兼容，实际不触发 |
| E016 | 流式中断 | SSE 连接中断 | "网络中断，请重试" | 重试1次，仍失败→整轮失败 |
| E017 | 事件摘要生成失败（V2 重新定义） | 请求4 summarizing 工具调用/JSON 解析失败 | "摘要生成失败，请重试" | 自动重试（summarizingMaxRetries），用尽→整轮失败 |
| E018 | 持久化失败 | drift transaction 异常 | "保存失败，请重试" | 事务回滚，整轮失败，用户重试 |

> **V2 错误码语义迁移**（2026-07-10）：
> - **E013 复用**：V1 = "检索部分失败"（静默降级，不提示用户）；V2 = "关键词提取失败"（extracting 步骤，可重试）。V1 的"检索部分失败"在 V2 中不再使用错误码，改为内联静默降级（单路异常时降级用单路结果，无错误码）。
> - **E017 复用**：V1 = "Embedding 生成失败"（静默降级，has_embedding=false）；V2 = "事件摘要生成失败"（summarizing 步骤，可重试）。V1 的"Embedding 生成失败"在 V2 中不再使用错误码，改为内联静默降级（embedding 失败时 has_embedding=false，事务仍提交，无错误码）。
> - **E011/E015 弃用**：V2 中 generating/reviewing 输出纯文本无格式约束，E011（生成格式错误）/E015（审查格式错误）不再产生。`RetryScheduler` 保留其映射供向后兼容，但实际不触发。格式错误现由 E013（extracting）/E017（summarizing）覆盖。
> - E013/E017 的专门提示文案已由 `StoryFailureClassifier.resolveFailureMessage` 与 i18n `messages.e013` / `messages.e017` 覆盖。

**错误码返回规范**：所有错误码通过 `FailureContext` 结构传递，包含：
- `errorCode`：错误码（E010-E018）
- `failedPhase`：失败阶段（V2: generating/extracting/retrieving/reviewing/summarizing/persisting）
- `errorMessage`：用户可见的错误提示（通俗层，由 `StoryFailureClassifier.resolveFailureMessage` 按 errorCode + category 解析）
- `retryable`：是否可重试（V2: E013/E017 可重试；V1 的 E013"检索部分失败"/E017"Embedding 失败"为静默降级不进 failed 状态）
- `errorCategory`：错误分类（`ErrorCategory` 枚举）。用于 UI 分层展示和技术诊断。默认 `unknown`，由失败分类器（`StoryFailureClassifier.classifyError`）在 `_fail` 时根据异常类型推断。手动覆盖优先于分类器结果（V2: E013/E017 固定为 `format`，E018 固定为 `persist`；V1: E011/E015 固定为 `format`）
- `httpStatus`：HTTP 状态码（`int?`）。网络/服务器错误时携带；非 HTTP 错误（格式异常、配置缺失）为 null
- `rawError`：原始异常信息（`String?`，异常 `toString()` 截断前 2000 字符，后放宽）。供技术用户诊断，UI 在"查看详情"中展示

**ErrorCategory 枚举**（9 值）：

| 分类 | 含义 | 典型错误码 | 用户建议 |
|------|------|-----------|---------|
| config | 配置错误（未配置供应商/模型/API Key） | E010 | 前往设置配置 API 供应商和模型 |
| network | 网络错误（连接失败/中断） | E010/E012/E016 | 检查网络连接后重试 |
| auth | 认证错误（401/403） | E010 | API Key 无效或无权限 |
| rateLimit | 限流（429） | E010 | 请求过于频繁，稍后重试 |
| server | 服务器错误（5xx/其他 4xx） | E010/E012/E014 | 服务器异常，稍后重试 |
| timeout | 超时（connection/receive/send_timeout） | E010 | 请求超时，检查网络后重试 |
| format | 格式错误（工具调用/JSON 解析失败） | E013/E017（V2）；~~E011/E015~~（V1 弃用） | 模型输出格式不符，可重试或切换模型 |
| persist | 持久化失败（drift transaction 异常） | E018 | 数据库写入失败，请重试 |
| unknown | 未分类（兜底） | 任意 | 请重试，如持续失败请反馈 |

> **分类规则**（`StoryFailureClassifier`）：`AppHttpException` 按 code/statusCode 分流——401/403→auth、429→rateLimit、5xx→server、其他 4xx→server、`connection_timeout`/`receive_timeout`/`send_timeout`→timeout、`connection_error`→network。非 HTTP 异常（如配置缺失）由调用方手动指定 `errorCategory` 参数覆盖。详见 DOC-09A-2 §6.8。

### 9.1 Simple 模式错误码（D4 扩展）

**背景**：D4（v0.2 诊断包）为 Simple 模式补全结构化错误处理，使 Simple 模式失败记录可写入 `failure_logs` 表并在诊断页（D3）与中级模式记录统一展示。Simple 模式无状态机、无失败阶段、无自动重试，故错误码体系与中级 E010-E018 平行但更精简。

**Simple 模式错误码 S001-S009**（共 9 个，D4 新增）：

| 错误码 | 分类 | 触发场景 | 用户提示（持久化到助手消息） |
|--------|------|---------|---------|
| S001 | config | 未配置供应商/模型/API Key | "配置不完整，请前往设置检查 API 供应商和模型（S001）" |
| S002 | network | 网络连接失败（connection_error / StreamError） | "网络连接失败，请检查网络后重试（S002）" |
| S003 | auth | 401/403 | "API Key 无效或无权限（S003）" |
| S004 | rateLimit | 429 | "请求过于频繁，请稍后重试（S004）" |
| S005 | server | 5xx + 其他 4xx | "服务器异常，请稍后重试（S005）" |
| S006 | timeout | connection/receive/send_timeout + TimeoutException | "请求超时，请检查网络后重试（S006）" |
| S007 | format | 模型响应格式异常（预留，当前 Simple 模式无格式校验） | "模型响应格式异常（S007）" |
| S008 | persist | 本地存储失败（drift 异常） | "本地存储失败（S008）" |
| S009 | unknown | 兜底 | "发生错误，请重试（S009）" |

**与中级 E010-E018 的差异**：

| 维度 | Simple（S001-S009） | Intermediate（E010-E018） |
|------|---------------------|--------------------------|
| 错误码粒度 | 按"错误分类"直接映射（1 分类 1 错误码） | 按"失败阶段 + 分类"细分（同分类可能有多个错误码，如 E010/E012/E014 同为 server 类） |
| 失败阶段 | 无（Simple 无状态机） | V2: generating/extracting/retrieving/reviewing/summarizing/persisting |
| 自动重试 | 无 | 按错误码查询 RetryConfig 决定 |
| 错误上下文 | `SimpleErrorContext`（4 字段：errorCode/errorCategory/httpStatus/rawError） | `FailureContext`（6 字段：含 failedPhase/retryable） |
| 分类表示 | `String`（值与 `ErrorCategory.name` 一致，避免 Simple domain 反向依赖 intermediate feature） | `ErrorCategory` 枚举 |
| UI 展示 | 错误作为助手消息 `error` 字段持久化，气泡内 `_ErrorMessage` 展示「友好提示（错误码）」 | FailureBar 顶部横幅 + 消息卡片错误态 + "查看详情"展开技术信息 |
| 诊断页展示 | `failure_logs` 表记录，mode='chat'，failedPhase=null | `failure_logs` 表记录，mode='intermediate'，failedPhase=非 null |

**分类器**（`SimpleFailureClassifier`，D4 新增）：
- `classifyError(error)`：与 `StoryFailureClassifier.classifyError` 同源逻辑——`AppHttpException` 按 statusCode/code 分流、`TimeoutException` → timeout、`_StreamErrorException`（toString 含 "StreamError"）→ network、其他 → unknown
- `errorCodeFromCategory(category)`：9 分类 → S001-S009 映射
- `resolveMessage(category)`：按分类返回 i18n `chat.failure.messages.<category>` 文案
- `formatDisplay(category, errorCode)`：组合「友好提示（错误码）」用于助手消息持久化展示

**Controller 接入**（`ChatModeController._recordError`，D4 新增）：构造 `SimpleErrorContext` + `unawaited(_failureLogRepository.insertLog(...))` 静默写入 failure_logs 表（mode='chat'，failedPhase=null）。9 处 catch 块统一调用 `_recordError`，错误分类可由 `overrideCategory` 手动覆盖（如配置检查 → config、本地存储 → persist、压缩失败 → unknown）。

> **设计决策**：Simple 模式 `errorCategory` 用 `String` 而非 `ErrorCategory` 枚举。`ErrorCategory` 枚举定义在 `intermediate_chat_state.dart`，Simple（chat domain）import 它会违反 Clean Architecture（跨 feature 依赖）。`String` 值与 `ErrorCategory.name` 一致（'config'/'network'/.../'unknown'），failure_logs 表本就存 String，类型一致，诊断页可统一展示两种模式的记录。

> **v2.12 contextBudget 设计说明**（2026-07-30）：
> - **上限固定不算 token，下限动态算 token**：上限代表"最大容忍"（50% 是"再多就压缩"的硬线，对所有模型都合理）；下限代表"压缩后剩余"（必须保证氛围语气细节足够，用绝对 token 数 32K 反推最合理）。
> - **非技术用户友好**：用户切换模型时，下限自动适配（128K 模型下限 33.3%、1M 模型下限 10%），无需手动调整。
> - **下限动态计算公式**：`recentMinRatio = max(0.10, 32000 / availableWindow)`，clamp 到 [0.10, 0.45]。
> - **约束条件**：`compactionTriggerRatio(0.5) > recentMinRatio(动态≥0.10)`，`compactionTriggerRatio + retrievalRatio + 0.05 + 0.10 ≤ 1.0`。当 `recentMinRatio + retrievalRatio + 0.05 + 0.10 > 0.5` 时（下限过高挤占其他区），UI 给出警告提示。

**generation 组**（故事模式独立生成参数，v1.12 新增 2026-07-18）：

故事模式不再复用 `broadcastChat` 的 temperature/topP/maxTokens/penalty，改用本组独立配置，以适配故事模式对创造性、话题多样性、用词丰富度的更高要求。会话级覆盖优先级高于本组（详见 §10.2）。

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| temperature | double | 0.8 | 温度参数（0.0-2.0）。控制生成随机性，故事模式略高于 Simple 0.7 以鼓励创造性，但不过高以免逻辑混乱 |
| top_p | double | 0.95 | 核采样（0.0-1.0）。与 temperature 配合控制质量，0.95 在保持质量的同时允许适度发散 |
| max_tokens | int | 8192 | 单次生成最大 token 数。0 表示不设置应用层输出上限，由模型或供应商决定实际长度；任意正整数均可配置 |
| presence_penalty | double | 0.6 | 存在惩罚（-2.0 ~ 2.0）。鼓励 LLM 谈论新话题，token 一旦出现后续采样统一施加惩罚。正值越大越鼓励新话题，故事模式用 0.6 避免剧情单调重复 |
| frequency_penalty | double | 0.3 | 频率惩罚（-2.0 ~ 2.0）。减少重复用词，token 每多出现一次惩罚递增。故事模式用 0.3 避免重复描写（如"她笑了笑"反复出现），保持较低值避免影响正常修辞 |

> **默认值调研依据**（综合类似产品）：
>
> | 参数 | 故事模式默认 | SillyTavern | ChatBox | Qwen | DeepSeek | 设计理由 |
> |------|--------------|-------------|---------|------|----------|----------|
> | temperature | 0.8 | 0.5-0.9 | 0.7 | 0.8 | 0.7 | 故事模式偏创造性，比 Simple 0.7 略高 |
> | top_p | 0.95 | 0.9-0.95 | 1.0 | 0.8 | 1.0 | 配合 temperature 控制质量，略低于 Simple 1.0 |
> | max_tokens | 8192 | - | 4096 | 8192 | 4096 | 为推理 token 和长篇故事回复留出余量；0 可交由模型/供应商决定 |
> | presence_penalty | 0.6 | 0.6 | 0 | 0 | 0 | 鼓励新话题，避免剧情单调重复（SillyTavern 推荐 0.6） |
> | frequency_penalty | 0.3 | 0.3 | 0 | 0 | 0 | 减少重复用词，避免描写冗余（SillyTavern 推荐 0.3） |
>
> **penalty 参数说明**：`presence_penalty` 和 `frequency_penalty` 都是 OpenAI Chat Completions API 的标准参数（[文档](https://platform.openai.com/docs/api-reference/chat/create)），所有兼容 OpenAI 协议的供应商（DeepSeek、OpenRouter、Qwen 等）均支持。两者都属于"软惩罚"——不影响 token 是否被采样，只在采样时调整 logits：
> - presence_penalty：token 一旦出现，后续统一施加惩罚（不管出现几次）→ 鼓励新话题
> - frequency_penalty：token 出现次数越多，惩罚越大 → 减少重复用词
> - 同时使用时效果叠加，建议从小值开始调整

> - **支持全局 + 会话级两层配置**（**2026-07-21 配置架构重构**修订）：原先仅全局、不暴露会话级覆盖的约束已撤销。会话级通过 `chat_sessions` 表新增 8 列 + `SessionPhaseModels` 实体承载。
> - **空串语义**（**2026-07-21 配置架构重构**修订）：某步骤的会话级 modelId 和 presetId 均为空串时，回退到该步骤的全局 `phase_models.<phase>_*`；全局仍为空串时：generating 阶段直接报错 E010（不再回退到 Simple/broadcastChat），其他阶段降级复用 generating 阶段的 NamingConfig。
> - **非阶段特定调用**（**2026-07-21 配置架构重构**修订）：控制器中 `_autoNameSession`（标题生成）改用 `ConfigurationResolver.resolveTitleNamingConfig()`（无参数，从 `common.title_model` 全局配置读取，详见下方 common.title_model 配置组）；`_maybeConsolidateMemories`（记忆提炼）等非四步流程的 LLM 调用，仍复用 generating 阶段的 NamingConfig（`RoundContext.namingConfig` 别名）。

#### common.title_model 配置组（**2026-07-21 配置架构重构**新增）

跨模式共享的会话标题生成模型配置，独立于业务模型。位于 `default_config.json` 顶层 `common` 节点下，与 `intermediate` 节点平级。Simple/Intermediate 模式的 `_autoNameSession` 均通过 `ConfigurationResolver.resolveTitleNamingConfig()` 读取本组配置。

| 参数 | 类型 | 默认值 | 说明 |
|------|------|--------|------|
| preset_id | String | ""（空串） | 标题模型供应商 ID。空串表示未配置，回落到生成模型（见下方降级策略） |
| model_id | String | ""（空串） | 标题模型 ID。空串表示未配置，回落到生成模型（见下方降级策略） |

- **使用方**：`ConfigurationResolver.resolveTitleNamingConfig()`（无参数，从 `common.title_model` 全局配置读取），由 Simple/Intermediate/Advanced 三模式的 `_autoNameSession` 调用
- **降级策略**（**2026-09-09 标题模型三级优先级**修订）：
  1. `common.title_model` 已配置 → 用配置的标题模型生成标题
  2. 未配置或解析失败 → 回落到该会话生成正文的模型（Simple 走 `resolveBroadcastGeneratingNamingConfig`（会话级模型 > `broadcast_chat.model_id`）、故事走 `resolveIntermediatePhaseNamingConfig` 'generating'、导演走 `resolveAdvancedGeneratingNamingConfig`）
  3. 生成模型也不可用或 LLM 生成失败 → `SessionTitleGenerator.fallbackTitle`（取用户首条消息前 20 字符）
- **持久化**：`SettingsRepository` user_overrides（key: `common.title_model.preset_id` / `common.title_model.model_id`）
- **UI 入口**：通用设置 → 高级子页 → `TitleModelSection`

> **设计动机**（**2026-07-21 配置架构重构**）：原设计 Simple/Intermediate 模式的标题生成复用各自模式的默认模型（`broadcastChat.modelId` / `intermediate.modelId`），导致：
> 1. 故事模式删除 `intermediate.modelId` 中间层后，标题生成无默认模型可复用
> 2. 标题生成为短文本任务（4-12 字），用业务模型（ generating 生成模型 / broadcastChat 模型）成本高、延迟大
> 3. 跨模式复用同一标题模型更合理（标题生成质量与业务模式无关）
>
> 独立配置节点 `common.title_model` 解决以上问题：跨模式共享、独立于业务模型、用户可配置小模型降本。

**consolidation 组**（批量记忆提炼）：

> - **5 个参数对应 5 层健康度防护**：`modify_confidence_threshold` 对应三重防护第三层；`max_updates_per_3turns` + `max_attr_value_length` 对应 5 层健康度防护的第 4/5 层；`key_entity_importance_threshold` + `injection_max_entities` 控制检索注入行为

> **与 v0.3 事实层配置的关系**：本组参数是 v0.3 Advanced 模式事实层配置的子集。v0.3 将追加 `fact_extraction_model` / `fact_conflict_resolution_strategy` / `fact_archive_after_rounds` 等参数。详见 DOC-11 §14.2 v0.3 升级路径、DOC-03 v0.3 设计（待建）。

**交互细节**：
- 压缩触发线条（v0.2.2 改名自"上限条"）：固定 50%，灰色不可拖动，仅展示百分比（不展示 token 数，用户决策：压缩触发线没必要算 token）
- 下限条：可拖动调整，展示百分比 + 预估 token 数（如 "33.3% (≈32K token)"），让用户感知"压缩后剩多少"
- 检索区条：可拖动调整，展示百分比 + 预估 token 数（如 "15% (≈14K token)"）
- 拖动下限/检索区时，实时校验约束条件，冲突时红色高亮 + 警告文案
- 切换模型时，下限自动重算（如果用户未自定义，即 `recentMinRatioOverride` 为 null）
- 当 `recentMinRatio + retrievalRatio + 0.05 + 0.10 > 0.5` 时（下限过高挤占其他区），UI 给出警告提示"下限过高，建议降低或切换更大上下文模型"

**审查开关**：
- 复用现有 `Switch` 组件样式
- 开启时显示副文案"将增加 1 次 LLM 请求，延迟增加约 10-20 秒"
- 关闭时（默认）生成即最终，3 次 LLM 调用；开启时 4 次 LLM 调用

| 配置入口 | 展示内容 | 可修改项 |

**草稿会话物化策略**（v2.12 新增；v2.24 修订 2026-08-03）：

3 个审查与预算字段物化策略分化（v2.24 调整）：

- **`recentMinRatioOverride` / `retrievalRatioOverride`（v2.24 改为快照独立模式）**：物化时从 `GlobalDefaultsSnapshot.contextBudget` 复制全局当前值到会话级字段（非 NULL）。后续全局配置变更不影响已物化的会话。会话设置面板「上下文预算」区段（§6.8 区段 5）提供「重置为全局」按钮，点击重新调用 `snapshotIntermediateDefaults()` 复制当前全局值。设计动机：上下文预算直接决定 token 分配，与模型 contextWindow 强相关；物化后用户切换会话模型时预算仍按物化时刻的全局基准计算，避免全局后续调整导致已设定故事节奏漂移。
- **`reviewEnabledOverride`（仍保留 NULL 语义）**：不复制全局默认值。理由：(1) 审查开关是离散布尔态，全局 `intermediate.reviewEnabled` 始终作为会话级字段的回退；(2) 避免每个会话复制字段造成数据冗余；(3) 用户如需为某故事单独配置，在会话设置面板「审查」区段手动设置即可。

- **系统提示词**：复制 `intermediate.system_prompt`（或草稿阶段用户已填写的值）到 `chat_sessions.system_prompt`
- **以下字段仅保留草稿值（NULL = 不覆盖）**：`max_context_messages` / `reasoning_effort` / `json_mode_override`
- **分步骤模型配置**（**2026-07-21 配置架构重构**新增）：8 个会话级分步骤模型字段（`drafting_preset_id` / `drafting_model_id` / `extracting_preset_id` / `extracting_model_id` / `revising_preset_id` / `revising_model_id` / `summarizing_preset_id` / `summarizing_model_id`）**保留 NULL（不复制全局默认值）**。理由：(1) 分步骤模型配置是可选的会话级覆盖，多数用户使用全局 `intermediate.phase_models.*` 即可；(2) 全局 `phase_models` 始终作为会话级字段的回退（两层优先级链：会话级 phase > 全局 phase），保留 NULL 时自动回退到全局；(3) 避免每个会话复制 8 个字段造成数据冗余。用户如需为某故事单独配置某阶段的模型，在会话设置面板「分步骤模型」区段（`IntermediatePhaseModelsSection` 会话级实例）手动设置即可

> **设计理由**：复制实际值（而非保持 NULL）后，后续修改全局配置不会影响已创建的会话——每个故事"诞生时"获得一份独立的配置快照，符合"每个对话独立配置"的产品诉求。`ConfigurationResolver.resolveIntermediateSettings` 仍按"会话级 > 全局"优先级合并，物化后的会话字段非 NULL 时直接覆盖全局值，物化后用户在面板修改值也直接写入会话字段。**例外**（**2026-07-21 配置架构重构**）：分步骤模型配置字段保留 NULL，由 `resolveIntermediatePhaseNamingConfig` 按两层优先级链动态解析（会话级 NULL → 自动回退到全局 phase_models），兼顾"独立配置快照"与"避免数据冗余"。

**会话级生成参数优先级**（v1.12 新增 2026-07-18，`ConfigurationResolver.resolveIntermediateSettings`）：
