# LMStory 中级模式详细设计（一）：状态机与检索

> **2026-08-11 当前状态**：状态顺序以 `compacting? → extracting → retrieving → generating → reviewing? → summarizing → persisting` 为准。较早的“压缩摘要兼任宏摘要”“独立宏摘要废弃”结论已被后续实现取代：累积压缩摘要延续上下文，分段宏摘要写入 macro 记忆并参与长期检索。关键实体默认阈值为 5；Schema 当前为 43。旧 HUD/`update_world` 仅属废弃历史。
>
> **2026-08-22 压缩管线修复说明**（四项，以代码为准）：
> 1. **压缩摘要次轮回填**：轮次启动时从持久化历史提取摘要（`StoryCompactionService.extractPersistedSummary`）回填 `RoundContext.compactionSummary`。修复此前摘要消息（role=system）被各阶段 user/assistant 过滤器静默丢弃、压缩后摘要从所有请求中消失的问题（剧情丢失 + 缓存前缀断裂）。故事模式与导演模式同修。
> 2. **累积式压缩真正落地**：`compact()` 现将 `existingCompactionSummary` 以独立 system 消息（`kIntermediateCompactionExistingSummaryInjection` 前缀）并入压缩 LLM 输入，新摘要须完整继承旧摘要信息。修复此前旧摘要从不进入压缩输入、再次压缩即丢失更早剧情的问题（v0.2.3 文档声称的"基于旧摘要+新对话生成"此前未实现）。
> 3. **保留量上限受触发线包络约束**（消除压缩死亡螺旋）：保留量上限 = (触发线 − 检索预留 − 基础上下文×1.2) × 0.7，低于原 recentMinTokenTarget（clamp 10%-45% 可用窗口）时取上限值。修复此前 保留量+检索预留+基础上下文 恒超触发线（contextWindow ≲ 100k 的模型）导致每轮重复压缩、每轮重写摘要的问题。
> 4. **边界查找改用 tiktoken 精确计数**（`TokenCounter.countTokensForEach`，单次 Isolate 批量编码）：原 chars/3.5 估算按英文校准，中文内容偏差 2-4 倍，会架空保留量约束并把中文会话过度压缩到保底 4 条。
>
> 另：extracting 步骤末条 user 消息的任务前缀包装（2026-08-05 方案）**保留**。2026-08-22 曾试行"任务说明改为独立稳定 system 消息 + 末条 user 消息保持原文"以对齐 prompt cache，真机验证复现 08-05 记录的失败模式（模型无视远处 system 说明，把原文末条 user 消息当角色扮演续写、输出正文，extract 持续 E013），已于 2026-08-23 回滚。结论：extract 的任务标记必须紧贴输入内容，缓存对齐的收益（每轮一条 user 消息）不值得冒续写风险；预览侧 `buildExtractMessagesV2` 已同步为与请求侧一致的包装结构（此前预览显示原文、与实际请求不符）。

## 1. v0.2.2 七步事务状态机

### 1.1 状态定义

中级模式每轮对话的核心状态机包含 9 个正常状态（7 个主阶段 + idle/failed）（v0.2.2 修订：废弃 macroSummarizing 辅助阶段，压缩摘要兼任宏摘要）：

| 状态 | 说明 | 数据层操作 | UI 表现 |
|------|------|-----------|--------|
| `idle` | 空闲，等待用户输入 | 无 | 正常输入框 |
| `compacting` | CompactionPoint 压缩中（条件触发） | 无（仅生成摘要存内存，持久化由 persisting 阶段同事务写入） | 上下文压缩指示（failure_bar 显示"上下文压缩"） |
| `extracting` | 请求1关键词提取中（结构化）— v0.2.2 前置到 generating 之前 | 无 | 提取小窗"提取关键词中" |
| `retrieving` | 程序检索中 — v0.2.2 改为 5 路并行检索 | 只读（FTS5 3 路 + Vector 2 路查询） | 检索小窗"检索记忆中" |
| `generating` | 请求2生成正文生成中（纯文本）— v0.2.2 注入记忆 | 无 | 生成面板/主区域流式显示（reviewEnabled=false 时生成即最终） |
| `reviewing` | 请求3审查修正生成中（纯文本）— v0.2.2 可选，默认关闭 | 无 | 主区域流式显示回复（仅 reviewEnabled=true 时进入） |
| `summarizing` | 请求4事件摘要生成中（结构化） | 无 | 摘要小窗"生成摘要中" |
| `persisting` | 持久化中 | drift transaction 写入 | 回复正常显示，底部"保存中" |
| `failed` | 整轮失败（重试用尽） | 无（事务已回滚） | 灰显 + 重试按钮 |

> 另有 5 个重试状态（`generatingRetry` / `extractingRetry` / `retrievingRetry` / `reviewingRetry` / `summarizingRetry`），由 `RetryScheduler.toRetryPhase` 映射，用于 UI 区分"首次尝试"与"重试中"。
>
> ~~`macroSummarizing` 状态已废弃~~（v0.2.2，2026-07-30）：原 DOC-10 v1.1 设计的独立 macroSummarizing 阶段（条件触发宏摘要生成）已废弃。压缩摘要兼任宏摘要——`compacting` 阶段触发的 CompactionPoint 压缩摘要同时写入 `experiential_memories`（`memory_level=macro`，`macroTriggerReason=compaction`）。详见 DOC-08 §3.5、§4.5。
>
> `compacting` 无对应 `*Retry` 状态（压缩失败映射 E018，0 次自动重试，直接进入 failed。用户可通过"从中断处继续"手动重试）。
>
> `reviewing` v0.2.2 改为可选（默认关闭）：`reviewEnabled=false` 时跳过 reviewing，生成即最终，直接进入 summarizing。`reviewEnabled=true` 时进入 reviewing 审查修正。`reviewingRetry` 状态仅在 `reviewEnabled=true` 时可能出现。


**状态顺序说明**（v0.2.2 检索前置 + 可选审查）：
- 主线 5 个必经阶段：`extracting → retrieving → generating → summarizing → persisting`
- 2 个可选阶段：
  - `compacting`：条件触发，位于 `extracting` **之前**（总占用超 `compactionTriggerRatio` 时触发压缩）
  - `reviewing`：默认关闭，位于 `generating` 与 `summarizing` **之间**（`reviewEnabled=true` 时进入审查修正）

**compacting 路径说明**（v0.2.2 新增）：
- **触发位置**：`extracting` 阶段之前（`_runCompactionPhase` → `_runExtractPhase`）
- **触发条件**：总占用（基础上下文 + 检索区 + 历史）超过 `contextWindow × compactionTriggerRatio`（默认 0.5）
- **未触发**：跳过压缩，直接进入 `extracting`（对用户透明，无 UI 反馈）
- **触发后流程**：`idle → compacting → extracting → retrieving → ...`
- **压缩产出**：LLM 将旧对话压缩为剧情宏观骨架摘要，作为稳定前缀注入 generating/reviewing（提升 LLM 缓存命中率）
- **双重职责**：压缩摘要兼任宏摘要功能，persisting 阶段同事务写入 `experiential_memories`（`memory_level=macro`, `macroTriggerReason=compaction`）
- **失败处理**：压缩失败映射 E018，0 次自动重试，直接进入 `failed`。用户可通过"从中断处继续"重试（跳过压缩直接进入 extracting）

**reviewing 可选化说明**（v0.2.2 新增）：
- **默认关闭**（`reviewEnabled=false`）：跳过 reviewing，生成即最终，直接进入 `summarizing`。3 次 LLM 调用（extracting/generating/summarizing）
- **手动开启**（`reviewEnabled=true`）：进入 reviewing 审查修正（按记忆审查修正生成正文 + 去 AI 味润色）。4 次 LLM 调用
- **复用检索结果**：开启时复用 retrieving 阶段已检索到的【世界设定】+【相关往事】，不重新检索——检索 query 来自 extracting 阶段（基于用户消息 + 历史对话），与生成内容无关
- **优先级**：会话级 `reviewEnabledOverride` > 全局 `reviewEnabled`（DB 列名保持 `revise_enabled_override`，Dart 字段名为 `reviewEnabledOverride`）

**~~macroSummarizing 阶段已废弃~~**（v0.2.2，2026-07-30）：
- 原 DOC-10 v1.1 设计的独立 `macroSummarizing` 状态（persisting 完成后条件触发的辅助阶段）已废弃
- **新方案**：压缩摘要兼任宏摘要——`compacting` 阶段触发的 CompactionPoint 压缩摘要同时写入 `experiential_memories`（`memory_level=macro`，`macroTriggerReason=compaction`），不再有独立的 `macroSummarizing` 阶段
- **UI 影响**：MacroSummaryPanel 组件从 UI 移除；VisualFlowTimeline 不再有 `macroSummarizing` 节点
- **v0.2.3 配置变更**：`macro_summary` 配置组（含 `macroBoostEnabled` / `macroBoost` / `macroIntervalRounds` / `macroSummaryEnabled`）已移除。分段宏摘要由 compacting 阶段触发，importance=3，参与语义检索（正常权重，不额外加权），与微摘要共存（不再去重）

**~~compact 降级路径已移除~~**（2026-07-16 移除；v0.2.2 进一步修订为可选 revising）：
- ~~原 compact 降级的 4 个触发条件（keywordsEmpty / memoriesEmpty / allLowQuality / fewAndLowQuality）已删除~~
- ~~`skipReviseWhenEmptyRetrieval` 配置项保留但不再生效（向后兼容）~~
- **v0.2.2 修订**：reviewing 改为可选（`reviewEnabled` 默认 false），与检索结果质量无关——生成已注入记忆，质量本身有保障。注入前质量过滤在 retrieving 阶段由 controller 完成（双阈值取严格：`finalScore >= absoluteThreshold(0.5) && finalScore >= maxScore × relativeThreshold(0.65)`）。详见 §3.6 与 DOC-09B §8.7。

### 1.3 数据流

v0.2.2 检索前置 + 可选审查后的数据流（主线 5 必经阶段 + 2 可选阶段）：

```
idle
  │ 用户输入 userInput
  ▼
[可选·条件触发] compacting（请求0，纯文本流式）
  │ 触发条件：总占用（基础上下文 + 检索区 + 历史）> contextWindow × compactionTriggerRatio（默认 0.5）
  │ 输入：原文区对话历史（旧消息）
  │ 输出：压缩摘要（剧情宏观骨架，纯文本）
  │   - 压缩摘要暂存到 round.compactionSummary
  │   - 兼任宏摘要，persisting 阶段同事务写入 experiential_memories（memory_level=macro）
  │   - 作为稳定前缀注入后续 generating/reviewing（提升 LLM 缓存命中率）
  │ 未触发时跳过本阶段，对用户透明
  ▼
extracting（请求1，结构化）  ← v0.2.2 前置到 generating 之前
  │ 输入：用户当前消息（优先）+ 最近 5 轮对话（按距离递减）+ extractKeywordsPrompt
  │   - 最近 5 轮 = history 末尾 10 条消息（user+assistant 配对），按时间正序
  │   - 优先级：用户当前消息 > 最近第1轮 > ... > 最近第n轮
  │ 输出：{ characters:[], items:[], locations:[], actions:[], plots:[] }（5 类关键词，工具调用优先，降级 JSON）
  │   - keywords 暂存到 round.draftKeywords + state.draftKeywords
  ▼
retrieving（本地）  ← v0.2.2 改为 5 路并行检索
  │ 输入：5 类关键词分路：
  │   - FTS5 3 路：characters / items / locations（精确匹配，OR 连接）
  │   - Vector 2 路：actions / plots（语义匹配，关键词拼接向量化）
  │ 操作：5 路并行混合检索（Future.wait，详见第 3 节）
  │   - 5 路结果按 memory_id 合并：finalScore = fts5Score × 0.5 + vectorScore × 0.5
  │   - 取 topK=12
  │   - 关键实体强制注入：importance >= 5 的事实层实体无论检索分数都注入（最多 3 个）
  │ 输出：List<ScoredMemory>（topK=12）+ FactRetrievalResult（事实层实体快照）
  │   - 检索结果暂存到 round.scoredMemories + state.retrievedMemories
  │   - 注入前质量过滤（双阈值取严格）：finalScore >= 0.5 && finalScore >= maxScore × 0.65
  │   - 全部不满足则【相关往事】区块省略
  ▼
generating（请求2，纯文本）  ★ v0.2.2 核心改造：注入记忆生成正文
  │ 输入：system_prompt_draft（V2）+ 压缩摘要（可选，稳定前缀）+ 最近 n 轮对话 + 【世界设定】+ 【相关往事】+ userInput
  │   - 消息结构：[system 角色提示词] + [system 压缩摘要?] + [history] + [system 世界设定?] + [system 相关往事?] + [user]
  │   - 记忆块（世界设定 + 相关往事）位于历史之后，提升 LLM 缓存命中率（v0.2.2 修订，原记忆块在历史前破坏缓存）
  │   - 【世界设定】来自事实层检索（FactContextBuilder.buildFactBlock）
  │   - 【相关往事】来自经历层检索（IntermediateContextBuilder._formatMemories）
  │ 输出：生成正文（纯文本，无 JSON/标记，已按记忆生成）
  │   - generatedText 流式显示在生成面板（reviewEnabled=false 时生成即最终，主区域同步流式显示）
  ▼
[可选·默认关闭] reviewing（请求3，纯文本）  ← v0.2.2 可选，reviewEnabled=false 时跳过
  │ 仅 reviewEnabled=true 时进入：
  │ 输入：前缀与 generating 完全一致（system_prompt_draft + 压缩摘要 + 最近 n 轮对话 + 【世界设定】+ 【相关往事】+ userInput）+ 末尾追加一条 user 消息（含审查后缀 kReviewingSuffixPromptV2 + 生成正文全文，用 --审查提示词-- / --生成内容-- 标记分隔）
  │   - 方案C：前缀与 generating 完全一致 + 末尾追加 user 消息，避免 LLM 弱化处理中间 system 消息
  │   - 复用 retrieving 阶段已检索结果，不重新检索
  │ 输出：回复正文（纯文本，无 JSON/标记）
  │   - replyText 流式显示在主区域
  │   - 双重功能：按记忆审查修正生成正文 + 去 AI 味润色
  │ reviewEnabled=false 时：replyText = generatedText（生成即最终），直接进入 summarizing
  ▼
summarizing（请求4，结构化）
  │ 输入：用户消息 + 回复正文（生成正文或审查后正文）+ 已知实体块 + extractSummaryPrompt
  │ 输出：5W1E 结构 + FactsDelta（工具调用优先，降级 JSON）：
  │   - 必填：what（事件）
  │   - 可选：when / where / who / significance / extra / summary（兼容字段，String?）
  │   - 元数据：tags / importance / event_ended
  │   - FactsDelta：事实层增量（create_entity / update_attr / delete_attr 操作列表）
  │   - eventSummary 暂存到 round.eventSummary + state.currentEventSummary
  │   - factsDelta 暂存到 round.factsDelta
  ▼
persisting（本地）
  │ 1. 同步调用 embedding API（5W1E 6 字段拼接文本向量化，带中文标签 时间/地点/人物/事件/意义/补充）
  │    - 若本轮触发了压缩：压缩摘要也同步向量化（按 summary 单字段，5W1E 6 字段为空字符串）
  │ 2. drift transaction 原子写入（详见 DOC-09C）
  │   - user message + reply → chat_messages
  │   - eventSummary 5W1E 6 字段 + summary（可选）+ tags + importance → experiential_memories（v21 加列 when_text/where_text/who_text/what_text/significance/extra）
  │   - embedding → experiential_memories.embedding BLOB（如成功，同表同事务）
  │   - summary + 5W1E 6 字段 → memories_fts（v21 重建为 7 内容字段索引）
  │   - FactsDelta → factual_entities + factual_attributes + factual_memory_history（事实层三表，DOC-11）
  │   - 若本轮触发了压缩：压缩摘要 → experiential_memories（memory_level=macro, macroTriggerReason=compaction）
  │   - session 元数据更新（currentNarrativeTime 等）
  │   - draft/keywords/retrievedMemories/retrievedFacts/reply/eventSummary/factsDelta → intermediate_round_artifacts（v18/v28 加列）
  │ 3. state.artifactsByTurnNumber 追加当前 turnNumber 的 entry
  ▼
idle
```

**v0.2.2 数据流关键变化**：

| 项 | v0.2.1 旧流程 | v0.2.2 新流程 |
|----|------|--------|
| 阶段顺序 | drafting → extracting → retrieving → revising → summarizing → persisting（旧称，现称"generating → extracting → retrieving → reviewing → summarizing → persisting"） | compacting? → extracting → retrieving → generating → reviewing? → summarizing → persisting |
| extracting 输入 | 用户消息 + 生成正文 | **用户当前消息 + 最近 5 轮对话**（生成正文尚未生成） |

| 生成正文是否注入记忆 | 否（reviewing 才注入） | **是**（generating 直接注入【世界设定】+【相关往事】） |
| reviewing | 始终执行 | **可选，默认关闭**（reviewEnabled=false 时生成即最终） |
| 检索通道 | 2 路（entities→FTS5，events→Vector） | **5 路并行**（characters/items/locations→FTS5，actions/plots→Vector） |
| topK | 3 | **12** |
| 关键实体注入 | 无 | **importance>=5 强制注入，最多 3 个**（2026-08-06：从4提升至5） |
| 质量过滤阈值 | 0.4 / 0.6 | **0.5 / 0.65**（绝对阈值 / 相对阈值） |
| 压缩机制 | 无 | **CompactionPoint**（压缩摘要兼任宏摘要） |
| LLM 请求数（默认） | 4 次 | **3 次**（开启 reviewing 时 4 次，触发压缩时 +1 次） |

### 1.4 流式输出方案（v0.2.2 七步事务）

v0.2.2 七步事务（compacting?/extracting/retrieving/generating/reviewing?/summarizing/persisting）后，文本步骤与结构化步骤分离，不再使用分隔标记：

**compacting / generating / reviewing（文本步骤）**：流式输出纯文本，直接累积显示，无标记/JSON 解析。

**extracting / summarizing（结构化步骤）**：采用**工具调用优先 + JSON 降级**方案：

1. **工具调用模式**（默认，`toolCallingEnabled=true`）：请求带 `tools` + `toolChoice=required`，LLM 返回 tool_calls，`ToolCallAccumulator` 累积参数后解析为结构化数据。流式过程中不显示（结构化数据无流式意义）。
2. **JSON 模式降级**（工具调用不支持/失败）：请求带 `response_format=json_object`，LLM 输出纯 JSON，等完整 JSON 后解析。
3. **提示词约束兜底**（JSON 模式也不支持）：纯提示词要求输出 JSON + 客户端容错解析（提取首个 `{` 到末尾 `}`）。

同一提示词（`extractKeywordsPrompt` / `extractSummaryPrompt`）兼容工具调用与 JSON 两种输出方式（"若提供工具则调用，否则直接输出 JSON"）。

> **分隔标记方案已删除**（V2 重构）：原 `<<<KEYWORDS>>>` / `<<<EVENT_SUMMARY>>>` 分隔标记方案在四步拆分后无用（文本步骤无需结构化，结构化步骤独立请求）。旧配置项 `draftSeparator` / `eventSummarySeparator` 标注 `@Deprecated`。详见 DOC-09B 第 8 节、DOC-09A-2 §6。

### 1.5 关键约束

- **同一会话同一时间只允许一轮生成**：`state.isSending` 锁，防止并发
- **草稿/关键词/检索结果持久化到独立 artifacts 表**：原约束"不持久化到 ChatMessage 字段，仅存在于 IntermediateChatState"导致历史轮次小窗在切换会话或重启后消失。修订为持久化到 `intermediate_round_artifacts` 表，通过 `(session_id, turn_number)` 关联到 assistant 消息。loadHistory 时批量加载填充到 `state.artifactsByTurnNumber`，UI 按消息索引推导 turnNumber 渲染对应历史小窗
- **ChatMessage 不新增字段**：复用 Simple 模式实体，草稿等中间产物走独立 artifacts 表（不污染 ChatMessage schema）
- **ChatSession.mode 新增 `intermediate` 值**：现有值 chat/advanced，新增 intermediate

## 2. 分支机制（Fork）

### 2.1 设计决策

中级模式采用**方案B：简化 Fork**——覆盖式重新生成，不支持多分支并存切换。

| 维度 | Simple 模式 | 中级模式 |
|------|------------|---------|
| Fork 模型 | 快照模型（活跃分支在主表，非活跃在 JSON 快照） | 无分支锚点 |
| 重新生成 | 创建新分支，保留旧回复为快照可切换 | 覆盖式，旧回复+旧事件摘要一起删除 |
| 编辑重发 | 同上 | 覆盖式 |
| 多分支切换 | 支持（左右箭头） | 不支持 |
| 分支导航 UI | 有 | 无 |

### 2.2 简化 Fork 的产品语义

- **重新生成**：用户点"重新生成"按钮 → 删除旧助手回复 + 删除旧事件摘要（含向量、FTS5 索引）→ 新回复重新走四步生成
- **编辑重发**：用户编辑用户消息后重发 → 同上删除 + 重新生成
- **无分支锚点**：中级模式会话没有 ForkAnchor，没有"左右切换分支"按钮
- **多存档切换体验**：用户如果想要"多个回复版本对比"，用 Simple 模式

### 2.3 简化 Fork 的理由

1. **记忆串戏问题**：中级模式引入经历记忆后，Fork 不同分支的事件摘要共享记忆库会导致检索串戏——分支A的事件被分支B检索到，造成剧情混乱
2. **避免记忆库复杂度**：要支持多分支+记忆隔离，需为每个分支维护独立记忆库或记忆版本，复杂度极高
3. **产品定位**：中级模式定位"有记忆的聊天"，不是"多版本创作工具"。多版本对比是 Simple 模式的职责
4. **开发量**：简化 Fork 复用 Simple 模式的删除逻辑，无需实现快照交换

### 2.4 重新生成的数据操作

用户点"重新生成"（`targetMessage` 可以是 assistant 或 user 消息）：

```
1. 守卫：phase=idle + canOperateMessage（§2.7）+ targetMessage.role ∈ {user, assistant}
2. 推导 assistantTarget：
   - 若 targetMessage.role=assistant，直接作为目标
   - 若 targetMessage.role=user，自动找到下一条 assistant 作为目标
     （找不到或下一条不是 assistant 则中止，不进入 failed）
   - 效果与点击 assistant 回复的"重新生成"一致：保留 user_N，删 assistant_N + 下游
3. 推导 targetTurn = _computeTurnNumber(assistantTarget)
   - assistant at index i -> turn = (i+1)~/2
4. 立即置 state.isPreparingRegenerate = true
   - DB 删除 await 期间 UI 显示 loading 遮罩，避免下游消息残留显示
5. 删除范围：assistant_N + 下游所有消息（不含 user_N）
   - messageIdsToDelete = messages.sublist(targetIndex).map(messageId)
   - 调 IntermediatePersistenceService.deleteRoundAndDownstream：
     · 从 chat_messages 删除 messageIdsToDelete
     · 从 experiential_memories 删除 turn >= targetTurn 的记录
       （embedding BLOB 随行删除，无独立向量表）
     · 从 memories_fts 删除对应索引
     · 以上在同一 drift transaction 内
   - 删除失败（catch）：置 isPreparingRegenerate = false 后返回（不进入 failed）
6. 更新 state：
   - messages = messages.sublist(0, targetIndex)（保留 user_N 及之前）
   - session.messageCount = remainingMessages.length
   - userInput = user_N.content（复用原用户输入）
   - regenerateTurnNumber = targetTurn（标识走 persistRegeneratedRound 分支）
   - isPreparingRegenerate = false（下游已截断，关闭遮罩；后续由四步生成小窗接管）
7. 调 _prepareAndRunRound() 重新走四步生成
8. 持久化阶段走 persistRegeneratedRound 分支：
   - 只写 assistant_N + 事件摘要（user_N 已存在，不重写）
   - turn_number 复用 targetTurn（避免轮次跳跃）
```

### 2.5 编辑重发的数据操作

用户编辑用户消息后重发（`targetMessage` 必须是 user）：

```
1. 守卫：phase=idle + canOperateMessage（§2.7）+ targetMessage.role=user
2. 推导 targetTurn = _computeTurnNumber(targetMessage)
   - user at index i → turn = (i+2)~/2
3. 立即置 state.isPreparingRegenerate = true（同 §2.4 步骤4，UI 遮罩）
4. 删除范围：user_N + assistant_N + 下游所有消息
   - messageIdsToDelete = messages.sublist(targetIndex).map(messageId)
   - 调 deleteRoundAndDownstream（同 §2.4 步骤5）
   - 删除失败（catch）：置 isPreparingRegenerate = false 后返回
5. 更新 state：
   - messages = messages.sublist(0, targetIndex)
   - session.messageCount = remainingMessages.length
   - userInput = newContent（用户编辑后的新内容）
   - regenerateTurnNumber = null（走 persistRound 分支，写 user + assistant + 事件摘要）
   - pendingUserMessage = 新建临时用户消息（UI 即时显示新内容气泡）
   - isPreparingRegenerate = false（下游已截断，关闭遮罩）
6. 调 _prepareAndRunRound() 重新走四步生成
7. 持久化阶段走 persistRound 分支：写 user_N + assistant_N + 事件摘要
```

**与重新生成的差异**：编辑重发删除 user_N（用新内容重写），走 persistRound 分支；
重新生成保留 user_N，走 persistRegeneratedRound 分支（只写 assistant）。

### 2.6 删除整轮的数据操作

用户点"删除整轮"（`targetMessage` 可以是 user 或 assistant）：

```
1. 守卫：phase=idle + canOperateMessage（§2.7）
2. 推导 targetTurn = _computeTurnNumber(targetMessage)
3. 删除范围：从 user_N 开始 + 下游所有消息
   - 若 targetMessage 是 assistant，回退一位到 user_N（targetIndex - 1）
   - messageIdsToDelete = messages.sublist(startIndex).map(messageId)
   - 调 deleteRoundAndDownstream（同 §2.4 步骤5）
4. 更新 state：
   - messages = messages.sublist(0, startIndex)
   - session.messageCount = remainingMessages.length
5. 保持 idle，不启动四步生成
```

**约束**：
- 删除助手回复时，必须同时删除对应的事件摘要（保持数据一致性）
- 删除用户消息时，必须同时删除后续助手回复 + 事件摘要
- 删除操作需确认（防误删，IntermediateConfirmDialog），与 Simple 模式一致

### 2.7 Fork 窗口判断（canOperateMessage）

为避免用户对早期消息频繁回退导致记忆库碎片化，Fork 操作限制在"最近 N 轮"窗口内：

```dart
bool canOperateMessage(ChatMessage message, {required int windowRounds}) {
  final targetTurn = _computeTurnNumber(message);
  if (targetTurn == null) return false;
  final totalRounds = state.session.messageCount ~/ 2;
  return targetTurn >= totalRounds - windowRounds + 1;
}
```

- `windowRounds`：从 `ForkConfig.regenerateWindowRounds` 读取，默认 5 轮
- 窗口外消息（`canOperate=false`）：⋮ 菜单中"重新生成/编辑重发/删除整轮"禁用并显示为 faint 色；点击时弹 SnackBar 提示"只能操作最近 N 轮的消息"
- "复制"动作不受窗口限制，始终可用
- `totalRounds` 基于 `session.messageCount ~/ 2`（user+assistant 配对为一轮）
- **messageCount 同步约束**（修复）：依赖 `state.session.messageCount` 的逻辑
  （如本处的 `totalRounds` 推导）必须确保 `_runPersistPhase` 持久化后已刷新
  `state.session.messageCount`（详见 DOC-09C §1 步骤5-6 注释）。修复前
  `_runPersistPhase` 漏刷新 messageCount，导致第二轮起 turnNumber/artifacts 错乱。

### 2.8 仅编辑消息内容（editMessageContent）

用户选择"仅编辑"（修正错别字等小修改，不重新生成）：

```
1. 守卫：phase=idle
2. 调 ChatRepository.updateMessageContent 更新数据库中该消息的 content
3. 更新 state.messages 中对应消息的 content（内存同步）
```

**与编辑重发（editAndResend）的差异**：

| 维度 | editMessageContent | editAndResend |
|------|-------------------|---------------|
| 数据库操作 | 仅更新消息文本 | 删 user_N + assistant_N + 下游 + turn≥N 事件摘要（事务） |
| 记忆清理 | 不清理 | 清理 experiential_memories + FTS5 索引 |
| 下游消息 | 保留 | 删除 |
| 重新生成 | 否 | 是（走四步生成） |
| 适用场景 | 修正错别字等小修改 | 修改内容后重新生成回复 |

**约束**：
- 仅针对已持久化的消息（pendingUserMessage 的编辑用 `editPendingUserMessage`）
- 不触发记忆清理、不删除下游消息、不重新生成
- 编辑后消息内容变化，但基于旧内容生成的事件摘要和下游回复不受影响

## 3. 检索算法实现

> **算法归属说明**：混合检索算法（FTS5 查询 + VectorEngine.batchSearch + 分数归一化 + 加权合并 + 关键事件加权）**整体实现在 `ExperienceRepositoryImpl`（Data 层）**，不在 UseCase 中。理由：
> - 混合检索本质是**复杂数据检索**（FTS5 SQL + 向量内存计算 + 评分排序），属 Data 层职责，非业务逻辑
> - FTS5 SQL 查询在 DB 内执行；Vector 通道由 Repository 从 `experiential_memories.embedding` BLOB 加载向量后调 `VectorEngine.batchSearch`（Core 层 Isolate 计算），拆到 UseCase 会引入跨层数据泄露
> - `searchExperiences` 的 8 个命名参数（检索权重/阈值/boost/ε）由 Controller 从 `IntermediateConfig` 传入，Repository 不持有配置——参数化保证了 Repository 的纯数据存取定位
>
> UseCase/Controller 的职责是**决定何时检索**（草稿完成后）和**如何使用结果**（注入 prompt 的"相关往事"区块），不参与检索算法本身。

### 3.1 检索在七步事务中的位置

v0.2.2 检索前置后，检索位于 extracting 与 generating 之间（reviewing 可选复用）：

```
请求1（extracting）输出 5 类 keywords → 【检索】 → 请求2（generating）消费检索结果
                                              ↑
                                       本节设计这一步
                                       v0.2.2 改为 5 路并行
```

- **输入**：extracting 步骤 LLM 输出的 5 类关键词（`ClassifiedKeywords`，分 characters/items/locations/actions/plots 五类），如 `{characters:["林川","师父"], items:["古碑"], locations:["后山"], actions:["运转青云功"], plots:["碑文显现"]}`
  - **entityTerms getter**：合并 characters + items + locations，走 FTS5 通道
  - **eventTerms getter**：合并 actions + plots，走 Vector 通道
- **输出**：注入到 generating LLM prompt 的"相关往事"区块（reviewing 开启时复用，不重新检索）
- **v0.2.2 核心变化**：检索从 generating 之后前置到 generating 之前，generating 阶段直接注入【世界设定】+【相关往事】生成正文，避免"生成已偏离记忆后 reviewing 只能打补丁"的锚定效应

### 3.2 注入格式（2026-07-22 修订：加免责声明）

```
【相关往事】
（以下为历史记忆参考，其中的角色不代表本轮已出场，终稿只应出场对话历史中实际在场的角色）
[7轮前·重要性5]
时间：黄昏时分
地点：青云门后山
人物：主角
事件：发现古碑，碑文残缺
意义：揭开后世碑文的伏笔
[3轮前·重要性4]
时间：上次下山时
人物：主角、师父
事件：师父传授青云功入门心法
[2轮前·重要性3]
事件：主角首次运转青云功，感应天地灵气
补充：当时灵气稀薄，仅作入门体验
```

- 按最终分数降序排列
- 每条以"X轮前·重要性N"为标题行（相对时序，X = currentTurn - eventTurn）
- 每条按 5W1E 字段非空情况展开为多行：时间（when）/ 地点（where）/ 人物（who）/ 事件（what，必填）/ 意义（significance）/ 补充（extra）
- `summary`（可选兼容字段）若存在则拼接进"事件"行
- 不带原始消息、不带 tags
- 由 `IntermediateContextBuilder._formatMemories` + `_formatSingleMemory` 生成

**相对时序的理由**：用"第N轮"标注可能让 LLM 误判时间关系（如第10轮回忆第3轮时，标注"第3轮"可能被误认为当前就是第3轮）。"X轮前"直接表达时间距离，LLM 自然用回忆口吻。

**多行结构化的理由**：单行 summary 在剧情密集场景下信息密度不足，5W1E 多行结构让 LLM 更易识别时间/地点/人物等关键要素的对应关系，提升 reviewing 阶段的引用准确度。空字段自动省略，不产生空行噪声。

**免责声明的理由**（2026-07-22 新增；v0.2.2 修订）：用户反馈 reviewing 阶段回复叫出了对话历史中不存在的名字，怀疑是 LLM 把往事 `who` 字段中的角色名误认为本轮已出场。在区块开头加免责声明"（以下为历史记忆参考，其中的角色不代表本轮已出场，回复只应出场对话历史中实际在场的角色）"，配合 `kReviewingSuffixPromptV2` 审查清单 A 项新增"不得在回复中引入对话历史中未出场的角色"注意，避免 LLM 把往事角色误写入回复。世界设定区块（【世界设定】）同理加免责声明（详见 DOC-09B §4.6）。**v0.2.2 修订**：检索前置后 generating 阶段也注入【相关往事】区块，免责声明同步生效于 generating prompt（`kGeneratingSuffixPromptV2` 审查清单 A 项）；reviewing 关闭时由 generating 承担"按记忆生成 + 不引入未出场角色"责任，reviewing 开启时由 reviewing 二次审查。

### 3.3 FTS5 查询构造（v0.2.2：3 路并行）

v0.2.2 从原单路 FTS5 扩展为 **3 路并行 FTS5**（与 5 类关键词中的 characters/items/locations 对齐）：

| 通道 | 关键词类 | 用途 | 示例 |
|------|---------|------|------|
| FTS5 通道 1 | characters | 角色名（含主角）精确匹配 | `林川 OR 师父` |
| FTS5 通道 2 | items | 关键物品/道具名精确匹配 | `古碑` |
| FTS5 通道 3 | locations | 出现场景/地点名精确匹配 | `后山` |

**3 路并行**：`Future.wait` 并发执行 3 路 FTS5 查询，任一通道失败自动降级（不影响其他通道）。3 路结果按 memory_id 合并（同 memory_id 的 fts5Score 取最大值或叠加，见 §3.6）。

**MATCH 表达式**（每路通道内）：关键词用 `OR` 连接，扩大召回。

```
输入关键词（通道 1 characters）：["林川", "师父"]
MATCH 表达式：'林川 OR 师父'

输入关键词（通道 2 items）：["古碑"]
MATCH 表达式：'古碑'

输入关键词（通道 3 locations）：["后山"]
MATCH 表达式：'后山'
```

- 用 OR 不用 AND：AND 会因任一关键词缺失而查不到，OR 召回广，由归一化和 topK 精排
- 关键词清洗：去除 FTS5 特殊字符（`"` `*` `(` `)` `:`），避免语法错误
- 中文分词：用默认 `unicode61` tokenizer（按字分词），中级模式够用
- 某类关键词为空时跳过该通道（如无 items 关键词则通道 2 不发起查询）

**SQL**（2026-07-19：memories_fts 重建为 7 内容字段索引；每路通道独立执行一次）：
```sql
SELECT memory_id, summary, when_text, where_text, who_text, what_text, significance, extra, rank
FROM memories_fts
WHERE memories_fts MATCH ? AND session_id = ?
ORDER BY rank
LIMIT ?
```
参数：`'<通道关键词 OR 连接>'`, sessionId, topK*2（topK 默认 12，v0.2.2 从 3 提升至 12）

- 7 内容字段：`summary` + 5W1E 6 字段（`when_text`/`where_text`/`who_text`/`what_text`/`significance`/`extra`），均参与 FTS5 MATCH 召回
- `rank` 是 FTS5 内置 BM25 分数（负值，越小越相关）
- 取 `topK*2` 条作为候选，给合并排序留余量
- 字段映射回 `experiential_memories` 后由 `_formatSingleMemory` 按非空字段渲染为多行结构化文本（见 §3.2）

### 3.4 Vector 查询构造（v0.2.2：2 路并行）

v0.2.2 从原单路 Vector 扩展为 **2 路并行 Vector**（与 5 类关键词中的 actions/plots 对齐）：

| 通道 | 关键词类 | 用途 | 示例查询文本 |
|------|---------|------|------|
| Vector 通道 1 | actions | 角色动作/行为语义匹配 | `"运转青云功 修炼"` |
| Vector 通道 2 | plots | 剧情事件/情节要点语义匹配 | `"碑文显现 古碑现世"` |

**2 路关键词向量化（Controller 职责，非 Repository）**：extracting 步骤输出的 `ClassifiedKeywords` 中：
- **actions 关键词**：用空格拼成查询文本，由 **IntermediateChatController** 调 EmbeddingService 生成 `actionsQueryVector`
- **plots 关键词**：用空格拼成查询文本，由 **IntermediateChatController** 调 EmbeddingService 生成 `plotsQueryVector`

同步阻塞，但发生在 extracting（请求1）完成后、不影响流式显示。生成的 `actionsQueryVector` / `plotsQueryVector: Float32List?` 通过参数传入 `ExperienceRepository.searchExperiences`——Repository 只做纯数据检索，不持有 EmbeddingService 依赖（网络调用不属 Repository 职责，ISP）。

> **设计决策**（实现时确认；v0.2.2 修订）：原文本表述"调 EmbeddingService 生成向量"未明确归属层级，现明确为 Controller 负责向量化、Repository 接收 queryVector 参数。Repository 在 queryVector 为 null 时跳过 Vector 通道（如向量化失败降级、或无可用 embedding 模型）。v0.2.2 检索前置后，关键词来源从 drafting 改为 extracting 步骤；2 路并行各自独立向量化（actions 与 plots 语义维度不同，分别向量化更精准）。

**2 路并行向量检索**（v0.2.2 主方案 = 纯 Dart 暴力检索）：

```dart
// 1. Repository 从 DB 加载该 session 全部候选向量（含 memory_id）
final candidates = await db.customSelect(
  'SELECT memory_id, embedding FROM experiential_memories '
  'WHERE session_id = ? AND has_embedding = 1 AND is_archived = 0',
  variables: [Variable.withString(sessionId)],
).get();
// 解析 BLOB → Float32List（小端字节序）

// 2. 2 路并行调 VectorEngine.batchSearch（Future.wait）
final results = await Future.wait([
  vectorEngine.batchSearch(
    queryVector: actionsQueryVec,    // actions 通道查询向量
    candidates: candidateVectors,
    candidateIds: candidateMemoryIds,
  ),
  vectorEngine.batchSearch(
    queryVector: plotsQueryVec,      // plots 通道查询向量
    candidates: candidateVectors,
    candidateIds: candidateMemoryIds,
  ),
]);
// 返回 List<VectorSearchResult>（memoryId, similarity），按 similarity 降序
// 2 路结果按 memory_id 合并（同 memory_id 的 vectorScore 取最大值或叠加，见 §3.6）
```

- `VectorEngine.cosineSimilarity` 返回值 ∈ [-1, 1]（1=完全相似，-1=完全相反）
- `vectorScore = (similarity + 1) / 2` 映射到 [0,1]（见 §3.5）
- 每路取 topK*2 条作为候选，给合并排序留余量
- session 隔离在步骤 1 的 SQL `WHERE session_id` 完成，无需 JOIN（见 §3.8）
- 某类关键词为空或向量化失败时跳过该通道（如 actions 为空则只走 plots 通道 + 3 路 FTS5）

**性能**：1536 维 × 1000 条 ≈ 5-15ms（ARM64 Isolate），2 路并行总耗时与单路基本持平（Isolate 内并发）。满足 Q-02 ≤50ms 目标。100% 召回率。

> **方案变更说明**：原计划用 sqlite-vec 虚拟表 `memory_vectors` 做 SQL KNN 检索，但 pub 包损坏废弃。改用纯 Dart 暴力检索后，向量仅存 `experiential_memories.embedding` BLOB 单一数据源，无独立向量表，无跨表同步开销。详见 DOC-05-8 §9.12、DOC-08 §5.3。

### 3.5 归一化算法

**FTS5 归一化**（min-max + 平滑因子）：
```
minRank = 最相关 rank（负得最多）
maxRank = 最不相关 rank
fts5Score = (rank - maxRank) / (minRank - maxRank)   // [0,1]，最相关=1
fts5Score = fts5Score × (1 - ε) + ε                   // ε=0.01，避免 0
```

**Vector 归一化**：
```
similarity = VectorEngine.cosineSimilarity(query, candidate)   // ∈ [-1, 1]
vectorScore = (similarity + 1) / 2   // 映射到 [0,1]，1=完全相似
```

### 3.6 合并排序 + 关键事件加权 + 检索优化（v0.2.2：5 路合并 + 新参数）

v0.2.2 从原 2 路合并扩展为 **5 路合并**（3 路 FTS5 + 2 路 Vector），并引入 4 个新参数：

```
finalScores = {}   // memory_id → score

// v0.2.2: FTS5 3 路通道贡献（characters / items / locations 各一路）
for channel in [charactersResults, itemsResults, locationsResults]:
    for result in channel:
        if result.memory_id not in finalScores:
            finalScores[result.memory_id] = 0
        // 同 memory_id 跨通道取最大值（避免某通道高分被另一通道低分稀释）
        finalScores[result.memory_id] = max(
            finalScores[result.memory_id],
            fts5Score(result) × fts5Weight,
        )

// v0.2.2: Vector 2 路通道贡献（actions / plots 各一路）
for channel in [actionsResults, plotsResults]:
    for result in channel:
        if result.memory_id not in finalScores:
            finalScores[result.memory_id] = 0
        finalScores[result.memory_id] += vectorScore(result) × vectorWeight

// 质量过滤（vectorScoreThreshold > 0 时启用）
for memory_id in finalScores:
    if vectorScore(memory_id) < vectorScoreThreshold and fts5Score(memory_id) == 0:
        skip memory_id   // 双低分记忆直接过滤

// 关键事件加权（2026-07-16 起：默认不生效）
for memory_id, score in finalScores:
    if memory.importance >= keyEventThreshold:   // 默认 999，永不触发
        finalScores[memory_id] = score × keyEventBoost   // 默认 1.0，不加权

// 时间衰减加权（recencyWeight > 0 且 currentTurnNumber != null 时启用）
for memory_id, score in finalScores:
    turnsAgo = currentTurnNumber - memory.turnNumber
    recencyBoost = turnsAgo <= 0 ? 1.0 : 0.5 ^ (turnsAgo / recencyHalfLife)
    finalScores[memory_id] += recencyBoost × recencyWeight

// importance 乘法加权（importanceWeight > 0 时启用）
// 2026-08-06 修订：从加法改为乘法，importance 只能放大相关性，不能凭空创造
for memory_id, score in finalScores:
    multiplier = 1.0 + (memory.importance - 3) × importanceWeight
    finalScores[memory_id] *= multiplier

// 2026-08-06 新增：基础相关性门槛（质量过滤启用时生效）
// 基础相关性 = fts5 × fts5Weight + vec × vectorWeight < 0.1 的记忆直接跳过
// 防止高 importance 低相关性记忆被加成推过阈值

// v0.2.2: 关键实体强制注入（事实层，importance >= keyEntityImportanceThreshold）
// 与经历层检索独立：由 FactContextBuilder.buildFactBlock 处理，不参与 finalScores 排序
// 详见 §3.11 事实层检索

// 降序排序，取 topK（v0.2.2: 默认 12，从 3 提升）
sorted = sortByScoreDesc(finalScores)
return sorted[:topK]

// v0.2.2 注：注入前质量过滤在 retrieving 阶段由 controller 完成（IntermediateContextBuilder._formatMemories），
// 不在 Repository 中。过滤规则（双阈值取严格，v0.2.2 从 0.4/0.6 提升至 0.5/0.65）：
//   finalScore >= absoluteThreshold(0.5) && finalScore >= maxScore × relativeThreshold(0.65)
// 两个条件都必须满足才注入。如果全部记忆都不满足阈值，【相关往事】区块省略（不强制注入至少1条）。
// 常量：_kMemoryAbsoluteThreshold = 0.5，_kMemoryRelativeRatio = 0.65
```

- **5 路结果按 memory_id 合并**（v0.2.2）：同一事件被多路都捞到，FTS5 跨通道取最大值（避免稀释），FTS5 与 Vector 之间叠加
- 只被部分通道捞到的事件，其他通道贡献 0
- importance≥4 的事件分数×1.5（关键事件加权）—— **2026-07-16 起默认不生效**：`keyEventThreshold` 默认 999（永不触发），`keyEventBoost` 默认 1.0（不加权）。原因：keyEventBoost 与 importanceWeight 功能重叠，统一由 importance 加权

**检索优化要点**（2026-07-08；2026-07-16 修订；v0.2.2 参数更新）：

| 优化项 | 触发条件 | 公式 | 默认值 |
|--------|---------|------|--------|
| 质量过滤 | `vectorScoreThreshold > 0` | `vec < threshold && fts5 < 0.02 -> 跳过` | 0.55（2026-07-16 起：0.3->0.55） |
| 时间衰减（recencyBoost） | `recencyWeight > 0 && currentTurnNumber != null` | `0.5^(turnsAgo/halfLife) × recencyWeight` | 0.05 / 半衰期 20 轮（2026-08-06：从0.15降低，因近期内容已在对话原文中） |
| importance 乘法加权（2026-08-06 修订） | `importanceWeight > 0` | `finalScore *= 1.0 + (importance-3) × importanceWeight` | 0.1 |
| 注入前质量过滤（双阈值取严格） | `IntermediateContextBuilder._formatMemories` | `finalScore >= absoluteThreshold && finalScore >= maxScore × relativeThreshold` | **0.5 / 0.65**（v0.2.2 从 0.4/0.6 提升） |
| **topK**（v0.2.2） | — | — | **12**（v0.2.2 从 3 提升） |
| **关键实体强制注入**（v0.2.2 新增） | `importance >= keyEntityImportanceThreshold` | 事实层实体无论检索分数都注入 | 阈值 **5**（2026-08-06：从4提升至5），上限 **3** 个 |

- **质量过滤**：双低分（Vector 不相关 + FTS5 无命中）的记忆直接跳过，避免噪声污染检索结果。`vectorScoreThreshold` 默认值从 0.3 提升至 0.55（等价 cosine > 0.1，过滤语义无关记忆）
- **时间衰减**（2026-08-06 权重降低）：近期记忆获得少量额外加成（`recencyBoost ∈ (0, 1]`，当前轮=1.0，每经半衰期衰减一半），权重从 0.15 降至 0.05。原因：近期对话原文已通过 CompactionPoint 保留在上下文中，recency 加成的主要作用是让"几轮前但不在原文窗口内"的记忆有轻微优先，而非让最近记忆总是被注入
- **importance 乘法加权**（2026-08-06 修订：从加法改为乘法）：importance 只能放大相关性，不能凭空创造相关性。`importance=3` 时不影响分数（乘数 1.0），`importance=5` 时提升 20%（乘数 1.2），`importance=1` 时降低 20%（乘数 0.8）。原加法公式在相关性为 0 时仍贡献固定加分，导致高 importance 低相关性记忆每轮都被注入
- **注入前质量过滤**（2026-07-16 新增；2026-07-19 扩展；v0.2.2 阈值提升）：在 `IntermediateContextBuilder._formatMemories` 中对 `searchExperiences` 返回的 topK 结果再次过滤。双阈值取严格：`finalScore >= absoluteThreshold(0.5)（绝对阈值） && finalScore >= maxScore × relativeThreshold(0.65)（相对阈值）`，两个条件都必须满足才注入。**无兜底**：如果全部记忆都不满足阈值，【相关往事】区块省略（不强制注入至少1条）。通过过滤的记忆再由 `_formatSingleMemory` 渲染为多行结构化文本（5W1E 字段非空展开，见 §3.2）
- **关键事件加权默认不生效**（2026-07-16 起）：`keyEventThreshold` 默认 999（永不触发），`keyEventBoost` 默认 1.0（不加权）。原因：keyEventBoost 与 importanceWeight 功能重叠，统一由 importance 加权
- **topK 提升**（v0.2.2）：从 3 提升至 12，配合 5 路并行检索的更广召回——5 路并行召回量大，3 条不足以覆盖；12 条在 token 预算可控的前提下提供更完整的上下文
- **关键实体强制注入**（v0.2.2 新增；2026-08-06 阈值收紧）：与经历层关键事件加权不同--关键实体是事实层（factual_entities）的二元判定（注入或不注入），`importance >= keyEntityImportanceThreshold`（默认 5，仅主角级别）的实体无论检索分数都注入，最多 `keyEntityMaxInject`（默认 3）个，避免关键角色因检索分数低被漏掉。2026-08-06 从 4 提升至 5：仅主角(5分)每轮自动注入，主角团核心成员(4分)改为仅提及时注入。详见 §3.11
- **基础相关性门槛**（2026-08-06 新增）：质量过滤启用时，基础相关性分数（`fts5×fts5Weight + vec×vectorWeight`）低于 0.1 的记忆直接跳过，不进入 importance/recency 加成计算。防止高 importance 但低相关性的记忆被加成推过阈值
- importance 改为乘法加权（2026-08-06），时间衰减仍为叠加式（加到 finalScore 上），不破坏原有的多路合并 + 关键事件加权逻辑
- 默认参数（0/null）= 不启用，行为与旧逻辑完全一致（向后兼容）

>    **2026-07-16 修订**：compact 降级模式**已移除**，revising 始终执行。**v0.2.2 进一步修订**：reviewing 改为可选（`reviewEnabled` 默认 false），与检索结果质量无关——生成已注入记忆，质量本身有保障。`skipReviseWhenEmptyRetrieval` 配置项保留但不再生效（向后兼容）。`round.skipRevise` 字段（v0.2.2 术语变更后 Dart 字段名应为 `round.skipReview`，DB 列名保持 `skip_revise`）保留但文档注释说明"恒为 false"；`round.replyText` 字段文档注释说明"reviewEnabled=false 时等于生成正文，reviewEnabled=true 时来自 reviewing 阶段"。注入前质量过滤改由 `IntermediateContextBuilder._formatMemories` 完成（双阈值取严格，v0.2.2 阈值 0.5/0.65，见 §3.6 注入前质量过滤行）。

> **V2 四步重构修订**（2026-07-10；v0.2.2 更新）：关键词来源从 generating（旧称 drafting，请求1，分隔标记解析）改为 extracting（请求1，工具调用/JSON）。v0.2.2 进一步将 extracting 前置到 generating 之前（检索前置）。语义变化：
> - 关键词格式错误（工具调用参数无效 / JSON 解析失败）→ 触发 **E013**（extracting 失败，`extractingMaxRetries` 重试），不再触发 E011。E011（generating 格式错误，旧称 drafting 格式错误）在 V2 中不再产生（generating 输出纯文本无格式约束）。
> - 合法空关键词（工具调用返回空 `ClassifiedKeywords`，5 类全空）→ 直接返回，不降级到 JSON 模式（修复点：原 `_parseKeywordsFromArguments` 空结果误降级 JSON 模式）→ 跳过 5 路检索，generating 无【相关往事】区块生成正文。
> - `parseKeywords`（`stream_marker_parser.dart`）仍用于 JSON 模式降级时的 fallback 文本解析，但分隔标记解析路径已废弃。
> - **v0.2.2 extracting 输入变化**：从"用户消息 + 生成正文"改为"用户当前消息 + 最近 5 轮对话"（生成正文尚未生成），优先级：用户当前消息 > 最近第1轮 > ... > 最近第n轮。

**重要原则**：
- 检索部分失败（单路/多路异常）→ 降级，不拖累整轮
- 检索完全失败（5 路都异常）→ 整轮失败（符合 DOC-08 第 6.2 节"无降级质量"原则）
- 检索失败 ≠ 整轮失败（除完全失败外），generating 可以在没有往事的情况下正常生成（生成即最终，或 reviewing 仅做润色）

### 3.8 session 隔离

- FTS5：`WHERE session_id = ?` 直接在 SQL 过滤
- Vector：在加载 `experiential_memories.embedding` BLOB 时用 `WHERE session_id = ? AND has_embedding = 1` 过滤候选集，传给 `VectorEngine.batchSearch` 时已只剩本 session 的向量——纯 Dart 内存计算，天然 session 隔离，无需 JOIN，无跨表过滤

```sql
-- 步骤1：加载本 session 候选向量（embedding BLOB）
SELECT memory_id, embedding
FROM experiential_memories
WHERE session_id = ? AND has_embedding = 1 AND is_archived = 0
```

```dart
// 步骤2：VectorEngine.batchSearch 在候选集内算 topK（已是本 session 子集）
final results = await vectorEngine.batchSearch(
  queryVector: queryVec,
  candidates: candidateVectors,   // 仅本 session
  candidateIds: candidateMemoryIds,
);
```

> **方案变更说明**：原 sqlite-vec 方案需 `memory_vectors JOIN experiential_memories` 过滤 session，且有 `k` 参数全局 KNN 与 `WHERE` 组合的技术风险。纯 Dart 方案天然无此问题——session 隔离在 SQL 加载阶段完成，候选集天然纯净。

### 3.9 embedding 同步生成

> **V1 启用说明**（2026-07-03）：embedding 链路自 V1 起启用。配置来源 `ConfigurationResolver.resolveEmbeddingConfig()` → `EmbeddingApiConfig?`（全局配置，非会话级），未配置（null）时检索与写入两阶段均跳过 embedding，FTS5 兜底。配置项 `intermediate.embedding_preset_id` / `intermediate.embedding_model_id` 通过设置页 UI 持久化到 `settings.user_overrides`，详见 DOC-09C §10.1。

embedding 在中级模式有两个调用点，均**同步阻塞**（用户决策，对比异步队列方案）：

**调用点1：retrieve 阶段查询向量化**（`IntermediateChatController._resolveQueryVector`；v0.2.2：2 路并行向量化）
- extracting（请求1）结束 → 拿到 5 类关键词 → 用 `eventTerms` getter（合并 actions + plots）拆分为两个查询文本，分别调用 embedding API 生成 `actionsQueryVector` 和 `plotsQueryVector`
  - **v0.2.2 变化**：从原单向量（events 或 entities 兜底）改为 2 路并行向量化（actions 与 plots 语义维度不同，分别向量化更精准）
- `actionsQueryVector` / `plotsQueryVector` 作为 `searchExperiences` 的参数传入，与历史记忆向量做 2 路并行余弦相似度检索
- 未配置 embedding（`EmbeddingApiConfig` 为 null）→ 两向量均 null → 仅 FTS5 3 路检索
- 调用失败 + `fallbackOnFailure=true` → 对应向量 null（降级 FTS5 + 另一路 Vector）
- 调用失败 + `fallbackOnFailure=false` → rethrow（由失败分类器触发 E010/E014）

**调用点2：persisting 阶段事件摘要向量化**（`IntermediateChatController._resolveEmbedding`）
- summarizing（请求4）结束 → 拿到完整事件摘要（5W1E 结构）→ 立即同步调用 embedding API
- **向量化对象**：由原 `eventSummary.summary` 改为 5W1E 6 字段拼接文本，带中文标签 `时间：{when}\n地点：{where}\n人物：{who}\n事件：{what}\n意义：{significance}\n补充：{extra}`。空字段省略（不产生空行）。`summary`（可选兼容字段）若存在则拼接进"事件"行（即 `事件：{what}（{summary}）`）。此变更让向量空间同时编码结构化语义，提升语义检索召回率
- 向量生成成功 → experiential_memories（含 embedding BLOB + has_embedding=1）原子事务写入
- 向量生成失败 → **降级**：事件摘要照常写入，`has_embedding=false`，下一轮该事件只走 FTS5 检索
- 未配置 embedding → embedding=null → has_embedding=false（FTS5 兜底）
- **v0.2.2 新增**：若本轮触发了压缩，压缩摘要也同步向量化（按 `summary` 单字段，5W1E 6 字段为空字符串），写入 `experiential_memories`（`memory_level=macro`）

**失败降级的理由**：同步阻塞的目的是"即时就绪"，正常情况成功即达成。失败时降级，事件仍可被 FTS5 检索，保住"能检索到"的核心价值；若 embedding 偶发故障就整轮失败，用户体验太差。embedding 失败降级归入 DOC-09A-2 §6 失败处理状态机统一描述。

### 3.11 事实层检索（DOC-11 中间方案，schemaVersion=22 启用）

> **设计动机**：长对话后 LLM 写错角色品种、性别、年龄，多实例串台（两只狗的 skills 归属混乱），用户明确改名后 LLM 仍用旧名。根本原因：设定信息从未被结构化提取，LLM 每轮只能从对话历史"临时记忆"。

> **方案定位**：v0.2 中级模式提前落地事实层子集——实体+属性双表 + FactsDelta 协议 + 三重防护 + 5 层健康度防护，但不含 v0.3 的 Agent Loop / HUD / state_snapshots / update_world。权威设计详见 `doc/design/11_事实层中间方案设计.md`。

#### 3.11.1 检索在七步事务中的位置

事实层检索与经历层检索**并行执行**于 retrieving 阶段（互不依赖）。v0.2.2 检索前置后，检索结果同时注入 drafting（必经）与 revising（可选，复用不重新检索）：

```
retrieving 阶段（v0.2.2：5 路并行）
  ├─ 经历层检索（§3.2-§3.10）
  │   └─ FTS5 3 路 + Vector 2 路 5 路混合检索 → ScoredMemory 列表（topK=12）
  └─ 事实层检索（本节）
      └─ FactContextBuilder.buildFactBlock → FactRetrievalResult
          ├─ factBlock: 注入 drafting prompt 的【世界设定】文本（revising 开启时复用）
          └─ facts: List<RetrievedFact>（供 UI 检索面板展示）
```

#### 3.11.2 检索算法（纯本地，无 LLM）

`FactContextBuilder.buildFactBlock` 执行步骤（DOC-11 §6.1；v0.2.2 参数化）：

1. **加载关键实体**：`FactualRepository.getKeyEntities(sessionId, keyEntityImportanceThreshold)` 走 `idx_factual_entities_session_importance` 索引，返回 importance >= 阈值（`keyEntityImportanceThreshold`，默认 5）的实体（强制注入），最多 `keyEntityMaxInject`（默认 3）个
2. **关键词命中匹配**：`FactualRepository.findByName(sessionId, keywords.entityTerms)` 走 `idx_factual_entities_session_name` 索引，匹配 `primaryName` 精确 OR `aliases` 数组包含
   - **v0.2.2 关键词来源**：从 2 类 `entities` 改为 5 类中的 `entityTerms` getter（合并 characters + items + locations）
3. **合并去重 + 上限截断**：关键实体优先（按 importance 降序、createdAt 升序），关键词命中的非关键实体次之，最多 `injectionMaxEntities` 个（默认 10）
4. **批量加载属性**：`FactualRepository.getAttributes(sessionId, entityIds)` 走 `idx_factual_attrs_session_entity` 索引
5. **格式化文本**：按实体类型分组（角色/宠物/NPC/地点/物品），每实体一行

#### 3.11.3 与经历层检索的差异

| 维度 | 经历层 | 事实层 |
|------|--------|--------|
| 数据模型 | append-only 事件日志（5W1E 6 字段） | 实体+属性双表（当前状态快照） |
| 检索方式 | FTS5 3 路 + Vector 2 路 5 路混合检索（v0.2.2） | 名字匹配 + 重要性筛选 |
| 排序 | finalScore（加权 + 归一化） | 无 score，二元判定（注入或不注入） |
| 关键实体强制注入 | 无（经历层关键事件加权默认不生效） | **有**（`importance >= 5` 强制注入，最多 3 个，2026-08-06：从4提升至5） |
| 注入位置 | 【相关往事】区块 | 【世界设定】区块（在【相关往事】之前） |
| 注入目标 | drafting（必经）+ revising（可选复用，v0.2.2） | drafting（必经）+ revising（可选复用，v0.2.2） |
| 失败降级 | 检索为空 → 跳过【相关往事】 | 异常 → 返回空结果，不阻塞经历层 |

> **设计理由**：事实层是"当前世界状态"快照，不需要按相关性排序——所有命中的实体全部注入即可。经历层是历史事件流，需要按相关性排序取 topK。

#### 3.11.4 性能影响

- 关键实体查询：`idx_factual_entities_session_importance` 索引，单次 <2ms
- 名字匹配：`idx_factual_entities_session_name` UNIQUE 索引，单次 <1ms
- 属性批量加载：`idx_factual_attrs_session_entity` 索引，N 个实体一次查询 <5ms
- 总耗时：通常 <10ms，与经历层检索并行执行，不增加 retrieving 阶段总时长

#### 3.11.5 失败降级

`FactContextBuilder.buildFactBlock` 内部 try-catch 全包，任何异常（如数据库损坏、schema 不匹配）返回空 `FactRetrievalResult(factBlock='', facts=[])`，**不抛异常**——事实层失败不应阻塞经历层检索和 drafting/revising 流程。日志记录失败原因供后续排查。v0.2.2 检索前置后，事实层失败影响 drafting 阶段（无【世界设定】区块），但 drafting 仍可正常生成草稿（仅损失事实层参考）。

## 4. 批量记忆提炼流程

### 4.1 设计动机

低重要性记忆（`importance < importanceStorageThreshold`，默认 3）按设计仍写入 `experiential_memories` 但**不建 FTS5 索引 / 不生成 embedding**，即不可被检索。这些记忆留存了原始事件信息，但随着对话推进，相似的低重要性记忆会不断累积——大模型在相近轮次可能反复提取相似事件（如多次"走进酒馆"），既浪费存储也稀释了检索信噪比。

**批量记忆提炼**（Memory Consolidation）在上下文 token 占用率超阈值时，异步调用 LLM 将多条低重要性记忆合并为少数高重要性剧情节点记忆，使后续轮次能检索到合并后的关键剧情。

### 4.2 触发条件

由 `_runPersistPhase` 在 `!isRegenerate && _consolidator != null` 时 `unawaited` 触发（不阻塞 UI、不影响主流程）。重新生成场景不触发（删除下游记忆后 context 收缩，无需合并）。

```
budget = contextWindow - maxTokens
usageRatio = totalTokens(state.messages) / budget
```

| 条件 | 默认值 | 说明 |
|------|--------|------|
| `budget > 0` | — | 配置异常（max_tokens ≥ context_window）时跳过 |
| `usageRatio > trigger_threshold` | 2.0（2026-07-19 起禁用，原 0.8） | 上下文占用率超阈值才值得合并；设为 2.0 等价于永不触发（占用率不可能 >1），合并流程当前禁用 |
| `unindexedCount >= min_artifacts_to_consolidate` | 3 | 未索引记忆太少不值得一次 LLM 调用 |

三个条件全部满足时进入合并流程。配置参数详见 DOC-09B §10.1 consolidation 组。

### 4.3 合并流程

```
1. 查询未索引记忆
   getUnindexedExperiences(sessionId, limit=max_artifacts_to_consolidate)
   → 按 turn_number 升序返回（时间顺序，便于 LLM 理解剧情流）
   → 仅未归档（is_archived=false）的记忆

2. 调用 LLM 合并（MemoryConsolidator.consolidate）
   - 使用 LlmService.chat 非流式接口（复用统一 LLM 调用层）
   - 系统提示词：prompts.consolidation_prompt（kConsolidationPrompt）
   - user 内容：按时间顺序列出待合并记忆（轮次/importance/summary/tags）
   - response_format: json_object（强制合法 JSON）
   - temperature=0.3（合并任务需稳定输出）
   - maxTokens=1500 / 超时 30s
   - 输出 JSON：{"consolidated":[{summary,tags,importance}]}
   - 失败/超时/JSON 解析失败 → 返回空列表（降级，记 warn 日志）

3. 生成 embedding（若 embedding 配置可用）
   - 对每条合并记忆调 EmbeddingService.embed
   - 失败降级：embedding=null，FTS5 兜底

4. 原子持久化（IntermediatePersistenceService.persistConsolidatedMemories）
   - 在单一 drift transaction 内执行：
     a. 对每条合并记忆：INSERT experiential_memories + UPDATE embedding + INSERT FTS5 索引
     b. 删除原始未索引记忆（experiential_memories + memories_fts）
   - 任一步骤失败 → 事务回滚，原始记忆不被删除（下次触发可重新合并）
   - LLM 返回空列表 → 跳过持久化（无可合并内容）
```

> **宏摘要字段说明**（2026-07-19）：宏摘要（macro summary）作为对若干相邻 micro 的聚合总结，**保持 `summary` 单字段，不采用 5W1E 结构**。理由：宏摘要是高密度剧情节点，单字段 `summary` 信息已足够；且宏摘要不带"具体时间/地点/人物"等微摘要元素，强行套用 5W1E 反而引入噪声。当前 `consolidation` 已禁用（`trigger_threshold=2.0`，见 §4.2），本节流程作为"恢复启用时的设计参考"保留。**恢复时需重新设计 5W1E 聚合规则**——若宏摘要改用 5W1E，则需在 `MemoryConsolidator.consolidate` 输出 JSON schema 中加入 5W1E 6 字段，并相应扩展 `ConsolidatedMemoryRecord`、`persistConsolidatedMemories` 与 FTS5 索引写入逻辑（参见 §3.3 7 内容字段索引）。

### 4.4 容错策略

- `unawaited` 触发：不阻塞 UI，失败仅记 warn 日志，不影响会话主流程
- LLM 失败/超时/JSON 解析失败 → 返回空列表，不持久化
- embedding 失败 → 降级为 `has_embedding=false`，FTS5 兜底
- 事务回滚 → 原始记忆保留，下次触发时重新合并

### 4.5 相关接口

| 组件 | 职责 |
|------|------|
| `MemoryConsolidator` | 调用 LLM 合并记忆 + JSON 解析容错 |
| `ExperienceRepository.getUnindexedExperiences` | 查询未建 FTS5 索引的记忆 |
| `ExperienceRepository.deleteExperiencesByIds` | 批量删除原始记忆（同事务） |

| `ConsolidatedMemoryRecord` | 持久化 DTO（summary/tags/importance/turnNumber/embedding）——宏摘要保持 summary 单字段，不采用 5W1E（见 §4.3 宏摘要字段说明） |
| `ConsolidationConfig` | 配置类（trigger_threshold/min/max_artifacts_to_consolidate） |
