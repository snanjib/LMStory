## 1. Chat 子系统

### 1.1 概述

Chat 子系统是 LMStory 的核心业务模块，负责会话管理、消息收发、流式交互、对话分支和上下文压缩。Simple 模式与 Advanced 模式共享基础设施，但各自拥有独立的 Controller 和 Page。

**参考项目**：ChatBox（<https://github.com/chatbox-org/chatbox>）的 Session 模块按职责拆分为 16 个文件（crud / messages / threads / forks / generation / orchestration 等），本子系统借鉴其拆分思路。

> **推荐回复子模块**（v0.2 新增 2026-07-29，仅中级模式）：`SuggestReplyGenerator`（Domain 层服务，`features/intermediate/domain/services/suggest_reply_generator.dart`）负责调用 LLM 生成候选用户回复。**服务职责**：(1) 拼装上下文（最近 1 轮 user+assistant 完整消息 + 前 2 轮 micro 摘要）；(2) 单次非流式 LLM 调用（禁用 reasoning，`responseFormat` 强制 JSON），输出 `{"replies": ["...", "...", "..."]}`；(3) 解析 JSON 并容错（markdown 代码块剥离、非数组降级、截断/补齐到 candidateCount）。**与 IntermediateChatController 协作**：Controller 的 `generateSuggestReplies()` 方法通过 `ConfigurationResolver.resolveSuggestReplyNamingConfig/Prompt` 解析模型与提示词后，委托 `SuggestReplyGenerator.generate()` 执行；`selectSuggestReply(index)` 返回选中候选由 UI 层插入输入框；`toggleSuggest()` 切换浮层展开/折叠；`closeSuggest()` 清空候选。**配置消费**：`SuggestReplyConfig`（7 字段：presetId/modelId/prompt/temperature=0.7/maxTokens=200/candidateCount=3/maxReplyLength=50）从全局 `intermediate.suggest_reply.*` 读取，会话级 3 字段覆盖。详见 DOC-09D。

```
    │                    currentAssistantMessageId, currentCompactionSummaryId, generatingAnchorUserMsgId, quoteText,
    │                    currentModelName, currentProviderName, contextWindowTokens）
    │   └── copyWith 使用 sentinel 模式：error、currentAssistantMessageId、currentCompactionSummaryId、generatingAnchorUserMsgId、quoteText 等用 sentinel 值区分"未提供"和"显式 null"
    ├── CancellationToken? _currentCancelToken
    ├── StreamSubscription<SseEvent>? _currentSubscription
    └── String? _cachedApiKey
    （流式状态已移至 StreamHandler.StreamState：thinkingStartTime, firstTokenLatency,
     accumulatedToolCalls, currentBranchIndex, currentUserMessage, isFinishing,
     isViewingOtherBranch, backgroundAssistantMessage, generatingAnchorUserMsgId）
    （Fork 回滚信息已移至 ForkManager.pendingForkRollback）
```

**Controller 仍为对外统一入口**，内部委托给各管理器，不暴露管理器实例。子类 override `dispatchSend` 时使用 StreamManager。

#### 错误持久化机制（v0.1 更新）

**核心原则**：任何错误都必须持久化到助手消息，保证错误可见性。Fork 操作失败时不再回滚分支，而是保留新分支并显示错误，用户可切换查看。

**错误持久化流程**：
1. `_persistErrorToMessage(errorText)` 总是持久化错误到助手消息：
   - 已有助手消息（流式中途失败）：更新该消息的 error 字段
   - 无助手消息（首个 token 前失败）：创建带 error 的助手消息并入库
   - 后台模式（`_isViewingOtherBranch` 为 true）：持久化到 `_backgroundAssistantMessage` 并入库
2. API 失败时（非用户取消）：持久化错误 + 清除 `_pendingForkRollback`（不回滚分支）
3. 用户主动取消时（CancelledException）：回滚 Fork 操作（恢复旧分支），不持久化错误

#### 结构化错误处理（v0.2 诊断包扩展）

**目的**：Simple 模式在 v0.1「错误持久化到助手消息」基础上，补充结构化错误上下文 + failure_logs 表写入，使 Simple 模式失败记录可在诊断页（D3）与中级模式记录统一展示。

**核心组件**（D4 新增）：
- `SimpleErrorContext`（chat domain entity）：4 字段精简版（errorCode/errorCategory/httpStatus/rawError），无 failedPhase/retryable（Simple 模式无状态机、无自动重试）
- `SimpleFailureClassifier`（chat domain service）：分类器，`classifyError` 同源 `IntermediateFailureClassifier`，`errorCodeFromCategory` 映射 S001-S009，`formatDisplay` 组合「友好提示（错误码）」用于助手消息展示
- `ChatModeController._recordError`（统一错误处理入口）：构造 `SimpleErrorContext` + `unawaited(_failureLogRepository.insertLog(...))` 静默写入 failure_logs 表（mode='chat'，failedPhase=null）

**9 处 catch 块统一接入**（D4 改造）：`_loadMessages`/`sendMessage`/`_sendToApi`(3 处配置检查 + 1 处 catch)/`StreamError`/`_handleStreamError`/`clearMessages`/`_compressHistoryCore`(3 处) 全部调用 `_recordError`，错误分类可通过 `overrideCategory` 手动覆盖（如配置检查 → config、本地存储 → persist、压缩失败 → unknown）。

**与 v0.1 的关系**：D4 不替换 `_persistErrorToMessage`，而是在其上游增加结构化分类 + 诊断表写入。`_recordError` 返回 `SimpleErrorContext`，调用方用 `formatDisplay` 生成展示文本，再交给 `_persistErrorToMessage` 持久化到助手消息。两条路径互补：助手消息错误卡片（用户可见）+ failure_logs 表（诊断页可见）。

**设计决策**：`errorCategory` 用 `String` 而非 `ErrorCategory` 枚举——`ErrorCategory` 定义在 `intermediate_chat_state.dart`，Simple（chat domain）import 它会违反 Clean Architecture（跨 feature 依赖）。String 值与 `ErrorCategory.name` 一致，failure_logs 表本就存 String，诊断页可统一展示。详见 DOC-09B §9.1。

#### 后台流式生成机制（v0.1 新增）

**核心原则**：流式生成期间用户切换分支查看不影响后台生成，生成完成后新分支相当于已完成的消息，不强制切换。

**后台模式流程**：
1. 流式生成期间用户切换分支（`switchFork` 检测 `state.isStreaming`）：
   - 将占位助手消息从 `state.messages` 移到 `_backgroundAssistantMessage`
   - 设置 `_isViewingOtherBranch = true`
   - 执行普通分支切换逻辑（交换快照）
2. 后台模式下 SSE 事件处理：
   - `_handleTextDelta` / `_handleThinkingDelta` / `_handleToolCallComplete` 更新 `_backgroundAssistantMessage`，不更新 `state.messages`
3. 后台模式下流式完成（`_finishStreaming` 检测 `_isViewingOtherBranch`）：
   - 调用 `_finishBackgroundStreaming` 将 `_backgroundAssistantMessage` 入库
   - 刷新 Fork 锚点，但不更新 `state.messages`（保持用户当前查看的分支）
4. 后台模式下流式出错（`_handleStreamError` / `_persistErrorToMessage`）：
   - 调用 `_persistErrorToBackgroundMessage` 将错误持久化到 `_backgroundAssistantMessage` 并入库
5. 用户切换回生成分支（`switchFork` 检测目标分支为生成分支）：
   - 调用 `_restoreBackgroundToState` 将 `_backgroundAssistantMessage` 恢复到 `state.messages`
   - 恢复 `currentAssistantMessageId` 和 `generatingAnchorUserMsgId`
   - 清除后台模式状态

#### Fork 操作回滚机制（v0.1 更新）

Fork 操作（`regenerateInNewFork` / `editAndResendInNewFork`）在创建新分支后、API 调用前记录回滚信息 `_pendingForkRollback`：

```
_ForkRollbackInfo:
  anchorUserMsgId → Fork 锚点用户消息 ID
  branchIndex → 本次创建的分支索引
  originalContent → 用户消息原始内容（仅 editAndResend 需要，regenerate 为 null）
```

**回滚流程**（仅用户主动取消时触发）：
1. 流式成功完成时清除 `_pendingForkRollback`（无需回滚）
2. API 失败时（非用户取消）：持久化错误到助手消息 + 清除 `_pendingForkRollback`（不回滚分支，保留新分支显示错误）
3. 用户主动取消时（CancelledException）：调用 `_rollbackForkIfNeeded()` 回滚分支：
   - 调用 `removeForkBranchWithSnapshot(sessionId, anchorUserMsgId, removedBranchIndex, currentTailMessages: [])` 回滚 `chat_session_branches` 记录
   - 该方法会自动从 `branch_snapshots` 恢复旧分支消息到 `chat_messages` 表
   - 若 `originalContent` 非空，恢复用户消息原文
   - 重新加载消息列表 + 刷新 ForkAnchor

#### 取消发送与 Fork 回滚（v0.1 实际实现新增）

**背景**：用户在 Fork 操作（重新生成/编辑重发）后、API 响应前点击"终止"按钮，若仅调用 `cancelSending()` 取消流，新创建的空分支会残留，导致：
- 用户消息变为最后一条（大模型回复为空）
- 不显示左右切换分支按钮（因新分支无消息）
- 已回复的那条无法切过去

**解决方案**：新增 `cancelSendingWithRollback()` 方法，UI 层终止按钮统一调用此方法：

```
cancelSendingWithRollback():
  1. cancelSending()              ← 取消流 + 清理 stream subscription
  2. _rollbackForkIfNeeded()      ← 回滚 Fork（若有待回滚操作）
  3. _refreshForkAnchors()        ← 刷新 ForkAnchor 列表
```

**关键点**：
- `regenerateInNewFork` / `editAndResendInNewFork` 末尾必须补充 `_refreshForkAnchors()` 调用，确保分支锚点正确显示
- 仅在有 `_pendingForkRollback` 时才执行回滚，普通发送终止不受影响

#### 自动命名机制（v0.1 实际实现新增，对标 ChatBox autoGenerateTitle）

**触发条件**：
1. 会话标题是默认值（"新建会话" / "New Chat"）或空
2. 消息数 >= 2（一问一答完成）

**触发时机**：`_finishStreaming()` 末尾异步调用 `unawaited(_autoNameSession())`，不阻塞 UI。

**命名流程**：
1. 取前 4 条非 system 消息，每条截取前 100 字符
2. 调用 `_resolveNamingConfig()` 解析 API 配置（复用会话 presetId/apiKey/modelId，回退到全局默认）
3. 调用 LLM（非流式 `http.post`，15 秒超时）：
   - System prompt: "根据以下对话内容，为这个会话生成一个简短的标题。要求：最多10个字，不要加引号，直接输出标题。使用与对话相同的语言。"
   - temperature: 0.3, max_tokens: 50, stream: false
4. 清理标题（去除引号、`<think>` 标签、首尾空格），限制 30 字符
5. 更新 DB + state

**回退策略**（LLM 调用失败/无可用 API 配置时）：
- `_applyFallbackName()`：截取第一条用户消息前 20 字符作为标题

**API 配置解析**（`_resolveNamingConfig`）：
1. presetId：会话 presetId → 默认 preset → 第一个 preset
2. apiKey：会话 preset 的 key → 遍历所有 preset 找第一个有 key 的
3. modelId：会话 modelId → 全局 broadcastChat.modelId
4. baseUrl：从 preset 获取，经 `ApiUrlResolver.resolve()` 补全

### 1.4 流式消息双层缓存

参考 ChatBox 的双层缓存策略，避免高频 I/O：

| 层级 | 存储 | 更新频率 | 用途 |
|------|------|---------|------|
| **内存层** | `ChatState.streamingContent` | 每个 text delta | UI 实时渲染 |

### 1.5 Fork 机制设计

参考 ChatBox 的 `messageForksHash` 设计，LMStory 采用**快照模型**实现分支：

> **v0.1 实际实现**：v0.1 采用快照模型——`chat_messages` 表**仅存储当前活跃分支的消息**，非活跃分支消息以 JSON 快照存储在 `chat_session_branches.branch_snapshots` 列。
> Controller 层通过 Repository 读写分支快照，切换分支时在 DB 行与 JSON 快照间交换消息。
> 此设计避免了"多分支消息共存于 `chat_messages` 表需要按 `branch_index` 过滤"的复杂逻辑。

**数据模型**：

```
chat_session_branches 表（持久化）:
  session_id + anchor_user_msg_id → 定位分叉锚点（UNIQUE 约束）
  active_branch_index → 当前激活分支
  branch_count → 分支总数
  branch_snapshots → JSON 数组，存储非活跃分支的消息快照
                     结构: [{"index": 0, "messages": [{...}, ...]}, ...]

chat_messages 表:
  仅存储当前活跃分支的消息（无需 branch_index 过滤）
  parent_user_msg_id → 标识该消息属于哪个锚点
  branch_index → 该消息在其分支中的索引（仅用于快照恢复时定位）

ForkAnchor（内存视图，映射 chat_session_branches 表）:
  parentUserMsgId → 锚点用户消息 ID
  activeIndex → 当前激活的分支索引（0-based）
  branchCount → 分支总数（来自 chat_session_branches.branch_count）
```

**核心操作**：

| 操作 | 流程 |
|------|------|
| **创建分支** | 1. 调用 `addAssistantBranchAndSnapshot(sessionId, anchorUserMsgId, tailMessages)`<br>2. 将锚点之后的"尾部消息"序列化为 JSON 存入 `branch_snapshots`<br>3. 从 `chat_messages` 表删除尾部消息<br>4. `chat_session_branches` 中 `branch_count++`，`active_branch_index` 指向新分支<br>5. 新分支消息后续生成时正常写入 `chat_messages` 表<br>6. **立即调用 `_refreshForkAnchors()` 刷新 state.forkAnchors**（让分支导航在生成过程中就显示）<br>7. 设置 `state.generatingAnchorUserMsgId = anchorUserMsgId`（占位气泡关联到锚点，使 SimpleForkNav 在生成过程中可切换到旧分支） |
| **切换分支** | 调用 `switchForkBranchWithSnapshot(sessionId, anchorUserMsgId, newActiveIndex, currentTailMessages)`<br>1. 当前尾部消息存入当前分支快照<br>2. 从目标分支快照反序列化消息<br>3. 删除 `chat_messages` 表尾部，插入目标分支消息<br>4. 更新 `active_branch_index`，返回新消息列表 |
| **删除分支** | 删除助手消息时调用 `removeForkBranchWithSnapshot` 维护 `chat_session_branches` 记录<br>- 删除非活跃分支：仅从 `branch_snapshots` 移除<br>- 删除活跃分支：删除 `chat_messages` 尾部 + 从快照恢复其他分支 |
| **导航方向** | 循环切换：`(activeIndex + direction + branchCount) % branchCount` |
| **失败回滚** | API 失败时不再回滚分支，而是持久化错误到助手消息（保留新分支显示错误，用户可切换查看）。仅用户主动取消时调用 `_rollbackForkIfNeeded` 回滚分支 |
| **流式期间切换** | 生成过程中点击分支导航时，不取消生成，进入后台模式：<br>1. 将占位助手消息移到 `_backgroundAssistantMessage`<br>2. 设置 `_isViewingOtherBranch = true`<br>3. 执行普通分支切换（交换快照）<br>4. 后台 SSE 事件更新 `_backgroundAssistantMessage`，不更新 `state.messages`<br>5. 流式完成时将后台消息入库，不强制切换回生成分支<br>6. 用户切换回生成分支时恢复后台缓冲区到 `state.messages` |

### 1.6 上下文压缩

两种模式采用完全不同的压缩策略，根本原因：Simple 模式对话历史是唯一的信息载体，Advanced 模式有独立的语义分层记忆系统。

#### Simple 模式：CompactionPoint 摘要压缩（参考 ChatBox）

Simple 模式没有独立记忆系统，对话历史是唯一的信息载体，必须用 LLM 生成摘要来保留信息。

> **v0.1 实际实现差异**：原始设计将压缩拆分为 CompactionDetector + CompactionExecutor + ContextBuilder + SummaryGenerator 四个独立组件。
> v0.1 实际实现合并为 `CompactionService`（Domain 层服务，负责阈值检查 + 非流式摘要 + 压缩点落库）+ `CompactionStreamer`（Domain 层服务，负责流式 LLM 摘要请求），主要差异：
> 1. 阈值语义：`compactionThreshold` 为百分比（0.4-0.9，默认 0.6），对标 ChatBox `compactionThreshold`，表示上下文占用比例
> 2. 摘要生成：自动压缩与手动压缩均走流式路径（`shouldCompact` 预检 → controller `_compressHistoryCore` → `compactWithStream` → `CompactionStreamer` + `HttpClient.streamPost` + `SseParser`），UI 展示占位摘要 → 流式打字 → 完成落库的完整过程。`checkAndCompact`（非流式）保留兼容但不再用于自动压缩
> 3. 失败处理：手动压缩失败时不回退，保留已生成的部分摘要 + error 字段，渲染为常驻失败卡片（用户手动关闭或重试）
> 4. 摘要消息角色：`role: 'system'`（实际代码），原始设计为 `role: assistant` ⚠️ **待修正**
> 5. 压缩点存储：`Map<String, dynamic>` 而非 `CompactionPoint` 实体
> 6. 防抖锁：`ChatModeState.isCompressing` 标志，压缩中禁止再次触发（菜单项禁用），防止连续点击产生重复摘要；同时 `currentCompactionSummaryId` 记录占位摘要消息 ID，UI 据此渲染流式生成状态（折叠态小窗预览 + 闪烁光标，展开态流式内容 + 光标）

#### 核心概念

| 概念 | 说明 |
|------|------|
| **CompactionPoint** | 压缩检查点，记录 `summaryMessageId`（摘要消息 ID）和 `boundaryMessageId`（被压缩的最后一条消息 ID） |
| **Summary Message** | 由 LLM 生成的对话摘要，标记 `isSummary = true`，作为 assistant 消息存入消息列表 |
| **Boundary** | 压缩边界，boundary 之前的消息不在上下文中使用，但**原始消息不删除** |

#### 触发机制

```
每次发送消息时（阻塞式，在 sendMessage 开头、用户消息插入前触发，对标 ChatBox）：
1. 计算当前上下文 token 数
2. 判断是否超过阈值（对标 ChatBox compaction-detector.ts）：
   availableWindow = max(contextWindow - 32000, floor(contextWindow × 0.5))
   thresholdTokens  = floor(availableWindow × compactionThreshold)
   isOverflow       = (currentTokens > thresholdTokens)
   - contextWindow: 模型上下文窗口大小（来源：模型缓存的 contextWindow 字段）
   - compactionThreshold: 压缩阈值（百分比，0.4-0.9，默认 0.6，可配置）
   - 安全下限 `contextWindow × 0.5` 防止预留过大时可用窗口为零或负值
   - contextWindow 未知（null）时不触发自动压缩；LMStory 中未知时使用默认值 96000（对标 ChatBox DEFAULT_CONTEXT_WINDOW）
3. 超过阈值 → 触发压缩
```

> **压缩时机**：自动压缩在 `sendMessage` 开头触发（用户消息插入前），而非 `_sendToApi` 中（用户消息插入后）。
> 对标 ChatBox 的阻塞式压缩，确保上下文顺序为「摘要 → 用户消息 → AI 回复」。

#### 压缩流程

```
触发压缩
  │
  ├── 1. 获取当前上下文消息（通过 getCompressedMessages，已按最新 CompactionPoint 截断并过滤旧摘要）
  ├── 2. 压缩范围 = 全部当前上下文消息（非摘要消息），对标 ChatBox runCompactionWithStreaming
  │     不再取前一半，避免摘要偏离最新上下文
  ├── 3. 调用 LLM 生成摘要（对标 ChatBox summarizeConversation 提示词）
  │     prompt = 全部当前上下文消息 + 聚焦"继续对话所需关键信息"的指令
  │     （讨论内容/关键决策/正在做什么/下一步，而非复述对话）
  ├── 4. 创建 summaryMessage（isSummary = true）
  ├── 5. boundary = 最后一条非摘要消息（对标 ChatBox lastNonSummaryMessage）
  └── 6. 创建 CompactionPoint { summaryMessageId, boundaryMessageId, createdAt } 并写入 DB
  
  > 注：原始消息不删除，通过 CompactionPoint 边界跳过。boundary 是"压缩到此为止"的终点，
  > 已被纳入摘要，不再出现在后续上下文中（对标 ChatBox slice(boundaryIndex+1)）。

```

#### 压缩后的上下文构建

```
原始消息: [sys, m1, m2, m3, m4, m5, m6, summary-1, m7, m8]
CompactionPoint: { boundaryMessageId: 'm6', summaryMessageId: 'summary-1' }

getCompressedMessages 返回: [summary-1]  (boundary=m6 之后无消息)
                              ↑ 仅摘要，直到用户继续发消息

后续用户发新消息 m9, m10 后:
getCompressedMessages 返回: [summary-1, m9, m10]
                              ↑ 摘要 + boundary 之后的新消息
```

> **关键修复**：`getCompressedMessages` 方法会过滤掉 boundary 之后的旧 `isSummary` 消息，
> 避免多次压缩时旧摘要被重复纳入压缩范围。`_loadMessages`、自动压缩、手动压缩均通过
> `getCompressedMessages` 获取过滤后的当前上下文消息，而非直接读取 DB 全量消息。

#### 关键设计点

- **原始消息不删除**：通过 CompactionPoint 边界跳过旧消息，删除摘要可恢复原始消息到上下文
- **摘要可编辑/可删除**（对标 ChatBox SummaryMessage）：
  - 编辑：用户可手动修正摘要内容，仅更新消息文本，不影响 CompactionPoint
  - 删除：删除摘要消息 + 关联的 CompactionPoint，原始消息恢复到上下文（压缩的"反悔"机制）
- **压缩范围 = 全部当前上下文**（对标 ChatBox）：不再取前一半，避免多次压缩后摘要偏离最新上下文
- **只使用最新 CompactionPoint**：多次压缩时按 `createdAt` 取最大值，`getCompressedMessages` 过滤 boundary 后的旧 `isSummary` 消息，避免重复压缩已摘要内容
- **boundary 不含本身**：对标 ChatBox `slice(boundaryIndex+1)`，boundary 消息已被纳入摘要，不再出现在后续上下文中
- **阻塞式执行**：在 `sendMessage` 开头同步完成压缩（用户消息插入前），确保上下文顺序为「摘要 → 用户消息 → AI 回复」，对标 ChatBox 阻塞式压缩
- **手动压缩**：用户可通过两种入口手动触发 `ChatModeController.compressHistory()`（守卫检查后委托 `_compressHistoryCore` → `compactWithStream` 流式路径，与自动压缩复用同一核心逻辑），跳过阈值检查直接执行压缩：
  - 聊天菜单（`_showChatMenu`）中的"压缩上下文"选项
  - 上下文用量详情面板（输入框工具栏触发器点击 → BottomSheet → "压缩对话"按钮，对标 ChatBox TokenCountMenu）
  - 需满足：非发送/流式状态且非摘要消息数 ≥ 2
- **压缩状态显示**：压缩过程中通过摘要横幅（`_CompactionSummaryCard`）实时展示流式生成状态——折叠态显示"正在生成摘要..." + 三点动画 + 小窗预览末尾闪烁光标；展开态显示流式 Markdown 内容 + 末尾闪烁光标（标签栏改用静态图标避免与内容区动画重复）。压缩完成/失败后转为常驻卡片（失败卡片含重试/关闭按钮），不再使用 SnackBar 反馈
- **CompactionPoint 摘要显示**：压缩生成的摘要消息以可展开卡片形式显示，背景色为 surfaceVariant，点击可展开查看完整摘要内容，也可删除摘要恢复原始消息（v0.1 实际实现新增）
- **可配置参数**：`auto_compaction`（开关）、`compaction_threshold`（百分比阈值，0.4-0.9，默认 0.6）、`output_reserve_tokens`（输出预留）

#### Advanced 模式：按组装策略选择压缩方式

Advanced 模式拥有独立的语义分层记忆系统，对话原文在上下文中的角色是"最近交互记录"而非"唯一信息载体"。重要信息已通过 `update_world` 写入记忆系统。压缩方式与工作上下文组装策略联动：

**缓存优先模式 → LLM 摘要 + CompactionPoint**

与 Simple 模式相同机制，牺牲一次额外 API 调用换取最大缓存命中率。截断后摘要作为稳定前缀，后续对话增长时缓存命中区更大。

```
截断前: [System, 事实类, 对话1..50, 状态面板, 经历类记忆, 输入]
截断后: [System, 事实类, summary, 对话31..50, 状态面板, 经历类记忆, 输入]
                         ↑ LLM 生成的摘要，稳定前缀
```

**语义优先模式 → 记忆摘要替代（零 API 成本）**

从经历类记忆中按时间范围自动提取结构化摘要（纯代码逻辑，不调用 LLM），放在事实类记忆之后、对话之前，形成更大的稳定前缀。截断时对话部分缓存断裂，但记忆摘要段保持稳定。

```
截断前: [System, 事实类, 对话1..50, 状态面板, 经历类记忆, 输入]
截断后: [System, 事实类, 记忆摘要(自动提取), 对话31..50, 状态面板, 经历类记忆, 输入]
                         ↑ 从经历类记忆自动生成的结构化摘要，零 API 成本
```

**记忆摘要的生成逻辑**（语义优先模式专用）：
- 范围：被截断对话对应时间段内的经历类记忆
- 格式：按 `narrative_period` 分组的结构化文本（非 LLM 生成，纯代码拼接）
- 示例：
  ```
  【第一章：初入江湖】
  - 主角进入青云门，拜师学艺
  - 习得青云功入门心法
  - 在后山遇到白狐，获得线索

  【第二章：森林试炼】
  - 主角进入迷雾森林
  - 击杀狼型魔物，获得魔核
  - 遭遇哥布林袭击，将其击退
  ```

**为什么不需要 LLM 摘要**（两种模式共同前提）：

| 信息类型 | 存储位置 | 是否依赖对话原文 |
|---------|---------|----------------|
| 世界事实 | 事实类记忆 | 否，独立存储 |
| 重要事件 | 经历类记忆 | 否，`update_world` 已写入 |
| 当前状态 | HUD 状态面板 | 否，始终是最新的 |
| 最近交互 | 对话原文 | 是，但仅作为上下文润滑 |

#### 两种模式 × 两种策略完整对比

| 维度 | Simple 模式 | Advanced + 缓存优先 | Advanced + 语义优先 |
|------|------------|---------------------|-------------------|
| 压缩方式 | LLM 摘要 + CompactionPoint | LLM 摘要 + CompactionPoint | 记忆摘要替代（自动提取） |
| 信息损失 | 无（摘要保留关键信息） | 无（摘要保留关键信息） | 无（重要信息已在记忆系统中） |
| 额外 API 调用 | 是（生成摘要） | 是（生成摘要） | 否 |
| 压缩触发 | token 阈值 | token 阈值 | 对话部分 token 预算 |
| 旧消息是否删除 | 否（保留，删除摘要可恢复） | 否（保留，删除摘要可恢复） | 否（保留，只是不在上下文中） |
| UI 表现 | 摘要消息（可展开/删除） | 摘要消息（可展开/删除） | 无感知（静默截断） |

### 2.3.4 API URL 智能解析（ApiUrlResolver）

**背景**：用户配置的 baseUrl 层级不统一，有人填 `https://api.openai.com`，有人填 `https://api.openai.com/v1`，甚至填完整端点 `https://api.openai.com/v1/chat/completions`。直接拼接会导致 `/v1/v1/chat/completions` 这类重复。另外，LLM 集成需要至少 3 个不同端点（`/chat/completions`、`/models`、`/embeddings`），用户只填一个 baseUrl 时需要规范化后派生其他端点 URL。

**工具类**：`lib/core/utils/api_url_resolver.dart` 的 `ApiUrlResolver`

**设计对标**：本工具采用"规范化 + 版本号保留"策略，对标 ChatBox 的 `normalizeOpenAIApiHostAndPath`（src/shared/utils/llm_utils.ts）。核心思路是：先把用户填写的 baseUrl 规范化到统一形式（去掉端点路径 + 补协议头），**保留** baseUrl 中的版本号（如 `/v1`、`/v3`、`/v4`），然后拼接 path 时：若 baseUrl 有版本号，去掉 path 的版本号前缀（避免 `/v3/v1/...` 重复）；若没有，path 保持原样（自带 `/v1`）。这样所有端点（chat/models/embeddings）都基于同一个规范化后的 baseUrl 拼接，避免了"用户填了 chat 完整 URL 但 list models 404"的问题，同时支持使用非 /v1 版本号的供应商（如火山引擎 /api/v3、智谱 GLM /api/paas/v4）。

**解析规则**：

1. **手动模式（raw 前缀）**：baseUrl 以 `raw:` 前缀开头 → 去掉前缀后**原样返回**，不做任何补全。用于供应商端点完全非标准的情况（如 `/v4/chat/completion` 单数）。注意：raw 模式下所有端点都会用同一个 URL，list models 可能 404，仅适用于用户明确知道自己在做什么的场景。手动模式通过 baseUrl 字段的前缀持久化，无需修改 DB schema。

2. **非 raw 模式 - 规范化 + 版本号保留**（对标 ChatBox normalizeOpenAIApiHostAndPath）：
   - **trim 空格**
   - **去末尾斜杠**（对标 ChatBox 第 15 行）
   - **自动补 `https://` 协议头**（对标 ChatBox 第 18-20 行）—— 用户填 `api.openai.com` 不带协议时自动补全
   - **去掉端点路径后缀**（对标 ChatBox 第 23-26 行，扩展到 3 个端点）—— 如果 baseUrl 以 `/chat/completions`、`/models`、`/embeddings` 结尾，剥离该后缀
   - **保留版本号后缀**（/v1、/v3、/v4 等）—— 关键设计：不强制改为 /v1，保留用户填写的版本号。火山引擎 /api/v3、智谱 GLM /api/paas/v4 等非标准版本号供应商能正常工作

   规范化后的 baseUrl 形如 `https://api.openai.com`（无版本号）、`https://openrouter.ai/api/v1`（保留 /v1）或 `https://ark.cn-beijing.volces.com/api/coding/v3`（保留 /v3）。

3. **拼接 path**：
   - 若规范化后的 baseUrl 已含版本号（/v1、/v3 等），去掉 path 的版本号前缀（避免 `/v3/v1/...` 重复）
   - 否则直接拼接 path（含 /v1）

**典型场景行为**：

| 用户输入 | path | 解析结果 |
|---------|------|---------|
| `https://api.openai.com` | `/v1/chat/completions` | `https://api.openai.com/v1/chat/completions` |
| `https://api.openai.com/v1` | `/v1/chat/completions` | `https://api.openai.com/v1/chat/completions`（保留 /v1，去掉 path 的 /v1） |
| `https://api.openai.com/v1/chat/completions` | `/v1/chat/completions` | `https://api.openai.com/v1/chat/completions`（剥离端点后缀，保留版本号） |
| `https://api.openai.com/v1/chat/completions` | `/v1/models` | `https://api.openai.com/v1/models`（剥离端点后缀，自动派生 models 端点） |
| `https://api.example.com/v3/chat/completions` | `/v1/chat/completions` | `https://api.example.com/v3/chat/completions`（保留 v3，去掉 path 的 /v1） |
| `https://api.example.com/v3` | `/v1/models` | `https://api.example.com/v3/models`（保留 v3，自动派生 models 端点） |
| `https://ark.cn-beijing.volces.com/api/coding/v3/chat/completions` | `/v1/chat/completions` | `https://ark.cn-beijing.volces.com/api/coding/v3/chat/completions`（火山引擎，保留 /api/coding/v3） |
| `https://ark.cn-beijing.volces.com/api/coding/v3/chat/completions` | `/v1/models` | `https://ark.cn-beijing.volces.com/api/coding/v3/models`（火山引擎，派生 models 端点） |
| `https://open.bigmodel.cn/api/paas/v4` | `/v1/chat/completions` | `https://open.bigmodel.cn/api/paas/v4/chat/completions`（GLM /v4 场景，去掉 path 的 /v1） |
| `https://open.bigmodel.cn/api/paas/v4` | `/v1/models` | `https://open.bigmodel.cn/api/paas/v4/models`（GLM /v4 场景，自动派生 models 端点） |
| `https://openrouter.ai/api/v1` | `/v1/chat/completions` | `https://openrouter.ai/api/v1/chat/completions`（保留 /v1） |
| `api.openai.com`（无协议） | `/v1/chat/completions` | `https://api.openai.com/v1/chat/completions`（自动补 https://） |
| `raw:https://api.example.com/v3/chat/completions` | `/v1/models` | `https://api.example.com/v3/chat/completions`（原样返回，可能 404） |

**调用点**：所有构建 API URL 的地方都必须经过 `ApiUrlResolver.resolve()`：
- `ChatModeController._generateTitle`：`/v1/chat/completions`（标题生成场景；v0.2 主对话路径已迁移到 LlmService → LlmProtocolAdapter，不再直接调用 ApiUrlResolver）
- `CompactionService` / `CompactionStreamer`：`/v1/chat/completions`
- `ModelTestService`：`/v1/chat/completions`
- `ApiPresetRepositoryImpl`：`/v1/models`
- `EmbeddingRemoteDS`：`/v1/embeddings`
- 各协议适配器（OpenAiAdapter / DeepSeekAdapter / AnthropicAdapter / GeminiAdapter）：内部 buildUrl / buildModelsUrl（DeepSeekAdapter 继承 OpenAiAdapter，复用其 URL 构造逻辑）

**辅助方法**：
- `isRawMode(baseUrl)`：判断是否处于手动模式
- `displayName(baseUrl)`：获取用于显示的 baseUrl（去掉 `raw:` 前缀）

**与 ChatBox 的差异**：
- ChatBox 把规范化后的 apiHost 作为 baseURL 传给 AI SDK，由 AI SDK 处理端点拼接；LMStory 自己拼接完整 URL
- ChatBox 的 listModels 是 `${apiHost}/models`（apiHost 已规范化），LMStory 是 `resolve(baseUrl, '/v1/models')`（resolve 内部规范化 + 版本号去重）
- ChatBox 有内置 provider 域名硬编码识别（openai.com / openrouter.ai / api.x.com），LMStory 不做域名识别，统一走规范化逻辑
- ChatBox 没有 raw 模式（早期注释提到 `#` 强制地址已废弃），LMStory 保留 raw 模式用于完全非标准端点
- 两者核心思路一致：规范化 baseUrl（去末尾斜杠、补协议、剥离端点后缀），保留用户填写的版本号，所有端点都基于这个基础 URL 拼接
- 关键修正（2026-07-26）：之前 LMStory 误读了 ChatBox 第 46-49 行的"强制补 /v1"逻辑，把 v3 强制改为 v1，导致火山引擎等用 /v3 的供应商 404。实际上 ChatBox 第 46 行的判断条件是 `!apiHost.endsWith('/v1') && !apiPath`，当用户填了完整 URL（apiPath 已被设为 /chat/completions）时不会强制补 /v1，会保留用户填的版本号。LMStory 现已修正为保留版本号策略

### 2.4 供应商配置与模型选择的关系（v0.1 重构）

**关键设计决策**：供应商配置和模型选择是解耦的。

- **供应商配置**：只是"连接信息（baseUrl + API Key）+ 模型id列表"的搭配组合，没有"激活/选择"概念。用户可配置多个供应商，每个供应商可有多个模型。
- **默认模型**：全局设置，新对话建立时默认填充。从所有供应商的所有模型里选一个，同时记录 `defaultPresetId` + `defaultModelId`。
- **会话级模型**：每个对话独立存储 `presetId` + `modelId`，可在对话设置里切换。

旧设计中的 `activePresetId`（激活预设）概念已废弃，重命名为 `defaultPresetId`，语义从"当前激活的供应商"改为"新对话默认填充的供应商"。

### 2.5 配置解析链

```
       ↓ 组装

```

### 4.3 事实类记忆的 key-value 设计

### 4.4 经历类记忆的时序设计

**双时间锚点**：

| 字段 | 类型 | 来源 | 作用 |
|------|------|------|------|
| `turn_number` | INTEGER | 系统自动递增 | 绝对时序，排序消歧的最终依据 |
| `narrative_time` | TEXT | LLM 在 `update_world` 中填写 | 自然语言时间标记（如"修炼第三天·清晨"） |
| `narrative_period` | TEXT | 从 `narrative_time` 提取 | 时段分组（如"修炼第三天"），用于折叠和区间检索 |

**检索评分公式**：

```
final_score = fts5_score × 0.5 + vector_score × 0.3 + temporal_score × 0.2

temporal_score 计算:
├── periodMatchScore: 精确匹配 narrative_period → 1.0, 相邻时段 → 0.5, 否则 → 0.0
├── recencyScore: 1.0 - (maxTurns - memory.turnNumber) / maxTurns（线性衰减）
└── temporal_score = periodMatchScore × 0.6 + recencyScore × 0.4

关键事件加权：importance ≥ 4 → final_score × 1.5

归一化方法:
├── FTS5 (BM25): Query-internal min-max + 平滑因子 ε=0.01
├── Vector (cosine): (cosine + 1) / 2 映射到 [0, 1]
└── Temporal: 已在 [0, 1] 范围内
```

**在上下文中的呈现格式**（v0.2 5W1E 多行结构化，由 `_formatMemories` + `_formatSingleMemory` 渲染）：

```
[历史记忆 — 若与当前面板冲突，以当前面板为准]
- [修炼第三天·清晨] 在森林深处遭遇哥布林袭击，将其击杀
- [修炼第一天·黄昏] 进入迷雾森林，击杀狼型魔物
- [启程日·午后] 离开青云门，踏上历练之路
```

> v0.2启用 5W1E 结构化字段后，单条记忆按多行渲染：

```
[历史记忆 — 若与当前面板冲突，以当前面板为准]
[修炼第三天·清晨]
  · 地点: 森林深处
  · 人物: 主角、哥布林
  · 事件: 遭遇哥布林袭击，将其击杀
  · 意义: 首次实战获胜，信心提升
  · 补充: 无
[修炼第一天·黄昏]
  · 地点: 迷雾森林入口
  · 人物: 主角
  · 事件: 进入迷雾森林，击杀狼型魔物
```

> 字段说明：`when/where/who/what` 必填，`significance/extra` 可选；`summary` 字段保留为 `String?` 用于宏摘要回填与向后兼容。embedding 向量化对象改为 5W1E 6 字段拼接文本。

### 4.5 工作上下文组装协议

**设计目标**：提供两种组装策略，用户可通过配置开关切换。

#### 组装策略

| 策略 | 配置项 | 排序依据 | 适用场景 |
|------|--------|---------|---------|
| **缓存优先** | `prompt_assembly.strategy = "cache_first"` | 稳定内容在前，最大化缓存命中率 | 长对话、token 成本敏感 |
| **语义优先** | `prompt_assembly.strategy = "semantic_first"` | 按信息权威性从高到低排列 | 短对话、状态一致性要求高 |

#### 缓存优先模式（默认）

排序原则：稳定内容在前（缓存命中），对话原文在位置3（半稳定，部分缓存命中），状态面板在经历类记忆之前（先建立正确状态认知，再看历史）。

```
┌─────────────────────────────────────────────────────────────┐
│ [1] system: System Prompt                                    │
│ [2] system: 事实类记忆（世界书）                              │
│     ─── 缓存命中区：[1]+[2] 前缀稳定 ───                      │
│ [3] user/assistant × N: 最近 N 轮对话原文                    │
│     ─── 半稳定区：N-1 轮与上轮相同，部分缓存命中 ───          │
│ [4] system: 当前状态面板（标签"绝对真理"）                    │
│ [5] system: 检索到的经历类记忆（含冲突警告）                  │
│ [6] user: 当前用户输入                                       │
│     ─── 变动区域：[4]+[5]+[6] 每轮刷新 ───                  │
└─────────────────────────────────────────────────────────────┘
```

信息流逻辑：对话了解上下文 → 状态面板锚定当前状态 → 历史记忆补充细节（以状态面板为基准校验） → 用户输入生成回复。

缓存收益估算（System Prompt ~500 + 事实类 ~500 + 对话 ~4000 tokens）：
- 缓存命中区 ~1000 tokens，半稳定区 ~4000 tokens，合计可命中 ~4600 tokens

#### 语义优先模式

排序原则：按信息权威性从高到低排列，状态面板紧跟事实类记忆，确保 LLM 在读取历史记忆前已建立正确的状态认知。

```
┌─────────────────────────────────────────────────────────────┐
│ [1] system: System Prompt                                    │
│ [2] system: 事实类记忆（世界书）                              │
│     ─── 缓存命中区：[1]+[2] 前缀稳定 ───                      │
│ [3] system: 当前状态面板（标签"绝对真理"）                    │
│ [4] system: 检索到的经历类记忆（含冲突警告）                  │
│ [5] user/assistant × N: 最近 N 轮对话原文                    │
│ [6] user: 当前用户输入                                       │
│     ─── 变动区域：[3]+[4]+[5]+[6] 每轮刷新 ───              │
└─────────────────────────────────────────────────────────────┘
```

信息流逻辑：事实类记忆建立世界认知 → 状态面板锚定当前状态 → 历史记忆补充细节（以状态面板为基准校验） → 对话原文提供交互上下文 → 用户输入生成回复。

缓存收益估算：缓存命中区 ~1000 tokens，变动区域较大。

#### 策略选择建议

| 场景 | 推荐策略 | 理由 |
|------|---------|------|
| 长篇叙事（>50 轮） | 缓存优先 | 对话占比大，缓存收益显著 |
| 短篇对话（<20 轮） | 语义优先 | 缓存收益有限，语义连贯性更重要 |
| 状态频繁变更的剧情 | 语义优先 | 状态面板位置靠前，LLM 更容易遵循 |
| token 成本敏感 | 缓存优先 | 减少重复计算，降低 API 费用 |

### 4.6 记忆折叠策略

**触发条件**：经历类记忆数量超过 `consolidation_threshold`（默认 500）

> v0.2备注：当前 `trigger_threshold` 已调整为 `2.0`（实际禁用），consolidation 流程在 v0.2 不触发；宏摘要仍使用单字段 `summary`（不采用 5W1E 结构）。

**折叠流程**：

1. 选择候选：`importance < 4` 且 `is_archived = false`，按 importance 升序 + turn_number 排序
2. 按 `narrative_period` 分组（同一时段内的事件折叠为一条摘要更有意义）
3. 每组（≥3 条）调用 LLM 生成摘要
4. LLM 失败 → 保留原事件不折叠，记录日志，下次重试
5. 成功 → 插入摘要事件（`is_summary = true`），标记原事件 `is_archived = true`

## 5. HUD 子系统（v0.2）

### 5.1 概述

HUD（状态面板）是 Advanced 模式的核心差异化功能，为用户提供当前角色/世界状态的可视化展示。

**核心设计决策**：HUD 不维护独立的状态存储，而是作为 **factual_memories 的只读视图**。这带来以下优势：
- 消除深度合并算法的复杂性和状态膨胀问题
- 状态更新退化为简单的 key-value upsert
- update_world 从"三写"简化为"两写"（事实 + 经历）
- HUD 面板可独立开发，与 Agent 架构完全解耦

### 5.2 子模块划分

```
HUD 子系统
├── HudController（状态面板控制器）
│   ├── 监听 factual_memories 变更
│   ├── 按 category 分组渲染
│   └── 面板折叠/展开状态管理
├── HudView（状态面板 UI）
│   ├── CharacterStatCard（角色属性卡片）
│   ├── WorldInfoCard（世界信息卡片）
│   └── CustomVarsCard（自定义变量标签）
└── StateFormatter（状态格式化器）
    ├── factual_memories → Prompt 注入格式
    └── factual_memories → HUD 面板渲染格式
```

### 5.3 update_world 双写协议

```
SSE Parser 检测到 tool_calls 完成
    │
    ▼
UpdateWorldUseCase.execute(input)
    │
    ├── drift 事务内:
    │   ├── MemoryRepository.upsertFacts(sessionId, input.factualUpdates)
    │   │   └── INSERT OR REPLACE 到 factual_memories 表
    │   │   └── key = "角色.李明.hp", value = "85"
    │   │   └── 删除语义: value = "__deleted__" → DELETE 该条记录
    │   │
    │   └── MemoryRepository.appendEvent(sessionId, input.eventSummary, ...)
    │       └── 插入 experiential_memories 表
    │       └── v0.2 EventSummary 的 5W1E 6 字段（when/where/who/what/significance/extra）
    │           同步写入 experiential_memories 的 when_text/where_text/who_text/what_text/significance/extra 6 列；
    │           summary 降级为可选（String?），用于宏摘要回填与向后兼容。
    │       └── 接口已预留，update_world 双写协议在 v0.3 启用（v0.2 经历类记忆由两步生成管道直接写入）。
    │
    └── 事务外（异步）:
        ├── EmbeddingQueue.enqueue(memoryId)
        └── HudController.refreshPanel()
```

**关键简化**：
- 无 StateSnapshot 表，无深度合并算法
- 事实更新为 upsert（key 存在则更新，不存在则插入）
- 删除通过 `__deleted__` 标记值实现（简单明确）
- update_world 的 state_patch 字段由代码层拆解为多个 factual_updates

### 5.4 update_world Tool Call Schema

LLM 输出的 state_patch 仍然是自由 JSON 结构（对 LLM 友好），代码层负责拆解：

```
LLM 输出:
{
  "state_patch": {
    "location": "迷雾森林",
    "characters": [{"name": "李明", "hp": 85, "mp": 50}]
  },
  "event_summary": "主角进入迷雾森林，与狼型魔物战斗",
  "importance": 4,
  "narrative_time": "修炼第三天·清晨",
  "tags": ["战斗", "森林"]
}

代码层拆解为 factual_updates:
[
  {"key": "当前地点", "value": "迷雾森林", "category": "世界"},
  {"key": "角色.李明.hp", "value": "85", "category": "角色"},
  {"key": "角色.李明.mp", "value": "50", "category": "角色"}
]
```

**拆解规则**：
- 顶层标量字段 → 直接映射为 key-value（key = 字段名）
- characters 数组 → 按 name 展开为 `角色.{name}.{attr}` 格式
- 嵌套对象 → 用 `.` 连接路径作为 key
- 值为 null → 转为 `__deleted__` 标记

### 5.5 与其他子系统的交互

| 子系统 | 交互方式 | 版本 |
|--------|---------|------|
| Chat (Advanced) | Chat 的 ToolExecutor 调用 UpdateWorldUseCase | v0.2 |
| Memory | UpdateWorldUseCase 写入 factual_memories + experiential_memories | v0.2 |
| Core (DB) | 通过 drift 事务保证双写原子性 | v0.2 |

### 5.6 状态膨胀防护

| 层级 | 机制 | 说明 |
|------|------|------|
| 存储层 | key-value upsert | 天然防膨胀：同一 key 更新而非追加 |
| 工具层 | update_world 描述要求 LLM 清理 | 系统提示词要求"更新时同时移除不再相关的内容" |
| 预算层 | 事实类记忆 token 预算 | 超出预算时提示 LLM 精简或按重要性截断 |
| 渲染层 | HUD 面板按 category 折叠 | 低优先级 category 默认折叠 |

| D4 | features/chat + features/intermediate | `simple_error_context.dart` 等 | Simple 模式结构化错误处理（与 D2 共享 `failure_logs` 表） |

#### D1 日志读取（Isolate 反向随机读）

诊断页（D3）需要展示日志文件最后 500 行。早期实现用 `File.readAsLinesSync()` 同步读取整个日志文件（最大 10MB），导致 UI 线程阻塞，触发 ANR / 应用崩溃。

**改造方案**：

- 调用方：`DiagnosticsController._readLogTail(maxLines: 500)`
- 实现路径：通过 Flutter `compute` 把读文件逻辑丢到 Isolate
- Isolate 顶层函数：`lib/core/utils/log_tail_reader.dart` 的 `readLogTail(LogTailParams params)`
- 算法：`RandomAccessFile` 从文件末尾向前按 64KB chunk 读取，累积够 maxLines 行即返回；总读取上限 1MB 防止极端情况
- 返回顺序：从旧到新（与 `File.readAsLines` 一致，UI 直接消费）

#### D1 文件落盘控制字符过滤

LLM 输出可能含 ASCII 控制字符（NULL `\x00`、BEL `\x07`、VT `\x0B`、ESC `\x1B`、DEL `\x7F` 等），落盘后用 txt 编辑器打开会显示为方块码或不可见字符。

**改造方案**：

- `FileLogSink.write` 调用 `_sanitizeForFile(record.toLine())` 过滤
- 正则 `[\x00-\x08\x0B-\x1F\x7F]` 一次替换为空，保留 `\n`(0x0A) 与 `\t`(0x09)
- `developer.log` 控制台输出保留原始字符（方便调试）
- `LogRecord.toLine()` 不重复过滤（注释说明 sanitize 在 sink 侧完成）

#### D3 调试日志开关（DebugLogOptions）

诊断页（D3）提供 5 个独立调试日志开关（默认全关，按需开启后即时生效）：

| 开关 | Preferences Key | 控制内容 |
|------|----------------|---------|
| `logPrompts` | `debug_log_prompts` | generating/reviewing 阶段拼接好的完整 messages |
| `logResponses` | `debug_log_responses` | reviewing 阶段解析出的最终 reply + EventSummary |
| `logMemories` | `debug_log_memories` | retrieving 阶段检索到的 ScoredMemory 列表（含分数） |
| `logKeywords` | `debug_log_keywords` | generating 阶段解析出的关键词列表 |
| `logPayloads` | `debug_log_payloads` | 每次 LLM 调用的完整 request/response body（含阶段标注，超长截断到 2000 字符） |

`logPayloads`（2026-08-04 新增）开启后，StreamRunner 在每次流式调用开始时记录完整请求 messages（含阶段标签如 `[generating]`、`[extracting]`），流结束时记录响应摘要（正文长度、思考长度、耗时）。工具调用模式下额外记录每个工具调用的名称和已解析参数 JSON；无工具调用时记录 fallback 文本。超长内容截断到 2000 字符避免日志膨胀。

所有 LLM 调用日志统一使用 `Logger('Intermediate.$phaseLabel')` 命名，通过 logger 名即可识别阶段。2026-08-04 移除了 SSE 解析器和 StreamRunner 中的 per-delta 碎片日志（每次 reasoning_content delta 写一条 info 日志），改为流结束后单条汇总。

### 7.3 协议适配器选择流程（v0.2 新增，DOC-12 §5）

**背景**：v0.1 阶段所有 LLM 请求假定 OpenAI 兼容协议；v0.2 阶段按 DOC-12 v1.1 引入多协议支持（OpenAI 兼容 / Anthropic / Gemini / OpenAI Responses），通过 `LlmAdapterFactory` 按 `preset.protocol` 字段在运行时选择适配器，调用方零感知协议差异。**2026-07-28 扩展**：`openaiCompatible` 协议下增加端点信息路由，DeepSeek 端点自动分发到 `DeepSeekAdapter`（处理思考模式下 `tool_choice:"required"` 不支持 + 不支持 `parallel_tool_calls` 两项兼容性差异，详见 DOC-12 §5.4.2）。

**调度入口**：`LlmRemoteDataSource`（`lib/features/chat/data/datasources/llm_remote_datasource.dart`），持有 `HttpClient` + `LlmAdapterFactory` 两个依赖。

**调用方覆盖范围**（v0.2 迁移后）：
- 中级模式：`IntermediateChatController` → `StreamRunner` → `LlmService.streamChat`
- Simple 模式：`ChatModeController._sendToApi` → `LlmService.streamChat`（v0.2 迁移：原 v0.1 直接持有 `HttpClient` + `SseParser` 手动拼 OpenAI Map 的实现已废弃）
- `CompactionService` / `CompactionStreamer`（仍直连 HttpClient + SseParser，未迁移）
- `ChatModeController._generateTitle`（标题生成，仍用 `http.post` 直连，非流式）
- `ModelTestService`（模型测试，仍直连）

> Simple 模式主对话路径迁移到 LlmService 是 v0.2 收口目标的第一步，消除了 Simple/Intermediate 模式在协议适配上的技术债。剩余的 CompactionService/ModelTestService 直连路径保留为后续独立任务。

**关键约束**：
- `LlmAdapterFactory` 为单例语义（同一协议同端点多次 `getAdapter` 返回同一实例），减少 GC 压力；解析器自身在 `parse()` 入口重置状态，单例可安全复用
- 测试场景可通过构造参数注入 mock 适配器
- `openaiResponses` 协议当前抛 `UnimplementedError`，待 v0.3+ 落地
- **供应商特化隔离原则**：通用适配器（`OpenAiAdapter`）严禁被某一家供应商的特化逻辑污染。任一供应商若存在与 OpenAI 标准不兼容的差异，应通过继承 `OpenAiAdapter`（或实现 `LlmProtocolAdapter`）的方式新建专属适配器，由 `LlmAdapterFactory` 按端点信息路由分发。`DeepSeekAdapter`（2026-07-28 新增）是首个按此模式落地的供应商专属适配器
- 详见详细流程图：DOC-04 §6.1
