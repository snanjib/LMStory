# 导演模式正文交付契约设计

- 状态：已实施（2026-08-31 设计定稿并同日实施）
- 实施备注：⑦ agentStop「预算耗尽但正文已收录」两态拆分随实施演化取消——§2.2 ④ 收割使该场景走成功落库路径，失败分支只剩零产出；⑧ 权威替换时点为 AgentToolCallReceived（协议解析完成即替换，等价 §4.3 的 LlmToolCallComplete，早于工具执行与 collectRound）
- 范围：导演模式（advanced）正文交付链路——`finish_round.prose` 交付契约、harness 全锚点强化（防正文重复输出）、工具参数流直播、四通道轮内捕获（空正文防线）、展示层去重、顺带修复两处现存缺陷
- 参考：《导演模式体验重构调研与方案.md》（直播分块 / maxSteps 软着陆 / 尾部执笔重述的地基）；《导演模式剧情节奏档位设计.md》§3（提示词措辞硬约束——本文 harness 锚点措辞同样遵守）

## 0. 结论摘要

1. **正文交付契约**：正文唯一权威载体是 `finish_round` 的 `prose` 参数（原 `reply` 参数改名并设为 required）。调用 finish_round 且 prose 合格 = 本轮写了正文；落库章节只来自 prose（文本回退除外，且带标记）。
2. **Harness 全锚点强化**（用户重点）：在模型行为的六个关键时刻点全部锚定"正文只进 prose 参数、content 只许简短播报"——工具 description、参数 description、执笔铁律、尾部执笔重述、maxSteps 最后通牒、空响应 nudge。措辞遵守节奏档位 §3 约束（正向措辞、零题材词、说明违反后果），目标是从源头压住"content 里再写一遍正文"的重复输出。
3. **参数流直播**：网关转发 `LlmToolCallArgs` 增量，经 prose 提取器（增量 JSON 字符串值提取 + hold-back 反转义）映射为现有 liveBlocks 文本块——稿件卡、滚动、时间线、collectRound 零改动。OpenAI 兼容 / Anthropic / GLM `tool_stream` 均可逐字直播；Gemini 原生与非流式回退端点退化为整块出稿。
4. **四通道轮内捕获**（空正文防线）：提交不变量（永不提交空 prose）+ 通道 A（prose 参数主路径）/ B（JSON 崩溃时从提取器缓冲收割）/ C（纯文本回退——软着陆后唯一信道，保留不废）/ D（可行动信封就地纠错）。唯一允许整轮重试的场景是模型全程零产出。
5. **展示层去重**（保险层）：数据层正文只有一份（prose），重复只发生在直播区；L2 args 前缀早折叠 + L3 锚窗终局折叠（`AgentProseDedup` 纯函数）保证最终时间线干净。
6. **顺带修复两处现存缺陷**：① step 级重试复用 stepIndex 不清直播块，半截文本与重试全文拼接污染稿件卡候选；② 闸门连拒 + 同参重提交 3 连击会被 doom-loop 误杀整轮。
7. 无数据库 schema 变更；无新配置键；故事模式（intermediate）不改。

## 1. 背景与根因（2026-08-31 调研）

### 1.1 用户报告

导演模式出现"思考+工具调用 → 输出正文 → 思考+工具调用"的轮次被判为整轮失败进入重试。追问确认需求：**一轮之内保证正文正确获取**，不以重试整轮兜底；正文与播报必须结构性区分；重复正文（content 与 prose 各一份）严重影响阅读感官，要从 harness 源头压制。

### 1.2 根因链

- 轮成功只认两条尾巴：纯文本自然停止（`completed`）或 finish_round 提交（`committed`）；判定在 `director_round_runner.dart` runRound ④⑤。正文在轮中段输出后，尾巴若落在 budgetDuration（默认仅 5 分钟墙钟）/ budgetTokens / maxSteps 二次到达 / doomLoop / 请求错误重试耗尽（默认 1 次）任一处 → `EAGENT` failed，**已完整流出的正文作废**。
- 系统提示词自己要求"record_event_memory 执笔后提交前用、任务完成即 finish_round"，即设计上正文就不在轮尾——模型必须把正文与工具调用捆进同一条消息，而轮判定只宽恕两种特定尾巴。
- 正文与播报无结构性区分：落库正文取 `lastNonEmptyText`（最后一个非空文本块），正文后再说过渡话会把过渡话存成正文。

### 1.3 方向决策（2026-08-31）

用户提出把写正文封装为工具调用（调用与否 = 写没写正文），调研确认三协议下长正文作为工具参数可行：OpenAI 兼容参数增量分片（`openai_adapter.dart:143-144`）、Anthropic `input_json_delta` 分片（`anthropic_sse_parser.dart:284-288`）、Gemini `functionCall` 原子到达（`gemini_sse_parser.dart:160-162`）。`ToolCall.fromRawArgs`（`tool_call.dart:20-43`）畸形 JSON 静默降级空 Map、`finish_reason=length` 可截断参数中途——两个风险点由工具体守卫与通道 B 兜住（见 §2.4、§5）。

**不另立 `write_prose` 工具**：finish_round 已是终结工具、已挂三道闸门、`explicitReply` 本就最优先；独立非终结工具会导致正文发射两遍（先 write_prose 再 finish_round.reply 传一遍）、多耗一步，且不改变轮尾判定。

## 2. 正文交付契约（核心语义）

### 2.1 finish_round.prose

- 参数名 `reply` → `prose`，schema `required: ['prose']`。
- `AgentRoundDraft.explicitReply` 语义收窄：**只**由 prose 参数写入（工具体内），不再有其他写入方。
- 落库正文来源优先级：`prose`（契约）> 文本回退（通道 C，带 `text_fallback` 标记）。原三级回退链（explicitReply → liveBlocks 末段 → 空）退役。

### 2.2 轮成功判定重构

`runRound` ⑤ 的判定从"停止原因"解耦为"有无可交付正文"：

| 结束形态 | 处置 |
|---|---|
| finish_round 提交成功（committed） | 照常落库，`deliveryChannel: tool_args` |
| 非 cancelled 结束 + 文本回退候选达标（最后一个 ≥200 字文本块） | `collectRound` 拾取落库，`deliveryChannel: text_fallback` |
| 非 cancelled 结束 + 无任何通道捕获正文 | `EAGENT` failed（唯一重试场景=模型零产出） |
| cancelled | 现状不变（不拾取） |

预算耗尽（duration/tokens/maxSteps 二次）、doomLoop、error 尾巴只要任何通道有正文即走拾取——贯彻"已交付正文不得蒸发"（与 maxSteps 软着陆注释同源的设计哲学，这次贯彻到底）。

### 2.3 终审闸门改审 prose

三道闸门（检索覆盖 / 事件记忆 / 文风 lint）的检查对象从 `pendingReply()` 回退链改为 `arguments['prose']`。`pendingReply` 依赖删除。文风"定向重写一次"语义变为"带修订再次调用 finish_round"——修订后参数变化，天然不触发 doom-loop 连击。

### 2.4 工具体守卫

```text
prose 缺失/为空（含畸形 JSON 降级空 Map）：
  failure 信封：「正文参数缺失或为空。可能原因：输出被「输出上限」截断
  （finish_reason=length 时推理占满预算），或参数未按协议携带完整正文。
  请调大输出上限后重发完整正文；若工具参数通道反复失败，直接输出完整
  正文文本结束本轮（系统会自动收录）。」不终结轮。
prose 首尾包裹 markdown 代码围栏（```）：
  剥离围栏后放行（低风险清理，兼顾弱模型习惯）。
finish_reason=length 且 prose 非空但显著短于常规（<200 字）：
  信封附截断诊断，建议调大输出上限重发。
```

守卫信封同时是通道 D 的入口：模型收到可行动原因后同轮纠错。

### 2.5 finish_round 失败软上限

finish_round 豁免 doom-loop（§7.2）后需要新的循环防线：`_TurnOutcome.finishAttempts` 计数连续失败（提交异常/守卫信封），≥5 次 → 判 `error` 停轮（"finish_round 反复失败"）。正常闸门流程（拒→修→过）2-4 次内闭环，不会触顶。

## 3. Harness 强化（防重复输出的源头工程）

### 3.1 锚点总表

模型在轮内做"往哪写正文"决定的六个关键时刻，全部有正确锚定。这是本设计对"防止模型在 content 输出正文、结尾又写一遍"的主回答——**harness 从厚度上压制，展示层折叠只是保险**。

| # | 时机 | 锚点位置 | 模型此刻在想什么 |
|---|---|---|---|
| ① | 决定调用工具时 | finish_round `description` | "调哪个工具、参数给什么" |
| ② | 写参数内容时 | `prose` 参数 description | "正文往这里写" |
| ③ | 每轮开工时 | 执笔铁律（冻结前缀） | "我这轮怎么干活" |
| ④ | 执笔前最后一刻 | 尾部执笔重述 penReminder（≥3 步未尝试 finish_round 时注入） | "马上写了，写哪、怎么写" |
| ⑤ | 预算将尽时 | maxSteps 最后通牒 | "收尾了，怎么交差" |
| ⑥ | 空响应弃疗时 | 空响应 nudge | "刚才发空了，现在补什么" |

### 3.2 措辞约束

继承《导演模式剧情节奏档位设计.md》§3（零题材词、正向措辞优先、说明违反后果）。机械格式约束（代码围栏类）允许适度否定句式，行为约束一律正向 + 后果说明："读者会在正文卡阅读 prose 里的文字；回复文本里再写一遍，读者会看到两遍"——后果式表述比单纯禁令有效。

### 3.3 锚点文案（定稿）

**① 工具 description**：

> 提交本轮：正文经 prose 参数交付——完整正文原文直接写入该参数，读者在正文卡阅读它。通过终审检查（事实出处、文风）后统一提交暂存变更并结束。回复文本另有职责：只写一两句过场播报，正文的唯一载体是 prose 参数。

**② 参数 description**：

> 本轮完整正文原文。读者只阅读这里的文字：直接写入正文本身，保留原始换行与标点；代码围栏、摘要转述都会破坏阅读。

**③ 执笔铁律**（冻结前缀，替换现有"完整正文一次性输出，不要分段挤牙膏"与"任务完成即 finish_round 提交"两句）：

> 正文一次性完整写入 finish_round 的 prose 参数（保留原始换行与标点）；回复文本只作一两句过场播报——读者在正文卡阅读正文，回复文本里再写一遍，读者会看到两遍。任务完成即 finish_round 提交，不做多余检查。

**④ 尾部执笔重述**（`kDefaultPenReminderText` 追加交付锚定；触发条件改为"≥3 步且全程未出现 finish_round 调用"，见 §7.3 联动）：

> 【执笔提醒】本条为最高优先级即时指令，须在本次回复中立即执行。即将进入正文。铁律：禁破折号；禁"不是A，而是B"式虚假对仗；禁凑三连排比；句长错落；允许毛边；直接以正文开始。正文完整写入 finish_round 的 prose 参数，回复文本只留一句过场。

**⑤ maxSteps 最后通牒**（`kMaxStepsFinalNotice`，软着陆后工具停用、模型只能纯文本——此即通道 C）：

> 本条为最高优先级即时指令，须在本次回复中立即执行。步数预算已用尽，所有工具已停用。立即用你已掌握的材料直接输出完整的叙事正文文本收尾（系统会自动收录为正文），然后结束本轮。

**⑥ 空响应 nudge**（`kEmptyStopNudge`）：

> 你刚才的回复是空的，本轮尚未交付正文。立即调用 finish_round 并把完整正文写入 prose 参数；若工具不可用，直接输出完整正文文本收尾（系统会自动收录）。不要再次返回空回复。

**⑦ 工具索引行**（`agent_system_prompt.dart` 的工具索引 `finish_round` 条目）同步为①的浓缩版。

**⑧ 协议差异声明（取向：缓存优先）**：

④/⑤ 原以尾部 `system` 消息注入为前提设计；Anthropic/Gemini 的请求体实现会把对话流中的 system 消息上提合并进顶层 system 块（OpenAI 兼容原位保留），"尾部 system"在这两家实际位于顶部，存在位置效应损失。决策**不改适配器结构**（避免破坏冻结前缀缓存），双对策：① Harness 侧轮尾强指令一律改走 `user` 合成消息（workbench-reminder 标记包裹），位置损失已消除；② ④/⑤ 及节奏指令公共头追加位置无关的服从强化句 `kPriorityObedienceClause`（"本条为最高优先级即时指令，须在本次回复中立即执行"）——语义只依赖「本条 + 本次回复」，任何角色/位置形态下效力一致，作为双保险。措辞守 §3.2 约束（④⑤ 的铁律句为机械格式约束，维持既有否定句式不变，新增句零否定）。

## 4. 参数流直播

### 4.1 网关扩展

`AgentLlmGateway.completeStep` 新增可选回调 `onToolArgDelta(String toolCallId, String toolName, String delta)`；`LlmServiceAgentGateway._completeStreaming` 把当前被丢弃的 `LlmToolCallArgs` 事件转发出去（`llm_service_agent_gateway.dart:167-169`）。`AgentRunner._completeWithRetry` 经 `AgentTurnSpec` 透传。子代理（`SubagentRunner`）不接（无正文交付职责）。

### 4.2 prose 提取器（核心纯函数，新文件 `agent_prose_extractor.dart`）

输入是完整参数 JSON 的增量分片（`{"prose":"正文…"}` 整体的分片，不是 prose 值的分片），需要增量提取 prose 字段的字符串值并反转义：

```text
状态机：seek-key（跳过 JSON 结构，定位 "prose" 键）
      → in-string（反转义输出正文）
      → done（字符串闭合）
hold-back：字符 '\' 到达时扣住，等下一片判定转义类型；
           '\u' 扣满 4 个 hex 才解码；
           字面 UTF-16 代理对高代理扣住等低代理合成。
其它键（未来 finish_round 若增参数）的值跳过不输出。
```

设计要点：提取器是流式的、与 JSON 最终解析成败**无关**——Complete 时 `fromRawArgs` 若因尾部截断解析失败，提取器缓冲里已提取的正文文本仍在（通道 B 的实现基础）。输出接 liveBlocks 追加（复用 `AgentLiveTranscript.appendText`），下游全兼容。emoji（字面 UTF-8 或 `\ud83d\ude00` 转义对）与 markdown 语法反转义后与 content 路径逐字符等价，渲染复用 `IntermediateMarkdownBody`，非新能力。

### 4.3 liveBlocks 映射与权威替换

- 参数增量 → `appendText(blocks, stepIndex, delta)`，与 content 直播同机制，稿件卡/滚动/时间线零改动。
- `LlmToolCallComplete` 到达且为 finish_round：用解析后的权威 prose **整块替换**该 step 的直播文本块（修正流式反转义可能的毛刺）；同时触发 L3 终局去重（§6.2）。
- 直播期间 finish_round 工具卡显示"正在执笔…"（`onProgress` 桥接现有机制），隐藏 argsPreview（避免正文在工具卡露一角）。

### 4.4 协议差异矩阵

| 协议 | 直播形态 |
|---|---|
| OpenAI 兼容（含 GLM `tool_stream`、DeepSeek） | 逐字直播，观感与 content 直播几乎无差 |
| Anthropic（`input_json_delta`） | 逐字直播 |
| Gemini 原生（functionCall 原子到达） | 提取器在 Complete 时一次输出，整块出稿；工具卡"正在执笔…"兜住等待观感 |
| 非流式回退（`streamingToolCallsReliable=false`） | 同上整块出稿 |

预算不会打断写作中：预算检查只在 step 边界（`agent_runner.dart:328-360`），请求一旦发出必然自然跑完或报错。

## 5. 失败路径与四通道捕获（空正文防线）

### 5.1 提交不变量

`collectRound` / finish_round 永不提交空 prose：参数空 → 不 commit、不落库，回可行动信封。空正文在提交动作上结构性不可能。

### 5.2 四通道

| 通道 | 场景 | 实现 |
|---|---|---|
| A 主路径 | prose 参数正常到达 | 提交，`tool_args` |
| B JSON 崩了文字活着 | 畸形 JSON / 尾部截断 | 提取器缓冲已含正文文本（§4.2），从缓冲收割；长度 ≥200 字才采信 |
| C 文本回退 | 契约违反（纯文本停止）/ 软着陆后工具停用 | nudge 一次后仍纯文本且最后一个 ≥200 字文本块达标 → 收割，`text_fallback`；软着陆后 content 是唯一信道，**此通道保留不废** |
| D 就地纠错 | 守卫信封 / 闸门拒 | 模型同轮重发（带修订），8 步预算足够 2-3 轮纠错；连续失败上限见 §2.5 |

通道 B/C 的收割判据统一为共享纯函数 `pickReplyBlock`（explicitReply > 最后一个 ≥200 字文本块 > 最后一个非空文本块），`collectRound` 与 `AgentTimelineAssembler` 同源使用（同时修掉"正文后过渡话被存成正文"的次生缺陷——`lastNonEmptyText` 单独退役）。

### 5.3 保证边界

一轮内拿到正文的充分条件：模型在轮内产出过正文（任何通道、任何格式）。唯一救不回的是模型全程零产出（请求全失败/立即空停）——那是"没内容可救"而非"有内容被流程弄丢"，此时 EAGENT + 用户重试是唯一合理动作。弱模型 JSON 写崩走 B、不走工具走 C、强模型截断走信封——业务流程不因一次格式错误整轮重来。

## 6. 展示层去重（保险层）

数据层正文只有 prose 一份，重复只发生在直播区（模型把正文又写进 content）。三层防御，harness（§3）为主、本层为保险：

### 6.1 L2 直播早折叠

参数流开头约 60 字（归一化空白后取前 40 字）与最近一个 ≥200 字 content 块做前缀比对；命中即把该 content 块折叠为占位行「（草稿已并入稿件）」，此后正文只在稿件卡出字。双显窗口压到秒级。

### 6.2 L3 终局折叠

`Complete` 权威替换后，对本轮所有 ≥200 字 content 块做近拷贝检测：长度比 + 首/中/尾三个 32 字锚窗（归一化后子串查找），命中即折叠。部分复制不算（残留当播报，不误伤）。纯函数 `AgentProseDedup`，直播态与 `AgentTimelineAssembler` 装配态同源共用。

### 6.3 残余声明

"content 已流完、args 前缀未到比对点"的极短窗口内理论上有一次短暂双显；L2 压秒级、L3 保终局干净。追求零双显需放弃参数直播（写完才出稿），本设计明确不取。

## 7. 顺带修复的现存缺陷

### 7.1 step 级重试直播块污染

`_completeWithRetry` 重试时复用同一 `stepIndex` 重发 `AgentStepStarted`（`agent_runner.dart:594`），导演侧不清直播块 → 失败尝试的半截文本与重试全文拼进同一块，污染稿件卡候选。修复：重发 `AgentStepStarted` 时 runner 清除该 step 的直播文本/思考块（新增事件字段 `attempt` 或在 runner 内直接处理，实施时定）。

### 7.2 doom-loop 闸门误杀

闸门 A 拒 → 同参重提（streak 2，A 豁免放行）→ 闸门 B 拒 → 同参重提（streak 3）→ 执行前被 doom 拦截整轮死亡（检测在执行前，`agent_runner.dart:516-540`）。修复：控制类工具（`permission == control`，即 finish_round）不进 doom 登记；循环防线由 §2.5 失败软上限接管。

### 7.3 penReminder 触发条件联动

触发判据从"≥3 步且未出 ≥200 字文本"改为"≥3 步且全程未出现 finish_round 调用"（runner 跟踪 appended 中 assistant 消息的 toolCalls）。语义更贴契约：执笔=发起 finish_round，重述在它之前一锚。

## 8. 测试计划

单测锁定（纯函数为主，全部可测）：

1. **提取器**：分片边界切断 `\n`/`\"`/`\uXXXX`/代理对各情形的正确反转义；prose 前有其他键时跳过；尾部截断时缓冲含已提取正文。
2. **守卫**：空参/畸形 JSON → 信封不终结轮；代码围栏剥离；length 截断诊断。
3. **闸门**：三闸审 prose 参数；文风拒 → 修订重提（参数变化）→ 过。
4. **doom**：闸门连拒两次 + 同参重提 3 连击 → 不触发 doom（豁免）；finish_round 连续失败 5 次 → 停轮。
5. **轮判定**：预算耗尽尾巴 + prose 已交付 → 落库 `tool_args`；同尾巴 + 仅有 ≥200 字文本 → 落库 `text_fallback`；零产出 → EAGENT。
6. **去重**：L2 前缀命中折叠；L3 锚窗命中/部分复制不折叠；Gemini 整块到达 → Complete 后出稿。
7. **直播重置**：step 重试开始 → 该 step 直播块清空，不与重试全文拼接。
8. **措辞回归**：harness 锚点文本变更的逐字节断言（仿节奏档位冻结前缀回归测试，防缓存前缀意外漂移）。

## 9. 明确不做什么

- **不做 `begin_prose`/`end_prose` 标记跨度**（已评估否决）：跨三个消息的状态机、纯 content 写正文触发"纯文本停轮"需运行循环加特例、忘写 `end_prose` 的恢复路径、未标记 content 仍需文本回退兜底——复杂度与新失败面超过折叠方案，且没有省掉任何通道。
- **不另立 `write_prose` 工具**（见 §1.3）。
- **不废文本回退通道**：软着陆后 content 是唯一信道（§5.2-C）。
- **无数据库 schema 变更**：deliveryChannel 进轮审计留痕（agentSteps trace 步骤 + 事件日志），不新表。
- **故事模式（intermediate）不改**：其六步管线正文走 reviewing 阶段产出，无此问题。
- **子代理不接参数流直播**：无正文交付职责。
