# 导演模式上下文用量指示设计

- 状态：已实施（2026-09-01 设计定稿并实施）
- 范围：导演模式（advanced）会话页上下文用量指示器——环形进度、点击详情面板、
  压缩触发线可视、缓存命中率、每轮请求 token 明细；删除「本会话累计」口径
- 参考：《导演模式剧情节奏档位设计.md》（设计文档体例）；《13_故事模式上下文机制设计.md》§5
  （压缩触发判定，本设计分母与其同源）

## 0. 结论摘要

1. 输入区常驻一个**纯环形进度指示器，环上无任何文字**（2026-09-01 定稿）。
   环的满刻度 = 压缩触发线（`contextWindow × compactionTriggerRatio`），环填充比例 =
   最近一次请求 `promptTokens / 触发线`。点击弹出详情 bottom sheet，所有文字信息收在里面。
2. 分子取**最近一轮最后一次请求的真实 `promptTokens`**（API 返回的 usage，含系统提示词、
   工具定义与全部历史），不用本地估算、不用轮内累加值（累加会把逐步增长的上下文重复计数）。
3. 环满即压缩：环形语义回答的是"离自动压缩还有多远"，比"占 1M 窗口的百分比"更有决策价值
   （1M 窗口下窗口占比长期低于 20%，指针式读数无感；触发线相对读数直接对应下一件事）。
   绝对口径（X 万 / 窗口 Y，Z%）保留在详情面板。
4. `AgentUsageAccumulator` 增加 last 三项（lastPromptTokens/lastCompletionTokens/
   lastCacheReadTokens，每次 add 覆盖）；`AgentWorkSummary` JSON 增加这三个可选字段随
   agent_summary 落库。旧轮次字段缺失时从事件日志最后一条 `stepEnd` 回填 promptTokens
   （`readEvents` 已有）；命中率旧数据不可回填，显示"—"。
5. 详情面板内置**「立即压缩」手动入口**（2026-09-01 补充定稿）：force 语义
   （不检查阈值与冷却），idle 时可用，压缩过程在面板内流式展示；落库口径与轮前
   自动压缩完全一致。对标 chat 模式既有先例（`chat_mode_controller.dart`
   `compressHistory`）。
6. 删除「本会话累计 · N 轮 · ~X tokens」显示（`_sumSessionTokens`、两个 widget 的显示分支、
   `sessionCost` i18n key）。累计总量口径从 UI 全面退场；wiki 中描述该口径的 `costBody`
   词条同步改写为新指示器的说明。
7. 费用金额估算**不做**（需要新建各模型单价配置体系，范围过大，另立专项）。

## 1. 背景与问题

### 1.1 现状

导演模式 L2 审计层底部每轮显示「本会话累计 · 130 轮 · ~9500.6k tokens」
（`advanced_chat_page.dart` `_sumSessionTokens` 把各轮 `AgentWorkSummary.totalTokens`
求和）。该数字是**会话历史各轮 prompt+输出 token 的累加值**，既不是当前上下文占用，
也不指向任何用户可执行的动作。真实案例：1M 窗口模型 130 轮后累计 ~9.5M token，
用户误以为"上下文已经爆了却没压缩"。

### 1.2 用户关心的两个问题

1. 当前上下文用了多少、离自动压缩（主线摘要出现）还有多远；
2. 每次请求大概消耗多少（输入/输出/缓存命中）。

累计总量对两者都没有回答，属于冗余口径（2026-09-01 定稿：删除）。

## 3. 数据链路

### 3.1 分子：最近一次请求的 promptTokens

- `AgentUsageAccumulator`（`agent_budget.dart`）增加字段：
  `lastPromptTokens / lastCompletionTokens / lastCacheReadTokens`（int，默认 0），
  `add()` 每次调用覆盖——最后一次 `add` 即该轮最后一次成功请求。
- 轮末（`director_round_runner.dart` 构建 `AgentWorkSummary` 处）把 last 三项写入
  summary；`AgentWorkSummary.fromJson/toJson` 增加三个**可空**可选字段
  （`agent_work_step.dart`），旧 JSON 解析回退 null，不破坏既有数据。
- 分母（触发线）解析：
  `contextWindow × compactionTriggerRatio`，与 `_runDirectorCompactionPhase` 调
  `service.shouldCompact` 用的**同一份** contextWindow 与 ContextBudget
  （`_resolveContextWindow` 解析窗口；ContextBudget 走 会话覆盖 → 全局 的既有解析链）。
  UI 侧通过 state 读取，严禁 UI 自行再估一套口径。
- `AdvancedChatState` 增加 `contextWindowTokens`（int?）与触发线所需比例值，
  每轮准备阶段刷新；会话打开（loadHistory）时也解析一次，保证非轮中可显示。

### 3.2 旧会话回填

- 打开会话装载 artifacts 时，若最新一轮 summary 缺 `lastPromptTokens`：
  用 `AgentEventLogRepository.readEvents(sessionId)` 取该会话最后一条
  `stepEnd` 事件的 `promptTokens` 回填显示（事件契约自导演模式起就有此字段，
  历史会话全部可用）。
- `cacheReadTokens` 未进过 durable 事件，旧数据无法回填：命中率显示"—"，
  不显示 0%（0% 会被误读为"缓存全未命中"）。
- 本设计不给 durable 事件加字段（事件契约保持稳定）；从本设计实施后的新轮次起，
  summary 内自带全部三项。

### 3.3 辅助指标口径

- 平均缓存命中率：详情面板显示**会话加权平均**（ΣcacheRead / Σprompt，
  仅统计有 cacheRead 字段的轮次）与**最近一轮**命中率两行。
- 每轮请求明细：过程行（`DirectorToolCard` 级别）不加东西，只在详情面板显示
  最近一轮"输入 X · 输出 Y（含缓存读 Z）"。
- 轮数：详情面板显示会话总轮数（原 `sessionRounds` 数据源
  `artifactsByTurnNumber.length` 保留，仅换展示位置）。

## 4. UI 设计

### 4.1 环形指示器（`DirectorContextRing`，新 widget）

- 位置：输入区（`InputToolbar` + `IntermediateChatInput` 所在底部 Column）内常驻，
  直径 ~24-28pt，纯圆环无文字（D2）。两个输入分支（正常/失败态）同样挂载。
- 填充语义：sweep = `lastPromptTokens / (contextWindow × ratio)`，上限 1.0。
- 状态色（无文字通道，替代数字告警）：
  - 占触发线 < 70%：主题次要色（淡）；
  - 70%–<100%：琥珀警示；
  - ≥ 100%（下一轮轮前将触发压缩）：红色满环一次，压缩完成后自然回落。
- usage 缺失（端点不回 usage 或窗口未知回退前无值）：空环（仅底色轨道），不显示比例。
- 点击 → 详情 bottom sheet（仿 `director_session_settings_sheet` 风格）：

```
上下文用量
  15.2万 / 100万 窗口 (15.2%)
  压缩触发线 50万 —— 到达后自动压缩并生成剧情主线摘要
缓存
  最近一轮命中率 87.3% · 会话平均 91.2%
最近一轮请求
  输入 15.2万 · 输出 1.8k（缓存读 13.2万）
会话
  130 轮
  [ 立即压缩 ]
```

### 4.3 手动压缩（「立即压缩」按钮）

语义对标 chat 模式手动压缩先例（`compressHistory`），适配导演模式架构：

- **入口与守卫**：详情面板底部按钮。仅 idle 相可用；generating/compacting 中按钮置灰
  （controller 层 busy 防抖兜底）。对话消息数不足（< `shouldCompact` 的
  `_minRecentMessages × 2` 同源下限）时点击返回 insufficient 提示，不发起请求。
- **force 语义**：跳过阈值判定与失败冷却，总是执行（对标 chat 模式"手动压缩
  不受冷却约束"）。
- **执行与展示**：复用 `CompactionService` 同一压缩管线。story_runtime 版
  `compact()` 目前仅非流式（`stream: false`），本设计要求为其新增流式路径
  （对标 chat 模式 `compactWithStream` 的 delta 回调形态）——压缩进行中详情面板
  原位切换为流式进度（摘要文本实时打字），完成后面板刷新为新用量。失败在
  面板内显示错误并提供重试；失败不写任何压缩状态（summary/boundary/宏摘要
  均保持原值），无落库残留。
- **落库口径**：与轮前自动压缩完全一致——compactionSummary、边界 messageId、
  分段宏摘要、压缩后历史在**单事务**内持久化（复用 `CompactionPersistenceData`
  的持久化路径，非轮次场景单独组装）；成功后 surface 刷新，宏摘要立即可被
  `read_compact_summary` 读到，环形用量自然回落。
- **与自动压缩的关系**：手动压缩只是提前触发同一件事，不改变自动触发的判定与时机；
  手动完成后下轮 `shouldCompact` 自然为 false，不会重复压缩。

## 6. 兼容与边界

1. 窗口未知：`_resolveContextWindow` 已回退 `defaultContextWindow = 96000`，
   与压缩判定同源同值，UI 不做第二套回退。
2. 会话级 `compactionTriggerRatioOverride` 调整后，环形满刻度随之变化
   （state 每轮刷新 + sheet 打开时重解析）。
3. 端点不返回 usage：环空态 + 详情"—"；不影响压缩判定（其本地估算口径独立存在）。
4. 重试步：`add()` 只在拿到响应时调用，重试失败不污染 last 值（实施时验证）。
5. 手动压缩与轮次互斥：generating 中按钮置灰 + controller busy 防抖双保险；
   手动压缩中途用户发送消息 → 以压缩事务为先（发送入口在压缩中被阻断，同
   chat 模式防抖语义）。手动压缩失败不落任何库（compactionSummary/boundary/
   宏摘要/历史全部保持原值）。
6. 仅导演模式；故事/chat 不动（`sessionCost` 本就是 advanced 独有 key）。
