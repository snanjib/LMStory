# 导演模式剧情节奏档位设计

- 状态：已实施（2026-08-31 设计定稿并同日实施）
- 范围：导演模式（advanced）剧情节奏三档（保守/平衡/激进）——配置键、会话列、全局与会话设置 UI、轮指令尾部注入、冻结前缀让权改写
- 参考：《导演模式设置体系设计.md》（配置面与 UI 地基）；§3 调研结论（2026-08-31 网络调研，来源附文内链接）

## 0. 结论摘要

1. 新增 `advanced.narrative_pacing` 三态配置（`conservative`/`balanced`/`aggressive`，默认 `balanced`），全局 `default_config.json` → `user_overrides` → `chat_sessions` 会话列三层解析，合并模式仿工具权限三态先例。
2. 节奏指令以**尾部 per-turn system 消息**注入轮 surface 的最后一位（历史与用户输入之后），每轮重复注入；**不进冻结前缀、不进 core blocks**——用户会话中随时换档，换档动作不得作废任何前缀缓存。
3. 冻结前缀《编辑部工作法》中原"一轮只推进一个关键事件"改写为**档位无关的让权句**，与尾部指令构成"三明治"两端；改写文本对所有档位逐字相同（缓存安全，配套逐字节回归测试）。
4. 三档指令文本全部使用**抽象判据 + 正向措辞**：零题材名词、零"禁止/不要"句式、每档给出正向的收束动作。措辞依据 §3 五条模型机制调研，其中"尾部指令每轮重复注入会放大题材词污染"是本设计最硬的措辞约束。
5. spawn 子代理为只读研究档（`director_round_runner.dart:302-305` 注释确认），不承担执笔，无需注入节奏指令。
6. 故事模式（intermediate）不做同款开关；其提示词有独立节奏段，未来如需可平移本方案。

## 1. 背景与问题定义

### 1.1 用户痛点

用户输入"我压入子弹瞄准"，期望看到举枪瞄准的写实细节与 NPC 的反应，由自己决定是否开枪；实际生成连瞄准带射击一并推进。此类"生成超出预期节奏"反复出现。

### 1.2 现状根因

- 导演模式提示词中**没有**故事模式那条"绝不生成用户的对话、动作、决定或内心想法"的对应约束（grep 零命中），替玩家做决定无明文拦截。
- 冻结前缀唯一的节奏规则是"一轮只推进一个关键事件"（`agent_system_prompt.dart:161`，【质量观】段），硬编码不可配置；且模型对"一个事件"的粒度理解（压弹→瞄准→射击→命中整条弧线）与用户预期（瞄准即为一步）不一致。
- 无任何节奏/推进幅度配置项（全库无 pacing 字段）。

### 1.3 档位的正确框架：语义景别，不是停笔点（2026-08-31 定稿）

档位**不是**"写到哪停下"，更不是字数/长度旋钮。每轮正文照常写满写足（生成长度三档基本恒定），三档的区别是**这一段固定长度的文字覆盖多大一块故事时间、替主角做多少决定**——保守档用同样篇幅把一个动作拍成特写（细节质感、NPC 反应层次写足），激进档用同样篇幅拍成远景蒙太奇。档位改变的是镜头景别，不是镜头长短。实现时严禁把档位做成 max_tokens 之类的文本长度旋钮。

> **修订（2026-09-08）**：「长度恒定」收窄为激进档专属——激进档正文照常写满写足；保守/平衡档不再要求写满，正文以把当轮要表达的内容交代完整为准，篇幅随叙事节奏自然伸缩。景别语义（§2）不变；"严禁做成文本长度旋钮"的边界同步收窄为：档位不得映射为硬性 token 上限/下限，篇幅约束只经尾部提示词软性表达。

## 2. 三档语义

### 2.1 统一轴

三档共用一个问题：**本轮生成的内容，允许超出用户输入的语义多远？** 最敏感的子问题是"引擎可否替主角做新的行动或选择"。轮的收束形态是该许可范围的自然结果，不是独立变量。

### 2.2 三档定义

| 档位 | 玩家侧（替主角做决定） | 世界侧（NPC/环境） | 轮的收束形态 |
|---|---|---|---|
| 保守 conservative | 绝不。只执行输入中已声明的动作并写实写透 | 有行动权（可拔枪指你），但只作为对已发生之事的回应，不主动开新事件线 | 以未决事态收束，把下一步选择交还主角 |
| 平衡 balanced | 允许**惯性外推**：输入语义强暗示的直接延续可代写（判据见 §2.3-4） | 惯性范围内的小的自然发展，不开大新线 | 惯性场景自然完结处 |
| 激进 aggressive | 不受可推测性限制 | 可引入新事件、意外、转折 | 一个关键事件加延伸（接近现状的明示授权） |

三档共有不变量：连贯性、既定事实、人设一致、文风铁律在任何档位不可破；激进≠可以违背设定。

**校准例**（仅用于人对齐。本表与 §2.3 的所有具体例子**一个字不得进入提示词**，依据 §3 机制③）：

| 用户输入 | 保守 | 平衡 | 激进 |
|---|---|---|---|
| 我压入子弹瞄准 | 写实瞄准细节 + NPC 反应，停 | 瞄准→射击→直接结果，停 | 射击→结果→冲突升级/后续剧情 |
| 我推开门走进屋 | 门开、屋内景象与屋内人即时反应，停 | 走进去、环视，若语义暗示则继续（走向柜台点酒） | 屋内突发变故、有人认出你等新事件 |
| 我开枪 | 扳机、弹道、命中与否、NPC 倒下，停 | 几乎与保守档相同 | 同左 + 同伙还击、展开枪战 |

第三行暴露重要性质：**声明越完整，三档越趋同**——档位差异只在输入留白处起作用。

### 2.3 边界情况（实现与措辞必须覆盖）

1. **过渡性动作豁免（保守档的生命线）**：无选择余地的衔接动作（被卫兵带进大牢、跟随队伍移动）可以代写，但一笔带过、弱化为环境描写。禁的是"决定"，不是"移动"；否则保守档叙事会卡死。
2. **"继续"类极端留白输入**：保守=世界侧推进（NPC 行动、局势自行发展）到下一个玩家决定点；平衡=把当前场景按惯性推完；激进=自由推进。故事模式提示词"用户输入只是（继续）就往前推剧情"的口径在导演模式保守档下按此收窄。
3. **档位趋同性**：见 §2.2 校准例第三行。
4. **平衡档"可推测"判据的操作化**：标准是"**强暗示的直接后果**"，不是"合理可能性之一"——瞄准后开枪是强暗示，瞄准后转身扫射不是。模型天然会高估可推测性（把射击外推成毙命甚至搜身），指令文本必须把判据写成"用户读完自己输入后会自然预期的下一步"，并靠抽象结构而非例子表达边界。

## 3. 调研结论与提示词写法约束（2026-08-31）

| # | 机制 | 证据 | 对本设计的约束 |
|---|---|---|---|
| ① | 位置效应：指令在上下文首尾最强，中间最弱（U 形曲线）；recency 偏置强 | [Lost in the Middle (TACL 2024)](https://aclanthology.org/2024.tacl-1.9/)、[多约束指令位置偏差 (arXiv 2502.17204)](https://arxiv.org/abs/2502.17204)、[Anthropic 上下文工程指南](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)（长材料顶部、最重要指令放末尾） | 尾部注入同时是**遵守度最优位**——缓存目标与效果目标同向。部分模型有 front-load 倾向，故冻结前缀也放一句让权声明，构成"三明治"两端 |
| ② | 否定式指令弱效（"粉红大象"）：否定语境下模型无法取消已激活的预测 | [Ettinger 2020 / Sean Trott 综述](https://seantrott.substack.com/p/llms-and-the-not-problem)、[16x Eval 分析](https://eval.16x.engineer/blog/the-pink-elephant-negative-instructions-llms-effectiveness-analysis)（正向改写是最可靠替代，有 10%+ 遵循提升报告）、[MIT 2025 否定研究](https://news.mit.edu/2025/study-shows-vision-language-models-cant-handle-negation-words-queries-0514) | 三档指令**零否定祈使句式**（含"不要/禁止/严禁/不另起/不受限"类），规则正向化：写"以未决事态收束、把选择交还"，不写"不要替用户开枪" |
| ③ | 示例与题材词污染：few-shot 示例题材泄漏进无关输出；示例还会侵蚀任务指令 | [OpenAI 社区报告](https://community.openai.com/t/few-shot-examples-leaking-into-responses-in-q-a-system/996675)、[Promptfoo: Few-Shot Weakens Task Prompts](https://www.promptfoo.dev/lm-security-db/vuln/few-shot-weakens-task-prompts-8c13bd1e/) | 指令只用抽象判据（"已声明的动作"），**零题材名词**；尤其尾部指令**每轮重复注入**，带题材词等于每轮给当前故事"递词"反复强化——§2.2 校准例只活在本文档 |
| ④ | 叙事惯性是统计性的：训练语料中"举枪"后几乎总是"扣扳机" | 由生成机制（逐 token 沿分布续写）推论 | 软措辞（"控制推进幅度"）压不住分布惯性；每档必须给**正向的、动作化的收束动作**让模型执行，而不是叫它"停下来" |
| ⑤ | 冲突指令无显式优先级时模型择一遵循 | 常见实践共识 | 冻结前缀"一轮只推进一个关键事件"改写为让权句（§5.6），显式声明以本轮节奏指令为准 |

## 4. 总体架构

### 4.1 配置与解析链

```
default_config.json            user_overrides (SP)           chat_sessions (drift)
advanced.narrative_pacing  ←─  advanced.narrative_pacing  ←─  narrative_pacing 列
("balanced")                   （扁平点分 key）               (TEXT NULL=跟随全局)

解析（每轮 runRound 组装时实时合并，不进物化快照）：
会话列非 NULL → 用会话值；NULL → advanced.narrative_pacing 全局值 → 缺省 balanced
非法值 → FormatException（仿 advanced.tools 先例，advanced_config.dart:126-137）
```

中途改全局或会话档位，下一轮 runRound 即生效。

### 4.2 注入链与缓存分析

轮 surface 现组装顺序（`director_round_runner.dart:329-353`）：冻结前缀 → core blocks（可 replace）→ append-only 历史 → 本轮用户输入 →（turn1）首回合能力提示。

| 候选注入位置 | 换档时的缓存代价 | 结论 |
|---|---|---|
| 冻结前缀 | 整条前缀作废 | 否决 |
| core blocks（历史之前） | 前缀保住，但整段历史作废 | 否决 |
| **尾部 per-turn 块（历史之后）** | 只作废尾部自身，而尾部本就每轮新算 | **采用** |

尾部注入在代码中已有同构先例：`kFirstTurnCapabilityHint`（surface 尾部 system 消息）与 `kDefaultPenReminderText`（轮内尾部执笔重述，`agent_runner.dart:819-828`）。代价为每轮约 200 token 重复 prefill，相对整条历史可忽略；换档瞬间不产生额外缓存作废。若尾部指令随轮历史持久化，旧指令在历史中逐字不变，仍不破坏缓存——但历史会残留旧档位指令，故指令文本带"本轮"字样声明以最新为准（§5.4）。

> **实施修订（2026-11-02）**：三档指令尾部统一追加「发言口径」尾句并收束整条指令（recency 最优位，紧跟保守档「一笔带过」形成顺序消歧）。根因＝用户实测：档位细则的简写许可被泛化到主角应答，出现「嗯/可以」式敷衍短发言。尾句要点：贴当下场景、双方关系、处境与心情，写贴合角色身份、像他亲口说出的发言；来源参照次序＝用户近期输入 > 上下文正文 > 子代理与工具带回的信息（三源链式，作用于发言的内容与口吻全体）。配套拍板两条：①发言落笔不带量词口径（「写实写透」类会诱发撑满应答，保守/平衡/激进档细则因此原文未动）；②公共头「本指令只规定叙事的景别」删「只」——尾句加入后指令范围已超出景别。尾句同守 §3 三条硬约束，`agent_pacing_test` 新增三组断言（三档携带+收束位、尾句零量词、头部无「只规定」）。

### 5.5 注入点

`director_round_runner.dart` surface 组装处，在 `AgentMessage.user(round.userInput)` 之后追加 `AgentMessage.system(pacingDirectiveFor(tier))`，**每轮注入**（不只 turn1）。最终顺序：历史 → 用户输入 →（turn1）首回合能力提示 → **节奏指令（surface 最后一位，recency 最优）**。若实施时发现个别供应商协议对尾部 system 消息有限制，退化为用户输入之前（`AgentMessage.user` 之前一位），其余不变。

> **实施修订（2026-09-02）**：注入角色从 `system` 改为 `user` 合成消息（workbench-reminder 标记包裹），从根上绕开 Anthropic/Gemini 适配器把 system 消息抽到顶层 system 块的问题，保住尾部 recency 位且冻结前缀缓存无恙。
>
> **协议差异声明（2026-09-02）**：Anthropic/Gemini 的请求体实现会把对话流中的 system 消息上提合并进顶层 system 块（OpenAI 兼容协议原位保留）——即"尾部 system"在这两家的实际位置是顶部，存在位置效应损失。对策两层：① 按上述修订，轮尾强指令一律走 user 通道，位置损失已消除；② 节奏指令公共头追加服从强化句 `kPriorityObedienceClause`（"本条为最高优先级即时指令，须在本次回复中立即执行"）——措辞只依赖「本条 + 本次回复」，位置无关，作为任何角色/位置形态下的双保险。适配器结构不变（保缓存优先）。

### 5.6 冻结前缀改写

`kAgentWorkRules`【质量观】段（`agent_system_prompt.dart:161`）：

- 原文：`正文承接上一轮的最后一个画面，一轮只推进一个关键事件。完整正文一次性输出，不要分段挤牙膏。`
- 改为：`正文承接上一轮的最后一个画面；每轮覆盖的故事时间跨度与可替主角做出的决定，以本轮注入的节奏指令为准。完整正文一次性输出，不要分段挤牙膏。`

改写文本对所有档位逐字相同——冻结前缀保持档位无关。
