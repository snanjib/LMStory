## 1. 目标

Advanced 的方向是为长篇故事加入可控的 **Agent Loop**：系统能在一次用户请求内规划、调用受限能力、观察结果并决定是否继续，同时保持可暂停、可审计、可恢复。

它必须复用而不是绕过现有故事基础：

- 故事状态机与失败恢复；
- 经历记忆、累积压缩摘要和分段宏摘要；
- `factual_entities`、`factual_attributes`、`factual_memory_history`；
- 现有多协议 LLM 适配层和会话级模型解析；
- drift 事务、轮次产物和诊断日志。

## 2. 候选子系统

下列模块仅表示职责边界，名称和接口需在立项后以代码评审确定。

| 子系统 | 职责 | 不负责 |
|---|---|---|
| Loop Orchestrator | 控制轮次、步数、预算、停止条件与取消 | 直接操作数据库、直接渲染 UI |
| Planner | 将用户目标转换为有限步骤或下一动作 | 无限自主运行、绕过权限 |
| Capability Registry | 暴露经过白名单、验证和权限约束的能力 | 自动暴露全部内部 Repository |
| Observation Builder | 把能力结果、错误和当前记忆转成下一步输入 | 新建第二套记忆存储 |
| Loop Persistence | 保存循环状态、动作、观察和恢复点 | 替代现有消息与轮次产物 |
| Agent UI | 展示进行中步骤、确认、取消与恢复 | 独立“世界状态 HUD” |

## 3. 与当前故事模式的关系

```text
用户输入
  ↓
现有故事上下文与记忆检索
  ↓
Agent Loop（未来，可选、有限步）
  ├─ 计划/选择能力
  ├─ 权限确认（必要时）
  ├─ 执行与观察
  └─ 停止/继续/失败恢复
  ↓
现有生成、摘要、事实提取与持久化基础
```

Agent Loop 不等于把当前 `extracting → retrieving → generating → reviewing? → summarizing → persisting` 简单包进无限循环。立项前必须定义哪些阶段可循环、一次循环的事务边界，以及中断后如何避免重复副作用。

## 4. 明确废弃的边界

- 不建设独立 HUD 子系统或 HUD 专用 Repository/Controller。
- 不恢复 `factual_memories` key-value 单表或 `state_snapshots`。
- 不采用旧 `state_patch` 展平协议。
- 当前模板数据中曾存在的 `update_world` 不是可执行能力，也不能作为未来接口规范。
- 不假设模型工具调用天然可信；所有有副作用的能力都需要 schema 校验、权限、幂等与审计。

## 5. 必须先决策的问题

1. Loop 是会话级显式模式，还是故事模式内按请求启用？
2. 默认与最大步数、token、时间和费用预算分别是多少？
3. 哪些能力只读、哪些写数据、哪些必须逐次确认？
4. 如何表示可恢复检查点并防止同一动作重复执行？
5. 事实写入继续使用总结阶段 `FactsDelta`，还是引入新的受限能力？两者如何避免重复？
6. 不同协议对工具调用、并行调用和结构化输出能力不一致时如何降级？
7. Web 与移动后台限制下，循环如何暂停和恢复？

这些问题未形成决策前，不创建承诺具体类名、表结构或视觉布局的详细实现任务。

## 6. 最低验收标准

- 每次循环有硬性停止条件，用户可随时取消。
- 所有副作用可审计；重试不会重复提交已成功动作。
- 崩溃或切后台后可明确恢复或安全终止。
- 不降低现有故事模式的数据一致性和失败恢复能力。
- 未实现的协议或能力不会出现在可选择 UI 中。
- UI 使用“步骤/动作/结果”呈现，不宣称存在未实现的实时世界 HUD。
