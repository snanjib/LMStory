## 1. 概述

v0.2.2 重构了故事模式的生成流程（检索前置 + 可选审查 + CompactionPoint），上下文组装机制需同步重新设计。本文档记录上下文空间分层、消息结构、预算分配、压缩机制等设计决策。

**核心问题（v0.2.2 前的旧设计缺陷）**：
- 固定开销不可控，可能导致压缩线不可达或死循环
- 比例分母不统一（availableWindow / remaining 混用），用户无法直观理解
- drafting 阶段历史前插入动态记忆块，破坏缓存命中（v0.2.2 阶段名重命名前称 drafting，对应新名 generating）
- 截断与压缩并存，逻辑冗余

## 2. 空间分层模型

```
模型上下文 contextWindow（100%）── 统一百分比基准（用户看到的 = 内部计算的）
│
├── 输出预留 outputTokenReserve     绝对值，不参与百分比分配
├── 基础上下文部分                  绝对值上限（~9%），不参与百分比分配
│   ├── 角色提示词 ≤ 2000 token
│   ├── 压缩摘要 ≤ 8000 token
│   └── 用户输入 ≤ 2000 token
│
├── 检索注入区                      contextWindow × retrievalRatio(15%)     ← 百分比限制
│   ├── 世界设定（事实层）
│   └── 相关往事（经历记忆）
│
├── 近期对话区                      上限由压缩触发线推算
│                                   下限 contextWindow × recentMinRatio
│
├── 压缩触发线                      contextWindow × compactionTriggerRatio(50%) ← 百分比限制
│   （总占用达此线触发压缩）
│
└── 余量（不分配）                  注意力缓冲，省 token
```

### 统一百分比原则

固定开销有明确上限（9000 token），输出预留也会在组装请求前解析为确定的绝对值。因此**两个可变长区域（检索注入区 + 近期对话区）直接用模型上下文的百分比限制**，运行时计算 `contextWindow × ratio`，所见即所得。

- **不需要"内外分离"**：用户看到的百分比 = 内部计算用的百分比
- **输出预留**：`maxTokens > 0` 时取配置值与模型 `maxOutput` 的较小值；`maxTokens = 0` 时固定使用 8192。该值仅用于上下文预算，不会在 0 语义下重新成为 API 上限
- **可用窗口**（contextWindow - outputTokenReserve）降级为辅助概念，仅在设置百分比默认值时参考
- 固定开销不总是达到上限（角色提示词可能只有 500 token），但不影响正确性--固定开销少时余量多一点，模型注意力更集中

## 3. 固定开销上限

### 为什么需要上限

固定开销（角色提示词 + 压缩摘要 + 用户输入）长度不可控。如果不设上限：
- 用户设超长角色提示词 -> 固定开销膨胀 -> 历史空间被挤压 -> 频繁压缩
- 压缩摘要无限增长 -> "压缩越多摘要越长"恶性循环 -> 固定开销更大 -> 更频繁压缩

### 上限值

| 组件 | token 上限 | 超限处理 |
|------|-----------|---------|
| 角色提示词 | ≤ 2000 | UI 警告建议精简 |
| 压缩摘要 | ≤ 8000 | LLM 压缩时控制长度，超限要求再精简 |
| 用户输入 | ≤ 2000 | 超限时截断或提示 |

### 三层防护

| 防护层 | 机制 | 作用 |
|--------|------|------|
| 第一层 | 压缩触发线基于"总占用"（§5.1） | 自动适应固定开销，压缩线永远可达 |
| 第二层 | 压缩摘要 token 上限（8000） | 防止摘要无限膨胀，固定开销有天花板 |
| 第三层 | UI 警告角色提示词过长 | 用户感知，主动精简 |

## 4. generating 阶段上下文组装

### 4.1 消息结构

```
① [system] 角色提示词            ★ 稳定（跨轮次不变）
② [system] 压缩摘要?             ★ 稳定（下次压缩前不变）
③ [user/assistant] 最近对话原文   ◐ 半稳定（旧消息不变，新消息追加末尾）
④ [system] 世界设定?             ✗ 动态（每轮检索结果不同）
⑤ [system] 相关往事?             ✗ 动态（每轮检索结果不同）
⑥ [user] 当前用户消息            ✗ 动态
```

**设计要点**：
- 历史紧接压缩摘要之后，旧消息能命中缓存（v0.2.2 修订，原记忆块在历史前破坏缓存）
- 记忆块（世界设定 + 往事）移到历史之后，语义为"先看背景惯性，再看本轮规则，最后看方向"
- ③ ④ ⑤ 为条件注入（无内容时省略）

### 4.2 缓存命中设计

**缓存命中区** = ① + ② + ③（旧消息部分）

| 部分 | 稳定性 | 缓存命中 |
|------|--------|---------|
| ① 角色提示词 | 跨轮次不变 | ✅ |
| ② 压缩摘要 | 下次压缩前不变 | ✅ |
| ③ 旧消息 | 不变（只有末尾追加新消息） | ✅（旧部分） |
| ③ 新消息 | 每轮新增 | ❌ |
| ④⑤ 记忆块 | 每轮检索结果不同 | ❌ |
| ⑥ 用户消息 | 每轮不同 | ❌ |

相比 v0.2.2 前的设计（记忆块在历史前，破坏全部缓存），缓存命中区从"只有角色提示词"扩大到"角色提示词 + 压缩摘要 + 旧历史消息"。

### 4.3 token 预算分配

```
模型上下文 contextWindow（100%）
│
├── 基础上下文部分    按实际算（有上限，见 §3）
├── 检索注入区        contextWindow × retrievalRatio(15%)
├── 近期对话区        剩余空间（不截断，到压缩线触发压缩）
└── 余量              不分配
```

**关键规则**：
- 近期对话区**不塞满**：实际历史不足剩余空间时全保留，不填充
- 近期对话区**不截断**：历史过长时靠压缩管理（§5），不直接砍消息
- 余量不分配给任何区：模型注意力更集中，省 token

## 5. 压缩机制

### 5.1 压缩触发条件

```
触发条件：总占用（基础上下文 + 检索区 + 历史）> contextWindow × compactionTriggerRatio(50%)
等价于：历史 > contextWindow × compactionTriggerRatio - 基础上下文 - 检索区
```

**为什么基于"总占用"而非"纯历史"**：
- 旧逻辑（历史 > availableWindow × recentMaxRatio）在固定开销大时压缩线不可达
- 新逻辑自动适应：固定开销越大，历史可用空间越小，越早触发压缩
- 压缩线永远可达，不会出现"死循环"

**用户可见**：会话配置中显示"当前上下文占用 X%"，达到 50% 时触发压缩。

### 5.2 压缩执行（v0.2.3 重构：分离压缩摘要与分段宏摘要）

- 复用 Simple 模式 CompactionStreamer（LLM 流式压缩）
- **压缩摘要**（累积式）：基于"旧摘要 + 新对话"生成，用于上下文注入（稳定前缀），存 `chat_messages`（`is_summary=true`）+ `compaction_points`
- **分段宏摘要**（分段式）：仅基于"新对话实际内容"生成，用于记忆检索 + 记忆查看器编年史，存 `experiential_memories`（`memory_level='macro'`，**参与语义检索**）
- 压缩摘要 prompt（故事模式专用）：保留主要事件时间线、角色出场、剧情阶段、关键转折；不保留具体对话内容、细节描写
- 分段宏摘要 prompt（`kIntermediateSegmentMacroPrompt`）：只总结实际发生的事件，禁止创造/续写
- 压缩摘要 token 上限 8000（与 §3 固定开销上限一致），超限时要求 LLM 再精简

**首次压缩 vs 后续压缩**（v0.2.3）：

| 场景 | 压缩摘要 | 分段宏摘要 |
|------|---------|-----------|
| 首次压缩（无旧摘要） | 正常生成 | `null`（压缩摘要兼作宏摘要，用压缩摘要文本作为 macro 记忆内容） |
| 后续压缩（有旧摘要） | 正常生成（累积式） | 并行生成（分段式，仅基于新增轮次实际对话，排除草稿/审查内容） |

> **v0.2.3 变更**：原设计压缩摘要"兼任宏摘要"且"不参加语义检索"。v0.2.3 后分离为两个独立摘要：压缩摘要（累积式，用于上下文注入）和分段宏摘要（分段式，用于记忆检索）。分段宏摘要**正常权重参与语义检索**，标注"段落摘要"（区别于微摘要的"事件记忆"）。详见 DOC-10 §2.2。

### 5.3 压缩后下限保护

```
压缩后历史保留量 = recentMinRatio × contextWindow
recentMinRatio = max(0.10, recentMinTokenTarget / contextWindow)  （null 时动态计算）
recentMinTokenTarget = 32000（默认）
```

**下限的作用**：确保压缩后仍有足够历史对话携带，避免"刚压缩完没有历史可读"。32K token 约等于 15-25 轮详细对话，足够保持近期氛围。

**下限保护**：当 recentMinRatio + 检索区 + 基础上下文 > compactionTriggerRatio 时（下限过高挤压缩线），UI 给出警告。

### 5.4 不截断原则

v0.2.2 废弃截断（`_reduceHistory`），只靠压缩管理历史长度：
- 有压缩机制后，截断（直接丢弃不生成摘要）是多余的
- 历史涨到压缩线 -> 触发压缩 -> 压缩后回到下限 -> 继续对话
- 不存在"砍掉不压缩"的中间态
- 截断逻辑代码待清理，仅保留极端兜底（压缩被关闭时防止超窗口）

## 6. 检索机制

### 6.1 五路并行检索

extracting 阶段提取 5 类关键词，retrieving 阶段 5 路并行检索：

| 关键词类 | 检索通道 | 用途 |
|---------|---------|------|
| characters（角色） | FTS5 | 精确匹配角色名 |
| items（物品） | FTS5 | 精确匹配物品名 |
| locations（地点） | FTS5 | 精确匹配地点名 |
| actions（动作） | Vector | 语义匹配动作 |
| plots（情节） | Vector | 语义匹配情节 |

- 5 路 Future.wait 并行，归并打分后取 topK=12
- 任一通道失败自动降级（该路返回空结果，不阻塞其他路）
- embedding 未配置时，Vector 通道降级为空（只走 FTS5 三路）
- 质量阈值：绝对 0.5 + 相对 0.65（双阈值取严格）

### 6.2 关键实体强制注入

importance ≥ 关键实体阈值（配置 `key_entity_importance_threshold`，默认 5）
的关键实体（如主角），不管检索分数高低都自动注入上下文。

2026-11-08（DEC-06）收口：自动携带的关键档案最多
`key_entity_auto_cap`（默认 10）份，且计入自动资料池总量
`injection_max_entities`（默认 20，关键档案 + 本轮相关填充）；排序为
importance 降序 → 活跃度（updatedAt/updatedTurn 新者在前）→ entityId
稳定兜底，不按创建早晚长期占位。forceWorld / forceDirective 两种
用户显式常驻通道各自受 `force_inject_safety_cap`（50）独立安全帽约束，
不占自动池配额（两个通道分别 50，不是合计 50）；同一实体跨通道只注
入一次。已知实体清单（summarizing 注入面）同批对齐同一总量：本轮
命中的 focus 实体全保留（更新目标不丢、防重复建档），其余按同一稳定
排序填充。

## 7. reviewing 阶段

### 7.1 消息结构

reviewing 只是在 generating 末尾追加一条 user 消息，前 6 条完全一致：

```
① [system] 角色提示词                  ← 与 generating ① 完全一致
② [system] 压缩摘要?                   ← 与 generating ② 完全一致
③ [user/assistant] 最近对话原文         ← 与 generating ③ 完全一致
④ [system] 事实类记忆检索结果?          ← 与 generating ④ 完全一致
⑤ [system] 经历摘要类记忆检索结果?      ← 与 generating ⑤ 完全一致
⑥ [user] 当前用户消息                  ← 与 generating ⑥ 完全一致
⑦ [user] 审查后缀 + 生成正文全文（合并，标记分隔）  ← reviewing 独有
```

最后一条 user 消息结构：
```
--审查提示词--
[kReviewingSuffixPromptV2 内容]

以下是你要修改的内容：
--生成内容--
[生成正文全文]
```

**设计要点**：
- 审查后缀从 system 消息改为合并到最后一条 user 消息（方案C），前缀与 generating 完全一致
- 审查后缀 + 生成正文在同一条消息，LLM 注意力集中
- 用标记（--审查提示词-- / --生成内容--）明确区分指令和内容
- 检索复用 retrieving 结果，不重新检索
- 压缩已在 compacting 阶段处理，reviewing 不触发压缩

### 7.2 预算分配

与 generating 统一原则（不塞满、不截断、去掉 dialogueBudgetRatio）：

```
模型上下文 contextWindow（100%）
│
├── 基础上下文部分（固定开销，有上限）
│   ├── 角色提示词 ≤ 2000          ┐
│   ├── 压缩摘要 ≤ 8000            │ 与 generating 共享
│   ├── 用户输入 ≤ 2000            ┘
│   ├── 审查后缀 ~700              ┐
│   ├── 生成正文（长度由前一生成请求决定） │ reviewing 独有
│   └── 审查请求 ~100              ┘
│   合计随生成正文实际长度变化
│
├── 检索注入区        contextWindow × retrievalRatio(15%)  ← 复用 retrieving 结果
├── 近期对话区        剩余空间（不塞满，不截断）
└── 余量              不分配
```

reviewing 比 generating 多占审查后缀、生成正文与审查请求本身；当 generating 使用 `maxTokens=0` 时，正文长度没有应用层硬上限，因此 reviewing 的输入占用必须按实际响应统计。reviewing 可选（默认关闭），这部分额外空间是审查能力的必要代价。

### 7.3 prompt 约束（kReviewingSuffixPromptV2）

三个审查维度 + 修正边界 + 输出要求：

**维度一：事实一致性**（先思考后输出，审查过程不体现在输出中）
- 事实层审查（对照【事实类记忆检索结果】）：角色属性、世界规则、物品属性
- 经历层审查（对照【经历摘要类记忆检索结果】）：已发生事件、角色发展、时间线、位置连续性
- 每类审查配有具体示例（如"设定中角色叫'李明'，生成正文写成'李明辉'就是错误"）
- 发现矛盾：仅修正矛盾部分，不扩大范围；未发现矛盾：不改情节

**维度二：AI味去除**（必须执行，即使无事实矛盾）
参考 [humanizer](https://github.com/blader/humanizer)（开源去 AI 味写作技能），10 条 AI 写作模式：
1. 夸大重要性与象征意义（"这一刻标志着..."）
2. 推广性语言（"壮丽的"、"充满活力的"）
3. AI高频词（"深刻的"、"不可或缺"、"彰显"）
4. 三段式节奏（强制三个一组）
5. 被动语态过多
6. 同义词轮换（"主角"/"主人公"/"他"交替）
7. 聊天痕迹与元叙述（"让我们看看..."）
8. 过度对冲（"可能也许大概"）
9. 通用积极结尾（"未来一片光明"）
10. 制造性短句戏剧（连续短句假紧张感）

每条模式给出"表现"和"修正方向"，遵循"替换不删除"原则。

**维度三：易读性**（必须执行）
- 合理分段，避免大段文字聚集（单段不超过5-6行）
- 确保标点完整，无无标点长句
- 对话和叙述适当分隔

**修正边界**：
- 不得从生成正文结尾续写新内容
- 段落数量基本守恒，可微调但不得大幅增减
- 不得另起炉灶完全重写
- 不得原样输出生成正文（必须做去AI味和易读性处理）

**修正后自检**：
- 是否引入新的事实矛盾？
- 是否续写了生成正文结尾之外的新内容？
- 输出是否保持了叙述者视角？

**输出要求**：
- 直接输出最终回复正文，不加"修正后："等任何前缀
- 不输出审查过程、JSON、标记或额外说明

### 7.4 注入标题改名

配置项默认值变更：
- `kFactInjectionTitle`：【世界设定】-> 【事实类记忆检索结果】
- `kMemoriesInjectionTitle`：【相关往事】-> 【经历摘要类记忆检索结果】

> **引用传递原则**：在编写所有提示词文本时，凡涉及可配置的值（注入标题、记忆引导语、生成正文注入前缀等），**不得硬编码**，必须通过占位符或变量引用传递。例如 reviewing prompt 中提到注入块标题时，使用 `{factInjectionTitle}` / `{memoriesInjectionTitle}` 占位符，在构建消息时替换为 PromptsConfig 的实际值。这样配置项变更时 prompt 自动跟随，无需同步修改 prompt 文本。
>
> 当前注入标题等仍保留为可配置项（PromptsConfig），未来可能改为硬编码常量，但 prompt 中的引用方式不变。
