## 0. 文档定位

本文档定义世界书（World Book）与角色卡（Character Card）功能的概念、架构落点、字段映射与触发机制。设计已完整闭环并经过审查修正（见文首状态与变更记录）。

**适用范围**：仅故事模式（`intermediate`）。对话模式（`chat`）无记忆系统，不支持世界书/角色卡。

> **边界修订（2026-09-02）**：导演模式（`advanced`）与故事模式共享事实层消费链，此前已实际支持消费世界书/角色卡投影，但缺少应用入口。现「应用角色卡 / 应用世界书 / 取消应用」区段已抽取为共享组件（`story_runtime/presentation/widgets/seed_resource_section.dart`），故事与导演的会话设置面板同款挂载，占用名预检与投影语义两模式一致。上文「仅故事模式」按「对话模式不支持」理解，导演模式列入适用范围。

**只记录已确认结论；待补项明确标注。**

## 1. 背景与动机

设计前状态：LMStory 以自研模板系统 + 事实记忆承载设定资产，没有「角色卡/世界书」一等公民资产，也不兼容 SillyTavern 格式。SillyTavern 的 PNG 角色卡（隐写元数据）与世界书 JSON 是社区通行的交换格式，本设计为此补上与该生态的互操作能力（只读导入）。

> （2026-08-19 更新：上段为设计前背景。本设计已实施——LMStory 现支持 SillyTavern 兼容只读导入：PNG 角色卡 V1/V2 `chara` + V3 `ccv3`（V3 优先）、纯 JSON 角色卡（V2/V3）、世界书 JSON（顶层 `entries`）；CHARX 不支持。）

目标：引入「世界书」「角色卡」两类**只读资源**，打通与 SillyTavern 生态的**只读导入**（导出后置，另作工具模块）。同时守住核心护城河——记忆系统不能因新增静态资源而退化。

## 2. 概念定位（已确认）

### 2.1 世界书 = 只读实体层记忆

- 世界书是**只读资源**：相当于**提前导入的只读实体层记忆**。
- **属性级只读基线（2026-09-14 v0.9 修订）**：导入内容（基线行）不可改写、不可删除；对话中**可**新增属性、追加别名与归档——一切生长落在独立 `source=auto` 演变行上与基线并存，与角色卡同款「基线 + delta」模型（§8.1）。
  - 原「不可修改、不可删除、对话中不能新增」为 v0.1-v0.8 的实体级冻结口径，已被上述属性级语义取代。
- 资源本体只能通过**导入 / 导出**发生变化。
- **不是**「在故事模式中维护的记忆」。

### 2.2 角色卡 = 只读基线 + 可演化 delta 的实体类记忆

- 角色卡是**只读资源**：作为**提前预制好的实体类记忆**。
- **导入内容的只读是硬性要求**：角色卡所有内容无论何时都**原样保留**，永不被修改、删除、替换。
  - 例：导入角色卡"性格 = 内向"，"内向"永远只读，只能追加"因xxx变得开朗起来"；对变化的修改也动不到"内向"。
  - 即：**不可变基线（角色卡导入内容）+ 可演化 delta（故事模式追加的变化）**。
- 角色卡**只作为记忆使用，与生成无直接关系**（不喂叙述者 persona / `systemPrompt`）。

### 2.3 角色卡 vs 角色提示词（重要区分）

| | 角色卡 | 角色提示词（`systemPrompt`） |
|---|---|---|
| 语义 | 故事中**某个角色**的实体类记忆 | **叙述者 persona**（视角/风格） |
| 消费路径 | 事实层实体 + 属性，经【世界设定】块检索注入 | 上下文位置①，会话级 > 全局 > `kDefaultRolePrompt` |
| 关系 | 与生成无直接关系 | 直接参与生成 |

角色卡**不**映射为 `systemPrompt`。

### 2.4 字段三分策略（已确认）

导入字段按用途三分：

| 分类 | 含义 | 处理 |
|---|---|---|
| **A. 投影进事实层（记忆）** | 参与检索/生成/记忆 | 落 `factual_entities` + `factual_attributes` |
| **B. 仅展示** | 不进事实层、不注入、不检索 | 在**全局资源库详情页**展示（§6） |
| **C. 不渲染** | 详情页也不展示 | 仅随原始卡 JSON 无损存档（服务将来导出） |

「丢弃」的准确含义 = **不投影、不注入、不渲染**；数据层面仍随资源表原始 JSON 无损保留，不算硬删。

## 3. 架构落点（已确认）

### 3.1 落在事实层三表

世界书与角色卡不新建独立记忆结构，落到现有事实层：

```
factual_entities（实体表）+ factual_attributes（属性表）+ factual_memory_history（审计表）
```

用**来源标记**区分三类，复用现有检索注入（`FactContextBuilder` 的【世界设定】块）、上下文组装（DOC-13 位置④）、事实查看器 UI：

| 来源（source） | 可变性 | FactApplier 是否可碰 |
|---|---|---|
| `auto`（现有 AI 自动提取） | 全程可演化 | ✅ 正常 |
| `worldbook`（世界书） | 基线冻结，可演化（同 card，v0.9 起） | ⚠️ 基线重定向：新增/别名/归档允许（§8.1） |
| `card`（角色卡基线） | 基线冻结，delta 可演化 | ⚠️ 同上：只允许追加 delta，不得覆盖基线（§8.1） |

### 3.2 资源表 + 会话内实体表（两层）

**已确认采用两层分离**，并区分全局资源与会话级资源：

```
资源层（可导入/导出、可复用）
├─ 全局资源库（character_cards / worldbook_entries）
└─ 会话级资源（绑定到某会话）

投影（导入时）
        ↓
会话内实体层（factual_entities / factual_attributes）
```

- 导入 = 从资源表「投影」到会话内实体。
- 同一张角色卡导入不同会话：**各生成独立实体**（倾向，§8.1 最终确认）。
- 资源表存**完整原始 JSON**（无损，服务将来导出工具）。

### 3.3 展示归属（已确认）

角色卡 / 世界书的**资源库与详情页**放在**全局**（类似「模板管理」页），**会话级不展示**。

## 4. 关键决策清单（已确认）

| # | 决策 | 结论 |
|---|---|---|
| 1 | 数据模型 | 资源表 + 会话内实体表，分全局/会话级；资源表存完整原始 JSON |
| 2 | 角色卡只读语义 | 硬性只读：导入内容永久原样保留；变化只能追加 delta（§2.2） |

| 4 | 角色卡字段映射 | 字段三分（A 投影 / B 仅展示 / C 不渲染），见 §7.1 |

| 11 | 许可证边界 | SillyTavern AGPL-3.0 只作规范/行为参考，代码独立实现不复制 |

## 5. 兼容性格式事实（样本确认）

### 5.1 角色卡 PNG 隐写与 JSON 结构

- 载体：PNG `tEXt` chunk，结构为 `keyword\0` + **base64(UTF-8 JSON)**。
- V1（TavernAI）：keyword = `chara`（无 `spec` 字段）。
- V2：keyword = `chara`，JSON 内 `spec:"chara_card_v2"`、`spec_version:"2.0"`。
- V3：keyword = `ccv3`，JSON 内 `spec:"chara_card_v3"`、`spec_version:"3.0"`。
- 同时存在时 **V3 优先**；V3 是 V2 超集。
- **JSON 结构为「V1 扁平 + V2/V3 `data`」混合**：顶层同时有 V1 扁平字段（name/description/personality/…/tags/avatar/talkativeness/fav）与 `spec`/`spec_version`/`data`；字段实际内容以 `data` 为准。
- V3 `data` 额外字段：`group_only_greetings`（数组，陪聊用，丢弃）。
- **真实卡片的 description/personality/scenario 可能为空**，内容全在 `character_book`（内嵌世界书）与 `extensions.depth_prompt`——内嵌世界书解析是**必需**，不是可选。
- 纯 JSON 导入（无 PNG）也是合法输入。

### 5.2 世界书词条：两套 JSON schema（必须都支持）

**A. 独立导出格式（SillyTavern 世界书导出，camelCase）**：

顶层 `{ "entries": { "<id>": <entry>, ... } }`（**字典**，键为 id 字符串）。词条字段：

`uid`(int) / `key`(数组) / `keysecondary`(数组) / `comment` / `content` / `constant`(bool) / `selective`(bool) / `selectiveLogic`(int) / `order`(int) / `disable`(bool) / `position`(int 枚举) / `depth`(int) / `probability`(int) / `useProbability`(bool) / `vectorized`(bool) / `excludeRecursion` / `preventRecursion` / `delayUntilRecursion` / `sticky` / `cooldown` / `delay` / `group` / `groupWeight` / `characterFilter`(dict) / `triggers`(数组) / `matchCharacterDescription` 等匹配源开关。

**B. 内嵌 character_book 格式（Character Card V2 规范，snake_case）**：

`data.character_book = { name, entries: [ ... ] }`（**数组**）。词条字段：

`id` / `keys`(数组) / `secondary_keys`(数组) / `comment` / `content` / `constant` / `selective` / `insertion_order` / `enabled` / `position`(字符串 "before_char"/"after_char") / `case_sensitive` / `use_regex` / `extensions`。

**类型容错（必做）**：真实卡片/世界书存在非标准类型——布尔用字符串 `"True"`/`"False"`、数组用字符串 `"[]"`、`extensions` 用 Python repr 字符串等。解析器必须容错归一化（字符串布尔→bool、字符串数组→list、忽略无法解析的扩展字段）。

**导入防护**：不设体积上限（2026-10-07 产品拍板取消原 10MB 上限：数据备份随会话增长易超限，需可经外部入口导入；JSON 嵌套深度守卫仍保留）；解析失败（base64 解码失败 / JSON 解析失败 / chunk 缺失）须整体失败并给出用户可读错误，不落半截资源。

## 6. 字段映射表

### 6.1 角色卡字段 → LMStory

导入一张角色卡 = 生成一个 `character` 类型实体 + 只读基线属性（A 类），并可选导入内嵌世界书（`lore` 实体）。

| SillyTavern 字段 | 分类 | 映射 |
|---|---|---|
| `name` | A | 实体 `primaryName` |
| `description` | A | 属性 `background`（single，只读基线） |
| `personality` | A | 属性 `personality`（single，只读基线） |
| `scenario` | B | 详情页展示（场景设定） |
| `creator_notes` | B | 详情页展示（创作者备注） |
| `tags` | B | 详情页展示（标签）；不映射 `category`（`category` 用于标记导入来源） |
| `creator` / `character_version` | B | 详情页展示 |
| `first_mes` / `mes_example` | B | 详情页展示（开场白/对话风格，纯展示不生成） |
| `system_prompt` / `post_history_instructions` / `alternate_greetings` | C | 不渲染，仅原始 JSON 存档 |
| `character_book` | — | **解析为世界书词条**（`lore` 只读实体） |
| `extensions` | C | 本体丢弃，但解析其中的 lorebook 键 |

> V3 多语言字段：**本期不实现**（主字段优先），后续迭代再支持 `zh-cn`/`zh` 优先回退。
> `extensions` 内藏 lorebook 的常见键：`character_book` / `embedded_lorebook`。
> **A 类约束**：A 类映射均为 `single` 类型（name→primaryName、description→background、personality→personality），恰好回避跨行去重；显式约束「A 类只投影 single 字段」，不投影 list/dict。

### 6.2 世界书词条 → LMStory

世界书词条 = `lore` 类型实体（DOC-11 已有 `lore` 类型，对应"通识性设定"）；v0.9 起为属性级只读基线（§8.1）。

> 解析器先将 §5.2 两套命名归一化为统一词条模型（`key`/`keysecondary`/`content`/`comment`/`constant`/`enabled`/`uid`/`vectorized`），再映射。`constant=true` 对应 importance=5 强制注入；`disable=true`（独立导出）或 `enabled=false`（内嵌）对应 `isArchived=true`。
>
> **实体强制注入开关修订（2026-08-14）**：`constant=true` 改映射为「实体强制注入开关」`forceInject=world`（注入【世界设定】），不再设 `importance=5`；评分统一为 2。详见 `doc/design/v0.2.3/实体强制注入开关设计.md` §3.3。
>
> **importance 缺省**：`constant=true` → importance=5；非 `constant` 词条 → importance=2（仅 FTS5/关键词触发召回，不强制注入）。
>
> **常驻注入上限冲突（审查补充）**：`constant=true` 映射 importance=5 后，仍受 `buildFactBlock` 的 `injectionMaxEntities`（默认 20，全局共享，与 auto 关键实体争槽）截断，「强制注入」措辞与实际不符。实施前需明确：常驻词条是否需要世界书专属子配额（如固定 N 个槽位，不被 auto 实体挤占）。
>
> **primaryName 确定**：首个非空 `key` 作 primaryName；无 key 时用 `comment`；key 重复或为空时去重/降级（避免撞 `idx_factual_entities_session_name` 唯一索引）。

| SillyTavern 字段 | 映射 | 说明 |
|---|---|---|
| `key` / `keysecondary` | 实体 `aliases`（首个 key 可作 `primaryName`） | 触发词 |
| `content` | 属性 `description`（`lore` schema 白名单无 `content` 字段） | 词条正文 |
| `comment` | 无 key 时的 `primaryName` / `category` | 标题 |
| `constant` | importance = 5（强制注入） | 常驻 |
| `enabled` | 禁用词条**不投影**（应用时跳过，不入实体库） | 启用（2026-09-13 按实现对齐）：实现为跳过投影（resource_projection_service 对 `!enabled` continue），非本表原先写的 isArchived 反义映射——禁用词条留在资源库可重新启用，但不再以归档实体形态进会话注入 |
| `vectorized` | 是否向量化 | 见 §8 |
| `uid` | `entityId`（或自增） | 内部 ID |
| 其余（`selective`/`selectiveLogic`/`insertion_order`/`position`/`depth`/`probability`/`case_sensitive`/`match_whole_words`/`scan_depth`/递归项/`automation_id`/`characterFilter`/`sticky`/`cooldown`/`delay`/`group`/`groupWeight`） | 无对应，忽略（记录导入日志） | 降级 |

> **属性级只读 2.0 语义注（2026-09-14 v0.9）**：上表投影产生的世界书属性行（`constant`/`enabled` 等映射结果）即**只读基线行**，永不改写、不可移除；剧情中的变化由 FactApplier 落同键 `source=auto` **演变行**并存（§8.1 守卫矩阵）。

## 7. 触发机制方案（已定方向）

### 7.1 现状

事实层当前**无 FTS5、无向量**（检索是纯 SQL `primaryName`/`aliases` LIKE 匹配，DOC-11 §6.1）。FTS5 与向量都在**经历层**（`memories_fts` + `has_embedding`）。世界书作为 `lore` 实体，需要"主题关键词匹配 content/key"，故需给事实层（至少世界书实体）新增检索能力。

### 7.2 方案

| 通道 | 收益 | 开销 | 结论 |
|---|---|---|---|
| **FTS5（词条 key+content 建全文索引）** | 字面/分词召回："货币"命中"货币汇率" | 一次性建 FTS5 虚拟表 + 导入插入；检索复用现有 FTS5 逻辑 | ✅ **必做** |
| **向量（词条 content 向量化参与语义检索）** | 语义召回："钱/交易"命中"货币汇率"，守住 LMStory 记忆护城河 | 导入时一次性 embedding（词条量少，成本低）；依赖 embedding 配置（无则降级）；BLOB 存储 | ⚠️ 可配置增强，默认开、可关、无 embedding 降级 FTS5 |

- 检索开销≈0：复用现有纯 Dart 向量引擎，不新增运行时成本。
- 最小可用集不依赖 embedding：FTS5 必做，向量可后置。

### 7.3 FTS5 具体接入（已定方向）

事实层当前无 FTS5（只有经历层 `memories_fts`）。世界书检索需给事实层新增 FTS5 能力：

- 新建 `factual_fts` 虚拟表，索引世界书 `lore` 实体（`source=worldbook`）的 `primaryName` + `aliases`(keys) + `description`(content)。（`comment` 非存储列，已映射为 `primaryName`/`category`，不单独索引。）
- retrieving 阶段：FTS5 匹配本轮提取的关键词（entities/items/locations 文本通道），命中即召回对应 `lore` 实体。
- 世界书实体在 FTS5 命中后，与现有实体名匹配合并去重，统一走【世界设定】注入。
- 向量（可选）：世界书词条 `description` 向量化，复用现有 actions/plots 向量通道；无 embedding 降级只走 FTS5。
- **演变行 FTS 同步（2026-09-14 v0.9）**：世界书实体新建 auto 演变 `description` 行时，重建该实体的 `factual_fts` 行；`description` 取值口径与 `memory_fts_rebuilder` 对齐——按入库顺序首条 description 行优先（有基线取基线，无基线取该新建 auto 行），防单边漂移（`fact_applier.dart`）。

## 8. 数据模型设计（已定）

### 8.1 「不可变基线 + 可演化 delta」数据模型（方案 A 已确认）

**关键约束**：`factual_attributes` 现有唯一索引 `idx_factual_attrs_entity_key(entity_id, attr_key)`（`app_database.dart`），需改为 `(entity_id, attr_key, source)` 才能容纳"同 attrKey 基线 + 演变两行"。

**Schema 变更**：
- `factual_entities` 加 `source` TEXT（`auto` / `worldbook` / `card`，默认 `auto`）+ `sourceRef` TEXT（nullable，指向 `cardId`/`bookId`）。
- `factual_attributes` 加 `source` TEXT（默认 `auto`）；`source != auto` 即只读基线。
- 唯一索引 `(entity_id, attr_key)` → `(entity_id, attr_key, source)`，并**新增 partial unique index** `UNIQUE (entity_id, attr_key) WHERE source='auto'`（保证 auto 行仍唯一）；schemaVersion 35 → 36。

**Repository API 变更**：`getAttribute(entityId, attrKey)`（单行）改为 `getAttribute(entityId, attrKey, source)` 或 `getAttributes(entityId, attrKey)`（返回基线+auto 多行）；FactApplier 6 个 apply 方法（`_applyCreateEntity`/`_applyUpdateAttr`/`_applyAppendList`/`_applyRemoveFromList`/`_applyAddAlias`/`_applyArchiveEntity`）+ FactContextBuilder + 记忆查看器逐个改。

**只读守卫（FactApplier，属性级只读 2.0，2026-09-14 v0.9 起世界书与角色卡同规）**：

导入实体（`source != auto`，世界书 worldbook + 角色卡 card）的**基线行**（导入内容）永不覆盖；一切生长落 `source=auto` 演变行并存。按动作对照（`fact_applier.dart`）：

| delta 动作（目标为导入实体） | 新语义 |
|---|---|
| `update_attr` 命中基线键 | **重定向**：写入/新建同 attrKey 的 `source=auto` 演变行，基线行不动。无 auto 行且新值 == 基线值 → 同值跳过（不建重复演变行） |
| `update_attr` 新 attrKey | 新建 `source=auto` 属性。lore 类型放宽自定义键（对齐 character——状态/下落/归属等）；其余类型 schema 白名单不动 |
| `update_attr` attrKey=`name` | **转 `add_alias`**：导入实体主名是种子身份标识不可改，改名意图转别名追加、旧主名保留（世界书 + 角色卡同收紧；导演模式暂存期预检见 §8.2） |
| `append_list` | 基线为 single 行 → 重定向为 update_attr 语义，演变值落新建 auto 行，不触碰基线 |
| `remove_from_list` | 无 auto 行 → 跳过（基线行天然不可移除）；有 auto 行 → 只删 auto 行的值，基线保留 |
| `add_alias` | 照常允许（v0.8 及此前世界书跳过） |
| `archive_entity` | 照常允许：归档 = 状态标记非删除，基线行原样在库，不违反「导入内容永久原样保留」 |
| `create_entity` 撞名 | 不再实体级早退，走统一转换：带 value → 转 `update_attr`（落演变行）；不带 value → 走 `add_alias` 转换路径（撞名情形通常被别名查重拦下，观察结果与旧冻结一致，但不再有 worldbook 专属早退分支） |

> v0.1-v0.8 的实体级守卫（世界书所有 delta 一律跳过、create_entity 命中即丢弃）已于 2026-09-14 移除；本表为其替代口径。

**注入聚合（FactContextBuilder）**：按 entityId+attrKey 合并，基线行在前、演变行在后，如 `性格：内向（初始）；因xxx变得开朗起来（演变）`。

### 8.2 世界书去重约束 + 只读完整性守卫（已定）

**去重**：
1. `{{known_entities}}` 纳入导入实体并加 `[导入设定]` 标记（2026-09-14：世界书与角色卡同标，替代原 `[只读设定]`——属性级只读下实体可演变，「只读」措辞会误导模型不敢写入；AI 提取实体无标记），让 LLM 知道"已有，别重复创建"（复用 DOC-11 实体去重规则）。
2. **提示词教育 + 导演暂存期预检**（2026-09-14 v0.9，取代原「静默跳过、无 LLM 反馈」取舍）：
   - extract_facts 提示词新增【记忆机制与只读基线】段（六条规则：不改写基线 / 变化照常 update_attr 以演变并存 / 可新增属性与别名 / 主名不可改（用 add_alias）/ 可归档 / 不对导入实体 merge 改身份）。
   - 导演模式 `update_facts` 暂存期预检（与 FactApplier 提交期守卫同口径）：改导入实体主名 → 暂存成功 + 回执提示「提交时将以别名记录」；`remove_from_list` 命中纯基线键 → 当场拒绝并给拒因。
   - 故事模式提交期的静默丢弃面在属性级化后近乎归零（合法意图全部有落点：基线键→演变、新键→auto 行、别名/归档→放行）。

**只读完整性（旁路守卫，独立审查修正）**：
3. **记忆查看器手动编辑**：`deleteEntityById` / `deleteAttributeById` / `updateEntityBasic` / `updateAttributeValue` 对 `source != auto` 的实体/基线行应拒绝（UI 隐藏入口 + Repository 层兜底拦截）。2026-09-14 v0.9 收窄为**行级**：基线行编辑/删除仍锁；只读实体的「新增属性」放行（新建行 `source=auto`，无基线语义）；属性行带「基线/演变」徽标区分（`factual_memory_tab.dart`）。

4. **覆盖式重写（重新生成/编辑重发/删除整轮）——`deleteFactsByTurns` 实为 5 步**（`factual_repository_impl.dart`）：
   ① 收集 `createdTurn >= fromTurn` 的实体（待删）；② 删除其属性 + 历史；③ `_rollbackSurvivingEntities` 回滚 `createdTurn < fromTurn` 的"幸存"实体（读其 `turnNumber >= fromTurn` 的历史：有更早历史则恢复旧值，无则**直接 DELETE 该属性**）；④ 删除本会话 `turnNumber >= fromTurn` 的历史；⑤ 删除待删实体本身。

   **关键约束（否则破坏基线）**：`factual_attributes` 表**无 `createdTurn` 列**（只有 `updatedTurn`），属性能否在步骤 ③ 存活**只取决于其 `factual_memory_history` 的 `turnNumber`**。因此：
   - 投影基线属性**要么不写 `factual_memory_history`，要么历史 `turnNumber` 强制为 0**（与实体 `createdTurn=0` 对齐），使其不被步骤 ③/④ 命中删除。
   - 重定向产生的 `source=auto` delta 行用**各自独立 `attributeId` + 各自历史**，步骤 ③ 按 `(entityId, attributeId)` 分组回滚，只命中 delta、不误伤基线（两行模型本身兼容）。

### 8.3 待定细节（已定）

- **同卡多会话**：各生成独立实体（资源=模板，会话=实例，互不影响演化）。
- **世界书注入上限**：`known_entities` 仅注入 `constant=true` + 本轮命中的世界书词条，上限 20（默认），避免大世界书撑爆 prompt。
- **`sourceRef`**：实体留 `sourceRef`（nullable）指向资源表 `cardId`/`bookId`，服务详情展示 + 导出溯源（见 §8.1）。
- **isArchived 语义**：世界书 `disable`/`enabled=false` 映射 `isArchived=true` 时，记忆查看器应标注为「停用」而非「已归档（死亡/销毁）」。

## 9. 资源层数据模型与导入/应用流程

### 9.1 资源表（全局资源库）

沿用「模板管理」范式（`templates` 表 + Repository + 管理页），资源库**全局**、跨会话复用，存**完整原始 JSON**（无损，服务详情展示 + 将来导出）。

| 表 | 关键字段 | 说明 |
|---|---|---|
| `character_cards` | `cardId`(unique)、`name`、`rawJson`(完整卡 JSON)、`sourceFormat`(v1/v2/v3/json)、`createdAt`/`updatedAt` | 角色卡资源 |
| `worldbooks` | `bookId`(unique)、`name`、`rawJson`(完整书 JSON)、`createdAt`/`updatedAt` | 世界书资源（词条存 rawJson，按需解析） |

- `name` 为反规范化列（资源库列表展示用），其余展示字段（tags/creator/scenario 等 B 类）从 `rawJson` 解析。
- 内嵌世界书（角色卡 `character_book`）不拆分为独立 `worldbooks` 资源，随卡存于 `rawJson`，应用卡时一并投影。

### 9.2 投影层（会话内实体）

「应用」= 从资源表解析 → 投影到 `factual_entities`/`factual_attributes`（`source=worldbook/card`，只读基线），绑定 `sessionId`。投影即"会话级资源"。

- 角色卡 → `character` 实体 + 只读基线属性（A 类字段）；内嵌世界书 → `lore` 实体。
- 世界书 → 每个词条一个 `lore` 只读实体。
- 实体 `sourceRef` 指向 `cardId`/`bookId`（可追溯详情 + 导出）。
- 投影实体 `createdTurn = 0`（会话预置，非对话产生），避免被 `deleteFactsByTurns` 误删（§8.2）。

### 9.3 导入与应用流程

```
导入（全局资源库页）→ 解析 + 存资源表（rawJson）
        ↓
会话中「应用」（会话设置选角色卡/世界书）
        ↓
投影到该会话事实层（只读基线实体）
```

- **同卡多会话**：各生成独立实体，互不影响演化（§8.3）。
- **应用时机**：世界书可会话任意时刻追加应用；角色卡主要在新建会话时应用（中途应用遇同名实体的合并/拒绝规则见 §9.4 第 2 条）。入口复用 `session_settings_sheet`（推荐，待确认）。
- **投影原子性**：整卡/整书「全投影或全不」——任一词条/属性失败即整体回滚，不在会话留下半套只读实体。

### 9.4 实施前需定的方案（审查补充）

以下 🟡 项需在实施前明确，否则实现时会产生歧义或数据风险：

1. **v36 迁移序列**（AGENTS.md 要求保留用户数据）：① `ALTER TABLE` 加 `source`/`sourceRef` 列；② 回填存量行 `source='auto'`；③ `DROP INDEX idx_factual_attrs_entity_key`；④ 重建复合唯一索引 `(entity_id, attr_key, source)` + partial unique index `(entity_id, attr_key) WHERE source='auto'`；⑤ 建 `character_cards`/`worldbooks` 资源表。

2. **中途应用合并语义 + 属性级 source**：§9.3「卡遇同名实体合并基线到已有 auto 实体」会产生混合 source 的实体，实体级 `source` 无法描述。**只读性以属性级 `source` 为准**；需明确：世界书/卡与已有同名实体（`idx_factual_entities_session_name` 唯一）的合并 vs 拒绝规则；重复应用（同卡同书再次应用）的幂等性。

3. **资源删除级联**：删全局库的卡/书后，已投影实体 `sourceRef` 悬挂。~~规定：禁止删除（有投影时）/ 级联标记 / 仅断开（清空 `sourceRef`）。~~ **已定案（2026-08-23 F1+F' 两波落地）**：走「级联删除」——资源删除时在同一事务内清理所有会话中该 `sourceRef` 的投影（属性/历史/实体/FTS），与「取消应用」（`deleteEntitiesBySourceRef` 成组移除）同口径；删除确认弹窗向用户披露后果。原「仅断开 sourceRef」方案废弃（断开后投影成为永久孤儿：取消应用不可见、记忆库只读守卫不可删、key 阈值实体每轮强制注入）。

4. **selective/递归/probability/sticky-cooldown 的过注入**：`selective` 词条降级为主键单触发会**过度注入**（非欠注入），与注入上限叠加、行为偏离 SillyTavern。记录该行为差异（至少文档化，暂不实现 selective 逻辑）。

5. **向量落点**：事实层当前无 embedding 存储（仅经历层有）。世界书向量需明确存哪（新列 / 新表 / 路由经历层）。该项可选，可降级为仅 FTS5。

### 9.5 外部"打开方式/分享"导入（2026-08-14 新增）

移动端（微信等第三方应用）内的资源文件无法经系统文件选择器访问（私有目录），新增系统级接收入口，与应用内 FilePicker 导入共用同一套导入逻辑（`ResourceImportService`，§5.1 的解析防护不变、均无体积上限）：

- **Android**：`MainActivity` 注册 `ACTION_VIEW` + `ACTION_SEND` intent-filter（mime `image/png`、`application/json`）。原生侧将 content:// 复制到 `cacheDir/incoming/`（单槽），经 MethodChannel `lmstory/incoming_file` 交付（`onIncomingFile` 推送 + `getInitialFile` 冷启动兜底）。
- **iOS**：`Info.plist` 声明 `CFBundleDocumentTypes`（`public.png`/`public.json`）。`IncomingFilePlugin` 经插件生命周期 openURL 回调接收（文件在 tmp/Inbox），同一 channel 协议交付。
- **Dart 侧**：`IncomingImportListener` 包裹主布局（onboarding 完成后生效），收到文件 → 弹确认框（文件名 + 识别类型）→ 确认后 `importAuto` 导入 → snackbar 结果 → 清理临时文件。
- **JSON 自动识别**（仅外部入口；应用内导入仍按按钮区分类型）：顶层含 `entries`（字典/数组）→ 世界书；含 `spec`/`spec_v2`/`spec_version`/`data` 对象或非空 `name` → 角色卡（V2/V3 纯 JSON 卡）；均不匹配则报错。不能用「WorldbookParser 不抛错」判定世界书——它对无 `entries` 的 JSON 静默返回空列表。
- **已知取舍**：注册 `image/png` 后 LMStory 会出现在所有 PNG 的系统"打开方式"列表中（无法只筛含卡元数据的 PNG）。
