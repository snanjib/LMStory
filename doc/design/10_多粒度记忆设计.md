## v0.2.3 重构说明（2026-08-04）

> **本段落为 v0.2.3 宏摘要重构的纲领性说明，后续各章节已据此修订。**

v0.2.3 对宏摘要机制进行了**根本性重构**，核心变更如下：

1. **移除独立宏摘要阶段**：废弃 v1.0~v1.5 的 `macro_summarizing` 独立阶段（双触发机制 + MacroSummaryPhaseHandler 工具调用 + JSON 降级链），改由**压缩服务在压缩时生成分段宏摘要**。

2. **分离压缩摘要与宏摘要职责**：
   - **压缩摘要（累积式）**：基于"旧摘要 + 新对话"生成，用于上下文注入（稳定前缀），存 `chat_messages`（`is_summary=true`）。
   - **分段宏摘要（分段式）**：仅基于"新对话"实际内容生成，用于记忆检索 + 记忆查看器编年史，存 `experiential_memories`（`memory_level='macro'`）。

3. **首次压缩 vs 后续压缩**：
   - **首次压缩**：压缩摘要兼作宏摘要（`segmentMacroSummary=null`，用压缩摘要文本作为 macro 记忆内容），避免无意义的重复 LLM 调用。
   - **后续压缩**：并行生成两个摘要。分段宏摘要仅基于新增轮次的**实际对话**（排除草稿/审查内容），失败降级为 `null` 不阻塞压缩。

4. **importance 固定为 3**（非 LLM 决定），**移除 macroBoost 加权机制**。

5. **宏摘要参与语义检索**：正常权重参与检索（与微摘要平等），在检索输出中标注为**"段落摘要"**（区别于微摘要的**"事件记忆"**）。

6. **宏摘要与微摘要共存**：不做多粒度去重（移除 `parentEventIds` 关联去重逻辑）。

7. **提示词变更**：移除 `kMacroSummaryPrompt`，新增 `kIntermediateSegmentMacroPrompt`（严格限制：只总结实际发生的事件，禁止创造/续写）。

8. **配置变更**：移除 `MacroSummaryConfig` 配置类，`microVectorizeThreshold` 移至 `RetrievalConfig`。

> **废弃内容标记**：本文档各章节中，v1.0~v1.5 描述的"双触发机制""MacroSummaryPhaseHandler""macroBoost 加权""多粒度去重"等内容均已**废弃**，下文以重构后的新设计为准。

## 0. 文档定位

本文档定义中级模式（v0.2）的**多粒度记忆系统**--在现有"每轮一摘要"的基础上引入 micro/macro 双层结构，解决事件碎片化与空洞摘要污染检索的问题。

> **v0.2.3 重构后**：宏摘要不再由独立阶段生成，而是**由压缩服务在压缩时生成分段宏摘要**。压缩摘要（累积式，用于上下文注入）与分段宏摘要（分段式，用于记忆检索）职责分离。详见 §2。

**适用范围**：仅中级模式（故事模式）。Simple 模式无记忆系统，Advanced 模式有独立的事实层方案。

**与现有文档的关系**：
- 与 DOC-08 §3 经历检索不冲突，本文档是对经历层记忆粒度的增强
- 涉及 DOC-02 §6.2 `experiential_memories` 表结构变更（加字段，非破坏性）
- 涉及 DOC-09A-1 §3 检索算法（宏摘要正常权重参与检索，标注"段落摘要"）
- 涉及 DOC-09C §1 持久化时序（分段宏摘要由压缩服务入库，非独立阶段）
- 涉及 DOC-13 §5 压缩机制（分离压缩摘要与分段宏摘要）

## 1. 设计动机

### 1.1 现有问题

当前每轮对话产出一条 `EventSummary`，写入 `experiential_memories` 并向量化。实际使用暴露两类问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| 空洞摘要 | "主角走了一段路" "主角和 NPC 说了两句话" | 单轮对话信息量不足以产出有意义的摘要 |
| 事件碎片化 | 同一事件被切成多条记忆（"遇到 NPC" → "和 NPC 对话" → "NPC 给了任务"） | 缺乏事件边界识别，强制每轮一摘要 |

### 1.2 后果

- **向量质量差**：空洞摘要的向量语义模糊，检索召回率低
- **检索结果碎片化**：召回的都是片段，缺乏完整事件上下文
- **token 浪费**：低质量记忆占满 topK=5，挤掉真正有用的记忆

### 1.3 设计目标

- **不破坏 append-only**：经历记忆保持只追加不修改，保证可追溯性
- **事件聚合**：相邻同事件轮次能被聚合成一条高质量宏摘要
- **检索质量提升**：宏摘要信息密度高，优先召回能提供完整事件上下文
- **可控成本**：低重要性微摘要不向量化，省 embedding API 调用
- **可配置**：宏摘要功能可开关，关闭后退化为现有行为

## 2. 核心设计：micro/macro 双层记忆

### 2.1 双层结构

> **v0.2.3 重构**：宏摘要不再由独立阶段触发生成，而是**由压缩服务在压缩时生成分段宏摘要**。压缩摘要与分段宏摘要职责分离。

```
微摘要（micro）：每轮一条，append-only
  ├─ 信息量足够（importance >= microVectorizeThreshold）-> 向量化 + FTS5 索引
  └─ 信息量不足（importance < microVectorizeThreshold） -> 仅 FTS5 索引，不向量化

分段宏摘要（macro）：压缩时生成，新增一条独立记录
  ├─ memory_level = 'macro'
  ├─ importance = 3（固定，非 LLM 决定）
  ├─ tags = ['compaction', 'macro_summary']
  ├─ macro_trigger_reason = 'compaction'
  ├─ 始终向量化 + FTS5 索引
  └─ 独立 turn_number（使用压缩时最后一轮的轮次号）
```

### 2.2 压缩时生成分段宏摘要（v0.2.3 重构）

> **废弃**：v1.0~v1.5 的双触发机制（事件结束触发 + 固定轮次兜底）已废弃。

宏摘要的生成时机从"独立阶段条件触发"改为"压缩时由压缩服务统一生成"。压缩服务在执行压缩时，**分离生成两个摘要**：

| 摘要类型 | 生成方式 | 输入 | 用途 | 存储 |
|---------|---------|------|------|------|
| 压缩摘要（累积式） | 基于旧摘要 + 新对话 | 旧压缩摘要 + 被压缩的对话原文 | 上下文注入（稳定前缀） | `chat_messages`（`is_summary=true`） |
| 分段宏摘要（分段式） | 仅基于新对话实际内容 | 本次压缩新增轮次的实际对话（排除草稿/审查内容） | 记忆检索 + 记忆查看器编年史 | `experiential_memories`（`memory_level='macro'`） |

#### 首次压缩 vs 后续压缩

**首次压缩**（会话首次触发压缩，无旧摘要）：
- 压缩摘要兼作宏摘要
- `segmentMacroSummary = null`（不单独调用 LLM 生成分段宏摘要）
- 用压缩摘要的文本作为 macro 记忆的 `summary` 内容写入 `experiential_memories`
- 避免无意义的重复 LLM 调用（首次压缩时两个摘要的输入范围相同，输出会高度雷同）

**后续压缩**（会话已有旧压缩摘要）：
- 并行生成两个摘要（两个独立 LLM 调用，可 `Future.wait` 并发）
- 压缩摘要：输入 = 旧压缩摘要 + 新对话原文（累积式）
- 分段宏摘要：输入 = 仅本次新增轮次的**实际对话**（分段式，排除草稿/审查内容）
- 分段宏摘要生成失败 -> 降级为 `null`，**不阻塞压缩**（压缩摘要照常写入）

### 2.3 分段宏摘要覆盖范围

```
压缩触发（总占用 > compactionTriggerRatio）
  ↓
确定本次压缩覆盖的轮次范围：[上次压缩点 + 1, 当前最后一轮]
  ↓
分段宏摘要内容：仅对范围内实际发生的对话做总结
  ├─ 排除草稿（drafting/generating 阶段的中间产物）
  └─ 排除审查内容（reviewing 阶段的审查后缀等）
  ↓
分段宏摘要 turn_number = 范围内最后一轮的轮次号
分段宏摘要 importance = 3（固定）
分段宏摘要 tags = ['compaction', 'macro_summary']
分段宏摘要 macro_trigger_reason = 'compaction'
```

**关键约束**（`kIntermediateSegmentMacroPrompt` 严格执行）：
- **只总结实际发生的事件**，禁止创造、续写或推测
- 分段宏摘要是对"这一段对话中发生了什么"的客观总结，不是故事续写

## 3. 数据结构变更

### 3.1 `experiential_memories` 表新增字段

## 4. 提示词设计

### 4.1 EventSummary 结构扩展

`EventSummary` 实体新增 `eventEnded` 字段：

```dart
class EventSummary {
  final String summary;
  final int importance;
  final List<String> tags;
  final int turnNumber;
  final bool eventEnded;  // 新增：LLM 判断本轮事件是否结束
```

#### 4.1B EventSummary 扩展为 5W1E 6 字段

```dart
class EventSummary {

  final String? whenText;       // 5W1E - When：事件发生的时间/叙事时序
  final String? whereText;      // 5W1E - Where：事件发生的地点/场景
```

### 4.2 `extract_summary_prompt` 改造

> **v0.2.3 废弃**：以下"事件边界判断"指引原用于双触发机制的"事件结束触发"。双触发机制已废弃后，此指引不再用于宏摘要触发判断。提示词中的事件边界判断段落保留以避免破坏性变更，但不再驱动宏摘要生成。

现有 `kExtractSummaryToolPrompt` 增加事件边界判断指引：

```
【事件边界判断】
除生成摘要外，还需判断"本轮是否标志着当前事件结束"。
事件结束的判断标准：
- 当前事件的核心冲突已解决（如战斗结束、任务完成）
- 场景发生显著切换（如离开当前地点、时间跳跃）
- 对话主题转向全新话题

不要把"对话停顿"或"等待用户回应"误判为事件结束。
事件通常持续 3-7 轮，过短的事件边界判断会损害记忆聚合质量。
```

`kExtractSummaryToolDefinition` 的 parameters 新增 `event_ended` 字段：

```json
{
  "name": "extract_summary",
  "parameters": {
    "type": "object",
    "required": ["summary", "importance", "tags", "event_ended"],
    "properties": {
      "summary": {"type": "string"},
      "importance": {"type": "integer", "minimum": 1, "maximum": 5},
      "tags": {"type": "array", "items": {"type": "string"}},
      "event_ended": {"type": "boolean", "description": "本轮是否标志着当前事件结束"}
    }
  }
}
```

#### 4.2B kExtractSummaryToolPrompt 重写为 5W1E 多字段提取

v0.2 5W1E 改造中，`kExtractSummaryToolPrompt` 重写为 5W1E 多字段提取，引导 LLM 按新闻学 5W1E 框架结构化输出事件信息：

```
【事件结构化提取（5W1E）】
本轮对话的事件请按 5W1E 6 字段结构化提取，每个字段独立产出：

- when（时间）：事件发生的叙事时序（如"第三日黄昏"、"出发后两个时辰"）；若无明显时间标记，可填"叙事时间未标记"。
- where（地点）：事件发生的场景/地点（如"青云山脚"、"客栈大堂"）；若无明确地点，可填"地点未标记"。
- who（人物）：事件涉及的人物/角色（如"主角、青云宗长老"）；多个角色用顿号分隔。
- what（内容）：事件核心内容/动作（如"主角接受宗门考核并觉醒灵根"）；用一句话概括。
- significance（意义）：事件对剧情/角色的意义（如"主角正式踏入修仙之路，灵根觉醒引发宗门关注"）；若无显著意义，可填"无显著意义"。
- extra（补充）：情感、氛围、伏笔、未在上述字段中的关键细节；若无补充，可填空字符串。

【事件边界判断】
除生成 5W1E 6 字段外，还需判断"本轮是否标志着当前事件结束"。
事件结束的判断标准：
- 当前事件的核心冲突已解决（如战斗结束、任务完成）
- 场景发生显著切换（如离开当前地点、时间跳跃）
- 对话主题转向全新话题

不要把"对话停顿"或"等待用户回应"误判为事件结束。
事件通常持续 3-7 轮，过短的事件边界判断会损害记忆聚合质量。

【输出说明】
- summary 字段可选填（可为空字符串）；若 LLM 觉得需要一句话总结，可填入；否则留空。
- what 字段必填，作为事件核心标识。
```

`kExtractSummaryToolDefinition` 的 `parameters` 调整：

- `required` 改为 `["what", "tags", "importance", "event_ended"]`（`summary` 移至可选）
- `properties` 新增 5W1E 6 字段（when/where/who/what/significance/extra，均 `type: "string"`）

```json
{
  "name": "extract_summary",
  "parameters": {
    "type": "object",
    "required": ["what", "tags", "importance", "event_ended"],
    "properties": {
      "summary": {"type": "string", "description": "可选；事件一句话总结，可留空"},
      "when": {"type": "string", "description": "5W1E - When：事件发生的时间/叙事时序"},
      "where": {"type": "string", "description": "5W1E - Where：事件发生的地点/场景"},
      "who": {"type": "string", "description": "5W1E - Who：事件涉及的人物/角色"},
      "what": {"type": "string", "description": "5W1E - What：事件核心内容/动作"},
```

### 4.3 新增 `kIntermediateSegmentMacroPrompt`（v0.2.3 重构）

> **废弃**：v1.0~v1.5 的 `kMacroSummaryPrompt` + `kMacroSummaryToolDefinition`（工具调用 + JSON 降级链）已废弃。

v0.2.3 重构后，新增提示词常量 `kIntermediateSegmentMacroPrompt`（fieldKey: `intermediate_segment_macro_prompt`），用于**压缩时生成分段宏摘要**。

**核心约束**：只总结实际发生的事件，禁止创造/续写。

```
【当前任务：生成分段宏摘要】

你将收到一段对话中实际发生的内容（仅用户与角色的实际对话，不含草稿或审查中间产物）。
请对这段对话中实际发生的事件做客观总结，产出一条分段宏摘要。

【分段宏摘要要求】
1. 只总结实际发生的事件：严格基于输入内容，不得创造、续写或推测未发生的内容
2. 保留关键信息：人物、地点、关键道具、重要转折点不能丢失
3. 去除冗余：重复的描述、过渡性的废话可以省略
4. 信息密度高：分段宏摘要的语义应该比任何一条微摘要都更丰富
5. 长度控制：100-300 字

【严格禁止】
- 禁止续写故事
- 禁止创造输入中不存在的情节
- 禁止推测角色的心理活动或未发生的对话

【输出说明】
直接输出分段宏摘要正文，不需要调用工具或输出 JSON。

【对话输入】
{{segment_conversation}}
```

> **与旧 `kMacroSummaryPrompt` 的差异**：
> - 输入从"微摘要列表"改为"实际对话原文"（分段宏摘要基于原始对话而非微摘要二次加工）
> - 移除工具调用（`macro_summary` 工具定义）和 JSON 降级链，改为直接输出纯文本
> - 移除 importance/tags 的 LLM 判断（importance 固定为 3，tags 固定为 `['compaction', 'macro_summary']`）
> - 新增"严格禁止创造/续写"约束

#### 4.3B 宏摘要保持 summary 单字段（不采用 5W1E）

**重要决策**：5W1E 改造中，宏摘要（含 v0.2.3 分段宏摘要）**保持 `summary` 单字段结构，不采用 5W1E**。

| 维度 | 微摘要（micro） | 宏摘要（macro） |
|------|----------------|----------------|
| 提示词输出结构 | 5W1E 6 字段 | `summary` 单字段 |
| DB 持久化 | 5W1E 6 字段各列填值 + `summary` 可空 | `summary` 填正文，5W1E 6 字段填空字符串（`''`） |
| FTS5 索引 | 7 内容字段都有值 | 仅 `summary` 有值，5W1E 6 字段为空字符串 |
| Embedding 向量化对象 | 5W1E 6 字段拼接文本 | `summary` 单字段 |

**决策理由**：

1. **宏摘要是事件聚合的高层摘要**，本身已对若干微摘要做了整体总结，`summary` 字段信息密度足够，无需再用 5W1E 拆分
2. **避免结构错位**：宏摘要的 5W1E 字段需要对多个微摘要的 5W1E 字段做"再聚合"（如多个 `when` 取哪个？多个 `who` 怎么合并？），引入不必要的复杂度且语义不清
3. **保持宏摘要的"高层视角"特性**：宏摘要是"事件主线"级别的总结，应当比微摘要更抽象，而非平行结构
4. **接口一致性**：宏摘要的 5W1E 6 字段在 DB 中填空字符串，保持 `ExperientialMemory` 实体接口统一，避免下游消费方（Repository/检索/上下文组装）需要按 `memoryLevel` 分支处理字段

> **持久化约定**：宏摘要的 `summary` 字段写入 LLM 产出的正文；`when_text`/`where_text`/`who_text`/`what_text`/`significance`/`extra` 6 列均写入空字符串（`''`），不写 `null`（便于 FTS5 INSERT 时所有内容字段都有非 NULL 值）。

### 4.4 UI 集成（提示词模板列表）

`intermediate_segment_macro_prompt` 接入"故事模式设置 -> 提示词模板"列表，作为第 9 段活跃提示词。改动清单：

## 5. 检索策略

### 5.1 宏摘要正常权重参与检索（v0.2.3 重构）

> **废弃**：v1.0~v1.5 的 macroBoost 加权机制（`finalScore += macroBoost`）已废弃。宏摘要与微摘要**平等参与检索**，正常权重打分。

`ExperienceRepositoryImpl.searchExperiences` 改造：

```
检索流程（v0.2.3 + 多粒度）：
  ├─ FTS5 通道：WHERE memory_level IN ('micro', 'macro')（两路都参与）
  ├─ Vector 通道：WHERE has_embedding=1 AND memory_level IN ('micro', 'macro')（两路都参与）
  ├─ 合并打分（正常权重，无 macro 加权）
  └─ 宏摘要与微摘要平等竞争 topK 名额
```

### 5.2 检索输出标注

宏摘要与微摘要在检索输出中通过**标注区分**，便于 LLM 理解记忆类型：

| 记忆类型 | memory_level | 检索输出标注 | 语义 |
|---------|-------------|-------------|------|
| 微摘要 | `micro` | **事件记忆** | 单轮事件的细节记录 |
| 分段宏摘要 | `macro` | **段落摘要** | 一段对话的事件总结 |

> **标注用途**：检索结果注入上下文时，每条记忆前缀标注其类型（如"[段落摘要] ..." / "[事件记忆] ..."），帮助 LLM 区分"高层总结"与"细节记录"。

### 5.3 宏摘要与微摘要共存（v0.2.3 重构）

> **废弃**：v1.0~v1.5 的多粒度去重逻辑（`parentEventIds` 关联去重，保留 macro 丢弃 micro）已废弃。

v0.2.3 后，宏摘要与微摘要**共存**，不做去重：

- 同一事件的宏摘要和微摘要可能同时被召回，**两者都保留**
- 宏摘要提供"事件主线视角"，微摘要提供"细节视角"，两者互补而非冗余
- 移除 `IntermediateContextBuilder._formatMemories` 中的去重逻辑

**理由**：分段宏摘要基于"实际对话"生成，微摘要基于"5W1E 结构化提取"生成，两者信息维度不同。共存比去重更能提供丰富的检索上下文。

## 6. 状态机与触发逻辑

### 6.1 宏摘要生成阶段（新增）

在现有四步生成流程后追加第五步 `macro_summarizing`：

```
drafting → extracting → retrieving → revising → summarizing → persisting → [macro_summarizing] → idle
                                                                       ↑
                                                              新增阶段（条件触发）
```

**触发判断**（在 persisting 完成后）：

```dart
Future<void> _maybeRunMacroSummary(RoundContext round) async {
  if (!round.config.memory.macroSummary.enabled) return;
  
  final lastMacroTurn = await _repo.getLastMacroTurnNumber(round.sessionId);
  final roundsSinceMacro = round.turnNumber - (lastMacroTurn ?? 0);
  
  // 双触发判断
  final eventEndTrigger = round.eventSummary.eventEnded;
  final roundLimitTrigger = roundsSinceMacro >= round.config.memory.macroSummary.triggerRoundLimit;
  
  if (!eventEndTrigger && !roundLimitTrigger) return;
  
  // 进入 macro_summarizing 阶段
  state = state.copyWith(phase: IntermediatePhase.macroSummarizing);
  
  // 收集范围内的微摘要
  final microSummaries = await _repo.getMicroSummariesInRange(
    sessionId: round.sessionId,
    fromTurn: (lastMacroTurn ?? 0) + 1,
    toTurn: round.turnNumber,
  );
  
  // 边界情况：范围内只有 1 条微摘要 → 跳过（无聚合价值）
  if (microSummaries.length < 2) return;
  
  // 调用 LLM 生成宏摘要
  final macroSummary = await _macroSummaryHandler.run(
    ctx: round,
    microSummaries: microSummaries,
  );
  
  // 持久化宏摘要
  await _repo.appendMacroExperience(
    sessionId: round.sessionId,
    summary: macroSummary.summary,
    importance: macroSummary.importance,
    tags: macroSummary.tags,
    turnNumber: round.turnNumber,
    parentEventIds: microSummaries.map((m) => m.memoryId).toList(),
    triggerReason: eventEndTrigger ? 'event_end' : 'round_limit',
  );
}
```

#### 6.1B 宏摘要持久化补 5W1E 空字符串

v0.2 5W1E 改造中，`appendMacroExperience` 接口扩展 5W1E 6 字段参数，宏摘要调用时 6 字段均传空字符串以保持接口一致性：

```dart
// 持久化宏摘要
await _repo.appendMacroExperience(
  sessionId: round.sessionId,
  summary: macroSummary.summary,         // 宏摘要正文
  importance: macroSummary.importance,
  tags: macroSummary.tags,
  turnNumber: round.turnNumber,
  parentEventIds: microSummaries.map((m) => m.memoryId).toList(),
  triggerReason: eventEndTrigger ? 'event_end' : 'round_limit',
  // 5W1E 6 字段填空字符串（宏摘要不采用 5W1E，保持接口一致性）
  whenText: '',
  whereText: '',
  whoText: '',
  whatText: '',
  significance: '',
  extra: '',
);
```

> **FTS5 INSERT 同步处理**：宏摘要的 `memories_fts` 行 5W1E 6 字段列均填空字符串（`''`），仅 `summary` 列有内容。微摘要的 `memories_fts` 行 7 内容字段均填实际值。

### 6.2 失败降级

## 7. 配置项设计

### 7.1 配置节点

记忆检索门槛位于 `assets/configs/default_config.json` 的 `intermediate.retrieval` 节点。v0.2.3 宏摘要重构删除了原 `intermediate.memory.macro_summary` 容器，`micro_vectorize_threshold` 搬到 retrieval 组；v0.2.2（2026-08-13）恢复了对应的 UI 入口（见 §7.4）。

```json
{
  "intermediate": {
    "retrieval": {
      "importance_storage_threshold": 3,
      "micro_vectorize_threshold": 4
    }
  }
}
```

### 7.2 配置项说明

| 配置项 | 类型 | 默认值 | 说明 |
|--------|------|--------|------|
| `importance_storage_threshold` | int | 3 | 存储索引门槛：importance 低于此值的记忆不建 FTS5 索引（无法检索），仍保留原始记录供后续批量提炼。设为 0 禁用门槛 |
| `micro_vectorize_threshold` | int | 4 | 向量化门槛：importance >= 此值才生成 embedding 语义向量；介于两门槛之间仅建 FTS5 |

### 7.3 配置类定义

门槛字段属于 `RetrievalConfig`（非已删除的 `MacroSummaryConfig`）：

```dart
class RetrievalConfig {
  final int importanceStorageThreshold; // 默认 3
  final int microVectorizeThreshold;    // 默认 4
  // ... 其他检索字段
}
```

### 7.4 UI 配置入口

门槛设置接入「故事模式设置 → 工具与记忆」子页，由 `IntermediateVectorizeThresholdSection` 组件承载，包含两个 1-5 分滑块：

- 存储索引门槛（Slider 1-5，默认 3）
- 向量化门槛（Slider 1-5，默认 4）

纳入低分（如 2 分）记忆需同时调低两个门槛（存储门槛 ≤ 向量化门槛）。

> **历史**：v0.2.3 宏摘要重构删除承载此阈值的 `MacroSummaryConfig`/`IntermediateMemorySection` 容器，阈值参数保留并搬到 retrieval 组但未重建 UI；v0.2.2 恢复该入口。

## 8. 微摘要向量化策略（两级门槛）

persisting 阶段按 importance 分级：

```
importance < importanceStorageThreshold (3)                       → 不建索引、不向量化（仅留原始记录）
importanceStorageThreshold (3) <= i < microVectorizeThreshold (4) → 仅 FTS5 索引
importance >= microVectorizeThreshold (4)                         → 向量化 + FTS5 索引
```

### 8.1 决策理由

- importance=3 的微摘要通常是过渡性事件（"主角走了一段路"），独立向量化意义不大，但建 FTS5 索引保留关键词检索能力
- importance>=4 的微摘要通常是关键事件细节（"主角觉醒灵根"），值得独立向量化以便精细语义检索
- importance<3 的低分记忆留给批量记忆提炼（memory_consolidator）后续合并为高 importance 记忆再建索引

门槛可在「设置 → 工具与记忆」调整（见 §7.4）。

## 9. 持久化时序

### 9.1 宏摘要持久化流程

```
macro_summarizing 阶段完成
  ↓
[drift transaction]
  1. appendMacroExperience → experiential_memories
     - memory_level = 'macro'
     - parent_event_ids = JSON 数组
     - macro_trigger_reason = 'event_end' | 'round_limit'
     - has_embedding = false（先写入）
  2. 调用 EmbeddingService.embed(macroSummary.summary) → Float32List
  3. updateEmbedding → 写 BLOB + has_embedding=true
  4. insertFtsIndex → memories_fts
  5. （可选）UPDATE chat_sessions.last_macro_turn
[COMMIT/ROLLBACK]
```

### 9.2 与微摘要持久化的关系

- 微摘要持久化在 `summarizing` → `persisting` 阶段完成（不变）
- 宏摘要持久化在 `persisting` → `macro_summarizing` 阶段完成（新增）
- 两者独立事务，互不影响

### 9.3 时序图

```
T1: drafting 完成
T2: extracting 完成
T3: retrieving 完成
T4: revising 完成
T5: summarizing 完成 → EventSummary{eventEnded: true}

T7: 判断触发条件 → 满足
T8: macro_summarizing 开始 → 收集微摘要 → LLM 调用 → 宏摘要入库
T9: idle
```

## 10. 边界情况处理

| 场景 | 处理 |
|------|------|
| 宏摘要功能关闭（`enabled=false` 或 `mode="off"`） | 跳过整个 macro_summarizing 阶段，行为同现状 |
| 宏摘要 LLM 调用失败 | 记录日志，不阻塞对话，下一轮重新判断触发 |
| 宏摘要向量化失败 | 降级为 `has_embedding=false`，仅 FTS5 索引（与微摘要降级逻辑一致） |
| 范围内只有 1 条微摘要 | **跳过宏摘要生成**（无聚合价值，等下一轮触发时再聚合） |
| 范围内微摘要全部 importance < 3 | 仍然生成宏摘要（聚合后 importance 由 LLM 综合判断） |
| 用户快速连续发消息（宏摘要未完成） | 宏摘要同步阻塞期间用户无法发消息（与 summarizing 阶段一致） |
| 重新生成回复 | 重新触发 summarizing，若 `eventEnded` 变化则重新判断宏摘要触发 |

## 12. 风险评估

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| LLM 误判事件边界（过早/过晚结束） | 宏摘要质量下降 | 固定轮次兜底（5 轮）兜住过晚；提示词强调"对话停顿 ≠ 事件结束"防过早 |
| 宏摘要 LLM 调用增加延迟 | 用户等待时间 +2-5s | 同步阻塞是用户选择（可关闭）；后续可扩展异步模式 |
| 宏摘要与微摘要同时被召回 | token 浪费 | 检索结果去重逻辑（§5.3） |
| 范围内微摘要过多导致宏摘要输入超长 | LLM 输入截断 | 范围超过 7 轮时截断（只取前后各 3 轮 + 中间摘要） |
| schemaVersion 变更影响测试 | 测试数据库重建 | dev 阶段覆盖式重建，无影响 |

## 13. 与事实层（DOC-11）的关系

多粒度记忆系统（本文档）与事实层中间方案（DOC-11）是**两个独立的增强**：

- **多粒度记忆**：解决"经历层记忆粒度问题"（事件碎片化、空洞摘要）
- **事实层**：解决"设定漂移问题"（角色改名、品种写错）

两者可独立实施，互不依赖。建议按用户决策的节奏：先实施多粒度记忆（本文档），稳定后再实施事实层（DOC-11）。
