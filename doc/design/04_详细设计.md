## 1. 关键功能流程图

### 1.1 Simple 模式消息发送流程（v0.1）

> **Controller 职责委托**：以下流程中，步骤 5 由 SettingsResolver 委托执行（解析运行时配置），步骤 3-4 和步骤 6-7 由 StreamManager 管辖的辅助类执行（压缩检查、上下文构建、流式发送），BranchManager 在此流程中不参与（仅在 Fork/Regenerate 流程中参与）。Controller 为对外统一入口，内部委托给各管理器。

```
用户点击发送
    │
    ▼
ChatModeController.sendMessage(userInput)
    │
    ├── 1. 压缩检查（阻塞式，在用户消息插入前触发，对标 ChatBox）
    │   │
    │   ▼
    │   CompactionDetector.needsCompaction(sessionId)?
    │   │
    │   ├── 否 → 跳过
    │   │
    │   └── 是 → CompactionExecutor.runCompaction()
    │       │
    │       ├── 1a. 获取当前上下文消息
    │       ├── 1b. 调用 LLM 生成摘要（流式）
    │       ├── 1c. 创建 summaryMessage (isSummary=true)
    │       ├── 1d. 找到 boundaryMessage
    │       ├── 1e. 创建 CompactionPoint
    │       └── 1f. 写入 DB（messages + compaction_points）
    │
    ├── 2. 创建 user Message 对象
    ├── 3. 追加到 ChatState.messages（内存）
    │
    ├── 4. 构建上下文消息列表
    │   │
    │   ▼
    │   ContextBuilder.buildContext(sessionId)
    │   │
    │   ├── 4a. 加载最新 CompactionPoint
    │   ├── 4b. 截取 boundary 之后的消息
    │   ├── 4c. 在前面插入 summaryMessage
    │   ├── 4d. 确保 system 消息在开头
    │   └── 4e. 返回 List<Message>
    │
    ├── 5. SettingsResolver 解析运行时配置
    │   └── resolve(sessionSettings, globalDefaults, preset)
    │
    ├── 6. StreamManager.dispatchSend(messages, settings)
    │   │
    │   ▼
    │   ChatRemoteDS.streamChat(messages, settings)
    │   │
    │   ├── HttpClient 发起 SSE 请求（含 stream_options.include_usage=true）
    │   └── SseParser 逐行解析
    │       │
    │       ├── onTextDelta → 更新 ChatState.streamingContent（含思考标签解析，首次计算 firstTokenLatency）

    │       ├── onStreamEnd(usage) → 进入步骤 7（携带 SseUsage，含 totalTokens 等）
    │       └── onError → 更新 ChatState.error
    │
    └── 7. 流结束处理
        ├── 7a. 创建 assistant Message 对象（含 modelName）
        ├── 7b. 写入 tokensUsed（来自 usage.totalTokens）、firstTokenLatency（来自 _streamStartTime 差值）
        ├── 7c. 一次性持久化 user + assistant 消息到 DB
        ├── 7d. 回填 dbId 到内存对象
        ├── 7e. 清除 ChatState.streamingContent
        └── 7f. 更新 session.lastActiveAt / messageCount
```

### 1.3 上下文压缩流程（Simple 模式）

```
sendMessage() 开头触发压缩检查（用户消息插入前，对标 ChatBox 阻塞式压缩）
    │
    ▼
CompactionDetector.needsCompaction(sessionId)
    │
    ├── 获取 contextWindow（模型缓存的 contextWindow 字段；未知时使用默认值 96000，对标 ChatBox DEFAULT_CONTEXT_WINDOW）
    ├── 计算 availableWindow = max(contextWindow - 32000, floor(contextWindow × 0.5))
    ├── 计算 thresholdTokens = floor(availableWindow × compactionThreshold)
    ├── 估算 currentTokens（从缓存聚合）
    │
    └── currentTokens > thresholdTokens ?
        │
        ├── 否 → 返回 false
        │
        └── 是 → 返回 true
            │
            ▼
CompactionExecutor.runCompaction(sessionId, force: false)
    │
    ├── 防重入检查（ongoingCompactions Set）
    │
    ├── 获取当前上下文消息
    │   └── ContextBuilder.buildContext(sessionId)
    │
    ├── 调用 LLM 生成摘要
    │   │
    │   ▼
    │   SummaryGenerator.generate(messages, fastModel)
    │   │
    │   ├── 组装 prompt: messages + "请为以下对话生成详细摘要..."
    │   ├── 使用快速模型（非会话模型）
    │   ├── 流式生成
    │   └── 清除 <think>...</think> 标签
    │
    ├── 创建 summaryMessage
    │   └── Message(role: assistant, content: summary, isSummary: true)
    │
    ├── 确定 boundaryMessage
    │   └── messages 中最后一条 isSummary=false 的消息
    │
    ├── 创建 CompactionPoint
    │   └── { summaryMessageId, boundaryMessageId, createdAt }
    │
    └── 写入 DB
        ├── 插入 summaryMessage 到 chat_messages
        └── 插入 CompactionPoint 到 compaction_points
```

> **压缩时机**：自动压缩在 `sendMessage` 开头触发（用户消息插入前），而非 `_sendToApi` 中（用户消息插入后）。
> 确保上下文顺序为「摘要 → 用户消息 → AI 回复」。`contextWindow` 未知（null）时不触发自动压缩。
> `compactionThreshold` 为百分比（0.4-0.9，默认 0.6），对标 ChatBox `compactionThreshold`，非绝对 token 数。
>
> **流式路径统一**：自动压缩与手动压缩均走 `compactWithStream` 流式路径——`shouldCompact` 预检阈值后委托 `_compressHistoryCore` 执行占位摘要 → SSE 流式打字 → 落库的核心逻辑。两条路径在 UI 侧均通过 `_CompactionSummaryCard` 横幅实时展示流式生成过程，无需非流式 `http.post` 调用。

### 1.4 分支（Fork）创建流程

#### 1.4.1 regenerateInNewFork — 重新生成（新分支）

```
用户点击 Regenerate 按钮（assistant 消息上）
    │
    ▼
ChatModeController.regenerateInNewFork(assistantMessageId)
    │
    ├── 1. 找到助手消息的锚点用户消息（parentUserMsgId）
    │   └── 如果找不到 → 设置 error 并返回
    │
    ├── 2. cancelSending()  ← 取消当前流式
    │
    ├── 3. 收集尾部消息 tailMessages = _getTailMessages(anchorUserMsgId)
    │   └── 锚点处的助手消息 + 之后所有消息
    │
    ├── 4. addAssistantBranchAndSnapshot() 保存快照并创建新分支
    │   ├── 将 tailMessages 保存为当前活跃分支的 JSON 快照
    ├── 从 chat_messages 表删除 tailMessages
    │   └── chat_session_branches: branch_count++, 返回 newBranchIndex
    │
    ├── 5. 记录 _pendingForkRollback（用于失败回滚）
    │   └── _ForkRollbackInfo(anchorUserMsgId, branchIndex, originalContent: null)
    │
    ├── 6. 截断消息列表到锚点用户消息（含）
    │   └── state.messages = messages.sublist(0, anchorIndex + 1)
    │
    └── 7. _sendToApi(userMessage, branchIndex: newBranchIndex)
        └── 流式成功 → 清除 _pendingForkRollback
        └── 流式失败 → _rollbackForkIfNeeded() 回滚分支记录
```

```
用户编辑用户消息并点击 Save & Resend

    ▼
ChatModeController.editAndResendInNewFork(userMessageId, newContent)

    ├── 1. cancelSending()  ← 取消当前流式
    │
    ├── 2. 原地更新用户消息内容（记录原文以便失败回滚）
    │   ├── originalContent = userMessage.content

    │
    ├── 3. 收集尾部消息 tailMessages = _getTailMessages(userMessageId)
    │   └── 锚点处的助手消息 + 之后所有消息
    │

    │   ├── 将 tailMessages 保存为当前活跃分支的 JSON 快照

    │   └── chat_session_branches: branch_count++, 返回 branchIndex
    │

    │   └── _ForkRollbackInfo(anchorUserMsgId, branchIndex, originalContent)

    ├── 6. 截断消息列表到编辑后的用户消息（含），更新内容

#### 1.4.3 Fork 操作回滚流程

```
流式 API 失败（_handleStreamError 或 _sendToApi catch）
    │
    ▼
_rollbackForkIfNeeded()
    │
    ├── 1. 读取 _pendingForkRollback（若为空则直接返回）
    │
    ├── 2. removeForkBranchWithSnapshot(sessionId, anchorUserMsgId, branchIndex, [])
    │   ├── 删除新创建的分支（活跃分支）
    │   └── 自动从快照恢复旧分支消息到 chat_messages 表
    │
    ├── 3. 若 originalContent 非空（仅 editAndResend 场景）
    │   └── updateMessageContent(userMessageId, originalContent) 恢复用户消息原文
    │
    └── 4. 重新加载消息列表 + 刷新 ForkAnchor
```

### 1.5 记忆混合检索流程（v0.2）

> **v0.3 完整设计**（待实施）。v0.2 中间方案的检索流程是"FTS5 + Vector 双路 0.5/0.5 混合"（无 Temporal 维度），事实层检索独立执行（关键实体+关键词命中匹配，详见 DOC-09A-1 §3.11）。本节的"FTS5 + Vector + Temporal 三路 0.5/0.3/0.2 混合"是 v0.3 完整设计。v0.3 启动时需要决定是否启用 Temporal 维度，详见 DOC-03 §4.1 事实层落地状态说明。

```
PromptAssembler 需要检索经历类记忆
    │
    ▼
MemoryRepository.hybridSearch(sessionId, query, topK: 10)
    │
    ├── 并行执行两个检索通道
    │   │
    │   ├── FTS5 全文检索（主通道）
    │   │   │
    │   │   ▼
    │   │   SELECT summary, memory_id FROM memories_fts
    │   │   WHERE memories_fts MATCH ? AND session_id = ?
    │   │   ORDER BY rank LIMIT topK × 2
    │   │   │
    │   │   └── 返回 List<FTS5Result> { memoryId, summary, fts5Score }
    │   │
    │   └── 向量语义检索（补充通道）
    │       │
    │       ▼
    │       VectorEngine.search(queryEmbedding, topK: topK × 2)
    │       │
    │       └── 返回 List<VectorResult> { memoryId, summary, vectorScore }
    │
    ├── 结果合并与评分
    │   │
    │   ▼
    │   对每个唯一 memoryId:
    │   │
    │   ├── fts5Score = FTS5 结果归一化 (0~1)，无则 0
    │   ├── vectorScore = 向量结果归一化 (0~1)，无则 0
    │   ├── temporalScore = 计算（见 1.5.1）
    │   │
    │   └── finalScore = fts5Score×0.5 + vectorScore×0.3 + temporalScore×0.2
    │       │
    │       └── 如果 importance >= 4 → finalScore × 1.5
    │
    ├── 按 finalScore 降序排序
    ├── 取 topK 条
    ├── 过滤 is_archived=true 的非摘要事件
    │
    └── 返回 List<ExperientialMemory>
```

#### 1.5.1 时序相关性评分算法

```
temporalScore(memory, currentTurnNumber, queryNarrativePeriod):
    │
    ├── 时段匹配分 (periodMatchScore):
    │   if memory.narrativePeriod == queryNarrativePeriod → 1.0
    │   elif memory.narrativePeriod 相邻 → 0.5
    │   else → 0.0
    │
    ├── 时序邻近分 (recencyScore):
    │   maxTurns = 当前会话最大 turn_number
    │   recencyScore = 1.0 - (maxTurns - memory.turnNumber) / maxTurns
    │   // 越近越高，线性衰减
    │
    └── temporalScore = periodMatchScore × 0.6 + recencyScore × 0.4
```

> **"相邻时段"判定规则**：比较 turn_number 间隔。若两条记忆的 turn_number 差值 ≤ 5 且 narrative_period 不同，视为相邻时段。此规则为启发式方法，未来可考虑让 LLM 在 update_world 中填充时段序号以实现更精确的相邻判定。

### 1.6 记忆折叠流程（v0.2）

```
经历类记忆数 > consolidationThreshold (默认 500)
    │
    ▼
ConsolidationUseCase.execute(sessionId)
    │
    ├── 1. 选择候选
    │   └── importance < 4 AND is_archived = false
    │       ORDER BY importance ASC, turn_number ASC
    │
    ├── 2. 按 narrative_period 分组
    │   │
    │   └── Map<String, List<ExperientialMemory>>
    │       "修炼第一天" → [m1, m2, m3]
    │       "修炼第三天" → [m4, m5, m6, m7]
    │       ...
    │
    ├── 3. 过滤：仅对 ≥3 条的组执行折叠
    │
    ├── 4. 对每组调用 LLM 生成摘要
    │   │
    │   ▼
    │   for each group:
    │   │
    │   ├── 组装 prompt:
    │   │   "请将以下事件摘要为一条简洁的总结：
    │   │    - [修炼第一天·清晨] 进入迷雾森林
    │   │    - [修炼第一天·午后] 击杀狼型魔物
    │   │    - [修炼第一天·黄昏] 遭遇哥布林袭击"
    │   │
    │   ├── 调用 LLM（快速模型）
    │   │
    │   ├── 成功 →
    │   │   ├── 创建摘要事件 (is_summary=true, archived_event_ids=[...])
    │   │   ├── 标记原事件 is_archived=true
    │   │   └── 从 FTS5 删除原事件，插入摘要事件
    │   │
    │   └── 失败 →
    │       ├── 保留原事件不折叠
    │       └── 记录日志，下次重试
    │
    └── 5. 返回折叠统计（折叠组数、保留组数、失败数）

### 1.13 手动压缩流程

> **v0.1 实际实现差异**：原始设计使用 CompactionExecutor + ChatState.isCompacting + 确认弹窗 + 流式摘要进度。
> v0.1 实际实现为流式压缩 + 常驻失败卡片 + 防抖锁 + 标题更新弹窗，不再使用 SnackBar 反馈。

```
用户点击聊天菜单（_showChatMenu）中的"压缩上下文"选项
    │
    ├── 1. 前置检查（ChatModeController.compressHistory）
    │   ├── 若 isCompressing == true → 返回 CompressResult.busy（菜单项已禁用，防御性）
    │   ├── 若 isSending || isStreaming → 返回 CompressResult.busy
    │   └── 若非摘要消息数 < 2 → 返回 CompressResult.insufficient
    │
    ├── 2. 设置防抖锁 state.isCompressing = true（菜单项禁用）
    │
    ├── 3. 创建占位摘要消息（placeholderId）
    │   ├── role: 'system', isSummary: true, content: ''
    │   ├── 写入 DB（addMessage）
    │   └── 设置 state.currentCompactionSummaryId = placeholderId
    │       （UI 据此渲染流式生成状态：折叠态显示"正在生成摘要..." + 小窗预览 + 闪烁光标）
    │
    ├── 4. 流式压缩（CompactionService.compactWithStream）
    │   ├── 解析 SummaryConfig（resolveSummaryConfig，失败调 onError）
    │   ├── CompactionStreamer.stream 发起 SSE 请求
    │   │   ├── onTextDelta: 增量更新 DB（updateMessageContent）+ state（打字效果）
    │   │   ├── onComplete: 写入 tokensUsed（updateMessageTokensUsed）+ 创建 CompactionPoint
    │   │   └── onError: 写入 error（updateMessageError），保留已生成 content
    │   └── 每个回调后 _loadMessages() 刷新 UI
    │
    ├── 5. 释放防抖锁 state.isCompressing = false + state.currentCompactionSummaryId = null（finally 块）
    │
    └── 6. 返回 CompressResult
        ├── success: UI 弹窗询问"是否用新摘要更新会话标题？"
        │   ├── 用户确认 → updateTitleFromSummary(force: true) → _autoNameSession
        │   └── 用户取消 → 保持原标题
        ├── busy: 静默处理（菜单已禁用）
        ├── insufficient: SnackBar 提示"压缩失败"（消息不足）
        └── failed: 失败卡片已作为常驻消息插入对话流，无需额外提示

失败卡片交互（CompactionFailedCard，对标 ChatBox 但改为常驻卡片）：
    ├── 视觉：error tint 背景（alpha 0.06）+ error 色全边框（alpha 0.25），禁用侧边条
    ├── 顶部：error_outline 图标 + "压缩失败"标题 + 关闭按钮（IconButton）
    ├── 中部：错误信息 + 已生成的部分摘要（SimpleMarkdownBody 渲染）
    ├── 底部：重试按钮（TextButton.icon，error 色）
    ├── 重试 → retryCompaction: 删除失败摘要 → 重新触发 compressHistory
    └── 关闭 → deleteFailedSummary: 删除失败摘要消息（无 CompactionPoint，安全）
```

**自动压缩失败冷却机制**（v0.1 bug 修复新增）：

`_compressHistoryCore` 维护 `ChatModeController._lastCompactionFailureTime` 字段，
用于避免 402（配额耗尽）/ 网络错误等场景下，自动压缩在每条消息发送时重复触发
导致的连续报错（用户反馈："发消息触发压缩连续报错 402"）。

```
sendMessage() 自动压缩触发点
    │
    ▼
检查 _lastCompactionFailureTime
    │
    ├── null（最近无失败）或 距上次失败 ≥ 60 秒 → 正常走 shouldCompact → _compressHistoryCore
    │
    └── 距上次失败 < 60 秒（冷却期内）→ 跳过自动压缩，仅记 warn 日志
        └── 用户消息照常发送（不阻断），用户可通过手动压缩按钮（compressHistory）绕过冷却
```

- **冷却时长**：60 秒（`_compactionFailureCooldown` 常量）
- **失败时**：`onError` 回调 / `CompactionException` catch / 通用 catch 三处均记录 `_lastCompactionFailureTime = DateTime.now()`
- **成功时**：`_compressHistoryCore` 正常返回前清空 `_lastCompactionFailureTime = null`
- **手动压缩不受冷却约束**：`compressHistory()` 和 `retryCompaction()` 直接调用 `_compressHistoryCore()`，用户主动重试总是允许

### 1.14 切换分支流程

```
用户点击分支指示器的左右箭头（如 "1/3 ◀ ▶"）
    │
    ▼
ChatModeController.switchFork(anchorUserMsgId, direction)
    │
    ├── 1. 查找 ForkAnchor（parentUserMsgId == anchorUserMsgId）
    │   └── 若找不到 → 直接返回
    │
    ├── 2. 循环计算新分支索引（使用 branchCount 作为 total）
    │   ├── next: (activeIndex + 1) % branchCount
    │   └── prev: (activeIndex - 1 + branchCount) % branchCount
    │
    ├── 3. 收集当前尾部消息（锚点之后的所有消息）
    │
    ├── 4. switchForkBranchWithSnapshot(sessionId, anchorUserMsgId, newActiveIndex, currentTailMessages)
    │   ├── 当前尾部消息存入当前分支快照
    │   ├── 从目标分支快照反序列化消息
    │   ├── 删除 chat_messages 表尾部，插入目标分支消息
    │   └── 更新 active_branch_index，返回新消息列表
    │
    └── 5. 更新 state.messages = [...锚点之前, ...新分支消息] + _refreshForkAnchors()
```

> **循环切换**：到头不停止，而是循环到另一端。例如 3 个分支时，从第 3 个点 next 会回到第 1 个。使用 `ForkAnchor.branchCount` 作为 total。

> **类名说明**：流程图中引用的 `CompactionDetector`、`CompactionExecutor`、`ContextBuilder`、`SummaryGenerator` 为 Chat 子系统内部的辅助类，属于 StreamManager 管辖范围。其接口定义将在接口设计文档（DOC-05）中详细规定。

#### 2.1.12 ScrollPositionCache（v0.1 实际实现新增）

```dart
/// 滚动位置 LRU 缓存（纯内存，不持久化）
/// 切换会话时保存/恢复滚动偏移量
class ScrollPositionCache {
  static const int maxEntries = 100;
  final _cache = <String, double>{}; // sessionId → scrollOffset（默认 LinkedHashMap，保持插入顺序）。reverse 列表坐标系：0 = 底部/最新，maxScrollExtent = 顶部/最旧

  /// 保存滚动位置
  void save(String sessionId, double offset);

  /// 读取滚动位置（不存在返回 null，读取会更新 LRU 顺序）
  double? restore(String sessionId);

  /// 清除指定会话的缓存
  void remove(String sessionId);
}

/// 全局滚动位置缓存 Provider（纯内存，应用生命周期内有效）
final scrollPositionCacheProvider = Provider<ScrollPositionCache>((ref) {
  return ScrollPositionCache();
});
```

**集成方式**（`ChatModePage`）：
- 列表方向：`ListView.builder` 使用 `reverse: true`，itemBuilder 内做 index 反转映射（`msgIndex = messages.length - 1 - adjustedIndex`），数据层 `state.messages` 仍保持升序（旧→新）。reverse 后初始 offset 即为 0（底部），进入会话天然在最新消息位置，无需 `jumpTo(maxScrollExtent)` 一次性构建全部历史消息，**根治长对话进入卡顿/ANR**
- offset 语义：reverse 后 `0 = 底部（最新）`，`maxScrollExtent = 顶部（最旧）`；保存/恢复/clamp 逻辑在 reverse 坐标系内闭环自洽
- 保存时机：`dispose()` 时调用 `ScrollPositionCache.save(sessionId, offset)` 保存当前滚动偏移量
- 恢复时机：消息首次加载完成时（`previous.messages` 为空 → `next.messages` 非空，非流式状态），通过 `ScrollPositionCache.restore(sessionId)` 读取缓存
- 定位策略：有缓存 → `_jumpToOffsetImmediate(cachedOffset)` 恢复位置（`offset.clamp(0, maxScrollExtent)` 防越界）；无缓存 → `_jumpToBottomImmediate()` 定位到最新消息（reverse 列表下实质 no-op，初始已在底部）
- 即时定位：使用 `jumpTo`（无动画），用户进入会话直接看到目标位置

#### 2.1.9 StatePatchParser（state_patch 拆解器，v0.2）

```dart
/// 将 LLM 输出的自由 JSON state_patch 拆解为扁平的 factual_updates
class StatePatchParser {
  static const String _deletedMarker = '__deleted__';

  static List<FactualUpdate> parse(Map<String, dynamic> patch) {
    final updates = <FactualUpdate>[];
    _flatten(patch, '', null, updates);
    return updates;
  }

  static void _flatten(
    Map<String, dynamic> obj,
    String prefix,
    String? category,
    List<FactualUpdate> updates,
  ) {
    for (final entry in obj.entries) {
      final key = prefix.isEmpty ? entry.key : '$prefix.${entry.key}';
      if (entry.value == null) {
        updates.add(FactualUpdate(
          key: key,
          value: _deletedMarker,
          category: category,
        ));
      } else if (entry.value is Map<String, dynamic>) {
        _flatten(entry.value as Map<String, dynamic>, key, category, updates);
      } else if (entry.key == 'characters' && entry.value is List) {
        _flattenCharacters(entry.value as List, updates);
      } else {
        updates.add(FactualUpdate(
          key: key,
          value: entry.value.toString(),
          category: category,
        ));
      }
    }
  }

  static void _flattenCharacters(List<dynamic> characters, List<FactualUpdate> updates) {
    for (final char in characters) {
      final map = char as Map<String, dynamic>;
      final name = map['name'] as String?;
      if (name == null) continue;
      for (final entry in map.entries) {
        if (entry.key == 'name') continue;
        if (entry.value == null) {
          updates.add(FactualUpdate(
            key: '角色.$name.${entry.key}',
            value: _deletedMarker,
            category: '角色',
          ));
        } else {
          updates.add(FactualUpdate(
            key: '角色.$name.${entry.key}',
            value: entry.value.toString(),
            category: '角色',
          ));
        }
      }
    }
  }
}
```

| 维度 | v0.2 中间方案（已落地） | v0.3 完整设计（待实施） |
|------|----------------------|----------------------|
| 数据载体 | `FactsDelta` 列表（6 种操作类型） | `FactualUpdate` 列表（key-value） |
| 操作类型 | createEntity / updateAttr / appendList / removeFromList / addAlias / archiveEntity | upsert（key 存在则更新，不存在则插入） + `__deleted__` 删除标记 |

| 防护机制 | 三重防护 + 5 层健康度防护（DOC-11 §7） | 深度合并算法 + 状态快照（待设计） |
| 审计日志 | `factual_memory_history` 表自动追加 | 无独立审计表（待设计） |
| 失败降级 | retrieving 不阻塞 + persisting 一致性优先（DOC-09A-2 §6.5.1） | 待设计 |

**FactsDelta 6 种操作类型**（详见 DOC-11 §4.2）：

## 3. 算法实现方案

### 3.1 SSE 解析状态机

```
状态定义:
  idle            → 初始状态，等待数据
  streamingText   → 正在接收文本内容
  toolCallDetected → 检测到 tool_calls 开始
  accumulatingArgs → 正在累积 tool_calls 的 JSON 参数
  executingTool   → tool_calls 参数完整，等待执行

状态转移表:

┌──────────────────┬─────────────────────────────┬───────────────────┬──────────────────────────────────────────────────────────┐
│ 当前状态          │ 输入事件                     │ 下一状态           │ 处理                                                     │
├──────────────────┼─────────────────────────────┼───────────────────┼──────────────────────────────────────────────────────────┤
│ idle             │ data: {"content":...}        │ streamingText     │                                                          │
│ idle             │ data: {"reasoning_content":...} │ streamingText   │ 发出 ThinkingDelta 事件                                   │
│ idle             │ data: {"tool_calls":...}     │ toolCallDetected  │                                                          │
│ idle             │ data: {"tool_calls":...}(完整)│ executingTool     │ 直接执行，跳过 accumulatingArgs                           │
│ idle             │ data: [DONE]                │ idle              │ 空流结束                                                  │
│ streamingText    │ data: {"content":...}        │ streamingText     │                                                          │
│ streamingText    │ data: {"reasoning_content":...} │ streamingText   │ 发出 ThinkingDelta 事件                                   │
│ streamingText    │ data: {"tool_calls":...}     │ toolCallDetected  │                                                          │
│ streamingText    │ data: [DONE]                │ idle              │ 正常流结束                                                │
│ streamingText    │ 连接中断                     │ idle              │ 保留已接收内容，通知 UI                                    │
│ toolCallDetected │ data: {"tool_calls":...}     │ accumulatingArgs  │                                                          │
│ accumulatingArgs │ data: {"tool_calls":...}     │ accumulatingArgs  │                                                          │
│ accumulatingArgs │ JSON 完整性检查通过           │ executingTool     │                                                          │
│ accumulatingArgs │ JSON 不完整                  │ accumulatingArgs  │                                                          │
│ accumulatingArgs │ 连接中断                     │ idle              │ 尝试修复已累积 JSON，失败则丢弃 tool_call                  │
│ accumulatingArgs │ data: [DONE]                │ idle              │ 尝试修复已累积 JSON（自动闭合括号），成功则执行 tool_call   │
│ executingTool    │ 执行完成，有后续文本           │ streamingText     │                                                          │
│ executingTool    │ 执行完成，无后续文本           │ idle              │                                                          │
│ any              │ 超时（可配置，默认 30s 无数据）│ idle              │ 保留已接收内容，持久化错误到助手消息，通知 UI 超时           │
└──────────────────┴─────────────────────────────┴───────────────────┴──────────────────────────────────────────────────────────┘
```

**JSON 修复算法**（accumulatingArgs → executingTool 转换时）：

```
repairJSON(rawString):
    │
    ├── 1. 去除首尾空白
    ├── 2. 统计括号:
    │   ├── openBraces = count('{')
    │   ├── closeBraces = count('}')
    │   ├── openBrackets = count('[')
    │   └── closeBrackets = count(']')
    │
    ├── 3. 补全闭合:
    │   ├── while closeBraces < openBraces → 追加 '}', closeBraces++
    │   └── while closeBrackets < openBrackets → 追加 ']', closeBrackets++
    │
    ├── 4. 去除尾部逗号:
    │   └── replaceAll(RegExp(r',\s*([}\]])'), r'$1')
    │
    └── 5. 尝试 jsonDecode
        ├── 成功 → 返回解析结果
        └── 失败 → 抛出 ToolCallParseException
```

> **并行 tool_calls 说明**：OpenAI API 支持单个响应中包含多个 tool_call。当前实现按顺序逐个处理：第一个 tool_call 走完状态机后，回到 idle，再处理第二个。未来可优化为并行执行。

### 3.2 上下文构建算法

#### 3.2.1 Simple 模式上下文构建

```
buildContext(sessionId):
    │
    ├── 1. 加载最新 CompactionPoint（按 createdAt 降序取第一条）
    │
    ├── 2. 加载所有消息
    │   └── chat_messages WHERE session_id = ? ORDER BY created_at
    │
    ├── 2a. 过滤错误消息
    │   └── 移除 error 字段非空且 content 为空的消息（API 报错、超时等），
    │       避免将错误内容作为上下文发送给 LLM
    │       （v0.1 实际实现：_buildMessagesForApi 中 content==null && toolCalls==null 的消息自动跳过）
    │
    ├── 3. 如果存在 CompactionPoint:
    │   ├── 找到 boundaryMessage 的索引
    │   ├── 截取 boundary 之后的消息
    │   ├── 过滤掉 isSummary=true 的消息（旧摘要）
    │   ├── 在前面插入 summaryMessage
    │   └── 确保 system 消息在开头
    │
    ├── 4. 如果不存在 CompactionPoint:
    │   └── 使用全部消息
    │
    └── 5. 返回消息列表
```

#### 3.2.2 Advanced 模式上下文组装（缓存优先）

```
assembleCacheFirst(sessionId, userInput):
    │
    ├── 1. [稳定前缀] System Prompt
    │   └── TemplateRepository.getByKind(systemPrompt)
    │
    ├── 2. [稳定前缀] 事实类记忆（全量）
    │   └── MemoryRepository.getAllFacts(sessionId)
    │       → 格式化为 "[世界书]\n- 门派·青云门：..."
    │
    ├── 3. [半稳定] 最近 N 轮对话原文
    │   ├── 加载消息列表
    │   ├── Token 预算控制:
    │   │   ├── 缓存优先: 超出预算 → LLM 摘要 + CompactionPoint
    │   │   └── 语义优先: 超出预算 → 截断 + 记忆摘要替代
    │   └── 返回 List<Message>
    │
    ├── 4. [变动] 当前状态面板
    │   └── MemoryRepository.getAllFacts(sessionId)
    │       → 格式化为 "[当前状态 — 绝对真理]\n..."
    │
    ├── 5. [变动] 检索到的经历类记忆
    │   ├── 提取检索关键词（从 userInput + 最近对话）
    │   ├── MemoryRepository.hybridSearch(sessionId, query, topK)
    │   └── 格式化为 "[历史记忆 — 若与当前面板冲突，以当前面板为准]\n..."
    │
    ├── 6. [变动] 用户输入
    │
    └── 7. Token 总量检查
        ├── 总 tokens ≤ contextWindow - outputReserve → 返回
        └── 超出 → 从步骤 3 开始缩减对话轮次，重试
```

#### 3.2.3 Advanced 模式上下文组装（语义优先，v0.2）

语义优先策略将权威信息（状态面板、经历类记忆）置于对话原文之前，确保 LLM 优先关注当前状态和历史事件。

```
输入: sessionId, userInput, contextWindow, outputReserve
输出: List<ChatCompletionMessage>

1. 计算 availableWindow = max(contextWindow - outputReserve, contextWindow × 0.5)
2. 加载事实类记忆（全量）
3. 提取检索关键词（从 userInput + 最近 2 轮对话）
4. 混合检索经历类记忆（FTS5×0.5 + Vector×0.3 + Temporal×0.2）→ 取 top-K
5. 加载最近 N 轮对话原文
6. 按 token 预算组装:
   a. System Prompt（固定）
   b. 事实类记忆格式化（步骤 2）
   c. 当前状态面板（factual_memories 格式化）
   d. 检索到的经历类记忆（步骤 4，含冲突警告）
   e. 对话原文（步骤 5，从旧到新）
   f. 用户输入
7. 如果总 token 超限:
   a. 先缩减对话轮次（从最旧开始移除，最少保留 2 轮）
   b. 再缩减经历类记忆（从最低分开始移除）
   c. 仍超限 → 截断事实类记忆（按 category 优先级：角色 > 世界 > 自定义）
8. 返回组装结果
```

**压缩策略（语义优先专用）**：当对话超出预算时，不调用 LLM 生成摘要，而是从经历类记忆中自动提取结构化摘要替代被截断的对话：

```
1. 确定截断范围: [startTurn, endTurn] = 被移除的对话轮次范围
2. 查询 experiential_memories WHERE turn_number IN [startTurn, endTurn]
3. 按 narrative_period 分组
4. 格式化为结构化文本:
   "【修炼第三天】主角进入迷雾森林，与狼型魔物战斗（HP 100→85）"
   "【修炼第三天】获得铁剑，击败哥布林"
5. 将结构化文本插入上下文（替代被截断的对话原文）
```

此压缩方式零 API 成本，但摘要质量依赖经历类记忆的完整性。

| E302 | `MigrationException` | 数据库迁移失败 | "应用需要更新" |

### 5.2 错误处理策略

| 场景 | 策略 | 恢复方式 |
|------|------|---------|
| SSE 连接中断 | 保留已接收内容，显示错误 | 用户点击重发 |
| API Key 无效 | 阻止发送，引导设置 | 用户更新 Key |
| 压缩 LLM 失败 | 跳过压缩，继续发送原始上下文 | 用户可手动重试压缩 |
| Tool Call 解析失败 | 跳过该 Tool Call，继续接收 | 自动恢复 |
| Embedding API 失败 | 由 `fallbackOnFailure` 决定：true=静默降级为 FTS5-only，false=抛 E104 让用户决策（重试/临时降级/中止） | 用户重试或选临时降级，后续可通过「重建向量索引」补全 |
| 记忆折叠 LLM 失败 | 保留原事件不折叠 | 下次触发时重试 |
| API 调用失败（普通发送） | 错误持久化到助手消息的 `error` 字段，消息气泡内显示错误卡片 | 用户点击重发 |
| API 调用失败（Fork 操作） | 回滚 Fork 分支，仅显示临时错误横幅 | 用户重试 Fork 操作 |

> **E104 语义扩展**（2026-07-21）：
> E104 原义为"Embedding API 限流"（仅 429 状态码），现扩展为"embedding 调用失败"（限流是子场景，由 `ErrorCategory.rateLimit` 区分）。配合 `fallbackOnFailure` 默认值由 `true` 改为 `false`（DOC-09C §10.1），embedding 失败时不再静默降级，而是显式抛 E104 让用户决策。用户可选择：
> - **重试**：自动重试 retrieving 阶段（`RetryScheduler` 中 E104 走 `retrievalMaxRetries`）
> - **临时降级继续**：本轮后续跳过 embedding 调用（`IntermediateChatState.embeddingDegradedForRound=true`），仅用 FTS5 检索，本轮生成的记忆 `has_embedding=false`
> - **中止**：取消本轮生成
>
> 临时降级产生的未向量化记忆可通过会话设置 → 记忆管理 → 重建向量索引补全（`IntermediateChatController.rebuildEmbeddings`）。

### 5.3 错误持久化机制（v0.1 实际实现，对标 ChatBox）

**目的**：API 调用失败时，将错误信息持久化到助手消息，切换分支时快照包含 error 字段，保证错误可见性。

**存储**：`chat_messages.error` 列（TEXT，nullable，schemaVersion=13 新增）

**持久化逻辑**（`ChatModeController._persistErrorToMessage`，v0.1.1 重构后委托 `MessageManager.persistErrorToMessage`）：

| 场景 | 处理方式 |
|------|---------|
| Fork 操作失败（regenerate/editAndResend） | 跳过持久化，由 `ForkManager.rollbackForkIfNeeded` 回滚分支 |
| 流式中途失败（已有助手消息） | 更新该消息的 `error` 字段（state + DB） |
| 首 token 前失败（无助手消息） | 创建带 `error` 的助手消息并入库 |

**UI 展示**：
- 消息气泡内：`_ErrorMessage` 组件，错误图标 + 错误文本，error 色调淡背景 + 边框
- 页面顶部：临时错误横幅（`state.error`），提供"重试"按钮，下次发送时清除

**快照兼容**：`ChatMessage.toJson()` 包含 `error` 字段，`fromJson` 读取 `error` 字段，分支切换时错误信息随快照保留。

> **章节定位**：本章同步 DOC-12 v1.1 落地的"供应商模板与多协议适配"详细设计，包括协议适配器选择流程、Anthropic/Gemini SSE 解析器状态机、thinking signature 跨轮回传流程 4 个子章节。完整多协议适配设计（含 4 个适配器实现要点、供应商差异速查表、`LlmRequest`/`LlmResponse` 扩展字段定义）见 **DOC-12**。

### 6.1 协议适配器选择流程

**触发场景**：调用方（`SimpleChatController` / `IntermediateChatController` / `CompactionService` / `ModelTestService`）通过 `LlmService` Domain 接口调用 `streamChat` 或 `chat` 时，`LlmRemoteDataSource` 按 `LlmRequest.protocol` 字段（来自 `ApiPreset.protocol`）选择对应协议适配器实例。

```
调用方构造 LlmRequest（含 protocol 字段，来自 ApiPreset.protocol）
    │
    ▼
LlmRemoteDataSource.streamChat(request) / chat(request)
    │
    ├── 1. 读取 request.protocol（LlmProtocol 枚举，4 值：openaiCompatible/openaiResponses/anthropic/geminiNative）
    │       同时读取 request.baseUrl + request.modelId（用于 openaiCompatible 协议下的端点路由）
    │
    ├── 2. _adapterFactory.getAdapter({protocol, baseUrl, modelId})
    │   │
    │   ▼
    │   LlmAdapterFactory.getAdapter({protocol, baseUrl, modelId}) switch:
    │   ├── openaiCompatible:
    │   │   ├── DeepSeekAdapter.isDeepSeekEndpoint(baseUrl, modelId) == true
    │   │   │   → 返回 _deepSeekAdapter（DeepSeekAdapter 单例，处理 DeepSeek 专属兼容性差异）
    │   │   │     DeepSeekAdapter 继承 OpenAiAdapter，重写 buildRequestBody：
    │   │   │       - tool_choice:"required" → 删除字段（降级为默认 auto，思考模式下 required 会 400）
    │   │   │       - parallel_tool_calls → 删除字段（DeepSeek 不支持并行工具调用）
    │   │   │       - 其他参数沿用父类 OpenAiAdapter 逻辑
    │   │   │     端点判定规则：baseUrl 含 "deepseek.com" 或 modelId 以 "deepseek-" 开头且不含 "/"
    │   │   │     （OpenRouter 路由的 "deepseek/xxx" 不认为是 DeepSeek 端点，由 OpenRouter 中间层处理兼容性）
    │   │   └── 否则 → 返回 _openaiAdapter（OpenAiAdapter 单例，通用 OpenAI 兼容协议）
    │   ├── anthropic         → 返回 _anthropicAdapter（AnthropicAdapter 单例）
    │   ├── geminiNative      → 返回 _geminiAdapter（GeminiAdapter 单例）
    │   └── openaiResponses   → throw UnimplementedError（v0.3+ 待落地）
    │
    ├── 3. adapter.buildUrl(baseUrl, modelId, stream: true/false)
    │   ├── OpenAi:    baseUrl + /v1/chat/completions
    │   ├── Anthropic: baseUrl + /v1/messages
    │   ├── Gemini:    baseUrl + /v1beta/models/{modelId}:(stream)?generateContent(?alt=sse)
    │   └── Responses: baseUrl + /v1/responses（v0.3+ 待落地）
    │
    ├── 4. adapter.buildHeaders(request)
    │   ├── OpenAi:    Authorization: Bearer {apiKey}
    │   ├── Anthropic: x-api-key: {apiKey} + anthropic-version: 2023-06-01（+ providerOptions.anthropic_beta）
    │   ├── Gemini:    x-goog-api-key: {apiKey}
    │   └── OpenRouter: Authorization: Bearer + 可选 HTTP-Referer/X-Title（来自 providerOptions.extra_headers）
    │
    ├── 5. adapter.buildRequestBody(request, stream)
    │   ├── OpenAi:    {model, messages, stream, temperature, tools, tool_choice, ...}
    │   ├── Anthropic: {model, messages, system（顶层）, max_tokens（必填）, tools（input_schema）, thinking, ...}
    │   ├── Gemini:    {contents, systemInstruction（顶层）, generationConfig（包裹采样参数）, tools, safetySettings, ...}
    │   └── Responses: {model, input, ...}（v0.3+ 待落地）
    │
    ├── 6a. streamChat 路径
    │   │
    │   ▼
    │   HttpClient.streamPost(url, headers, body)
    │   │
    │   ▼
    │   原始 SSE 字符串流（可能跨 chunk 切分）
    │   │
    │   ▼
    │   adapter.parseStream(rawStream)
    │   │
    │   ├── RawSseChunkParser.parse（底层共享，按 \n\n 切分事件块）
    │   │   └── 输出 ({event, data}) 元组流
    │   │
    │   └── 协议层解析器（OpenAiSseParser / AnthropicSseParser / GeminiSseParser）
    │       └── 输出统一 LlmStreamEvent 流（LlmTextDelta / LlmThinkingDelta / LlmThinkingBlockComplete / LlmToolCallStart / LlmToolCallArgs / LlmToolCallComplete / LlmStreamDone / LlmStreamError）
    │
    └── 6b. chat 路径（非流式）
        │
        ▼
        http.post(url, headers, body) → response
        │
        ▼
        jsonDecode(response.body) → Map<String, dynamic>
        │
        ▼
        adapter.parseResponse(json) → LlmResponse
            ├── content: String（最终文本）
            ├── usage: LlmUsage?
            ├── toolCalls: List<ToolCall>?
            ├── reasoningContent: String?（OpenAI/DeepSeek/Gemini 用，无 signature）
            └── thinkingBlocks: List<LlmThinkingBlock>?（Anthropic 专用，含 signature）
```

**关键约束**：
- `LlmAdapterFactory` 持有适配器实例而非每次 `new`（单例语义），原因：减少 GC 压力，解析器在 `parse()` 入口重置状态可安全复用；测试场景可通过构造参数注入 mock 适配器（详见 DOC-12 §5.3）
- 调用方零感知协议差异——`LlmService` Domain 接口不变，`SimpleChatController` 等 v0.1 调用方无需修改
- `openaiResponses` 协议当前抛 `UnimplementedError`，待 v0.3+ 落地

### 6.2 Anthropic SSE 解析器状态机

**实现位置**：`lib/core/network/sse/anthropic_sse_parser.dart`，类 `AnthropicSseParser`，实现依据 DOC-12 §6.3 + §5.4.4。

**与 OpenAI 兼容协议的关键差异**：
- 无 `data: [DONE]` 结束标记，靠 `message_stop` 事件判断流结束
- 增量数据嵌套在 `delta` 字段内，按 `delta.type` 区分 4 种 delta
- 工具调用参数通过 `input_json_delta.partial_json` 分片累积
- thinking 块含 `signature_delta`，需完整累积用于多轮回传（详见 §6.4）

#### 6.2.1 6 个事件类型

| 事件类型 | 用途 | 携带的关键字段 |
|---------|------|---------------|
| `message_start` | 初始化 Message 对象 | `message.usage.input_tokens`（首事件 usage） |
| `content_block_start` | 开始 content block | `index` + `content_block.type`（text/thinking/tool_use）+ `id`/`name`（tool_use 时） |
| `content_block_delta` | 增量更新 block | `index` + `delta.type`（4 种 delta）+ delta 内容 |
| `content_block_stop` | 结束 block | `index`（按 block 类型发出对应完成事件） |
| `message_delta` | 顶层变更 | `usage.output_tokens`（末尾累计） + `stop_reason` |
| `message_stop` | 流结束 | 无（发出 `LlmStreamDone`） |

#### 6.2.2 4 种 delta 类型

| delta.type | 用途 | 累积位置 | 输出事件 |
|-----------|------|---------|---------|
| `text_delta` | 文本增量 | 无（每个 delta 直接发） | `LlmTextDelta(text)` |
| `input_json_delta` | 工具参数 JSON 分片 | `_argsBuffer`（在 content_block_stop 时整体解析） | `LlmToolCallArgs(toolUseId, partial_json)`（实时）+ `LlmToolCallComplete`（结束时） |
| `thinking_delta` | 思考内容增量 | `_thinkingBuffer` | `LlmThinkingDelta(thinking)`（实时） |
| `signature_delta` | 思考签名增量 | `_signatureBuffer` | 无（在 content_block_stop 时通过 `LlmThinkingBlockComplete` 一次性携带完整 signature） |

#### 6.2.3 状态管理（Map<int, _ContentBlockState>）

解析器维护 `Map<int, _ContentBlockState> _blocks` 按 `index` 跟踪每个活跃的 content block：

```
事件处理状态机:

  message_start
      │
      │ 记录 _inputTokens
      ▼
  content_block_start (index=N, type=text/thinking/tool_use)
      │
      ├── _blocks[N] = _ContentBlockState(index=N, type, toolUseId?, toolName?)
      ├── if type==tool_use → yield LlmToolCallStart(id, name)
      │
      ▼
  content_block_delta (index=N, delta.type=...)
      │
      ├── block = _blocks[N]（若不存在则丢弃）
      ├── text_delta        → yield LlmTextDelta(text)
      ├── input_json_delta  → block.appendArgs(partial_json) + yield LlmToolCallArgs(id, partial_json)
      ├── thinking_delta    → block.appendThinking(thinking) + yield LlmThinkingDelta(thinking)
      └── signature_delta   → block.appendSignature(signature)（不发出事件，累积签名）
      │
      ▼
  content_block_stop (index=N)
      │
      ├── block = _blocks.remove(N)
      ├── if block.type==text        → 无特殊处理（文本已发）
      ├── if block.type==thinking    → yield LlmThinkingBlockComplete(thinking, signature)
      └── if block.type==tool_use     → 解析 block.rawArgs → Map → yield LlmToolCallComplete(id, name, args)
      │
      ▼
  message_delta
      │
      └── 记录 _outputTokens（累计 output_tokens）
      │
      ▼
  message_stop
      │
      ├── _streamStopped = true
      └── yield LlmStreamDone(usage=_buildUsage())
              └── usage = LlmUsage(input=_inputTokens, output=_outputTokens, total=input+output)

  流自然结束（未收到 message_stop 时）
      │
      └── 兜底 yield LlmStreamDone(usage=_buildUsage())

  解析异常（jsonDecode 失败 / 流中断）
      │
      └── yield LlmStreamError(code=PARSE_ERROR / STREAM_ERROR)
```

**实例复用安全性**：每次调用 `parse()` 入口会清空 `_blocks` / `_streamStopped` / `_inputTokens` / `_outputTokens`，工厂持有单例可安全复用。

### 6.3 Gemini SSE 解析器状态机

**实现位置**：`lib/core/network/sse/gemini_sse_parser.dart`，类 `GeminiSseParser`，实现依据 DOC-12 §6.2 + §5.4.5。

**与 OpenAI/Anthropic 的关键差异**：
- 无 `event:` 字段，所有事件都是 `data: {json}`
- 无 `[DONE]` 结束标记，靠流自然关闭判断结束（兼容性处理：检测到 `[DONE]` 也识别）
- 每个 chunk 是完整的 `GenerateContentResponse`，包含 `candidates` 数组
- 文本增量在 `candidates[0].content.parts[].text`
- 推理内容通过 `parts[].thought: true` 标识（Gemini 2.5+ 特性）
- 工具调用 `functionCall` 完整返回（不增量），含 `name` + `args` 对象
- usage 在最后一个 chunk 的 `usageMetadata` 字段

#### 6.3.1 状态机（无复杂状态机，每个 chunk 独立解析）

```
原始 SSE 流
    │
    ▼
RawSseChunkParser.parse(rawStream)
    │
    ▼
({event, data}) 元组流（Gemini 无 event，event=null）
    │
    ├── data == '[DONE]'（兼容性，某些代理可能添加）
    │   └── yield LlmStreamDone(usage=_lastUsage) + _streamEnded=true
    │
    ▼
jsonDecode(data) → Map<String, dynamic>
    │
    ▼
_handleChunk(json)
    │
    ├── 1. 提取 usageMetadata（最后 chunk 携带）→ 缓存到 _lastUsage
    │   ├── promptTokenCount（非 prompt_tokens / input_tokens）
    │   ├── candidatesTokenCount（非 completion_tokens / output_tokens）
    │   ├── totalTokenCount
    │   └── thoughtsTokenCount（Gemini 特有，不计入 candidatesTokenCount）
    │
    ├── 2. 提取 candidates[0].content.parts（先处理 parts 再处理 finishReason，保证已生成内容能发出）
    │   │
    │   └── 遍历 parts:
    │       ├── 文本内容（part.text 非空）
    │       │   ├── part.thought == true  → yield LlmThinkingDelta(text)
    │       │   └── 否则                   → yield LlmTextDelta(text)
    │       │
    │       └── 函数调用（part.functionCall 非空）
    │           ├── name = functionCall.name
    │           ├── args = functionCall.args（对象，非 JSON 字符串）
    │           ├── 去重：if _emittedToolCallNames.contains(name) → 跳过
    │           │   │  （Gemini 偶尔在后续 chunk 重复携带已完成的 functionCall）
    │           │   └── 否则 → _emittedToolCallNames.add(name)
    │           ├── toolCallId = 'gemini_$name'（Gemini 不返回 id，用 name 生成）
    │           ├── yield LlmToolCallStart(toolCallId, name)
    │           └── yield LlmToolCallComplete(toolCallId, name, arguments=args)
    │
    └── 3. 检测 finishReason（parts 处理后再检查）
        ├── 'STOP'        → yield LlmStreamDone(usage=_lastUsage) + _streamEnded=true
        ├── 'MAX_TOKENS'  → yield LlmStreamDone(usage=_lastUsage) + _streamEnded=true
        ├── 'SAFETY'      → yield LlmStreamError(code=SAFETY_BLOCKED) + LlmStreamDone + _streamEnded=true
        │                  （内容被安全过滤拦截）
        ├── 'RECITATION'  → yield LlmStreamError(code=RECITATION_BLOCKED) + LlmStreamDone + _streamEnded=true
        │                  （内容触发版权引用过滤）
        └── 其他（LANGUAGE/BLOCKLIST/...）→ 不主动结束流，等待后续 chunk

  流自然关闭（无 finishReason 或收到 [DONE]）
    │
    └── 兜底 yield LlmStreamDone(usage=_lastUsage)

  解析异常
    │
    └── yield LlmStreamError(code=PARSE_ERROR / STREAM_ERROR)
```

#### 6.3.2 关键设计点

| 维度 | 实现策略 |
|------|---------|
| 工具调用去重 | 维护 `Set<String> _emittedToolCallNames`，按 `name` 去重（Gemini functionCall 无 id 字段，用 name 作 key） |
| finishReason 处理 | STOP/MAX_TOKENS → 正常结束；SAFETY/RECITATION → 先发错误再结束；其他 → 不主动结束 |
| usage 提取 | 在每个 chunk 都尝试提取 `usageMetadata`，缓存到 `_lastUsage`，最后随 `LlmStreamDone` 发出 |
| 流结束判定 | 双重兜底：收到 `message_stop` / `STOP` / `MAX_TOKENS` / `SAFETY` / `RECITATION` 时发 `LlmStreamDone`；流自然关闭时若未发过也兜底发一次 |
| thinking 双轨制 | Gemini 3 用 `thinkingLevel`，Gemini 2.5 用 `thinkingBudget`（适配器在 buildRequestBody 时按模型 ID 选择，本解析器只识别 `thought:true` 标识） |
| 实例复用安全 | 每次 `parse()` 入口清空 `_emittedToolCallNames` / `_streamEnded` / `_lastUsage`，工厂单例可安全复用 |

### 6.4 thinking signature 跨轮回传流程

**背景**：Anthropic Claude 的 thinking block 由两部分组成——`thinking`（明文）+ `signature`（服务端加密签名）。多轮对话中必须原样回传完整 thinking block（含 signature），否则 Anthropic 服务端 signature 验证失败（400 错误）。

**与 OpenAI/DeepSeek/Gemini 的差异**：
- OpenAI/DeepSeek 用 `reasoning_content` 字符串（无 signature 概念），跨轮回传只需字符串
- Gemini 用 `parts[{thought:true, text:...}]` 标识（无 signature，thought 标识即可）
- Anthropic 必须用结构化 thinking block（含 signature），不能简化为字符串

#### 6.4.1 数据结构

```dart
// LlmThinkingBlockComplete 事件（DOC-12 §6.4 新增）
class LlmThinkingBlockComplete extends LlmStreamEvent {
  final String thinking;    // 完整思考内容明文
  final String signature;   // 服务端加密签名（跨轮回传必需）
}

// LlmThinkingBlock 值对象（LlmResponse.thinkingBlocks 元素）
class LlmThinkingBlock {
  final String thinking;
  final String signature;
}

// LlmResponse 扩展字段
class LlmResponse {
  final String? reasoningContent;        // OpenAI/DeepSeek/Gemini 用
  final List<LlmThinkingBlock>? thinkingBlocks;  // Anthropic 专用（含 signature）
  // 两者互斥：OpenAI/DeepSeek/Gemini 用 reasoningContent，Anthropic 用 thinkingBlocks
}
```

#### 6.4.2 跨轮回传流程

```
第 N 轮（Anthropic 流式响应）
    │
    ▼
AnthropicSseParser.parse(rawStream)
    │
    ├── content_block_start (index=K, type=thinking)
    │   └── _blocks[K] = _ContentBlockState(type=thinking)
    │       └── _thinkingBuffer / _signatureBuffer 初始化为空 StringBuffer
    │
    ├── content_block_delta (index=K, delta.type=thinking_delta)
    │   └── block.appendThinking(thinking) + yield LlmThinkingDelta(thinking)（实时 UI 展示）
    │
    ├── content_block_delta (index=K, delta.type=signature_delta)
    │   └── block.appendSignature(signature)（不发出事件，纯累积）
    │
    └── content_block_stop (index=K, type=thinking)
        └── yield LlmThinkingBlockComplete(thinking=block.thinkingText, signature=block.signature)
            │
            ▼
        调用方（IntermediateChatController / SimpleChatController）缓存事件信息
            │
            ├── 方式 A：流式累积到 ChatMessage.thinkingContent（仅 thinking 文本，UI 展示用）
            └── 方式 B：缓存到 List<LlmThinkingBlock>（含 signature，用于下轮请求构造）
                └── 同时持久化到 chat_messages.reasoning_content 列（schemaVersion 25，详见 DOC-12 §3.3）
                    ⚠️ 注：v0.1/v0.2 仅内存缓存单次请求，不持久化 signature；
                    signature 跨轮持久化待 v0.3（详见 DOC-12 §11 风险表）

第 N+1 轮（构造 assistant 消息回传）
    │
    ▼
调用方构造 LlmRequest.messages（含上一轮的 assistant 消息）
    │
    ├── 读取缓存的 List<LlmThinkingBlock>
    │
    ▼
AnthropicAdapter._convertMessages(messages)
    │
    ├── 对每个 assistant 消息:
    │   ├── 重建 content 数组（保持顺序）
    │   ├── 若 thinkingBlocks 非空 → 在 content 数组中插入 thinking block:
    │   │   {type: 'thinking', thinking: block.thinking, signature: block.signature}
    │   ├── 文本回复 → {type: 'text', text: ...}
    │   └── 工具调用 → {type: 'tool_use', id, name, input}
    │
    └── 构造的 messages 发送给 Anthropic API
        │
        ▼
    Anthropic 服务端验证 signature 通过 → 正常返回响应
    （若 signature 缺失或不匹配 → 返回 400 错误）
```

#### 6.4.3 调用方回传规则对照

| 协议 | 思考内容回传字段 | 回传要求 |
|------|----------------|---------|
| OpenAI / DeepSeek | `messages[i].reasoningContent` | 字符串，无 signature 概念 |
| Anthropic | `messages[i].thinkingBlocks`（content 数组中的 thinking block） | 必须含 signature，否则 400 |
| Gemini | `messages[i].parts[{thought:true, text:...}]` | 无 signature，thought 标识即可 |

适配器在 `_convertMessage` / `_convertMessages` 时按上表规则从 OpenAI 风格 messages 还原为协议原生格式。详见各适配器的 `_convertMessage` 方法实现。

#### 6.4.4 v0.2 限制与 v0.3 扩展

| 维度 | v0.2 现状 | v0.3 计划 |
|------|----------|----------|
| signature 持久化 | 仅内存缓存单次请求，不持久化到 DB | 持久化到 `chat_messages` 表（扩展 schema） |
| 跨会话恢复 | 不支持（重启后丢失） | 支持（从 DB 加载） |
| Fork 分支切换 | thinkingContent 跟随快照，signature 不跟随 | signature 也纳入快照 |
| 多轮工具调用 | 部分支持（仅当本会话内连续轮次） | 完整支持（任意轮次间隔） |
