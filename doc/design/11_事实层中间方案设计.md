## 0. 文档定位

本文档定义中级模式（v0.2）的**事实层中间方案**——在不引入 v0.3 Agent Loop 的前提下，提前落地事实层数据结构与结构化提取机制，解决长对话后设定漂移问题（角色改名、品种写错等）。

**适用范围**：仅中级模式（故事模式）。

**与 v0.3 的关系**：本文档是 v0.3 事实层的"前置子集"，数据结构对齐 v0.3（`factual_entities` + `factual_attributes` 两表），但不实现 Agent Loop、HUD、状态冲突解决等高级特性。

**与 DOC-10 的关系**：多粒度记忆（经历层增强）与事实层是两个独立增强，可独立实施。建议先实施 DOC-10，稳定后再实施本文档。

## 1. 设计动机

### 1.1 现有问题

中级模式当前只有经历层（`experiential_memories`），缺乏事实沉淀机制。实际使用暴露的问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| 设定漂移 | 长对话后 LLM 写错角色品种、性别、年龄 | 设定信息从未被结构化提取，LLM 每轮只能从对话历史"临时记忆" |
| 多实例串台 | 两只狗的技能归属混乱 | 扁平 key 存储（如 `pet.skills`）无法区分个体 |
| 改名失效 | 用户明确改名后，LLM 仍用旧名 | 旧名从未被覆盖，仍存在于对话历史 |

### 1.2 设计目标

- **结构化沉淀**：实体（人/物/地/NPC）+ 属性（name/species/age/skills）分离存储
- **多实例隔离**：每个实体独立 ID，属性按 entityId 隔离，杜绝串台
- **追加优先 + 冲突修改**：默认追加新事实，仅直接矛盾时才修改，三重防护防 LLM 乱改
- **零额外 API 成本（检索）**：事实检索纯本地 SQL，不调 LLM
- **失败不阻塞对话**：事实层失败降级为纯经历层，对话照常进行

## 2. 核心设计：实体 + 属性双表结构

### 2.1 数据模型

```
FactualEntity（实体表）：每个"东西"一条记录
  ├─ entityId: ent_001
  ├─ type: character / pet / npc / location / item
  ├─ primaryName: "旺财"（主名，用于检索和展示）
  ├─ aliases: ["小金毛", "财财"]（别名，用户可能换称呼）
  ├─ importance: 4（关键实体=5，路人=1）
  └─ createdTurn: 3（第几轮出现的）

FactualAttribute（属性表）：实体的各项属性，每个属性一条记录
  ├─ entityId: ent_001（指向 FactualEntity）
  ├─ attrKey: "species" / "age" / "skills" / "personality"
  ├─ value: "金毛" / "3个月" / '["接飞盘"]'
  ├─ valueType: single / list / dict
  ├─ updatedAt, updatedTurn, updateReason（审计用）
  └─ importance: 4（属性重要性，用于注入筛选）
```

### 2.2 两只狗的正确存储示例

```
FactualEntity：
  ent_001: type=pet, primaryName="旺财", aliases=["小金毛"], importance=4, createdTurn=3
  ent_002: type=pet, primaryName="小白", aliases=[], importance=4, createdTurn=3

FactualAttribute：
  ent_001 / species / "金毛" / single
  ent_001 / age / "3个月" / single
  ent_001 / skills / "[]" / list
  
  ent_002 / species / "萨摩耶" / single
  ent_002 / age / "2个月" / single
  ent_002 / skills / '["接飞盘"]' / list  ← 小白学会接飞盘时只更新这条
```

旺财的 skills 完全不受影响，杜绝串台。

## 3. 数据结构定义

### 3.1 `factual_entities` 表

| 字段名 | 类型 | 约束/默认 | 说明 |
|--------|------|-----------|------|
| `id` | IntColumn | autoIncrement PK | 内部主键 |
| `entityId` | TextColumn | NOT NULL UNIQUE | 业务主键（如 `ent_001`） |
| `sessionId` | TextColumn | NOT NULL | 所属会话 |
| `type` | TextColumn | NOT NULL | 实体类型：`character` / `pet` / `npc` / `location` / `item` |
| `primaryName` | TextColumn | NOT NULL | 主名 |
| `aliases` | TextColumn | 默认 `'[]'` | 别名 JSON 数组字符串 |
| `category` | TextColumn | nullable | 分类标签（如"主角宠物"） |
| `importance` | IntColumn | 默认 3 | 重要性 1-5 |
| `isArchived` | BoolColumn | 默认 false | 是否归档（角色死亡/物品销毁） |
| `createdAt` | DateTimeColumn | currentDateAndTime | 创建时间 |
| `createdTurn` | IntColumn | NOT NULL | 出现轮次 |
| `updatedAt` | DateTimeColumn | nullable | 最后修改时间 |
| `updatedTurn` | IntColumn | nullable | 最后修改轮次 |

**索引**：
```sql
CREATE UNIQUE INDEX idx_factual_entities_session_name ON factual_entities(session_id, primary_name);
CREATE INDEX idx_factual_entities_session_type ON factual_entities(session_id, type);
CREATE INDEX idx_factual_entities_session_importance ON factual_entities(session_id, importance);
```

### 3.2 `factual_attributes` 表

| 字段名 | 类型 | 约束/默认 | 说明 |
|--------|------|-----------|------|
| `id` | IntColumn | autoIncrement PK | 内部主键 |
| `attributeId` | TextColumn | NOT NULL UNIQUE | 业务主键 |
| `entityId` | TextColumn | NOT NULL | 指向 FactualEntity.entityId |
| `sessionId` | TextColumn | NOT NULL | 所属会话（冗余，加速查询） |
| `attrKey` | TextColumn | NOT NULL | 属性名（如 `species` / `age` / `skills`） |
| `value` | TextColumn | NOT NULL | 属性值（单值存字符串，多值存 JSON 数组字符串） |
| `valueType` | TextColumn | 默认 `'single'` | 值类型：`single` / `list` / `dict` |
| `importance` | IntColumn | 默认 3 | 属性重要性 1-5 |
| `createdAt` | DateTimeColumn | currentDateAndTime | 创建时间 |
| `updatedAt` | DateTimeColumn | nullable | 最后修改时间 |
| `updatedTurn` | IntColumn | nullable | 最后修改轮次 |
| `updateReason` | TextColumn | nullable | 修改原因（审计用） |

**索引**：
```sql
CREATE UNIQUE INDEX idx_factual_attrs_entity_key ON factual_attributes(entity_id, attr_key);
CREATE INDEX idx_factual_attrs_session_entity ON factual_attributes(session_id, entity_id);
```

### 3.3 `factual_memory_history` 表（审计日志）

记录所有 UPDATE/APPEND/REMOVE 操作的历史版本，用于审计和回滚。

| 字段名 | 类型 | 说明 |
|--------|------|------|
| `id` | IntColumn | PK |
| `entityId` | TextColumn | 实体 ID |
| `attributeId` | TextColumn | 属性 ID（可空，CREATE_ENTITY 时无） |
| `action` | TextColumn | `CREATE_ENTITY` / `UPDATE_ATTR` / `APPEND_LIST` / `REMOVE_FROM_LIST` / `ADD_ALIAS` / `ARCHIVE_ENTITY` |
| `oldValue` | TextColumn | 旧值（CREATE 时为空） |
| `newValue` | TextColumn | 新值 |
| `reason` | TextColumn | 修改原因 |
| `confidence` | IntColumn | LLM 置信度 1-5 |
| `turnNumber` | IntColumn | 触发轮次 |
| `createdAt` | DateTimeColumn | 时间戳 |

### 3.4 schemaVersion 变更

实际实施时递增 schemaVersion 21 → 22（v0.2 dev 阶段，覆盖式重建策略）。

> **历史设计 vs 实际实施差异**：v1.0 设计时（2026-07-17）基于 schemaVersion=18 推测，计划"递增 18→19"。实际实施时（2026-07-20）schemaVersion 已演进至 21（ 5W1E），故本次落地递增 21→22。

> **与 DOC-10 的关系**：DOC-10 在 schemaVersion 18→19 加 3 字段（多粒度记忆）；本文档在 schemaVersion 21→22 新增 3 张表（事实层）。两者独立，无合并需求。

> **dev 模式策略**：与 schemaVersion 16~21 一致，dev 阶段覆盖式重建（删除数据库文件后采用新 Schema）。正式发版时需合并到统一 `MigrationStep`。详见 DOC-02 §6.5、DOC-09C §5。

## 4. FactsDelta 协议

### 4.1 动作枚举

```dart
enum FactAction {
  createEntity,     // 新建实体
  updateAttr,       // 修改单值属性（如角色改名）
  appendList,       // 追加列表属性（如学会新技能）
  removeFromList,   // 从列表移除（如遗忘某技能）
  addAlias,         // 添加别名（用户换称呼）
  archiveEntity,    // 实体归档（角色死亡/物品销毁）
}
```

> **MERGE_ENTITY 暂不实现**：合并实体逻辑复杂（属性冲突解决），v0.2 阶段先不引入。若 LLM 发现同一实体被重复创建，通过 `addAlias` + `archiveEntity` 手动处理。

### 4.2 FactsDelta 数据结构

```dart
class FactsDelta {
  final FactAction action;
  final String? entityId;          // update/append/remove/addAlias/archive 时必填
  final String? entityType;        // createEntity 时必填
  final String? primaryName;       // createEntity 时必填
  final String? attrKey;           // updateAttr/appendList/removeFromList 时必填
  final String? value;             // 新值
  final String? reason;            // 修改类操作必填（审计用）
  final int confidence;            // 1-5，低置信度的修改不生效
  final int? importance;           // 1-5，create_entity 时由 LLM 评分，决定检索注入频率
                                   // null 时由系统按实体类型赋保守默认值
}
```

### 4.3 各场景的 FactsDelta 示例

| 场景 | FactsDelta |
|------|-----------|
| 新养狗旺财 | `CREATE_ENTITY(pet, "旺财", {species:"金毛", age:"3个月"}, confidence=5)` |
| 小白学接飞盘 | `APPEND_LIST("ent_002", "skills", "接飞盘", confidence=5)` |
| 旺财改名叫大黄 | `UPDATE_ATTR("ent_001", "name", "大黄", reason="用户改名", confidence=5)` |
| 旺财学会握手 | `APPEND_LIST("ent_001", "skills", "握手", confidence=4)` |
| 用户叫旺财"小金毛" | `ADD_ALIAS("ent_001", "小金毛", confidence=4)` |
| 旺财死亡 | `ARCHIVE_ENTITY("ent_001", reason="剧情中死亡", confidence=5)` |
| 本轮无事实变更 | 不产出 FactsDelta，只产出 EventSummary |

### 4.4 extract_facts 工具定义

```json
{
  "name": "extract_facts",
  "description": "提取本轮对话中发生的事实变更（实体创建、属性修改等）。每轮必须调用此工具：有事实变更时传入 deltas 数组，无事实变更时传入空数组 []。禁止跳过调用。",
  "parameters": {
    "type": "object",
    "required": ["deltas"],
    "properties": {
      "deltas": {
        "type": "array",
        "description": "本轮的所有事实变更列表",
        "items": {
          "type": "object",
          "required": ["action", "confidence"],
          "properties": {
            "action": {
              "type": "string",
              "enum": ["create_entity", "update_attr", "append_list", 
                       "remove_from_list", "add_alias", "archive_entity"]
            },
            "entityId": {"type": "string", "description": "非 create_entity 时必填"},
            "entityType": {"type": "string", "description": "create_entity 时必填", 
                           "enum": ["character", "location", "item", "lore", "organization", "misc"]},
            "primaryName": {"type": "string", "description": "create_entity 时必填"},
            "attrKey": {"type": "string", "description": "update_attr/append_list/remove_from_list 时必填"},
            "value": {"type": "string"},
            "reason": {"type": "string", "description": "修改类操作必填"},
            "confidence": {"type": "integer", "minimum": 1, "maximum": 5},
            "importance": {"type": "integer", "minimum": 1, "maximum": 5,
                           "description": "create_entity 时必填。实体重要性评分，决定检索注入频率。评分核心原则：评估该实体在今后剧情中出现的可能性，而非实体在世界观中的地位。5=主角/4=主角团核心/3=常驻配角/2=特定场景/1=路人。除主角团外一律不超过3分。"}
          },
          "additionalProperties": false
        }
      }
    },
    "additionalProperties": false
  }
}
```

### 4.5 为什么用单工具 + 数组参数（不用多工具调用）

- **语义清晰**：一次工具调用 = 一轮的全部事实变更，LLM 不会漏
- **事务友好**：整个 deltas 数组要么全成功要么全失败（drift 事务）
- **降级链兼容**：降级到 JSON 模式时，`{summary, facts:[...]}` 天然支持
- **省 token**：共享一次工具调用开销

## 5. 提示词设计

### 5.1 新增 `extract_facts_prompt`

新增提示词常量 `kExtractFactsToolPrompt`（fieldKey: `extract_facts_prompt`），作为 summarizing 阶段的系统提示词之一：

```
【当前任务：提取事实变更】

你正在协助一个互动故事系统。除了生成事件摘要外，你还需要识别本轮对话中发生的"事实变更"——即对世界设定、角色属性、物品状态等的修改。

【事实变更规则（必须严格遵守）】
1. 默认追加：能追加就追加，不修改现有事实
2. 冲突时修改：只有当新事实与旧事实【直接矛盾】时才修改
   - 直接矛盾的例子：角色名从"李逍遥"变成"王小明"（用户明确改名）
   - 非矛盾的例子：角色多了个新技能（应追加，不修改）
3. 必须标注变更类型：create_entity / update_attr / append_list / remove_from_list / add_alias / archive_entity
4. update_attr 必须给理由：说明为什么修改（如"用户在第8轮明确改名"）
5. 低置信度不修改：如果不确定是否真的冲突，选择追加而非修改

【已知实体上下文】
{{known_entities}}

【识别要点】
- 新出现的角色/宠物/物品/地点 → create_entity
- 角色改名 → update_attr（attrKey="name"）+ add_alias（旧名进别名列表）
- 学会新技能/获得新物品 → append_list
- 角色死亡/物品销毁 → archive_entity
- 用户换称呼 → add_alias

【不要做的事】
- 不要把"主角走了一段路"当作事实变更（这是经历，不是事实）
- 不要在没有明确证据时修改属性（如不要因为"看起来"就改性别）
- 不要为每轮都强行产出事实变更（没有就跳过，不调用 extract_facts）

【输出格式】
调用 extract_facts 工具，传入 deltas 数组。每个 delta 必须包含 action 和 confidence 字段。
```

**2026-07-25 修订（事实层主动性强化）**：

提示词 `kExtractFactsToolPrompt` 进行以下强化（代码为权威，此处仅记摘要）：

1. **新增【信息源优先级】段落**：明确用户消息中关于实体的说明（性格、背景、设定、关系）优先级高于模型回复。用户主动补充角色信息时必须沉淀为事实变更。解决"用户说了角色设定但多轮后实体仍为空"的问题。

2. **【事实变更规则】新增第3条**：性格/背景等 single 类型属性的持久转变（如敞开心扉、态度软化）用 `update_attr` 覆盖，而非只追加。在 reason 中说明转变原因。

3. **【识别要点】新增触发场景**："角色心理或态度的持久转变"（敞开心扉、态度软化、性格成长、信念动摇、放下执念），并增加临时情绪 vs 性格转变的区分指引（情绪短暂不提取，性格转变持久需提取）。

4. **调整保守倾向**：从"大部分轮次没有事实变更"改为"用户明确陈述属性或发生持久转变时应主动产出"，保留"确实无变更时不强行产出"的兜底约束。

**2026-07-26 修订（属性提取引导强化，解决"实体创建但属性为空"问题）**：

用户反馈"换模型后实体能创建，但属性值始终为空，即使文中明确提到角色特点"。排查发现根因：提示词未引导 LLM 在 `create_entity` 时携带属性，且 `personality/background/description` 等关键属性需 confidence>=4，LLM 默认给 3 被系统拒绝。修复方向：

1. **工具定义 `attrKey` 描述明确说明 create_entity 时也可用**：原描述只提"update_attr/append_list/remove_from_list 时必填"，新增"create_entity 时可选（用于在创建实体的同时初始化一个属性）"。

2. **`confidence` 字段描述新增引导**：明确"当用户明确陈述属性或剧情发生持久转变时，应给 confidence=4-5；仅在 LLM 自己推断的隐含信息时才给 3"。

3. **schema 白名单段落标注关键属性**：每个属性后追加 `★关键属性` 标记，明确"关键属性需 confidence>=4 才能修改，LLM 在用户明确陈述时应主动给高 confidence"。

4. **【识别要点】新增"已知实体属性缺失时主动补充"场景**：若 `known_entities` 中某实体存在但缺关键属性，且本轮用户消息或回复正文中明确提及该属性 → 应发起 `update_attr` 补充，并给 confidence=4-5。

5. **新增【正反例】段落**：
   - 正例1：`create_entity` 创建实体同时携带属性（一步到位）
   - 正例2：`update_attr` 补充已知实体缺失属性
   - 正例3：多属性同时提取（`create_entity` 一个属性 + `update_attr` 另一个属性）
   - 反例1：confidence 太低被系统拒绝（personality 是关键属性，需 confidence>=4）
   - 反例2：`create_entity` 不带属性导致属性缺失

**修复目标**：LLM 明确知道 (a) `create_entity` 可同时携带属性；(b) 关键属性需要高 confidence；(c) 已知实体属性缺失时应主动 `update_attr` 补充。

**2026-08-10 修订（update_attr 语义失真防护 + 实体去重强化）**：

用户反馈两个问题：(1) 属性更新导致语义失真——如旧值"在莱茵哈特家侍奉了三代人"被新值"在莱茵哈特家当了n年管家"覆盖，"三代人"的经历信息丢失；(2) 实体重复——"异世界庄园"和"庄园"被创建为两个独立实体。修复方向：

1. **新增【update_attr 使用约束】段落**：明确区分"状态变更"（旧状态不再成立，允许覆盖）与"信息补充/经历追加"（禁止覆盖，必须合并）。允许场景：状态变更（在职->离职）、性格持久转变（冷漠->多疑）、明确更正、信息精炼。禁止场景：经历/历史的补充、新细节的添加、同一事件的不同描述。

2. **新增信息合并规则**：当 `update_attr` 的新值与旧值描述同一方面且信息不冲突时，新值必须包含旧值的有用信息（新值 = 旧值信息 + 新增信息）。无法合并时优先用 `append_list` 到自定义属性。

3. **新增【实体去重规则】段落**：创建新实体前必须检查 `{{known_entities}}` 列表，若新名是已有实体的简称/全称/别称/不同表述，用 `add_alias` 而非 `create_entity`。

4. **新增正反例**：正例——实体去重（add_alias）、信息合并（update_attr 合并新旧值）；反例——经历覆盖（用新描述替换旧经历）。

5. **【不要做的事】新增两条**：不要用新描述覆盖旧经历、不要在未检查已有实体列表的情况下创建新实体。

**修复目标**：LLM 明确知道 (a) `update_attr` 只用于状态变更，经历/历史信息必须合并而非覆盖；(b) 创建新实体前必须检查已有实体列表，避免重复创建。

### 5.2 `known_entities` 上下文注入

提示词中的 `{{known_entities}}` 占位符在运行时被替换为本会话当前所有未归档实体的摘要：

```

- [ent_001] 宠物"旺财"（别名：小金毛）：物种=金毛, 年龄=3个月, 技能=[]
- [ent_002] 宠物"小白"：物种=萨摩耶, 年龄=2个月, 技能=["接飞盘"]
```

**注入策略**：
- 默认注入 importance >= `keyEntityImportanceThreshold - 1`（默认即 4）的未归档实体

- **本轮命中实体强制注入（2026-08-13 漏洞A修复）**：`focusEntityIds`（本轮 retrieving 阶段检索命中的实体 ID）对应的实体即使 importance 低于阈值也注入——让事实更新步骤看得见候选实体，避免对已有实体（如"庄园"）误判为新建（如"异世界庄园"）产生重复。focus 实体全量保留不参与关键实体收紧、排在前面；base 实体按 importance 降序填充剩余配额。由 `SummarizePhaseHandler._buildKnownEntitiesBlock` 从 `ctx.retrievedFacts` 取命中实体 ID 传入。

**降级处理**：

### 6.5 检索可达性硬化（2026-09-09 记忆模块审查）

用户报告「记忆库有一字不差的实体，`query_facts` 却报未命中」。根因不是数据缺失，而是**检索路径只依赖部分索引**：

- `factual_fts` 按设计只索引世界书 `lore` 词条（DOC-15 §7.3），`source=auto/card` 与手动新建实体**永无索引行**；
- 关键词查询此前把整串当一个 FTS 短语（`"图书馆 值班员"` 要求字面连续出现），模型惯用的空格分隔关键词列表 100% 召不回；
- `findByName` 为精确匹配（不 trim、无子串/大小写兜底），且未命中时不会自动降级关键词。

**现行原则：索引只用于排序，不作为唯一可达路径。**

| 通道 | 覆盖 | 作用 |
|---|---|---|
| `findByName` | 主名/别名精确 | 最快路径；`name` 参数 |
| `searchWorldFacts` | `factual_fts`（世界书词条） | 关键词排名 |
| `searchEntitiesByText` | 主表 `primary_name`/`aliases`/属性值 LIKE | **可达性兜底**（不依赖索引） |

配套不变量（均有测试锚定）：

1. 词元切分统一走 `MemoryQuery`（Unicode 空白/标点切分、`<3` 字符走 LIKE、LIKE 通配符转义）；
2. `query_facts` 的 `name` 精确未命中时**无条件**降级关键词 + 主表子串；
3. 未命中信封必须说明检索覆盖面，并区分「本轮新建待落幕提交」与「已归档」——不诱导重复建档；
4. `searchWorldFacts` 最终实体查询带 `session_id` 过滤（不依赖索引行正确性）；
5. `updateEntityBasic` 改名同步 `factual_fts`；`deleteFactsByTurns` 删除实体时同事务清索引行；
6. 非世界书实体的别名更新对 `factual_fts` 是**有意的 no-op**（不扩张索引覆盖面）。

## 7. update 策略与三重防护

### 7.1 三重防护机制

| 防护层 | 机制 | 作用 |
|--------|------|------|
| **提示词约束** | "尽量追加，有冲突时修改" + 必须标注类型和理由 | 第一道防线，让 LLM 谨慎 |
| **冲突检测** | 系统自动检测 key 是否已存在 + 值是否真的不同 | 防止 LLM 把"追加"误标成"修改" |
| **重要性阈值** | importance >= 4 的关键事实，confidence >= 4 才允许修改 | 保护核心设定（角色名/种族等）不被轻易改 |

### 7.2 各动作的防护规则

```dart
class FactApplier {
  void apply(FactsDelta delta, FactualEntity? entity, FactualAttribute? attr) {
    switch (delta.action) {
      case FactAction.createEntity:
        // 防护：检查 primaryName 是否已存在（防重复创建）
        if (entity != null) {
          // 已存在同名实体 → 改为 addAlias
          _applyAddAlias(entity.entityId, delta.primaryName!);
          return;
        }
        // importance 优先使用 LLM 评分（clamp 1-5），未提供时按类型赋保守默认值
        final importance = delta.importance?.clamp(1, 5)
            ?? _defaultImportanceForType(delta.entityType);
        _createEntity(delta, importance);
        break;
        
      case FactAction.updateAttr:
        // 防护1：必须指向已存在实体
        if (entity == null) throw FactException('entity not found');
        // 防护2：值必须真的不同
        if (attr?.value == delta.value) return;  // 无变化，跳过
        // 防护3：关键属性（importance>=4）需要高置信度
        if (attr!.importance >= 4 && delta.confidence < 4) {
          _log.warn('低置信度修改关键属性被拒绝');
          return;
        }
        _updateAttr(attr, delta);
        break;
        
      case FactAction.appendList:
        // 防护：值不能已在列表中
        final list = _parseList(attr?.value);
        if (list.contains(delta.value)) return;  // 已存在，跳过
        _appendList(attr!, delta);
        break;
        
      case FactAction.addAlias:
        // 防护：别名不能与已有主名或别名冲突
        if (entity?.aliases.contains(delta.value) == true) return;
        _addAlias(entity!, delta);
        break;
        
      case FactAction.archiveEntity:
        // 防护：必须指向已存在实体
        if (entity == null) throw FactException('entity not found');
        _archiveEntity(entity, delta);
        break;
    }
  }
}
```

#### 实体类型默认 importance 值（2026-08-06 修订）

LLM 未提供 importance 时，系统按实体类型赋保守默认值。2026-08-06 从"角色=5，设定=4"改为更保守的策略，避免配角/一次性NPC被每轮强制注入。

| 实体类型 | 默认 importance | 说明 |
|---------|----------------|------|
| character | 3 | 默认3分（常驻配角），主角应由 LLM 主动打4-5分 |
| location | 2 | |
| item | 2 | |
| lore | 3 | 通识性设定默认3分，具体规则应由 LLM 打2分 |
| organization | 2 | |
| misc | 1 | |

### 7.3 事务原子性（2026-07-22 修订：单变更容错）

**原设计**：所有 FactsDelta 在一个 drift 事务中应用，任一 delta 失败则整个事务回滚，保证事实层状态一致性。

**修订原因**：实际使用中 LLM 输出的 FactsDelta 格式问题频发（字段缺失、entityId 不存在、schema 不匹配等），整轮回滚导致 `persistRound` 事务回滚，**经历记忆也无法写入**。用户表现为"新对话记忆库一直为空"——这是 v0.2 事实层中间方案上线后最严重的可用性问题。

**修订后策略**：单变更容错。`FactApplier.applyDeltas` 对每个 delta 独立 try-catch，单个 delta 抛异常时记录日志并跳过，不向上传播，不再导致整轮事务回滚。经历记忆始终能写入，事实层部分成功的 delta 保留，失败的 delta 记录日志供后续排查。

```dart
Future<int> applyDeltas(
  String sessionId,
  List<FactsDelta> deltas,
  int turnNumber,
  FactualConfig config,
) async {
  if (!config.enabled || deltas.isEmpty) return 0;

  var appliedCount = 0;
  for (final delta in deltas) {
    try {
      final applied = await _applySingleDelta(
        sessionId,
        delta,
        turnNumber,
        config,
      );
      if (applied) appliedCount++;
    } catch (e, stack) {
      _logger.error(
        'Failed to apply single delta, skipping',
        detail: 'action=${delta.action}, entityId=${delta.entityId}, '
            'attrKey=${delta.attrKey}, error=${e.runtimeType}: $e',
        error: e,
        stackTrace: stack,
      );
    }
  }
  return appliedCount;
}
```

**权衡**：牺牲少量原子性（事实层部分 delta 可能成功部分失败）换取可用性（经历记忆始终能写入）。考虑到 v0.2 事实层为"中间方案"且 LLM 输出格式问题频发，此权衡是合理的——记忆系统可用性优先于事实层严格一致性。v0.3 完整设计中可重新评估是否恢复严格原子性（依赖更成熟的 `update_world` 工具 + 深度合并算法降低格式问题频率）。

**事务边界说明**：`FactApplier.applyDeltas` 不开自身事务，由调用方（`IntermediatePersistenceService.persistRound` / `persistRegeneratedRound`）在 drift transaction 内调用。事务仍包裹经历记忆写入 + 事实层写入，但事实层内部不再向上抛异常，事务不会因事实层单个 delta 失败而回滚。

### 7.4 实体健康度防护（防属性膨胀与过度更新）

#### 7.4.1 问题背景

事实层在实际使用中容易遇到两类健康度问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| 相似属性堆积 | personality 同时存"温顺""乖巧""听话"三个近义词 | 描述性属性被设计为 list 类型，LLM 持续 append 近义词 |
| 主角过度更新 | 主角每轮都产出 FactsDelta，历史表爆炸 | LLM 把"临时状态"误当"持久事实"提取；缺乏频率限制 |
| 属性值膨胀 | location.description 越更新越长 | 每次 update 都加内容，无长度上限 |

#### 7.4.2 属性 schema 白名单（第一层防护）

每种实体类型预定义固定的属性 schema，LLM 只能使用预定义的 attrKey，不能发明新的：

| 实体类型 | attrKey | valueType | 允许 update | 允许 append |
|---------|---------|-----------|------------|------------|
| character | name | single | ✅ | ❌ |
| character | gender | single | ❌ | ❌ |
| character | age | single | ✅ | ❌ |
| character | species/race | single | ❌ | ❌ |
| character | personality | **single** | ✅ | ❌ |
| character | skills | list | ❌ | ✅ |
| character | relationships | dict | ✅ | ✅ |
| character | background | **single** | ✅ | ❌ |
| pet | name | single | ✅ | ❌ |
| pet | species | single | ❌ | ❌ |
| pet | age | single | ✅ | ❌ |
| pet | personality | **single** | ✅ | ❌ |
| pet | skills | list | ❌ | ✅ |
| npc | name | single | ✅ | ❌ |
| npc | role | single | ❌ | ❌ |
| npc | personality | **single** | ✅ | ❌ |
| npc | relationship_with_protagonist | **single** | ✅ | ❌ |
| npc | background | **single** | ✅ | ❌ |
| location | name | single | ✅ | ❌ |
| location | description | **single** | ✅ | ❌ |
| location | features | list | ❌ | ✅ |
| item | name | single | ✅ | ❌ |
| item | description | **single** | ✅ | ❌ |
| item | owner | single | ✅ | ❌ |

**核心约束**：描述性属性（personality/description/background）全部设为 `single` 类型，只能 `update` 不能 `append`。

**LLM 产出 APPEND_LIST 但目标属性是 single 类型时**：系统自动转为 `UPDATE_ATTR`（覆盖），而不是堆积。

**LLM 产出未在 schema 中的 attrKey 时**：系统拒绝入库，记录警告日志。LLM 自动提取路径严格白名单，不支持自定义属性。

**用户手动编辑路径**（2026-07-25 更新）：记忆查看器（MemoryBrowserPage）的实体编辑界面允许用户手动添加自定义属性（不在白名单内）。自定义属性在 UI 上标注"自定义"，LLM 后续无法自动更新这些属性（因 FactApplier 的 schema 白名单检查会拒绝）。这提供了用户灵活性，同时保持 LLM 自动提取的严格性。

**AttributeSchema 扩展**（2026-07-25 新增）：

`AttributeSchema` 类新增以下成员，配合实体编辑界面优化：

| 成员 | 用途 |
|------|------|
| `_labels` | 各 attrKey 的中文友好标签映射（按 entityType -> {attrKey -> 中文标签}），用于 UI 下拉选择展示 |
| `labelFor(entityType, attrKey)` | 获取 attrKey 的中文标签，不在白名单内返回 null（自定义属性场景） |
| `attrKeysFor(entityType)` | 获取某实体类型的所有预定义 attrKey 列表，用于下拉选项 |

**attrKey 别名映射**（2026-07-26 新增，模型适配兼容）：

某些模型（如 agnes-2.0-flash）不严格遵守 schema 白名单，会使用 `description` 等非标准字段描述角色/NPC。`AttributeSchema` 新增 `_attrKeyAliases` 别名映射表和 `normalizeAttrKey(entityType, attrKey)` 方法，将非标准字段自动映射到标准字段：

| 实体类型 | LLM 产出的非标准字段 | 映射到的标准字段 | 原因 |
|---------|---------------------|-----------------|------|
| character | description / history | background | character 无 description 字段，语义上 description ≈ background |
| npc | description / history | background | npc 无 description 字段，语义上 description ≈ background |
| pet | description | personality | pet 无 description 也无 background，语义上 description ≈ personality |
| location | — | — | location 已有 description 字段，无需映射 |
| item | — | — | item 已有 description 字段，无需映射 |

`FactApplier` 在 `_applyCreateEntity` / `_applyUpdateAttr` / `_applyAppendList` / `_applyRemoveFromList` 中均调用 `normalizeAttrKey` 进行标准化，确保所有 attrKey 在 schema 白名单检查前已被映射到标准字段。标准化命中时输出 info 日志（`attrKey normalized: original=description → normalized=background`），便于排查模型行为。

**设计权衡**：别名映射是"模型适配层"的兜底机制，优先级低于提示词约束（提示词明确告知 LLM 用标准字段）。当模型遵守提示词时，别名映射不会触发；当模型不遵守时，别名映射保证属性不丢失。未来若模型行为改善，可移除别名映射。

#### 7.4.3 提示词约束（第二层防护）

`extract_facts_prompt` 追加识别要点：

```
【事实变更识别要点（必须严格遵守）】
1. 只提取"持久性事实"——即后续剧情中可能被引用的设定
2. 不要提取"临时状态"——情绪、当前动作、当前位置不算事实
   - 错误：主角现在很开心（临时状态）
   - 正确：主角性格开朗（持久事实）
3. 不要每轮都强行产出事实变更——大部分轮次没有事实变更
4. 只在以下情况产出事实变更：
   - 新角色/物品/地点首次出现
   - 用户明确改名/更正设定
   - 角色获得新技能/新物品
   - 角色死亡/物品销毁
   - 关系发生实质性变化（如结为好友、反目成仇）
5. 属性值简洁精炼，不超过 200 字
```

#### 7.4.4 系统级去重（第三层防护）

```dart
class FactApplier {
  void applyAppendList(FactualAttribute attr, FactsDelta delta) {
    final list = _parseList(attr.value);
    // 精确匹配去重
    if (list.contains(delta.value)) {
      _log.info('跳过重复值: ${delta.value}');
      return;
    }
    // 语义相似度去重（编辑距离/包含关系，不调 embedding API）
    if (_isSemanticallySimilar(delta.value, list)) {
      _log.info('跳过语义相似值: ${delta.value}');
      return;
    }
    _appendList(attr, delta);
  }
  
  bool _isSemanticallySimilar(String newValue, List<String> existing) {
    for (final v in existing) {
      if (_editDistance(newValue, v) <= 2) return true;
      if (v.contains(newValue) || newValue.contains(v)) return true;
    }
    return false;
  }
}
```

**注意**：语义相似度检测用编辑距离/包含关系，不调 embedding API（成本太高）。

#### 7.4.5 更新频率限制（第四层防护）

同一实体在最近 3 轮内最多允许 4 次更新：

```dart
class FactApplier {
  Future<bool> _checkUpdateFrequency(String entityId, int currentTurn) async {
    final recentUpdates = await _historyRepo.countRecentUpdates(
      entityId: entityId,
      fromTurn: currentTurn - 2,  // 最近 3 轮（含本轮）
    );
    if (recentUpdates >= 4) {
      _log.warn('实体 $entityId 最近 3 轮已更新 4 次，本次跳过');
      return false;
    }
    return true;
  }
}
```

> **默认值调整**（2026-07-26）：默认值从 `2` 调整为 `4`。原值 `2` 在以下场景过严：
> 1. 实体已存在时（如遗留数据、跨会话复用），第一轮的 `create_entity` deltas 会
>    自动转换为 `update_attr`（见 §5.3），多个属性初始化会快速用完配额
> 2. 角色多属性演化（如同时更新 personality + relationship + background）
>    在 2 次配额下难以一次完成
> 调整为 `4` 既保留防滥用能力，又允许合理的多属性初始化场景。

**配置项**（接入 §9 配置）：
```json
"factual": {
  // ... 现有配置 ...
  "max_updates_per_3turns": 4
}
```

#### 7.4.7 防护体系总览

| 防护层 | 机制 | 解决的问题 |
|--------|------|-----------|
| 属性 schema 白名单 | 预定义 attrKey，描述性属性 single 类型 | 相似属性堆积 |

## 8. 状态机集成

### 8.1 summarizing 阶段扩展

```
summarizing 阶段（v0.2 + 事实层）：
  ├─ LLM 请求（同时支持 extract_summary + extract_facts 工具）
  ├─ 解析响应：
  │   ├─ extract_summary 工具调用 → EventSummary（不变）
  │   └─ extract_facts 工具调用 → List<FactsDelta>（新增）
  └─ 降级链：
      工具调用失败 → fallbackText 解析 JSON → JSON 模式 → 只有 EventSummary（事实层不更新）
```

### 8.2 persisting 阶段扩展（2026-07-22 修订：单变更容错）

```
persisting 阶段（v0.2 + 事实层）：
  [drift transaction]
    1. INSERT user message → chat_messages
    2. INSERT assistant message → chat_messages
    3. appendExperience → experiential_memories（微摘要，不变）
    4. embedding != null → updateEmbedding
    5. indexForRetrieval=true → insertFtsIndex
    6. UPDATE session
    7. INSERT intermediate_round_artifacts
    8. 【新增】applyFactsDeltas → factual_entities + factual_attributes + factual_memory_history
       （单变更容错：单个 delta 失败只记录日志，不回滚事务）
  [COMMIT]
```

事实层写入与经历层写入在**同一事务**中，但 `FactApplier.applyDeltas` 内部对每个 delta 独立 try-catch（§7.3），单个 delta 失败不向上抛异常，事务不会因事实层单个 delta 失败而回滚。经历记忆始终能写入。

### 8.3 失败降级（2026-07-22 修订：单变更容错）

```
事实层单个 delta 失败
  ↓
FactApplier.applyDeltas 内部 try-catch 捕获
  ↓
记录日志（action / entityId / attrKey / error），跳过该 delta
  ↓
继续应用后续 delta，事务不回滚
  ↓
经历记忆正常写入，事实层部分成功的 delta 保留
```

**注意**：单变更容错后，事实层失败不再导致整轮失败。只有 persisting 阶段的其他步骤（消息写入、经历记忆写入等）失败才会触发整轮重试 → E012。事实层失败的 delta 通过日志记录供后续排查，可在记忆库查看器中手动补录。

### 8.4 summarizing 阶段双工具并行容错（DOC-11 §4.4，2026-07-20 修复）

**问题背景**：summarizing 阶段 LLM 同时调用 `extract_event_summary` + `extract_facts` 两个工具。当 LLM 只调用 `extract_facts`（不调用 `extract_event_summary`）时，原代码降级 summary 到 JSON 模式后**丢失了已解析的 factsDeltas**——`SummarizePhaseResult(summary: summary)` 未传递 `factsDeltas` 参数。

**修复**：summarizing 阶段降级 JSON 模式时，保留 `_parseFactsSafely` 已解析的 `factsDeltas`：

```dart
// 修复前（丢失 factsDeltas）
return SummarizePhaseResult(summary: summary);

// 修复后（保留 factsDeltas）
return SummarizePhaseResult(summary: summary, factsDeltas: factsDeltas);
```

**设计原则**：facts 工具独立于 summary 工具——summary 降级不应丢弃已解析的事实变更。详见 DOC-09A-2 §6.5.1 失败降级表中的"LLM 只调用 extract_facts"行。

> **测试覆盖**：`summarize_phase_handler_test.dart` 测试 25 验证此场景（LLM 只调 facts → factsDeltas 解析成功 + summary 降级 JSON 模式）。

### 8.5 summarizing 阶段双工具调用提示词引导强化（2026-07-26 修复）

**问题背景**：用户反馈"换模型后实体能创建但属性值为空"。日志显示 LLM 调用了 `extract_event_summary` 但跳过了 `extract_facts` 工具调用，导致 `facts=0`。

**根因分析**：
1. `kExtractSummaryToolPrompt` 的【输出方式】段落只引导 LLM 调用 `extract_event_summary`，未提及 `extract_facts`
2. `_buildMessages` 注入两条独立 system message，LLM 把第一条当主任务，第二条当附加项
3. `tool_choice: "required"` 在 OpenAI API 协议中只要求"至少调用一个工具"，无法强制并行调用两个

**修复方案**：
1. **`kExtractSummaryToolPrompt` 【输出方式】段落改为"必须同时调用两个工具"**：明确列出 `extract_event_summary` + `extract_facts`，要求缺一不可
2. **`kExtractFactsToolPrompt` 【输出方式】段落呼应**：明确告知"必须同时调用 extract_event_summary"，禁止只调用 `extract_facts`
3. **`_buildMessages` 合并两条 system message 为一条**：避免 LLM 把两段提示词当主任务/附加项，让两个工具处于同等地位

**关键代码位置**：
- `lib/core/config/intermediate_prompts_v2.dart`：kExtractSummaryToolPrompt / kExtractFactsToolPrompt 的【输出方式】段落
- `lib/features/intermediate/presentation/controllers/phases/summarize_phase_handler.dart:290-306`：`_buildMessages` 合并实现

### 8.6 串行兜底机制（兼容不支持 parallel_tool_calls 的模型，2026-07-26 修复）

**问题背景**：用户使用 agnes-2.0-flash 模型测试时，事实记忆依然为空。日志显示：

```
L12-L37: 模型调用了 extract_event_summary 工具，参数完整（who/when/where/what/tags/narrativeTime/summary 全有）
L38:     [WARN] LLM 未调用 extract_facts 工具
L39:     facts=0
L40:     Facts not applied (no deltas)
```

尽管 §8.5 已强化提示词要求"同时调用两个工具"，并设置了 `parallel_tool_calls: true` 参数，agnes-2.0-flash 模型依然只调用 `extract_event_summary`，完全跳过 `extract_facts`。

**根因分析**：
1. agnes-2.0-flash 模型不支持 `parallel_tool_calls` 参数（官方文档未提及该参数支持）
2. 模型在多工具可用时，只调用第一个工具（即 `extract_event_summary`），即使提示词明确要求"必须同时调用两者"
3. 这是**模型能力问题**，单靠提示词或参数无法解决

**修复方案——串行兜底机制**：

在原有"工具调用 → JSON 模式"降级链中插入"串行兜底"层，兼容不支持并行工具调用的模型：

```
工具调用（双工具并行注入）
  ↓
解析 summary
  ↓
检测：两个工具是否都被调用？
  ├─ 是 → 完成（支持并行的模型走此路径，无额外开销）
  ├─ 仅 summary 被调用 → 串行兜底：单独发起 extract_facts 调用
  ├─ 仅 facts 被调用 → 走原有 JSON 降级路径（summary 是必填核心任务）
  └─ 都未被调用 → 降级 JSON 模式
```

**关键设计点**：

1. **触发时机**：仅在 summary 已成功解析后，才检查 facts 是否被调用并触发兜底。避免 summary 失败时多发起一次无效 LLM 调用，保持原有 summary 失败降级测试不变。

2. **失败容错**：串行兜底失败（如网络异常、模型仍不调用工具）不抛异常，记 warn 日志，facts 返回空列表。这与 §4.4 "事实层失败不阻塞经历层"原则一致——summary 已成功不应被 facts 兜底失败拖累。

3. **不增加配置开关**：这是模型能力兼容机制，对支持并行的模型（如 agnes-2.5-pro-alpha）无副作用——首次并行调用成功后不会触发兜底。无需用户手动配置。

4. **复用消息构建**：兜底请求复用 `_buildMessages` 构建的 messages（system prompt 已包含两个工具的说明），只注入单个工具，`tool_choice=required` 强制调用。

**关键代码位置**：
- `lib/features/intermediate/presentation/controllers/phases/summarize_phase_handler.dart`：
  - `run()` 方法步骤 1.3：兜底触发逻辑（`hasSummary && !hasFacts` 时调用 `_runSingleToolCall`）
  - `_buildToolCallRequest()` 方法：增加 `tools` 参数支持自定义工具列表
  - `_runSingleToolCall()` 方法：单工具调用请求构建

**对比方案与决策**：

| 方案 | 优点 | 缺点 | 是否采纳 |
|------|------|------|----------|
| 串行兜底（已采纳） | 支持并行的模型无额外开销，不支持的模型自动兜底 | 不支持的模型多一次 LLM 调用，成本翻倍 | ✅ |
| 合并为一个工具 | 一次调用完成两任务 | 工具参数变多，合并后逻辑复杂 | ❌ |
| 分两次请求 | 不依赖模型并行能力 | 永远多一次 LLM 调用，包括支持的模型 | ❌ |
| 放弃该模型支持 | 代码不改 | 该模型在该场景不可用 | ❌ |

**测试覆盖**：原有 36 个测试全部通过，未破坏现有行为。新增测试用例（如需）应覆盖：
- 模型只调用 summary → 触发 facts 兜底 → 返回完整 facts
- 模型只调用 summary → facts 兜底失败 → facts 为空，summary 正常返回
- 模型同时调用两个工具 → 不触发兜底（验证支持并行的模型无额外开销）

## 10. 实体匹配与消歧

### 10.1 别名匹配

检索时按 `primaryName` 或 `aliases` 匹配：

```dart
Future<List<FactualEntity>> findByName(String sessionId, List<String> names) async {
  final result = <FactualEntity>[];
  for (final name in names) {
    final entities = await _db.factualEntities
        .where((e) => e.sessionId.equals(sessionId))
        .where((e) => e.primaryName.equals(name) | e.aliases.contains(name))
        .get();
    result.addAll(entities);
  }
  return result;
}
```

### 10.2 多匹配消歧

若一个名字匹配到多个实体（如同名角色），优先选择 `importance` 最高的。若仍无法消歧，全部注入 prompt 让 LLM 自行判断（基于上下文）。

### 10.3 新实体检测

LLM 在 `extract_facts` 中产出 `CREATE_ENTITY` 时，系统先检查 `primaryName` 是否已存在：

- **已存在 + 携带 `attrKey`+`value`** → 转为 `UPDATE_ATTR`（v1.3 新增）
- **已存在 + 无 `attrKey`/`value`** → 改为 `ADD_ALIAS`（把新名加到已有实体的别名列表）
- **不存在** → 创建新实体（若携带 `attrKey`+`value`，同时初始化属性）

这避免了"同一实体被重复创建"的问题。

**v1.3 修复背景**：原实现实体已存在时一律转 `ADD_ALIAS`，丢弃了 LLM 通过 `CREATE_ENTITY` 携带的 `attrKey` + `value` 信息。当 LLM 因 `{{known_entities}}` 占位符替换失败而不知道 `entityId` 时，会尝试用 `CREATE_ENTITY` 给已存在实体加属性，原逻辑直接丢弃属性信息，导致 `factual_attributes` 表永远无新记录。

修复后，实体已存在且携带 `attrKey` + `value` 时，自动转为 `UPDATE_ATTR` 更新属性；不携带属性时保留原 `ADD_ALIAS` 逻辑。转 `UPDATE_ATTR` 后会经过完整的三重防护 + 5 层健康度防护（schema 白名单、长度上限、更新频率限制等），与正常 `UPDATE_ATTR` 调用一致。

## 15. 边界情况处理

| 场景 | 处理 |
|------|------|
| 事实层功能关闭（`enabled=false`） | 跳过 extract_facts 工具调用，只调用 extract_summary |
| LLM 不调用 extract_facts | 视为本轮无事实变更，正常继续 |
| LLM 调用 extract_facts 但 deltas 为空 | 视为本轮无事实变更，正常继续 |
| CREATE_ENTITY 时 primaryName 已存在 | 改为 ADD_ALIAS，不创建新实体 |
| UPDATE_ATTR 时 entityId 不存在 | 跳过该 delta，记录警告日志 |
| APPEND_LIST 时 attrKey 不存在 | 自动创建属性记录，再追加 |
| 事实层写入失败 | 单变更容错：单个 delta 失败只记录日志不回滚（2026-07-22 修订，原为整轮事务回滚） |
| known_entities 为空（首轮） | 提示词中显示"暂无已知实体" |
| 实体数超过 injection_max_entities | 只注入 importance 最高的 + 本轮命中的 |

## 16. 与 DOC-10（多粒度记忆）的协同

虽然两文档可独立实施，但同时启用时有协同效应：

- **宏摘要 + 事实层**：宏摘要聚合事件，事实层稳定设定，两者互补
- **检索优先级**：宏摘要（经历层）+ 事实层 优先注入，微摘要作为细节补充
- **prompt 结构**：
  ```
  【世界设定】（事实层，稳定不变）
  【相关往事】（宏摘要优先，微摘要细节）
  【草稿】（待修正）
  ```

建议同时启用时，revising prompt 的注入顺序为：世界设定 → 相关往事 → 草稿。
