## 1. 背景与目标

### 1.1 问题

当前供应商配置存在以下局限：

1. **内置供应商硬编码**：仅 3 个（OpenAI/DeepSeek/OpenRouter）写死在 `ApiPresetRepositoryImpl` 静态常量中，扩展需改代码
2. **无协议类型字段**：所有供应商假定 OpenAI 兼容，端点硬编码 `/v1/chat/completions`，SSE 只认 OpenAI 格式
3. **新建流程无模板选择**：用户从空白开始配置，需手填 baseUrl，新手不友好
4. **fork-on-write 机制冗余**：修改内置即 fork 副本，与 ChatBox 覆盖式体验差异大
5. **不支持 Claude/Gemini 原生协议**：无法使用 Claude 的文学性优势（故事模式需要）

### 1.2 目标

- **供应商模板系统**：内置模板（预填 baseUrl/协议/官网），用户新建时选模板即可，只需填 API Key
- **多协议支持**：支持 4 种协议（OpenAI 兼容 / OpenAI Responses / Anthropic 原生 / Gemini 原生）
- **覆盖式配置**：借鉴 ChatBox，内置供应商支持覆盖式更新 + 重置，移除 fork-on-write
- **多账号支持**：用户可"基于模板新建"创建自定义实例，支持同一供应商多账号

### 1.3 范围

- **包含**：模板注册表、协议适配层、SSE 解析器分层、UI 改造、数据库迁移
- **不包含**：Embedding 多协议适配（v0.1/v0.2 仅 OpenAI 兼容）、Claude thinking signature 跨轮持久化（v0.3）、Vertex AI（仅 AI Studio）、Azure（复用 OpenAI 协议，本期不做特殊处理）

## 2. 总体架构

### 2.1 分层结构

```
                    LlmService（Domain 层接口，不变）
                           │
                   LlmRemoteDataSource（调度器）
                           │
            按 preset.protocol 分发到 4 个适配器
                           │
        ┌──────────┬───────┴────────┬──────────────┐
        ▼          ▼                ▼              ▼
  OpenAiAdapter  ResponsesAdapter  AnthropicAdapter  GeminiAdapter
        │          │                │              │
        └──────────┴───────┬────────┴──────────────┘
                           │
                   RawSseChunkParser（底层共享）
```

**设计原则**：
- `LlmService` 接口不变，调用方（SimpleChatController 等）零感知
- 每个协议独立适配器，实现"构造请求 URL/Header/Body + 解析响应/SSE"
- SSE 解析分两层：底层共享切分逻辑，协议层各自解析事件格式
- 协议类型存在 `ApiPreset.protocol` 字段，运行时按此字段选择适配器

### 2.2 供应商模板系统（借鉴 ChatBox 注册表模式）

- 模板在代码里静态注册（不进数据库）
- **供应商列表初始为空**，不自动初始化内置 preset（避免首次安装出现大量未配 Key 的占位项）
- 用户通过"+新建"基于模板创建 preset（`isBuiltIn=false`，记录 `templateId`）
- 基于 `templateId` 的 preset 可"重置"为模板默认值，也可删除
- 用户可"基于模板新建"创建多个实例支持多账号

enum LlmProtocol {
  openaiCompatible,   // OpenAI Chat Completions（含 DeepSeek/OpenRouter 等兼容供应商）

## 5. 协议适配层

### 5.1 适配器接口

```dart
// lib/core/network/llm_adapters/llm_protocol_adapter.dart
abstract class LlmProtocolAdapter {
  /// 构造完整请求 URL（含路径）
  ///
  /// [baseUrl] 为供应商根 URL（如 `https://api.openai.com`）
  /// [modelId] 用于 Gemini 等需要把模型名拼到路径里的协议
  /// [stream] 区分流式/非流式端点（如 Gemini `:streamGenerateContent`）
  String buildUrl(String baseUrl, String modelId, {required bool stream});

  /// 构造请求头（含认证 + 协议特有 header）
  ///
  /// [request] 提供完整请求上下文：
  /// - `request.apiKey`：认证凭据
  /// - `request.providerOptions['extra_headers']`：协议特有 header
  ///   （如 OpenRouter 的 HTTP-Referer/X-Title）
  /// - `request.providerOptions['anthropic_beta']`：Anthropic beta 特性标识
  ///
  /// 适配器自行决定需要注入哪些协议 header（如 Anthropic 始终注入
  /// `anthropic-version: 2023-06-01`），调用方无需感知协议差异。
  Map<String, String> buildHeaders(LlmRequest request, {Map<String, String>? extra});

  /// 构造请求体 JSON
  ///
  /// 将统一的 [LlmRequest] 转换为协议特定的请求体结构：
  /// - OpenAI: `{model, messages, stream, ...}`
  /// - Anthropic: `{model, messages, system, max_tokens, ...}`
  /// - Gemini: `{contents, systemInstruction, generationConfig, ...}`
  Map<String, dynamic> buildRequestBody(LlmRequest request, {required bool stream});

  /// 解析流式响应为统一事件流
  Stream<LlmStreamEvent> parseStream(Stream<String> rawStream);

  /// 解析非流式响应
  LlmResponse parseResponse(Map<String, dynamic> body);

  /// 获取模型列表的端点 URL（用于"获取模型"功能）
  String buildModelsUrl(String baseUrl);
}
```

### 5.2 适配器实现要点

| 适配器 | 端点 | 认证头 | 关键差异 |
|--------|------|--------|----------|
| `OpenAiAdapter` | `/v1/chat/completions` | `Authorization: Bearer` | 现有逻辑重构下沉；通用 OpenAI 兼容协议，不携带任何供应商特化逻辑 |
| `DeepSeekAdapter` | `/v1/chat/completions` | `Authorization: Bearer` | 继承 `OpenAiAdapter`，仅处理 DeepSeek 专属兼容性差异（§5.4.2）：思考模式下 `tool_choice:"required"` 不支持、不支持 `parallel_tool_calls`。路由由 `LlmAdapterFactory` 在 `openaiCompatible` 协议下按端点判定自动分发（§5.3） |
| `OpenAiResponsesAdapter` | `/v1/responses` | `Authorization: Bearer` | `input` 替代 `messages`，`output` 数组结构 |
| `AnthropicAdapter` | `/v1/messages` | `x-api-key` + `anthropic-version: 2023-06-01` | `system` 顶层字段、`max_tokens` 必填、`tools` 字段名 `input_schema`、`thinking` 参数 |
| `GeminiAdapter` | `/v1beta/models/{model}:generateContent` | `x-goog-api-key` | `contents` 替代 `messages`、role 是 `user`/`model`、`generationConfig` 包裹采样参数、`systemInstruction` 顶层 |

**供应商特化隔离原则**：通用适配器（`OpenAiAdapter`）严禁被某一家供应商的特化逻辑污染。任一供应商若存在与 OpenAI 标准不兼容的差异，应通过继承 `OpenAiAdapter`（或实现 `LlmProtocolAdapter`）的方式新建专属适配器，由 `LlmAdapterFactory` 按端点信息路由分发。`DeepSeekAdapter`（2026-07-28 新增）是首个按此模式落地的供应商专属适配器。

### 5.3 适配器工厂

```dart
// lib/core/network/llm_adapters/llm_adapter_factory.dart
class LlmAdapterFactory {
  /// 构造时创建单例适配器，支持依赖注入（测试场景）
  LlmAdapterFactory({
    OpenAiAdapter? openaiAdapter,
    DeepSeekAdapter? deepSeekAdapter,
    AnthropicAdapter? anthropicAdapter,
    GeminiAdapter? geminiAdapter,
  })  : _openaiAdapter = openaiAdapter ?? OpenAiAdapter(),
        _deepSeekAdapter = deepSeekAdapter ?? DeepSeekAdapter(),
        _anthropicAdapter = anthropicAdapter ?? AnthropicAdapter(),
        _geminiAdapter = geminiAdapter ?? GeminiAdapter();

  final OpenAiAdapter _openaiAdapter;
  final DeepSeekAdapter _deepSeekAdapter;
  final AnthropicAdapter _anthropicAdapter;
  final GeminiAdapter _geminiAdapter;

  /// 按协议类型 + 端点信息（baseUrl + modelId）获取适配器
  ///
  /// **路由规则**：
  /// - `openaiCompatible` 协议下，若 [DeepSeekAdapter.isDeepSeekEndpoint]
  ///   判定为 DeepSeek 端点（baseUrl 含 `deepseek.com` 或 modelId 以
  ///   `deepseek-` 开头且不含 `/`），返回 [DeepSeekAdapter]
  ///   （处理 DeepSeek 专属兼容性差异：tool_choice=required 降级、
  ///   跳过 parallel_tool_calls）；否则返回 [OpenAiAdapter]
  /// - 其他协议直接返回对应适配器
  ///
  /// OpenAI Responses 协议返回 ResponsesAdapter（2026-11-02 落地）。
  LlmProtocolAdapter getAdapter({
    required LlmProtocol protocol,
    required String baseUrl,
    required String modelId,
  }) {
    switch (protocol) {
      case LlmProtocol.openaiCompatible:
        if (DeepSeekAdapter.isDeepSeekEndpoint(baseUrl, modelId)) {
          return _deepSeekAdapter;
        }
        return _openaiAdapter;
      case LlmProtocol.anthropic:
        return _anthropicAdapter;
      case LlmProtocol.geminiNative:
        return _geminiAdapter;
      case LlmProtocol.openaiResponses:
        return responsesAdapter; // 2026-11-02 落地
    }
  }
}
```

`LlmRemoteDataSource` 持有 `LlmAdapterFactory`，按 `preset.protocol` + 端点信息（`baseUrl` + `modelId`）获取适配器。

**为什么 `getAdapter` 需要 `baseUrl` + `modelId` 参数（2026-07-28 变更）**：

原 `getAdapter(LlmProtocol protocol)` 签名仅按协议分发，无法区分同一 `openaiCompatible` 协议下的不同供应商端点。DeepSeek 端点存在两项与 OpenAI 标准不兼容的差异（§5.4.2），需要路由到 `DeepSeekAdapter` 处理。为此扩展 `getAdapter` 签名为 `{protocol, baseUrl, modelId}`，由 `DeepSeekAdapter.isDeepSeekEndpoint` 静态方法判定是否为 DeepSeek 端点。

判定规则（满足任一即认定为 DeepSeek 端点）：
- `baseUrl` 含 `deepseek.com`（官方端点 `api.deepseek.com` / beta 端点）
- `modelId` 以 `deepseek-` 开头且不含 `/`（排除 OpenRouter 的 `deepseek/xxx` 形式，OpenRouter 作为中间层会自行处理兼容性）

判定大小写不敏感。

**单例语义说明**：工厂持有适配器实例而非每次 `new`，原因：
1. 适配器内部 SSE 解析器有状态（如 `_blocks` Map），每次 `new` 会重置状态，但解析器自身在 `parse()` 方法入口会重置，单例可安全复用
2. 减少 GC 压力（高频调用场景）
3. 测试场景可通过构造参数注入 mock 适配器

| 入参 | 处理 | 原因 |
|------|------|------|
| `tool_choice:"required"` | 删除字段（降级为默认 `auto`） | 思考模式下 400 |
| `tool_choice:"auto"` / `"none"` | 正常发送 | DeepSeek 支持 |
| `parallel_tool_calls:true` | 删除字段 | DeepSeek 不支持 |
| `thinking` / `reasoning_effort` | 正常发送（ThinkingParamBuilder 构建） | DeepSeek-V3.2+ 支持思考+工具调用 |
| `tools` 字段 | 正常发送 | 工具定义本身不受影响 |

#### 5.4.6 输出 Token 上限统一策略（v1.6）

`LlmRequest.maxTokens` 使用统一产品语义：正整数表示应用层上限，`0` 表示不设置应用层输出上限。正整数在模型 `maxOutput` 元数据已知时取较小值，避免向供应商发送超出模型能力的数值。各协议映射如下：

| 协议 | `maxTokens > 0` | `maxTokens = 0` |
|------|-----------------|-----------------|
| OpenAI-compatible | 普通模型发送 `max_tokens`；o1/o3/o4 发送 `max_completion_tokens` | 省略对应输出上限字段 |
| Gemini native | 发送 `generationConfig.maxOutputTokens` | 省略 `maxOutputTokens`，使用模型/供应商默认行为 |
| Anthropic Messages | 发送必填的 `max_tokens` | 优先使用模型 `maxOutput` 元数据；元数据缺失时回退 8192，不再直接报错 |

该策略只控制协议请求。故事模式上下文组装另行计算输出预留，`maxTokens=0` 时仍预留 8192 token，避免输入占满上下文窗口。

#### 5.4.7 OpenAI Responses（openaiResponses 协议，2026-11-02 落地）

GPT-5.4 起 Chat Completions 工具调用仅限 `reasoning_effort:"none"`；GPT-6 Astra / 6.1 Sol / 6.1 Terra 在 CC 上完全不支持工具调用（GPT-6 Sol/Luna 仅 effort=none）——导演/中级模式的工具链在这些模型上必须走 Responses（背景与双证据见 `doc/reports/2026-11-02_API兼容性审计/`）。

| 差异点 | 说明 |
|--------|------|
| 端点 | `POST {baseUrl}/responses`（ApiUrlResolver 归一化同 CC；端点后缀剥离表已含 `/responses`） |
| 认证 | `Authorization: Bearer`（同 CC，含 extra_headers 透传） |
| 消息结构 | `input` items 替代 `messages`：system 提取到顶层 `instructions`；assistant 文本 → message item；tool_calls → 独立 `function_call` items（call_id/name/arguments 原始 JSON 串）；role:"tool" → `function_call_output` item（call_id + output） |
| 工具定义 | 扁平格式 `{type:'function', name, description, parameters}`（非 CC 的嵌套 function 对象）；tool_choice 取值同 CC |
| 输出上限 | `max_output_tokens`（无 max_tokens / max_completion_tokens） |
| 采样参数 | 官方规则：推理档位非 none 时必须移除 temperature/top_p——档位启用（low/medium/high）时不发；档位未配置时经统一判定（供应商开关 + moonshot 端点家族 + 模型名单，见 §5.4.1）取整下发 |
| 推理参数 | `reasoning:{effort}`（档位映射）；Responses 无关闭取值，disabled 不发参 |
| 结构化输出 | `response_format` → `text.format`（json_object / json_schema{name,schema,strict}） |
| 无 penalties/stop/seed/n | 这些 CC 参数在 Responses 参数表中不存在，一律不发 |
| 流式 | `event:`+`data:` 双行；终止信号 `response.completed` 事件（无 [DONE] 哨兵，中转追加时兼容）；usage 恒随 completed 返回（无 stream_options.include_usage） |
| usage | `input_tokens`/`output_tokens`/`total_tokens` + `input_tokens_details.cached_tokens`（与 CC 命名不同，适配层归一到 LlmUsage） |
| 截断语义 | `status=incomplete` + `incomplete_details.reason`（max_output_tokens 归一为 CC 词表 `length`）；`status=failed` 上抛 finishReason=failed |
| reasoning 回放 | `reasoning_content` 不回放——Responses 的 reasoning item 携带服务端加密内容，无法从明文字符串重建；省略后模型自行重新推理（可用，损失推理连续性） |

### 5.6 思考参数统一适配（v1.3 已落地；v1.7 端点化路由）

**背景**：原 `OpenAiAdapter.buildRequestBody` 只有 3 条思考参数路径（`providerOptions.thinking` / DeepSeek V4 thinking / 默认 `reasoning_effort`），缺少 Qwen3 / GLM-4.6 / Kimi / OpenRouter 适配，导致这些模型即使 `supportsReasoning=true` 也无法开启思考。同时故事模式 4 阶段使用独立模型配置（`phaseModels`），原单一 `supportsReasoning` 字段查的是 Simple 模式默认模型，与故事模式实际模型脱节，导致 `reasoningEffort` 永远为 null，思考参数完全不发送。

**解决方案**：两件套——`ThinkingParamBuilder`（统一参数构建）+ `ModelCapabilityInferrer`（能力兜底推断）。v1.4 起，所有适配器（OpenAI/DeepSeek/Anthropic/Gemini）统一执行"disabled 最高优先级"规则，且 reasoningEffort 无条件传递由适配器层过滤。

#### 5.6.1 ThinkingParamBuilder：端点家族 × 模型能力两步路由（v1.7）

文件：`lib/core/network/llm_adapters/thinking_param_builder.dart`

**v1.7 重构（2026-09-09）**：路由从「纯 modelId 推断方言」改为两步——第一步按 `baseUrl` 判定**端点家族**，第二步在家族内按 modelId 做**能力判定**（是否本厂思考模型、支持哪些档位），modelId 不再直接决定键名。

> **背景（两次同模式故障）**：
> - 2026-09-08：AMD OpenAI 兼容端点 `developer.amd.com.cn` + `DeepSeek-V4-Flash-Vision-Exp`，模型名命中 DeepSeek 分支发出官方方言 `thinking:{type:enabled}`，第三方端点只认 `reasoning_effort` → 400（BAD_REQUEST 不可重试）→ 导演轮 EAGENT。
> - 2026-09-08：GLM-5.3 发 medium 档被端点 400 拒收。
>

**优先级**（从高到低，2026-07-28 修订）：

1. `reasoningEffort == disabled`（显式禁用）→ 按 modelId 路由发送**显式关闭参数**，优先级最高，覆盖 providerOptions 透传
   - **背景**：原代码把 disabled 与 null 都当作"不发参数"，但对绝大多数思考模型（DeepSeek-V3.1+/V4、Qwen3、GLM-4.6、Kimi K2-thinking 等），不发参数 = 模型默认行为 = 开启思考，导致"禁用"按钮无效
   - **各模型关闭参数**：DeepSeek-V3.1+/V4 用 `thinking:{type:disabled}`，Qwen3 用 `enable_thinking:false`，GLM-4.6 用 `thinking:{type:disabled}`，Kimi 用 `enable_thinking:false`，Agnes 2.0 Flash 用 `chat_template_kwargs:{enable_thinking:false}`，OpenRouter 用 `reasoning:{enabled:false}`
   - **不支持关闭的纯思考模型**（DeepSeek-R1、OpenAI o-series）返回空 Map，调用方应理解为"该模型无法关闭思考，需切换模型才能禁用"
2. `providerOptions.thinking` 或 `providerOptions.reasoning` 存在 → 直接透传（高级用户手动配置，仅在用户未显式禁用时生效）
3. `reasoningEffort` 启用（非 null 非 disabled）→ 按 modelId 适配原生参数
4. `reasoningEffort == null`（未配置）→ 返回空 Map（不发送任何思考参数，跟随模型默认行为）

> **disabled vs null 语义差异**（2026-07-28 新增）：
> - `null`（未配置/跟随全局）→ 不发参数，跟随模型默认行为（对思考模型通常为开启思考）
> - `disabled`（显式禁用）→ 发送厂商原生关闭参数，强制关闭思考
> - 用户在会话设置中选"跟随全局"→ 存 null；选"禁用"→ 存 disabled。两者行为不同，UI 必须明确区分。

**调用方**：
- `OpenAiAdapter.buildRequestBody`：故事模式所有 LLM 请求（drafting / extracting / revising / summarizing + macro_summary）
- `ChatModeController._buildRequestBody`：Simple 模式聊天请求

**SSE 思考链解析**：本类只负责请求参数构建，响应解析由 `SseParser` 统一处理（兼容 `delta.reasoning_content` 和 `delta.reasoning` 两种字段，详见 §6.2）。

#### 5.6.5 故事模式思考的特别意义

故事模式不同阶段对思考的需求不同：

| 阶段 | 思考价值 | 默认推荐 |
|------|---------|---------|
| drafting（草稿） | **避免低级错误**：理清剧情逻辑、人物动机、时间线连贯性 | medium |
| extracting（提取） | 关键词提取任务简单，思考价值低 | disabled 或 low |
| revising（终稿） | **"去 AI 味"+"审查草稿"**：识别草稿中的 AI 口吻、逻辑漏洞、人设崩坏 | high |
| summarizing（摘要） | 事件摘要 + 事实提取，需要思考判断重要性 | medium |

**用户配置入口**：通用设置 → 高级 → 思考预算（`reasoningEffort` 全局默认值），可在会话级设置覆盖。

## 6. SSE 解析器分层

### 6.1 底层 RawSseChunkParser（共享）

```dart
// lib/core/network/sse/raw_sse_chunk_parser.dart
class RawSseChunkParser {
  /// 按双换行切分事件块，提取 event:/data: 字段
  Stream<({String? event, String data})> parse(Stream<String> rawStream);
}
```

协议无关，所有协议复用。

### 6.2 协议层解析器

| 解析器 | 复杂度 | 关键逻辑 |
|--------|--------|----------|
| `OpenAiSseParser` | 低（现有重构） | `choices[0].delta` 结构，字段 content/reasoning_content/reasoning/tool_calls |
| `AnthropicSseParser` | 高（状态机） | 6 事件类型 + 4 delta 类型，维护 content_block 索引 |
| `GeminiSseParser` | 中 | `candidates[0].content.parts` 数组，`thought: true` 标识推理 |
| `ResponsesSseParser` | 中 | `event:`+`data:` 双行（复用 RawSseChunkParser 的 event 字段）；`response.output_text.delta` 文本、`response.reasoning_summary_text.delta` 思考摘要、function_call 按 item_id 累积（`args.done` 完整串优先，`output_item.done` 兜底）、`response.completed` 携带 usage（input/output 命名）并终止（无 [DONE] 哨兵）、failed/incomplete/error 语义收尾（max_output_tokens 归一为 length） |

### 6.3 Anthropic SSE 事件类型

| 事件 | 用途 |
|------|------|
| `message_start` | 初始化 Message 对象 |
| `content_block_start` | 开始 content block，含 index 和类型 |
| `content_block_delta` | 增量更新 block（text_delta/input_json_delta/thinking_delta/signature_delta）|
| `content_block_stop` | 结束 block |
| `message_delta` | 顶层变更（stop_reason、cumulative usage）|
| `message_stop` | 流结束 |

### 6.4 统一事件类型

保持现有 `LlmStreamEvent` sealed class 不变，新增 `LlmThinkingBlockComplete` 事件：

| 事件类型 | 用途 | 各协议支持情况 |
|----------|------|---------------|
| `LlmTextDelta` | 文本增量 | OpenAI / Anthropic / Gemini |
| `LlmThinkingDelta` | 思考内容增量（字符串） | OpenAI（reasoning_content）/ Anthropic（thinking_delta）/ Gemini（thought:true）|
| `LlmThinkingBlockComplete` | **思考块完成（含 signature，v1.1 新增）** | Anthropic 专用（content_block_stop 时发出，含完整 thinking + signature） |
| `LlmToolCallStart` | 工具调用开始（含 id + name） | OpenAI / Anthropic / Gemini |
| `LlmToolCallArgs` | 工具调用参数增量 | OpenAI / Anthropic；Gemini 完整返回不发此事件 |
| `LlmToolCallComplete` | 工具调用完成（arguments 已解析为 Map） | OpenAI / Anthropic / Gemini |
| `LlmStreamDone` | 流正常结束（含 usage） | 全部协议 |
| `LlmStreamError` | 流内错误 | 全部协议 |

**`LlmThinkingBlockComplete` 设计说明**（v1.1 新增）：

Anthropic Claude 的 thinking block 由两部分组成：
- `thinking`：思考内容明文
- `signature`：服务端加密签名，多轮对话中必须原样回传，否则 400 错误

`LlmThinkingDelta` 只承载增量文本，无法表达 signature。因此新增 `LlmThinkingBlockComplete` 事件，在 Anthropic 流式响应的 `content_block_stop`（type=thinking）时发出，携带完整 thinking 文本 + signature。

调用方（如 `IntermediateChatController`）应缓存此事件信息，在下一轮请求构造 assistant 消息时写入 `thinking` block 含 signature。OpenAI/DeepSeek/Gemini 适配器不发此事件（它们用 `LlmThinkingDelta` 累积字符串，无 signature 概念）。

详见 `lib/features/chat/domain/services/llm_service.dart` 中 `LlmThinkingBlockComplete` 和 `LlmThinkingBlock` 类注释。

### 7.2 LlmResponse 新增字段

```dart
class LlmResponse {
  final String content;
  final LlmUsage? usage;
  final List<ToolCall>? toolCalls;

  /// LLM 思考/推理内容（来自 reasoning_content 字段）
  ///
  /// DeepSeek V4 thinking 模式 / Gemini thought:true 标识使用此字段。
  /// 多轮工具调用场景下，调用方需将此字段回传给 API。
  final String? reasoningContent;

  /// Anthropic 结构化 thinking blocks（含 signature，v1.1 新增）
  ///
  /// 仅 Anthropic 协议响应有值，OpenAI/DeepSeek/Gemini 为 null。
  /// 多轮对话中调用方必须将此列表原样回传到下轮请求的 messages 中，
  /// 否则 Anthropic 服务端 signature 验证失败（400 错误）。
  ///
  /// 与 [reasoningContent] 互斥：OpenAI/DeepSeek/Gemini 用 reasoningContent，
  /// Anthropic 用 thinkingBlocks，两者不会同时有值。
  final List<LlmThinkingBlock>? thinkingBlocks;
}
```

`LlmThinkingBlock` 是值对象，含 `thinking`（明文）+ `signature`（加密签名）两个字段。

### 7.3 调用方回传规则

| 协议 | 思考内容回传字段 | 回传要求 |
|------|----------------|---------|
| OpenAI / DeepSeek | `messages[i].reasoningContent` | 字符串，无 signature 概念 |
| Anthropic | `messages[i].thinkingBlocks`（content 数组中的 thinking block） | 必须含 signature，否则 400 |
| Gemini | `messages[i].parts[{thought:true, text:...}]` | 无 signature，thought 标识即可 |

适配器在 `_convertMessages` 时按上表规则从 OpenAI 风格 messages 还原为协议原生格式。详见各适配器的 `_convertMessage` 方法实现。

### 7.4 NamingConfig 扩展（v1.4 已落地，2026-07-28）

**背景**：v1.1 落地 `LlmRequest.protocol` / `providerOptions` 两字段后，适配器层已实现读取逻辑（OpenRouter extra_headers / Anthropic anthropic_beta / Gemini thinkingConfig / DeepSeek thinking 等），但 `NamingConfig`（`configuration_resolver.dart` 中承载 API 配置的值对象）仅有 `baseUrl` / `apiKey` / `modelId` 3 个字段，导致：

1. **协议适配错误分发**：所有用 NamingConfig 构造 LlmRequest 的地方 `protocol` 恒为默认值 `openaiCompatible`，Claude/Gemini 适配器实际无法被选中，Claude/Gemini 请求会错误走 `OpenAiAdapter` 必然失败
2. **providerOptions 透传机制失效**：适配器侧已实现读取 `request.providerOptions` 的逻辑，但无任何调用方填充该字段，透传机制完全空转

**解决方案**（v1.4 三步修复）：

1. **NamingConfig 加 2 字段**：`protocol`（`LlmProtocol`，默认 `openaiCompatible` 兼容 v0.1 旧数据）+ `providerOptions`（`Map<String, dynamic>?`，nullable）
2. **resolve 方法填充**：`ConfigurationResolver.resolveTitleNamingConfig` / `resolveIntermediatePhaseNamingConfig` 从 `ApiPreset.protocol` / `ApiPreset.providerOptions` 提取并填充到 NamingConfig
3. **11 个 LlmRequest 构造点透传**：所有调用方从 NamingConfig 透传 `protocol` + `providerOptions` 到 LlmRequest

**11 个 LlmRequest 构造点清单**：

| # | 文件 | 阶段/用途 | NamingConfig 来源 |

## 11. 风险与限制

| 风险 | 缓解措施 |
|------|----------|
| Claude 不支持 `response_format`（JSON Schema） | 故事模式两步生成在 Claude 上降级为 `output_config.format`(2026-01 GA) 或 strict tool + 解析容错 |
| Claude `thinking` signature 跨轮验证 | v0.1/v0.2 仅内存缓存单次请求，不持久化；v0.3 再做 |
| Anthropic SSE 状态机复杂 | 参考 ChatBox `@ai-sdk/anthropic` 实现，先写全覆盖单元测试再集成 |
| ⚠️ DeepSeek 模型名 2026-07-24 停用（今天生效） | 紧急任务：迁移到 `deepseek-v4-flash`/`deepseek-v4-pro`，V4 架构通过 `thinking` 参数切换思考模式 |
| DeepSeek reasoning_content 续传 | tool call 场景必须完整回传，chat_messages 表需考虑存储 reasoning_content 字段 |
| DeepSeek 废弃参数 | V4 已废弃 presence_penalty/frequency_penalty，UI 层对 DeepSeek 模型应隐藏这两个设置项 |
| Gemini 安全过滤拦截 | 角色扮演场景需主动设置宽松 `safetySettings`（如 BLOCK_ONLY_HIGH），否则剧情可能被误判 |
| Gemini thinking 双轨制 | 按模型 ID 判断用 `thinkingLevel`(Gemini 3) 还是 `thinkingBudget`(Gemini 2.5)，不可同时用 |
| OpenAI 推理模型参数限制 | o1/o3/o4 系列不支持 temperature/top_p 等，适配器需按模型过滤参数避免 400 |
| OpenAI o1-preview/o1-mini 极度受限 | 不支持 system role/tools/streaming，检测到时需特殊处理（system 合并到 user） |
| Embedding 仅支持 OpenAI 兼容 | UI 上明确提示；Gemini embedding 768 维与 OpenAI 1536 维不可混算 |
| Anthropic OAuth 违规 | 仅支持 API Key 认证，不要实现 OAuth 路径（违反 2026-04 服务条款） |
| OpenAI OAuth 不适用移动端 | Codex CLI 的 redirect_uri 硬编码 localhost，第三方移动 App 不可用 |
| 思考参数适配依赖 modelId 关键词匹配 | `ModelCapabilityInferrer` 和 `ThinkingParamBuilder` 基于 modelId 模式匹配，新模型上线需手动补充关键词；用户可在模型编辑对话框手动勾选 `reasoning` 能力覆盖推断结果 |
| Qwen3 thinking_budget 档位硬编码 | low=4096/medium=8192/high=16384 是基于 Qwen3 推荐值的硬编码，后续模型迭代可能需要调整 |
| DeepSeek V3.1+ reasoning_effort 仅 high 档发送 | low/medium 不发 `reasoning_effort`（默认中等思考），仅 high 档额外发参数；如供应商后续支持 low/medium 档位需更新逻辑 |
| 故事模式各阶段思考档位无法独立配置 | 当前 `reasoningEffort` 是全局/会话级配置，4 阶段共用同一档位；v0.3+ 可考虑支持阶段级独立配置（如 drafting=medium / revising=high） |
