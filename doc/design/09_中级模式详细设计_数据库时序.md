## 1. 持久化阶段完整时序

```
summarizing 完成（解析出 eventSummary，V2 四步流程的最后一步）
  │ V2 四步流程：generating → extracting → retrieving → reviewing → summarizing → persisting（v0.2.2 阶段名重命名：drafting→generating、revising→reviewing）
  │ 前置步骤产出已存入 RoundContext：
  │   - generatedText（generating 产出，纯文本；v0.2.2 重命名：draftText → generatedText）
  │   - draftKeywords（extracting 产出，结构化；字段名保留兼容，artifacts 表列名）
  │   - retrievedMemories（retrieving 产出）
  │   - replyText（reviewing 产出，纯文本；2026-07-16 移除 compact 降级后 reviewing 始终执行，replyText 始终为 reviewing 产出）
  │   - eventSummary（summarizing 产出，5W1E 结构化：when/where/who/what/significance/extra）
  │
  ▼
[两级向量化决策]（DOC-10 §8.2，schemaVersion=19 启用）
  │ 基于 eventSummary.importance 与两个阈值比较：
  │ - importanceStorageThreshold（默认 3）：FTS5 索引门槛
  │ - microVectorizeThreshold（默认 4）：embedding 向量化门槛
  │
  │ importance < 3              → 不建 FTS5、不建 embedding（仅留原始记录）
  │ 3 <= importance < 4         → 仅建 FTS5（indexForRetrieval=true, embedding=null）
  │ importance >= 4             → 建 FTS5 + embedding（indexForRetrieval=true, embedding=Vec）
  │
  ▼
[同步调用 embedding API]（仅当 importance >= microVectorizeThreshold 时调用）
  │ timeout: 5000ms
  ├── 成功 → embedding = Vec<f32>
  └── 失败 → embedding = null（降级 has_embedding=false，FTS5 索引仍建）
  │
  ▼
[开启 drift transaction]
  │
  ├─ 0. CompactionPoint 压缩持久化（仅在本轮触发了压缩时执行）
  │     条件：compaction != null（compacting 阶段产出了压缩摘要）
  │     写入三部分（均在同一事务内，保证原子性）：
  │     a. INSERT 摘要消息 → chat_messages
  │        (sessionId, role=system, content=压缩摘要, isSummary=true, createdAt)
  │        摘要消息 createdAt 早于 user/assistant，排序时位于对话之前
  │     b. INSERT 压缩点记录 → compaction_points
  │        (sessionId, summaryMessageId, boundaryMessageId, createdAt)
  │        summaryMessageId ↔ boundaryMessageId 映射，供 fork/删除操作定位压缩范围
  │     c. INSERT 宏摘要记忆 → experiential_memories
  │        (memory_level=macro, macro_trigger_reason=compaction, importance=5,
  │         tags=['compaction', 'macro_summary'], turnNumber=当前轮次)
  │        + INSERT FTS5 索引 → memories_fts（供记忆查看器浏览，不参与 macroBoost 检索）
  │     双重职责：压缩摘要既是 generating/reviewing 的稳定前缀，
  │     又作为宏摘要留档。compacting 阶段仅生成摘要存内存，本步骤同事务持久化。
  │
  ├─ 1. INSERT user message → chat_messages
  │     (sessionId, role=user, content=userInput, createdAt)
  │
  ├─ 2. INSERT assistant message → chat_messages
  │     (sessionId, role=assistant, content=replyText, createdAt)
  │
  ├─ 3. INSERT event summary + embedding → experiential_memories
  │     (memoryId=UUID程序生成, sessionId, summary(可空，DB NOT NULL 用空字符串兜底), importance, tags, turnNumber,
  │      when_text, where_text, who_text, what_text, significance, extra（5W1E 6 字段）,
  │      embedding=BLOB(如成功且importance>=microVectorizeThreshold), has_embedding=(embedding!=null), createdAt)
  │     memoryId 作为业务主键对外暴露（不用自增 id，Repository 不暴露 dbId）；embedding BLOB 与 summary 同表同事务写入（纯 Dart 方案）
  │     DOC-10 §8.2：importance < microVectorizeThreshold 的微摘要 has_embedding=false（仅 FTS5 检索）
  │     embedding 向量化对象 = 5W1E 6 字段拼接文本（带中文标签）
  │       格式："时间:{when} 地点:{where} 人物:{who} 事件:{what} 意义:{significance} 额外:{extra}"
  │
  ├─ 4. INSERT FTS5 索引 → memories_fts
  │     (summary, when_text, where_text, who_text, what_text, significance, extra,
  │      memory_id, memory_type='experiential', sessionId)
  │     FTS5 重建为 7 内容字段索引（summary + 6 个 5W1E 字段，均非 UNINDEXED）
  │
  ├─ 5. UPDATE session → chat_sessions
  │     SET lastActiveAt=now, messageCount=messageCount+2
  │
  ├─ 6. INSERT intermediate_round_artifacts（V2 四步扩展）
  │     (sessionId, turnNumber, generatedText, draftKeywords JSON,
  │      retrievedMemories JSON, replyText, eventSummary JSON,
  │      retrievedFacts JSON（DOC-11 v22 新增）, createdAt)
  │     注：RoundContext 字段名 generatedText（v0.2.2 重命名：draftText → generatedText），
  │         DB 列名仍为 draft_text（保留不变，向后兼容）
  │     持久化生成正文/关键词/检索结果/回复正文/事件摘要/事实检索结果，使历史轮次小窗切换会话后仍可见
  │     V2 新增字段：reply_text（reviewing 产出的最终回复，区别于 draft_text）
  │                 event_summary（summarizing 产出的事件摘要 JSON）
  │     DOC-11 v22 新增字段：retrieved_facts（retrieving 阶段产出的事实检索结果 JSON，
  │                          RetrievedFact.toJson 列表，含 entity+attributes+isKeyEntity+isKeywordMatched）
  │     若 artifacts=null（无中间产物）则跳过此步骤
  │
  │     turnNumber 推导（修复后，对齐 _computeTurnNumber 的 UI 公式）：
  │     - 普通场景：turnNumber = state.messages.length ~/ 2 + 1
  │     - 重新生成场景：turnNumber = state.regenerateTurnNumber（覆盖该轮）
  │     - 与 UI 关联公式（intermediate_chat_body.dart）对齐：
  │       assistant at index i → turn = (i+1)~/2
  │     - 修复原因：原实现 turnNumber = state.session.messageCount ~/ 2 + 1，
  │       但 _runPersistPhase 持久化后未刷新内存 messageCount，第二轮起算成 1，
  │       artifacts 错误覆盖第一轮。改基于 messages.length 推导消除同步时机依赖，
  │       同时在 state.copyWith 中追加 session.messageCount 刷新（与
  │       regenerateMessage / editAndResend / deleteRound 风格一致）。
  │
  ├─ 7. APPLY 事实变更 deltas → factual_entities / factual_attributes / factual_memory_history
  │     （DOC-11 v22 新增，仅在 factsDeltas 非空且 factual.enabled=true 时执行）
  │     FactApplier.applyDeltas(sessionId, deltas, turnNumber, config) 在本事务内执行：
  │     - 逐个 delta 应用（createEntity / updateAttr / appendList / removeFromList / addAlias / archiveEntity）
  │     - 每个 delta 经三重防护 + 5 层健康度防护检查（DOC-11 §7）
  │     - 通过检查的 delta 写入 factual_entities / factual_attributes，并追加 factual_memory_history 审计日志
  │     - 被防护跳过的 delta 不计入失败（appliedCount 不递增）
  │     - 任一 delta 抛硬错误（如 schema 不允许的 attrKey）→ 整个事务 ROLLBACK（DOC-11 §7.3 原子性）
  │     原子性保证：与经历层 persisting 同事务，事实层失败回滚整轮（绝不牺牲一致性，DOC-11 §8.3）
  │
  ▼
[提交 transaction]
  ├── 全部成功 → COMMIT → phase=idle
  └── 任一失败 → ROLLBACK → phase=failed (E018)
```

### 1.1 重新生成持久化时序（persistRegeneratedRound）

用于"重新生成"场景：用户消息（user_N）已存在，仅写新的 assistant 回复 + 事件摘要。与 §1 的差异：**不写 user 消息，messageCount +1（非 +2）**。

```
重新生成流程（regenerateMessage）完成 summarizing 阶段（V2 四步流程）
  │ 前置：deleteRoundAndDownstream 已删除旧 assistant_N + turn≥N 事件摘要
  │       state.regenerateTurnNumber = targetTurn（标识走本分支）
  ▼
[同步调用 embedding API]
  ▼
[开启 drift transaction]
  │
  ├─ 0. CompactionPoint 压缩持久化（仅在本轮触发了压缩时执行）
  │     同 §1 步骤 0：写入摘要消息 + compaction_points + experiential_memories(macro)
  │     重新生成场景同样可能触发压缩（若原文区 token 超阈值）
  │
  ├─ 1. INSERT assistant message → chat_messages
  │     (sessionId, role=assistant, content=replyText, createdAt)
  │     注：不写 user message（user_N 已存在）
  │
  ├─ 2. INSERT event summary + embedding → experiential_memories
  │     turn_number = targetTurn（复用原轮次，避免跳跃）
  │     字段列表/embedding 向量化对象同 §1 步骤 3（含 5W1E 6 字段）
  │
  ├─ 3. INSERT FTS5 索引 → memories_fts
  │     字段列表同 §1 步骤 4（7 内容字段：summary + 6 个 5W1E 字段）
  │
  ├─ 4. UPDATE session → chat_sessions
  │     SET lastActiveAt=now, messageCount=messageCount+1
  │
  ├─ 5. INSERT intermediate_round_artifacts（V2 四步扩展）
  │     同 §1 步骤 6，持久化重生轮次的生成正文/关键词/检索结果/回复正文/事件摘要
  │     若 artifacts=null 则跳过此步骤
  │
  ▼
[提交 transaction]
  ├── 全部成功 → COMMIT → phase=idle
  └── 任一失败 → ROLLBACK → phase=failed (E018)
```

### 1.2 删除时序（deleteRoundAndDownstream）

用于"重新生成/编辑重发/删除整轮"的删除阶段。在重新生成/编辑重发场景中，删除先于持久化执行；在删除整轮场景中，删除是唯一操作（不重新生成）。

```
[开启 drift transaction]
  │
  ├─ 1. DELETE FROM experiential_memories
  │     WHERE session_id = ? AND turn_number >= ? AND is_archived = 0
  │     （删除 turn ≥ fromTurnNumber 的经历记忆）
  │     注：is_archived=1 的摘要记忆不删（归档记忆独立于轮次）
  │
  ├─ 2. DELETE FROM memories_fts
  │     WHERE memory_id IN (步骤1 删除的 memory_id 集合)
  │     （删除对应 FTS5 索引）
  │
  ├─ 3. DELETE FROM chat_messages
  │     WHERE message_id IN (messageIdsToDelete)
  │     （循环 ChatRepository.deleteMessage，物理 DELETE 无级联）
  │     messageIdsToDelete 由 Controller 从 state.messages 按索引推导
  │
  ├─ 4. UPDATE session → chat_sessions
  │     SET lastActiveAt=now, messageCount=remainingMessages.length
  │
  ├─ 5. DELETE FROM intermediate_round_artifacts
  │     WHERE session_id = ? AND turn_number >= fromTurnNumber
  │     （删除 turn ≥ fromTurnNumber 的中间产物，避免悬空数据）
  │     与步骤 1 的 experiential_memories 删除范围一致
  │
  ├─ 6. FactApplier.deleteFactsByTurns（事实层清理，v0.2 事实层中间方案新增）
  │     WHERE sessionId = ? AND createdTurn >= fromTurnNumber
  │     （删除目标轮次及下游创建的实体 + 其属性 + 其历史）
  │     （删除当前会话 turnNumber >= fromTurnNumber 的审计历史）
  │     非待删实体的属性保留当前值，由新轮次 factsDeltas 覆盖
  │     _factApplier 为 null 时（事实层禁用）跳过此步
  │     不开自身事务，嵌套在当前 drift transaction 内
  │
  ├─ 7. 清理 compaction_points 孤儿记录（v0.2.3 新增）
  │     对 messageIdsToDelete 中每个 messageId 调
  │     ChatRepository.deleteCompactionPointBySummaryId(sessionId, messageId)
  │     （压缩摘要消息被删时，对应的 compaction_points 记录也需删除，
  │      避免 loadHistory 时 filterByCompactionPoint 指向已删除消息）
  │     循环逐条删除，未命中也无副作用（无对应记录即跳过）
  │
  ▼
[提交 transaction]
  ├── 全部成功 -> COMMIT
  └── 任一失败 -> ROLLBACK -> 抛异常（Controller 捕获后 phase=failed）
```

> **删除范围差异**（DOC-09A-1 §2.4-§2.6）：
> - 重新生成：删 assistant_N + 下游消息（保留 user_N）
> - 编辑重发：删 user_N + assistant_N + 下游消息
> - 删除整轮：删 user_N + 下游消息（若 target 是 assistant，回退到 user_N 起删）

### 1.3 批量记忆提炼时序（persistConsolidatedMemories）

> **禁用说明**（2026-07-19）：consolidation 已禁用——`default_config.json` 中 `consolidation.trigger_threshold=2.0`（高于任何 importance 取值 1-5 的归一化阈值，等价于永不触发），`_runConsolidation` 判定 `enabled=false` 直接返回。本节时序保留作为设计参考，**当前 v0.2 dev 阶段不执行**；未来若重新启用 consolidation，5W1E 改造后合并记忆的 INSERT 需追加 6 个 5W1E 字段、FTS5 INSERT 需扩展为 7 内容字段（同 §1 步骤 3-4 规范）。

用于上下文 token 超阈值时异步合并低重要性记忆。由 `_runConsolidation` 在 `_runPersistPhase` 末尾 `unawaited` 触发（不阻塞 UI）。详见 DOC-09A-1 §4。

```
[开启 drift transaction]
  │
  ├─ 1. 对每条合并记忆 ConsolidatedMemoryRecord：
  │     ├─ a. INSERT INTO experiential_memories
  │     │     (memory_id, session_id, summary, importance, tags, turn_number,
  │     │      is_archived, is_summary, has_embedding, created_at)
  │     │   VALUES (?, ?, ?, ?, ?, ?, 0, 0, ?, ?)
  │     │   （turn_number 取参与合并的原始记忆最大 turnNumber）
  │     │
  │     ├─ b. 若 record.embedding != null：
  │     │   UPDATE experiential_memories
  │     │   SET embedding = ?, has_embedding = 1
  │     │   WHERE memory_id = ?
  │     │   （embedding 为 Float32List 小端字节序 BLOB）
  │     │
  │     └─ c. INSERT INTO memories_fts (memory_id, session_id, summary)
  │         VALUES (?, ?, ?)
  │         （合并后记忆达 importanceStorageThreshold，必须建 FTS5 索引）
  │
  ├─ 2. DELETE FROM memories_fts
  │     WHERE session_id = ? AND memory_id IN (originalMemoryIds)
  │     （删除原始记忆的 FTS5 索引行——未索引记忆为空操作，兼容边界场景）
  │
  ├─ 3. DELETE FROM experiential_memories
  │     WHERE session_id = ? AND memory_id IN (originalMemoryIds)
  │     （删除参与合并的原始未索引记忆）
  │
  ▼
[提交 transaction]
  ├── 全部成功 → COMMIT（合并记忆可检索，原始记忆已清理）
  └── 任一失败 → ROLLBACK（原始记忆保留，下次触发可重新合并）
```

> **事务原子性**：合并记忆写入 + 原始记忆删除在同一 drift transaction 内，保证"要么全部成功，要么原始记忆不被删除"。LLM 返回空列表时不进入本流程（无持久化操作）。

> **不更新 session 元数据**：合并操作不改变 messageCount / lastActiveAt（消息未变，仅记忆层重组）。

### 1.4 宏摘要持久化时序（persistMacroSummary，DOC-10 §4.3）

> **触发条件**（DOC-10 §2.2）：summarizing 步骤 LLM 输出 `event_ended=true`（事件结束判断）或累计 `macroIntervalRounds` 轮未生成宏摘要（固定轮次兜底）。详见 DOC-09A-1 §3.10、DOC-10 §6.1。

宏摘要持久化在每轮 persistRound（§1）完成**后**独立执行，作为同一轮的附加宏摘要入库。宏摘要写入与微摘要写入**分属两个独立事务**——微摘要事务（§1）提交后再执行宏摘要事务（本节），互不影响：

```
summarizing 完成（解析出 eventSummary + eventEnded 判断）
  │
  ▼
[宏摘要触发判断]（IntermediateChatController._shouldTriggerMacro）
  ├── 不触发（eventEnded=false 且未达 macroIntervalRounds 阈值）→ 跳过本节，phase=idle
  └── 触发（eventEnded=true 或 达 macroIntervalRounds 阈值）→ 进入宏摘要生成
      │
      ▼
[MacroSummaryPhaseHandler 执行]
  │ 1. 读取触发范围微摘要：getMicroSummariesInRange(sessionId, lastMacroTurn+1, currentTurn)
  │ 2. LLM 调用（kMacroSummaryPrompt + kMacroSummaryToolDefinition）
  │    工具调用优先，失败降级 JSON 模式（与 SummarizePhaseHandler 同构）
  │ 3. 解析输出：summary / importance / tags
  │    宏摘要保持 summary 单字段（不采用 5W1E，5W1E 拆分会丢失多轮聚合语义）
  │
  ▼
[同步调用 embedding API]（宏摘要 summary 向量化，单字段文本）
  ├── 成功 → embedding = Vec<f32>
  └── 失败 → embedding = null（降级 has_embedding=false，宏摘要仍入库）
  │
  ▼
[开启 drift transaction]（与 §1 微摘要事务独立）
  │
  ├─ 1. INSERT macro summary → experiential_memories
  │     (memoryId=UUID, sessionId, summary, importance, tags,
  │      turnNumber=currentTurn, memoryLevel='macro',
  │      parentEventIds=JSON([micro1.memoryId, micro2.memoryId, ...]),
  │      macroTriggerReason='event_end' | 'round_limit',
  │      when_text='', where_text='', who_text='', what_text='', significance='', extra=''（5W1E 6 字段空字符串兜底）,
  │      embedding=BLOB(如成功), has_embedding=(embedding!=null), createdAt)
  │     parentEventIds 关联本宏摘要聚合的所有微摘要 memoryId；宏摘要 5W1E 统一空字符串
  │
  ├─ 2. UPDATE embedding（若步骤1 写入 has_embedding=false 但 embedding != null）
  │     UPDATE experiential_memories SET embedding=?, has_embedding=1
  │     WHERE memory_id=?
  │     （与 §1 步骤3 相同的两步写入模式：先 appendExperience 写 has_embedding=false，
  │      再 updateEmbedding 单独写入 BLOB，避免事务内 BLOB 写入失败导致整事务回滚）
  │
  ├─ 3. INSERT FTS5 索引 → memories_fts
  │     (summary, when_text='', where_text='', who_text='', what_text='', significance='', extra='',
  │      memory_id, memory_type='experiential', sessionId)
  │     宏摘要建立 FTS5 索引后可被关键词检索召回
  │     FTS5 表为 7 内容字段统一结构，宏摘要 5W1E 填空字符串（不影响 trigram 分词）
  │
  ▼
[提交 transaction]
  ├── 全部成功 → COMMIT → phase=idle（宏摘要可被检索）
  └── 任一失败 → ROLLBACK → 宏摘要不入库，phase=idle（不阻断本轮，下次触发可重新生成）
```

> **事务独立性**：宏摘要事务与微摘要事务（§1）独立，宏摘要失败不回滚微摘要。理由：宏摘要是对已有微摘要的二次聚合，失败时微摘要仍可独立支撑检索，不应因宏摘要失败而丢弃本轮全部持久化成果。

> **失败降级**：宏摘要 LLM 调用失败或持久化失败时，phase 直接回到 idle（不进入 failed 状态）。理由：宏摘要属增量增强，非本轮核心流程；失败时仅损失"宏摘要优先召回"能力，micro 检索仍正常工作。详见 DOC-10 §6.2。

> **不更新 session 元数据**：宏摘要入库不改变 messageCount / lastActiveAt（消息未变，§1 已更新过）。

> **parentEventIds 关联**：宏摘要通过 `parent_event_ids` 字段（JSON 数组字符串）关联聚合的微摘要 memoryId 列表。检索时多粒度去重（DOC-09A-1 §3.6）依赖此字段判断"某条 micro 是否已被某条 macro 聚合"。

> **macroTriggerReason 取值**：
> - `event_end`：LLM 判断事件结束触发（extracting 步骤输出 `event_ended=true`）
> - `round_limit`：固定轮次兜底触发（累计 `macroIntervalRounds` 轮未生成宏摘要）

## 3. 并发控制

**单会话串行**：同一会话同一时间只允许一轮对话进行（generating→...→idle 或 failed）。Controller 通过 `phase` 字段判断，非 `idle` 状态时禁用输入框。

**跨会话并行**：不同会话可并行进行（每个会话独立 Controller 实例）。

**取消语义**：用户在任意阶段点"取消"：
- 立即停止当前 LLM 请求（取消 SSE 订阅）
- 清理临时状态（streamingGenerated/streamingReply 等）
- 不进入 failed 状态，直接回到 idle
- 数据层不持久化任何内容（事务未开启或已回滚）

## 5. 建表脚本（Schema 定义）

> **修订**（V2 四步扩展 + DOC-10 多粒度记忆 + 5W1E + DOC-11 事实层中间方案）：v0.2 不涉及发版，dev 阶段直接重建数据库采用新 Schema——代码 `schemaVersion=22`（v16 新表 failure_logs/intermediate_round_artifacts；v17 chat_sessions 加列 json_mode_override；v18 intermediate_round_artifacts 加列 reply_text/event_summary；v19 experiential_memories 加列 memory_level/parent_event_ids/macro_trigger_reason + idx_exp_session_level 索引；v20 略；v21 experiential_memories 加列 5W1E 6 列 + memories_fts DROP/CREATE 重建为 7 内容字段索引；v22 新建 factual_entities/factual_attributes/factual_memory_history 三表 + 7 个索引，DOC-11 事实层中间方案）。dev 阶段不写迁移块（dev 数据 disposable）。**正式发版时** v22 onUpgrade 迁移需实现：v21 全部迁移 + 3 个 createTable（事实层）+ 7 个 createIndex（事实层索引）。以下脚本在 `@DriftDatabase` 初始化时执行。

```dart
// dev 阶段：@DriftDatabase 初始化时执行（数据库文件删除后重建）
// 发版时：包装为 migration_step 的 onUpgrade（v20→v21）
Future<void> createIntermediateTables(Database database) async {
  // 1. 新建 experiential_memories 表
  //    memory_id 为业务主键（UUID 程序生成，对外暴露）；id 为自增主键（内部用，见 DOC-05-5 §4.5）
  //    DOC-10 v1.1（v19）追加 memory_level/parent_event_ids/macro_trigger_reason 3 字段
  //    v21 追加 5W1E 6 字段（when_text/where_text/who_text/what_text/significance/extra，
  //      均 nullable TEXT，实体字段 String?）；summary 保持 NOT NULL 用空字符串兜底
  await database.customStatement('''
    CREATE TABLE experiential_memories (
      memory_id TEXT NOT NULL UNIQUE,
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      session_id TEXT NOT NULL,
      summary TEXT NOT NULL,
      importance INTEGER NOT NULL,
      tags TEXT NOT NULL,
      turn_number INTEGER NOT NULL,
      narrative_time TEXT,
      narrative_period TEXT,
      when_text TEXT,
      where_text TEXT,
      who_text TEXT,
      what_text TEXT,
      significance TEXT,
      extra TEXT,
      embedding BLOB,
      has_embedding INTEGER NOT NULL DEFAULT 0,
      is_archived INTEGER NOT NULL DEFAULT 0,
      is_summary INTEGER NOT NULL DEFAULT 0,
      archived_event_ids TEXT,
      memory_level TEXT NOT NULL DEFAULT 'micro',
      parent_event_ids TEXT,
      macro_trigger_reason TEXT,
      created_at TEXT NOT NULL
    )
  ''');

  // 2. 新建索引
  await database.customStatement('''
    CREATE INDEX idx_exp_session_archived_imp
    ON experiential_memories (session_id, is_archived, importance)
  ''');
  await database.customStatement('''
    CREATE INDEX idx_exp_session_turn
    ON experiential_memories (session_id, turn_number)
  ''');
  await database.customStatement('''
    CREATE INDEX idx_exp_session_embedding
    ON experiential_memories (session_id, has_embedding)
  ''');
  // DOC-10 §3.2：多粒度记忆索引（按会话+层级查询宏摘要）
  await database.customStatement('''
    CREATE INDEX idx_exp_session_level
    ON experiential_memories (session_id, memory_level)
  ''');
  // 注：idx_exp_session_period（session_id, narrative_period）推迟到 v0.3
  //     理由：v0.2 阶段 narrative_period 始终为 NULL（见 DOC-09A-1 §1.5），
  //     建此索引无意义且浪费空间；v0.3 引入叙事周期后再创建

  // 3. 新建 memories_fts 虚拟表（FTS5，trigram 分词器支持中文）
  //    tokenize='trigram'：UTF-8 字符级 3 字符滑动窗口；≥3 字符查询走 MATCH，<3 字符 fallback LIKE
  //    7 内容字段索引（schemaVersion=21：summary + 6 个 5W1E 字段，均非 UNINDEXED）
  //    宏摘要 5W1E 填空字符串（仅 summary 参与索引，空字符串不影响 trigram 分词）
  await database.customStatement('''
    CREATE VIRTUAL TABLE memories_fts USING fts5(
      summary,
      when_text,
      where_text,
      who_text,
      what_text,
      significance,
      extra,
      memory_id UNINDEXED,
      memory_type UNINDEXED,
      session_id UNINDEXED,
      tokenize='trigram'
    )
  ''');

  // 4. 不建 memory_vectors 虚拟表
  //    v0.2 定案：sqlite-vec pub 包损坏废弃，主方案 = 纯 Dart 暴力检索
  //    向量仅存 experiential_memories.embedding BLOB（§5.1 已定义），检索时由
  //    VectorEngine.batchSearch 加载计算。详见 DOC-08 §5.3 + DOC-05-8 §9.12。

  // 5. 新建 intermediate_round_artifacts 表（V2 四步扩展）
  //    持久化每轮四步生成的生成正文/关键词/检索结果/回复正文/事件摘要，使历史轮次小窗切换会话后仍可见。
  //    通过 (session_id, turn_number) 关联到 assistant 消息和 experiential_memories，
  //    不污染 ChatMessage 字段（DOC-09A-1 §1.5 硬约束修订）。
  //    V2 新增字段：
  //      - reply_text：reviewing 产出的最终回复（区别于 draft_text）
  //      - event_summary：summarizing 产出的事件摘要 JSON
  //    v0.2.2 术语变更：DB 列名 draft_text/reply_text 保留不变（向后兼容），
  //      Dart 实体字段名对应 generatedText/replyText（draftText → generatedText 重命名）
  await database.customStatement('''
    CREATE TABLE intermediate_round_artifacts (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      session_id TEXT NOT NULL,
      turn_number INTEGER NOT NULL,
      draft_text TEXT,
      draft_keywords TEXT NOT NULL,
      retrieved_memories TEXT NOT NULL,
      reply_text TEXT,
      event_summary TEXT,
      created_at INTEGER NOT NULL
    )
  ''');

  // 6. intermediate_round_artifacts 索引
  //    idx_ira_session_turn：按 session + turn 查询（loadArtifactsBySession 主路径）
  //    普通索引（非 UNIQUE）——同会话同轮次唯一性由 persistRound 同事务 INSERT 保证，
  //    deleteRoundAndDownstream 先 DELETE 再 INSERT 避免冲突
  await database.customStatement('''
    CREATE INDEX idx_ira_session_turn
    ON intermediate_round_artifacts (session_id, turn_number)
  ''');

  // 不删除任何现有表，不修改任何现有表结构
}

// v0.2 schemaVersion=22 新增（DOC-11 事实层中间方案，2026-07-20）
// 详见 doc/design/11_事实层中间方案设计.md §3
Future<void> createFactualTables(Database database) async {
  // 1. factual_entities 表（实体表，每实体一条记录）
  //    primary_name 会话内唯一（idx_factual_entities_session_name UNIQUE）
  //    type 限定 character/pet/npc/location/item（DOC-11 §3.1）
  await database.customStatement('''
    CREATE TABLE factual_entities (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      entity_id TEXT NOT NULL UNIQUE,
      session_id TEXT NOT NULL,
      type TEXT NOT NULL,
      primary_name TEXT NOT NULL,
      aliases TEXT NOT NULL DEFAULT '[]',
      category TEXT,
      importance INTEGER NOT NULL DEFAULT 3,
      is_archived BOOLEAN NOT NULL DEFAULT FALSE,
      created_at INTEGER NOT NULL,
      created_turn INTEGER NOT NULL,
      updated_at INTEGER,
      updated_turn INTEGER
    )
  ''');

  // 2. factual_attributes 表（属性表，每属性一条记录）
  //    (entity_id, attr_key) 唯一约束（idx_factual_attrs_entity_key UNIQUE）
  //    value_type: single/list/dict，value 字段对应存字符串/JSON数组/JSON对象
  await database.customStatement('''
    CREATE TABLE factual_attributes (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      attribute_id TEXT NOT NULL UNIQUE,
      entity_id TEXT NOT NULL,
      session_id TEXT NOT NULL,
      attr_key TEXT NOT NULL,
      value TEXT NOT NULL,
      value_type TEXT NOT NULL DEFAULT 'single',
      importance INTEGER NOT NULL DEFAULT 3,
      created_at INTEGER NOT NULL,
      updated_at INTEGER,
      updated_turn INTEGER,
      update_reason TEXT
    )
  ''');

  // 3. factual_memory_history 表（审计日志，每次 FactApplier.apply 后追加一条）
  await database.customStatement('''
    CREATE TABLE factual_memory_history (
      id INTEGER PRIMARY KEY AUTOINCREMENT,
      entity_id TEXT NOT NULL,
      attribute_id TEXT,
      action TEXT NOT NULL,
      old_value TEXT,
      new_value TEXT,
      reason TEXT,
      confidence INTEGER,
      turn_number INTEGER NOT NULL,
      created_at INTEGER NOT NULL
    )
  ''');

  // 4. factual_entities 索引
  //    idx_factual_entities_session_name UNIQUE：主名唯一约束 + 按名查找（DOC-11 §10.1 别名匹配主路径）
  await database.customStatement('''
    CREATE UNIQUE INDEX idx_factual_entities_session_name
    ON factual_entities (session_id, primary_name)
  ''');
  //    idx_factual_entities_session_type：按类型筛选（注入时按 character/pet/npc/location/item 分组）
  await database.customStatement('''
    CREATE INDEX idx_factual_entities_session_type
    ON factual_entities (session_id, type)
  ''');
  //    idx_factual_entities_session_importance：关键实体查询（importance >= 阈值）
  await database.customStatement('''
    CREATE INDEX idx_factual_entities_session_importance
    ON factual_entities (session_id, importance)
  ''');

  // 5. factual_attributes 索引
  //    idx_factual_attrs_entity_key UNIQUE：属性唯一约束 + 单属性查询（getAttribute 主路径）
  await database.customStatement('''
    CREATE UNIQUE INDEX idx_factual_attrs_entity_key
    ON factual_attributes (entity_id, attr_key)
  ''');
  //    idx_factual_attrs_session_entity：批量加载命中实体的所有属性（getAttributes 主路径）
  await database.customStatement('''
    CREATE INDEX idx_factual_attrs_session_entity
    ON factual_attributes (session_id, entity_id)
  ''');

  // 6. factual_memory_history 索引
  //    idx_factual_history_entity：实体修改历史查询（审计 UI）
  await database.customStatement('''
    CREATE INDEX idx_factual_history_entity
    ON factual_memory_history (entity_id, created_at)
  ''');
  //    idx_factual_history_entity_turn：更新频率限制查询（DOC-11 §7.4.5，最近 3 轮更新计数）
  await database.customStatement('''
    CREATE INDEX idx_factual_history_entity_turn
    ON factual_memory_history (entity_id, turn_number)
  ''');
}
```

> **建表脚本修订说明**：
> - **experiential_memories 新增 `memory_id TEXT NOT NULL UNIQUE`**：对齐 08 §5.1 与 DOC-05-5 §4.5 接口设计"Repository 不暴露 dbId"硬约束。memory_id 为 UUID 业务主键，id 保留为自增主键仅供内部使用。
> - **memory_vectors 表移除**：原设计的 `memory_vectors` vec0 虚拟表（TEXT memory_id + session_id + distance_metric=cosine）已废弃。sqlite-vec pub 包损坏（`src/` 缺失 `sqlite-vec.c`），v0.2 改用纯 Dart 暴力检索，向量仅存 `experiential_memories.embedding` BLOB 单一数据源。
> - **idx_exp_session_period 推迟到 v0.3**：v0.2 阶段 narrative_period 始终为 NULL（DOC-09A-1 §1.5 约束），建索引无意义；v0.3 引入叙事周期后再创建。

**Schema 变更策略说明**：v0.2 不涉及发版，按项目规则"默认为新改动覆盖原来的数据库内容，不需要考虑已有历史数据"——dev 阶段直接删除数据库文件重建，无需编写迁移逻辑。dev 数据 disposable。

> **向量检索方案**：v0.2 主方案 = 纯 Dart 暴力检索。`experiential_memories.embedding` BLOB 字段直接存储向量（Float32List 小端字节序），检索时由 ExperienceRepositoryImpl 加载该 session 全部 `has_embedding=1` 的向量到内存，调用 `VectorEngine.batchSearch`（Core 层 Isolate 内余弦相似度）返回 topK。1536 维 × 1000 条 ≈ 5-15ms，满足 Q-02 ≤50ms。v0.3 升级路径：vec1（SQLite 官方向量扩展）出现 Dart 绑定后重新评估 SQL KNN。
