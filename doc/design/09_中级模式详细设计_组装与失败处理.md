## 4. 上下文组装计算

### 4.1 总览

中级模式每轮对话发起**3-4 个独立 LLM 请求**（v2.12 检索前置生成 + 可选审查），每个请求的 prompt 独立组装：

```
请求0 compacting（压缩，条件触发）prompt:
  compactionStreamer + 全部当前上下文消息
  -> 输出：压缩摘要（累积式，作为后续 prompt 的稳定前缀）+ 分段宏摘要（分段式，写入 experiential_memories macro 级别，importance=3，参与语义检索）
  -> v0.2.3：首次压缩时压缩摘要兼作分段宏摘要（仅生成一个摘要）；后续压缩时并行生成两个摘要

请求1 extracting（关键词提取）prompt:
  extractKeywordsPrompt + 压缩摘要?（稳定前缀）+ 历史对话（独立消息）+ 用户当前消息
  -> 2026-08-05 改造（缓存优化）：从"用户消息+最近5轮对话揉成1条user"改为独立消息形式，旧历史跨轮不变命中 prompt cache
  -> 提示词强调：关键词仅从用户消息提取，历史仅供揣测语境
  -> 输出：{characters, items, locations, actions, plots}（5 类分类关键词，与记忆库结构对齐）

请求2 generating（生成）prompt:    ★ v2.12 核心改造：注入记忆
  system_prompt_draft（V2）+ 压缩摘要（稳定前缀）+ 最近 n 轮对话 + 【世界设定】 + 【相关往事】 + 用户消息
  → 输出：纯文本生成正文（已按记忆生成）

请求3 reviewing（审查修正，可选；reviewEnabled=true 时执行）prompt:
  方案D（2026-08-05）：去掉压缩摘要和历史对话（审查不需要，生成时已基于历史）
  [system]角色提示词（命中 generating 缓存前缀）+ [system]审查提示词 + [system]【世界设定】? + [system]【相关往事】? + [user]用户消息+生成内容
  -> 事实一致性维度强化：对照事实类检查人物设定，对照经历类检查剧情连贯性
  -> 输出：纯文本审查后正文（三维度审查：事实一致性 + AI 味去除 + 易读性）

请求4 summarizing（摘要）prompt:
  extractSummaryPrompt + 用户消息 + 回复正文（生成正文或审查后正文）
  → 输出：{what(必填), when?, where?, who?, significance?, extra?, summary?(可选), tags, importance, event_ended, narrativeTime?}
    （工具调用/JSON，5W1E 多字段提取，2026-07-19；2026-07-25 叙事时间机制）
```

**v2.12 架构调整关键变化**：
- **检索前置**：extracting 从 generating 之后前置到 generating 之前，输入从"用户消息 + 生成正文"改为"用户消息（优先）+ 最近 n 轮对话（按距离递减）"。理由：生成正文已生成后再检索，模型注意力被生成正文锚定，记忆注入形同虚设；检索前置让写生成正文前先掌握世界设定和相关往事。
- **generating 注入记忆**：generating 阶段从"完全不注入记忆"改为"注入【世界设定】（事实层）+【相关往事】（经历层）"。检索结果在 retrieving 阶段已准备好，generating 直接使用，reviewing 阶段也复用同一份检索结果（不重新检索）。
- **reviewing 可选**：`reviewEnabled=false`（默认）时跳过 reviewing，生成即最终，3 次 LLM 调用（extracting + generating + summarizing）；`reviewEnabled=true` 时增加 reviewing 阶段做审查修正，4 次 LLM 调用。
- **reviewing prompt 软约束**：删除"段落数量守恒""情节要点守恒""不得另起炉灶"等硬约束（这些是导致 LLM 锚定生成正文、审查不严谨的元凶），仅保留去 AI 味和简单逻辑检查；新增"仅在发现明确事实矛盾时修正，不得主动改写情节""如果生成正文与记忆一致，直接输出生成正文原文，不要为改而改"。
- **CompactionPoint 引入**：达到 `compactionTriggerRatio`（0.5）触发压缩，压缩摘要作为稳定前缀注入 generating/extracting prompt，提升 LLM 缓存命中率（2026-08-05 修订：reviewing 方案D 去掉压缩摘要，仅 generating/extracting 注入）。
- **废弃宏摘要**：废弃独立 macroSummarizing 阶段。v0.2.3 修订：压缩摘要与分段宏摘要职责分离--压缩摘要（累积式）-> 上下文注入，分段宏摘要（分段式，importance=3）-> 记忆检索 + 记忆查看器（参与语义检索，标注"段落摘要"）。首次压缩时压缩摘要兼作分段宏摘要。

generating 带"压缩摘要 + 最近 n 轮对话 + 记忆块"（缓存友好）；reviewing（2026-08-05 改造）去掉历史和压缩摘要，仅保留角色提示词（命中 generating 缓存）+ 审查提示词 + 检索区 + 用户消息+生成内容；extracting（2026-08-05 改造）改为"压缩摘要?+历史对话(独立消息)+用户消息"，与 generating 共享前缀提升缓存命中；summarizing 的输入是"用户消息+回复正文"（2026-07-16 修订：原仅注入上一阶段产出，现加入用户消息，避免漏掉用户原话中的关键实体和核心事件）。

> **v2.9 配置快照语义**（2026-07-22）：上下文组装中所有从会话级字段读取的配置（system_prompt / temperature / topP / maxTokens / presencePenalty / frequencyPenalty / maxContextMessages / phaseModels 等）均为**快照值**而非运行时引用。会话物化时（首条消息 OR generating 期间首次配置变更）由 `ConfigurationResolver.snapshotIntermediateDefaults()` 读取当前全局配置生成 `GlobalDefaultsSnapshot`，控制器将会话级草稿值与快照值合并写入 `chat_sessions` 表会话级字段。后续全局配置变更不影响已物化的会话。`resolveSettings` / `resolveIntermediateSettings` 读取会话级字段时获取的是物化时刻的快照值；仅当用户在会话设置面板中显式清除某字段（如选择"使用默认模型"）时，该字段才回退到全局配置。§4.5 / §4.6 中"优先级：会话级 > 全局级 > 默认"仍成立，但"全局级"回退仅在用户显式清除字段时触发（物化后字段默认非 null）。详见 DOC-05-6 §5.1 v1.6、DOC-08 §7.5 v2.9。

### 4.2 n 值定义（复用 maxContextMessages）

- `maxContextMessages` 是消息条数（int?，NULL = 无限制），与 Simple 模式统一
- "n 轮" = `maxContextMessages / 2`（一轮 = 1 user + 1 assistant = 2 条消息）
- **NULL（无限制）处理**：加载全部历史对话，由 token 预算控制兜底砍最旧轮次
- **N 条处理**：加载最近 N 条，token 预算控制兜底（N 条仍超窗口时再砍）
- 不新增配置项，避免配置膨胀

> **v0.2.2 阶段 2-F 更新**：故事模式引入 CompactionPoint 压缩机制后，原文区由 `recentMinRatio` + `compactionTriggerRatio` 动态控制，不再需要上述"最近 n 轮原文"的硬性消息数截断。`IntermediateContextBuilder` 和控制器不再读取 `maxContextMessages`，本节 n 值机制仅在 Simple 模式生效。`ChatSession` 实体字段保留（Simple 模式仍使用）。

### 4.3 token 预算控制（完整版，多级缩减）

**contextWindow 解析**（2026-07-29 新增；2026-08-04 修订）：

```
// 2026-08-04 修复：从 generating 阶段的 phaseModels 解析，而非 resolveModelDisplayInfo
// （后者用 Simple 模式的 session.presetId/modelId，中级模式会话这两个字段为空，
//  导致回退到默认 96000，远小于用户配置的 200k 模型）
// resolveContextWindowForPhase 内部对 null/空串返回默认 96000，无需外部 ??
modelWindow = resolveContextWindowForPhase(
    presetId: generatingNamingConfig?.presetId,
    modelId: generatingNamingConfig?.modelId,
)  // 返回非空 int，未知时返回默认 96000
effectiveLimit = session.effectiveContextLimit ?? globalIntermediate.context.effectiveContextLimit
contextWindow = (effectiveLimit != null && effectiveLimit > 0 && effectiveLimit < modelWindow)
    ? effectiveLimit    // 用户主动限制（应对 TPM 限制）
    : modelWindow       // 默认行为（使用模型窗口）
```

**用途**：应对 TPM 限制（如腾讯云 500万 TPM）。模型窗口虽大（如 GLM5.2=1M），但单次请求塞太多会触发 429。用户可通过会话级或全局 `effective_context_limit` 主动限制每次请求塞入的 token 数。取 `min(配置值, 模型窗口)` 避免配置超过模型能力。

**生效范围**：仅 generating（请求2）/reviewing（请求3，启用时）阶段。reviewing（2026-08-05 改造）去掉历史后无需 dialogueBudget 计算；extracting 的历史由 compacting 阶段管理（超阈值压缩），无需额外预算裁剪；summarizing 输入简单（仅 system+user 两条消息），无需应用。

**v2.12 上下文预算分配**（2026-07-30 新增）：

引入 `contextBudget` 配置项（详见 DOC-09B §10），将模型上下文（`contextWindow`）按百分比切分为四个区（v0.2.2 修订：`outputReserve`/`output_reserve` 标注 @Deprecated，统一用 `maxTokens`；`availableWindow = contextWindow - maxTokens` 降级为辅助概念，仅在下限动态计算时参考）：

```
availableWindow = contextWindow - maxTokens              // 辅助概念（outputReserve 已废弃，统一用 maxTokens）
fixed_overhead = 角色提示词(≤2000) + 压缩摘要(≤8000) + 用户输入(≤2000)  // 固定开销（有上限，不参与百分比分配）
retrieval_budget = contextWindow × retrievalRatio       // 检索区（默认 0.15）
recent_min = contextWindow × recentMinRatio             // 原文区下限（动态或自定义）
compaction_trigger = contextWindow × compactionTriggerRatio  // 压缩触发线（总占用达此线触发压缩，固定 0.5）

约束：compactionTriggerRatio(0.5) > recentMinRatio(动态≥0.10)
      compactionTriggerRatio + retrievalRatio + 固定开销比例 + 余量 ≤ 1.0
```

> **v0.2.2 修订**（2026-08-05 补充）：原 `recentMaxRatio`（原文区上限）改名为 `compactionTriggerRatio`（压缩触发线），语义从"原文区上限"变为"总占用触发线"。触发条件从"原文区 token > availableWindow × recentMaxRatio"改为"总占用（基础上下文 + 检索区 + 历史）> contextWindow × compactionTriggerRatio"。原 `dialogueBudgetRatio`/`dialogue_budget_ratio` 标注 @Deprecated（generating 统一为"不塞满、不截断"，不再按比例切分对话预算；reviewing 2026-08-05 方案D 去掉历史后无 dialogue_budget）。详见 `doc/design/13_故事模式上下文机制设计.md`。

**预算参数**（详见 DOC-09B §10 `intermediate.contextBudget`）：

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `compactionTriggerRatio` | 0.5 | 压缩触发线（固定，UI 不可改）。总占用达此线时触发 CompactionPoint 压缩 |
| `recentMinRatio` | null | 原文区下限百分比。null=动态计算 `max(0.10, recentMinTokenTarget/contextWindow)`，非 null=用户自定义 |
| `retrievalRatio` | 0.15 | 检索区比例（含【世界设定】+【相关往事】） |
| `recentMinTokenTarget` | 32000 | 下限动态计算的目标 token 数（约 15-25 轮详细对话，足够保持近期氛围） |

**下限动态计算**（当 `recentMinRatio` 为 null 时）：
```dart
double computeRecentMinRatio({required int availableWindow, required int recentMinTokenTarget}) {
  final raw = recentMinTokenTarget / availableWindow;
  return raw.clamp(0.10, 0.45); // 下限保护：最低 10%，最高 45%（避免挤占其他区）
}
```

**不同上下文下的具体 token 值**（仅供理解，UI 中上限不展示 token）：

| 模型上下文 | availableWindow | 原文区上限(固定) | 原文区下限(动态) | 检索区 |
|-----------|-----------------|-----------------|-----------------|--------|
| 128K | 96000 | 48K (50%) | 32K (33.3%) | 14K |
| 256K | 224000 | 112K (50%) | 32K (14.3%) | 34K |
| 1M | 968000 | 484K (50%) | 32K (10%，触发下限保护) | 145K |

**压缩过程**（CompactionPoint，详见 §5）：
```
原文涨到上限（50%）→ 触发压缩 → 压缩到下限（动态，约32K token）→ 继续对话
压缩量 = 上限 - 下限（128K模型约16K token，1M模型约452K token）
```

**预算计算**（generating 阶段；2026-08-05 修订：reviewing 方案D 去掉历史后无需 dialogueBudget 计算）：
```
budget = contextWindow - maxTokens               // maxTokens 默认 8192（outputReserve 已废弃，统一用 maxTokens）
fixed_tokens = system_prompt + compaction_summary + user_input  // 固定部分（v2.12 新增压缩摘要）
remaining_budget = budget - fixed_tokens - retrieval_budget
```

**预算分配**（generating 请求2；reviewing 请求3 启用时仅计算 retrieval_budget，无 dialogue_budget）：
```
dialogue_budget = remaining_budget              // 对话轮次（原文区，已扣除检索区）
memories_budget = retrieval_budget              // 检索经历 + 世界设定（检索区，固定 15%）
```

> **v2.12 修订**：原 v2.6 的 `dialogue_budget = remaining_budget × 0.7 / memories_budget = remaining_budget × 0.3` 比例分配被废弃，改为基于 `contextBudget` 配置项的百分比分配。检索区从对话预算中独立切分（固定 15%），避免记忆注入挤占对话预算。事实层【世界设定】注入文本（DOC-11 §6.3）从 `memories_budget` 切片占用，与【相关往事】共享 15% 预算。`factBlock` 通常小于 200 token（关键实体 ≤ `injectionMaxEntities` 默认 10 条 × 每条约 15-20 token），与【相关往事】（topK=12 × 每条约 80-120 token）合并占用后仍可在 15% 预算内运行；若 `factBlock` 较大挤占经历层预算，先按 §4.3 多级缩减顺序砍【相关往事】（保【世界设定】），最后兜底截断生成正文。generating（请求2）启用时同样有 memories 部分（v2.12 核心改造：注入【世界设定】+【相关往事】）；reviewing 关闭时（默认）无 reviewing 阶段，dialogue_budget = remaining_budget；reviewing 启用时（2026-08-05 方案D）去掉历史后也无 dialogue_budget，仅计算 retrieval_budget。extracting/summarizing 输入简单（仅生成正文/回复正文 + 短系统提示），token 占用小，无需复杂预算控制。

**多级缩减顺序**（从最先砍到最后砍）：

| 缩减级 | 操作 | 保留下限 | 说明 |
|--------|------|---------|------|
| 1 | 砍对话轮次 | 最近 2 轮（4 条消息） | 从最旧开始砍，保最近 |
| 2 | 砍检索经历 | 1 条 | 从最低分开始砍，保最高分 |
| 3 | 兜底：截断生成正文 | 保留前 50% | 异常情况，记日志警告 |

正常情况第 1 级就够，第 3 级是兜底（说明 system_prompt + 生成正文 + 用户消息本身已超窗口，属于配置异常）。

> **v2.12 修订**：第 1 级"砍对话轮次"在 CompactionPoint 已触发压缩后仍超预算时执行。压缩摘要作为稳定前缀固定不缩减（详见 §5）。

**填充算法**：
```
function assembleContext(request_type, ...):
    messages = [system_prompt]

    # v2.12 新增：压缩摘要作为稳定前缀（compacting 阶段产出）
    if compactionSummary != null:
        messages += [compactionSummary]  // system 角色，紧跟 system_prompt 之后

    # 填充对话轮次（从最近往前填，超 budget 砍最旧）
    dialogue = fillDialogue(history, dialogue_budget, min_rounds=2)
    messages += dialogue

    if request_type in ('generate', 'review'):  # v2.12：generating 也注入记忆
        # 填充检索经历（按分数降序填，超 budget 砍最低分）
        memories = fillMemories(retrieved, memories_budget, min_count=1)
        messages += [formatFactBlock(facts)]   # 【世界设定】（DOC-11 §6.3，v2.12 generating 也注入）
        messages += [formatMemories(memories)] # 【相关往事】（DOC-09A-1 §3.2 定义的格式）

    if request_type == 'review':
        messages += [formatGenerated(generatedText)]

    messages += [user_input]
    return messages
```

> **2026-08-05 方案D 修订**：上述填充算法为 generating 阶段的通用流程。reviewing 阶段（方案D）的填充逻辑不同：跳过 `compactionSummary` 和 `dialogue`（去掉历史和压缩摘要），在 `system_prompt` 之后插入审查提示词（独立 system 消息），`formatGenerated(generatedText)` 与 `user_input` 合并为末尾一条 user 消息（用 `【用户消息】` / `【需要审查的生成内容】` 标记分隔）。详见 §4.6 结构图。

### 4.4 缓存前缀策略

复用 DOC-08 第 4.3 节的拼接顺序，稳定内容前置：

**system_prompt 拆分**：
```

[差异后缀] 任务说明 + 输出格式           ← generate 和 review 不同
```

> **v2.12 缓存命中区扩大**（2026-07-30；2026-08-05 修订）：引入 CompactionPoint 后，压缩摘要作为稳定前缀紧跟 system_prompt 之后（详见 §5）。缓存命中区从原"只有角色提示词（200-1000 token）"扩大为"角色提示词 + 压缩摘要（3000-6000 token）"，缓存命中区扩大 3-6 倍。压缩摘要生成后到下次压缩前完全不变，generating 和 reviewing（启用时）的"角色提示词 + 压缩摘要 + 历史对话 + 记忆块"前缀完全一致，跨请求 prefix caching 命中率显著提升。**2026-08-05 方案D 修订**：reviewing 去掉压缩摘要和历史后，仅角色提示词与 generating 一致，缓存命中区缩小但省去大量历史 token。

**请求3（审查修正，reviewEnabled=true 时）拼接顺序**（2026-08-05 方案D：去掉压缩摘要和历史，审查后缀改为独立 system 消息）：

**缓存命中预期**：2026-08-05 方案D 后预期 30-50%（相比方案C 的 60-75% 有所降低），因 reviewing 去掉历史和压缩摘要后，仅角色提示词命中 generating 缓存前缀。但省去了大量历史对话 token（半稳定段 ③ 和稳定段 ② 均不注入），总 token 消耗显著下降，综合成本仍优于方案C。审查阶段不需要历史--生成时已基于历史生成，审查仅对照检索结果检查事实一致性。

> **事实层对缓存的影响**（DOC-11 §6.3，2026-07-20 新增；2026-07-22 修订；v2.12 修订；v0.2.2 修订；2026-08-05 修订）：事实层【世界设定】注入文本在请求2（generating，v2.12 新增注入）/请求3（reviewing，启用时）的"变化后缀"段中。v0.2.2 修订位置：位于历史对话之后、当前用户消息之前（与【相关往事】同为记忆块 ④⑤，v0.2.2 记忆块整体移到历史后以提升缓存命中；原 v2.12 位于用户消息之后）；2026-08-05 方案D 中 reviewing 去掉历史和压缩摘要，【世界设定】+【相关往事】仍保留（复用 retrieving 结果），用户消息+生成内容合并为末尾 user 消息 ⑧（不再单独注入）。`factBlock` 每轮可能变化（关键实体集合稳定但属性可能被更新，详见 DOC-11 §6.3），故不进入"半稳定"前缀；但同一轮内 reviewing 请求只发起一次，不影响"跨请求缓存命中"统计。若长期开启事实层且关键实体属性高频更新，缓存命中率可能下降 5-10%（具体取决于供应商缓存策略），属于可接受范围。

仅保存修改后的助手正文时，同时撤销该轮活跃往事和当前稿件快照里的出处标记。原摘要保留，按原条件参与检索。再次重生成后按原编号切回，读到的是编辑后的正文。其他稿件可随各自的正文和原输入恢复有效标记。

> **2026-08-05 方案D 说明**：方案D 从方案C 进一步演进--去掉压缩摘要（②）和历史对话（③），审查后缀从末尾 user 消息改为独立 system 消息（⑦），用户消息+生成内容合并为末尾一条 user 消息（⑧，用 `【用户消息】` / `【需要审查的生成内容】` 标记分隔）。去掉历史和压缩摘要的理由：审查阶段不需要历史（生成时已基于历史生成），仅保留角色提示词（①，命中 generating 缓存前缀）+ 审查提示词（⑦，独立 system）+ 检索区（④⑤，复用 retrieving 结果）。缓存命中预期从方案C 的 60-75% 降至 30-50%，但省去了大量历史 token，综合成本更优。事实一致性维度强化：对照【世界设定】检查人物设定（名字/性格/技能等），对照【相关往事】检查剧情连贯性（事件/物品/地点等）。以下"双 system 主次结构"和"生成正文合并到最后的 user 消息"两条说明描述的是 v2.22 的历史设计，**已被方案D 取代**。详见上方 ASCII 图与 `doc/design/13_故事模式上下文机制设计.md` §7。

- **reviewing 可选**（v2.12 新增）：`reviewEnabled=false`（默认）时跳过 reviewing，生成即最终；`reviewEnabled=true` 时执行 reviewing 做审查修正。开关粒度：会话级 `reviewEnabledOverride` > 全局 `intermediate.reviewEnabled`（DB 列名保持 `revise_enabled_override`，Dart 字段名为 `reviewEnabledOverride`，详见 DOC-09B §10）。
- **reviewing 复用 retrieving 结果**（v2.12 新增）：reviewing 不重新检索，直接复用 retrieving 阶段已检索到的【世界设定】+【相关往事】结果。检索 query 来自 extracting 阶段（基于用户消息+历史对话），与生成正文内容无关，无需重新检索。
- **双 system 主次结构**（2026-07-22 修订）：第一条 system 是审查后缀（`kReviewSuffixPromptV2`，编辑任务指令），让 LLM 明确"本轮我是编辑，任务是审查修正生成正文"；第二条 system 是角色提示词（生成正文生成规则，与 generating 的 system 文本完全一致 → 跨请求缓存命中）。审查后缀中明确告知 LLM"生成正文和对话历史均基于第二条 system 提示词生成，审查时必须符合该提示词要求"。旧设计把角色提示词作为主、审查后缀作为后缀拼接，导致 LLM 仍以"叙述者"视角处理，审查指令被弱化。
- **生成正文合并到最后的 user 消息**（2026-07-22 修订）：原 v2.13 将生成正文用 `system` 角色注入（避免与历史 `assistant` 消息混淆），但实测发现 LLM 弱化处理中间 system 消息，导致 reasoning tokens 中出现"找不到生成正文"的问题。现改为：生成正文 + `draftInjectionPrefix` 前缀 + 修正请求文本，合并为最后一条 `user` 消息。历史里的 `assistant` 消息混淆问题通过 `draftInjectionPrefix`（"【生成正文】（待修正）\n"）前缀标注解决，不再依赖角色隔离。
- **v2.12 软约束**（2026-07-30 修订）：删除原硬约束"段落数量守恒""情节要点守恒""不得另起炉灶""不得从草稿结尾续写"——这些是导致 LLM 锚定生成正文、审查不严谨的元凶。生成正文已注入记忆生成（generating 阶段），reviewing 的职责从"重写"降级为"轻量修正"。新增"仅在发现明确事实矛盾时修正，不得主动改写情节""如果生成正文与记忆一致，直接输出生成正文原文，不要为改而改"。
- 用户输入放在生成正文前，让模型知道本轮用户意图
- **世界设定（事实层，DOC-11 §6.3，2026-07-20 新增；2026-07-22 加免责声明）** 用 `system` 角色注入，位置在用户消息之后、`【相关往事】`**之前**。理由：事实层是"当前世界状态"快照，逻辑上应优先于"历史往事"被模型感知；先建立"世界是什么样的"再带入"发生过什么"更符合人类创作者的心智流程。`factBlock` 为空字符串时不注入（事实层未启用或本轮无任何命中实体）；`factBlock` 仅含标题（`【世界设定】`，无实体行）时仍注入，显式提示 LLM 当前会话无世界设定，避免模型凭空虚构角色/地点。事实层注入文本由 `FactContextBuilder._formatFactBlock` 生成，按 `character`/`pet`/`npc`/`location`/`item` 五类分组，每个实体一行，含属性+登场轮次+归档信息（详见 DOC-11 §6.2）。失败降级见 §6.5.1。**2026-07-22 新增免责声明**：区块开头加 "（以下为世界设定参考，其中的角色不代表本轮已出场，审查后正文只应出场对话历史中实际在场的角色）"，防止 LLM 把往事/设定中角色误认为本轮已出场（用户反馈：审查后正文叫出不存在的名字）。
- 检索经历用 `system` 角色注入，提供修正参考（无记忆时省略）。**2026-07-22 新增免责声明**：区块开头加"（以下为历史记忆参考，其中的角色不代表本轮已出场，审查后正文只应出场对话历史中实际在场的角色）"，防止 LLM 把往事 `who` 字段中的角色名误认为本轮已出场。
- 最后一条 `user` 消息为用户消息+生成内容（2026-08-05 方案D 修订，原为审查后缀+生成正文全文合并为一条 user 消息）。方案D 中审查后缀已移至独立 system 消息（⑦），末尾 user 消息（⑧）改为 `【用户消息】\n{userInput}\n\n【需要审查的生成内容】\n{generated}` 格式。v2.12 修订后修正请求文本改为软约束版："请基于以上生成正文与相关往事，先审查生成正文的事实一致性、叙事质量和AI味，再生成最终回复。仅在发现明确事实矛盾时修正，不得主动改写情节；如果生成正文与记忆一致，直接输出生成正文原文，不要为改而改。"
- **2026-07-19 修订（v2.15）**：删除原"允许原样输出"暗示——原 user 消息文本 "若初稿已足够好可原样输出"与 system prompt 中的同义明文构成三重暗示，导致 LLM 经常原样输出生成正文而不做实质审查。新提示词（`kReviewSuffixPromptV2`）改为两步结构：(1) 在 reasoning tokens 中完成生成正文审查（A 事实与一致性 / B 叙事质量 / C AI 味集群清单 8 项，参考 humanizer-main 项目），(2) 基于审查结果生成审查后正文。审查依赖 reasoning 能力：支持 reasoning 的模型在 reasoning tokens 中完成，不支持的在心中完成，均不输出审查正文。**v2.12 修订**：删除原硬约束"段落数量守恒 + 情节要点守恒"（防止通过删减段落来"去味"的硬约束改为软约束）；集群原则（单个修辞痕迹不算问题，多个痕迹集群出现才需要改，防过度修正）保留。详见 `lib/core/config/intermediate_prompts_v2.dart` 的 `kReviewSuffixPromptV2`。**2026-07-22 修订**：审查清单 A 项措辞从"与往事一致"改为"与对话历史一致"，并新增"不得在审查后正文中引入对话历史中未出场的角色"注意，避免反向诱导 LLM 把往事中角色名写入审查后正文。

### 4.6.1 请求1 extracting / 请求4 summarizing prompt 结构（V2 新增；2026-07-16 修订；v2.12 修订：extracting 输入改造；2026-08-05 修订：extracting 缓存优化）

extracting 和 summarizing 是 V2 新增的结构化步骤，prompt 结构简单。**v2.12 修订**：extracting 输入从"用户消息 + 生成正文"改为"用户当前消息（优先）+ 最近 n 轮对话（按距离递减）"--因 extracting 从 generating 之后前置到 generating 之前（检索前置），此时生成正文尚未生成。**2026-08-05 改造（缓存优化）**：extracting 从"用户消息+最近5轮对话揉成1条 user 消息"改为独立消息形式（压缩摘要? + 历史对话独立消息 + 用户消息），与 generating 共享前缀（角色提示词->压缩摘要->历史）提升 prompt cache 命中率。提示词强调：关键词仅从用户消息提取，历史仅供揣测语境。summarizing 输入保持"用户消息 + 回复正文"不变（回复正文为生成正文或审查后正文）：

**summarizing 5W1E 提取指引**（2026-07-19 新增）：

`kExtractSummaryToolPrompt` 重写为 5W1E 多字段提取，引导 LLM 从回复正文中结构化提炼事件六要素：

| 字段 | 中文 | 必填 | 说明 |
|------|------|------|------|
| `what` | 事件 | 必填 | 核心动作/情节，动宾短语，"发生了什么" |
| `when` | 时间 | 可选 | 5W1E·何时：单条事件的**相对**时间描述（如"傍晚"、"次日清晨"、"三年后"）。注意：与 `narrativeTime` 不同——`when` 是单条事件的相对时间标记，`narrativeTime` 是绝对时间锚点（如"来公寓第三天"），两者共存 |
| `narrativeTime` | 绝对叙事时间 | 必填 | v0.2 叙事时间机制启用（2026-07-25）：绝对故事内时间锚点（如"来公寓第三天"），LLM 每轮输出后由控制器 upsert 到 `chat_sessions.current_narrative_time` 作为会话级状态。**判断规则**：参照本轮内容与【最近叙事时间线】中最近一轮的值，若本轮时间未推进则**直接沿用最近一轮的字面值**（保持表述一致，避免同一时间出现不同表述如"搬进公寓第一天"vs"搬进新家第一天"）；若本轮时间推进则基于信号输出新的绝对时间；若首轮无历史时间线则根据本轮内容归纳出初始绝对时间。禁止留空。详见 DOC-08 §5.7 |
| `where` | 地点 | 可选 | 事件发生地，具体名词，如"古碑前"、"酒馆" |
| `who` | 人物 | 可选 | 涉及人物列表，逗号分隔，如"勇者、长老" |
| `significance` | 意义 | 可选 | 事件对剧情/人物的影响，节点式描述，如"揭示勇者身世" |
| `extra` | 补充 | 可选 | 不属于 5W1E 但需保留的额外信息（氛围、伏笔、因果链等） |
| `summary` | 旧摘要 | 可选 | 原 V2 单字段摘要，**降级为可选**；保留用于向后兼容与宏摘要归并；5W1E 已覆盖其语义，新数据建议留空 |
| `tags` | 标签 | 必填 | 主题标签数组，便于检索分类 |
| `importance` | 重要性 | 必填 | 1-5 刻度（详见 §6.10.3 提示词优化要点） |
| `event_ended` | 事件终结 | 必填 | bool，标记本事件是否完结（用于事件边界识别） |

**通用性原则**（避免 5W1E 沦为叙事模板）：
- 5W1E 是**结构化记忆载体**，不是回复正文的格式约束——reply 仍为自由叙事文本，5W1E 仅在 summarizing 步骤提取
- 缺失字段宁可不填（输出 null/省略），不要硬凑——例如纯对话场景可能没有 `where`/`significance`
- `what` 必填保证每条记忆都有可检索的最小语义单元；其他字段按场景灵活
- LLM 输出 JSON 示例（kExtractSummaryToolPrompt 内嵌）：
  ```json

   "tags":["身世","古碑"],"importance":5,"event_ended":false}
  ```

**向后兼容**（parseEventSummary / _parseSummaryFromArguments）：
- 旧格式仅有 `summary` 字段：自动用 `summary` 反填 `what`（`what ??= summary`），其他 5W1E 字段为 null
- 新格式 5W1E 齐全：直接解析；若 `what` 缺失但 `summary` 存在，同样反填 `what`
- 持久化层 5W1E 字段以独立列存储（详见 §6.5），`summary` 列保留供宏摘要归并使用

## 5. 压缩机制

### 5.1 中级模式引入 CompactionPoint（v2.12 修订）

> **v2.12 修订（2026-07-30）**：本节原为"中级模式**不使用** CompactionPoint"，v2.12 架构调整后改为**引入 CompactionPoint 机制**。原因：用户深度体验故事模式超过 1M 上下文容量后发现滑动窗口机制导致每轮 prompt 前缀不同，prefix caching 完全不命中，计费昂贵；引入压缩摘要作为稳定前缀可扩大缓存命中区 3-6 倍。

中级模式**引入 CompactionPoint 机制**（v2.12 新增），与 Simple 模式复用同一 `CompactionStreamer` 但语义不同：

| 维度 | Simple 模式 | 中级模式（v2.12） |
|------|------------|------------------|
| 摘要定位 | "继续对话所需"（讨论/决策/正在做什么/下一步） | "对话流向的宏观骨架"（主要事件时间线、角色出场、剧情阶段、关键转折点） |
| 触发时机 | token 阈值：`max(contextWindow - 32000, floor(contextWindow × 0.5)) × compactionThreshold` | 总占用达 `contextWindow × compactionTriggerRatio`（0.5）触发 |
| 压缩范围 | 全部当前上下文消息（含旧摘要） | 原文区消息（不含压缩摘要本身） |
| 摘要位置 | 紧跟 system prompt 之后 | 紧跟 system_prompt 之后（与 generating/extracting 共享稳定前缀；2026-08-05 修订：reviewing 方案D 不注入压缩摘要） |
| 兼任宏摘要 | 否 | **v0.2.3：职责分离**（压缩摘要->上下文注入，分段宏摘要->记忆检索+记忆查看器；首次压缩时压缩摘要兼作宏摘要） |
| 参与语义检索 | 是（作为上下文） | **v0.2.3：分段宏摘要参与语义检索**（importance=3，正常权重，标注"段落摘要"；微摘要标注"事件记忆"） |

**核心定位（v0.2.3 修订：四层信息架构）**：

| 机制 | 定位 | 内容 | 粒度 | 去向 |
|------|------|------|------|------|
| **压缩摘要** | "对话流向"的宏观骨架（累积式） | 主要事件时间线、角色出场、剧情阶段、关键转折 | 粗（骨架） | 上下文注入（稳定前缀） |
| **分段宏摘要** | "本次压缩段落"的剧情总结（分段式） | 本次压缩新增轮次的剧情段落摘要 | 中（段落） | 记忆检索 + 记忆查看器（v0.2.3 新增） |
| **经历检索** | "相关事件"的细节参考 | 5W1E 事件级细节、实体属性快照 | 细（血肉） | 记忆检索（标注"事件记忆"） |
| **最近对话原文** | "氛围语气"的载体 | 具体对话、细节描写、角色心理 | 原文（最细） | 历史区 |

> **v0.2.3 压缩产出变更**：压缩时生成压缩摘要（累积式，-> 上下文注入）+ 分段宏摘要（分段式，-> 记忆检索 + 记忆查看器）。首次压缩时压缩摘要兼作分段宏摘要（仅生成一个摘要）。后续压缩时并行生成两个摘要（两个 LLM 调用或单次调用双输出），互不依赖。详见 DOC-08 §4.5。

**压缩摘要 prompt（故事模式专用）**：
- 保留：主要事件时间线、角色出场情况、剧情阶段、关键转折点
- 不保留：具体对话内容、细节描写、氛围语气、角色台词

**触发与压缩过程**：
```
原文涨到上限（50%）-> 触发压缩 -> 压缩到下限（动态，约32K token）-> 继续对话
压缩量 = 上限 - 下限（128K模型约16K token，1M模型约452K token）
```

**压缩产出写入**（v0.2.3 修订，与 persisting 同事务，详见 §6.5）：
- 压缩摘要（累积式）：
  - `chat_messages`（is_summary=true）
  - `compaction_points` 表
- 分段宏摘要（分段式，v0.2.3 新增）：
  - `experiential_memories`（memory_level='macro'，importance=3，参与语义检索，标注"段落摘要"）
  - 首次压缩时压缩摘要兼作分段宏摘要（仅写入一处，不重复）
  - 后续压缩时分段宏摘要独立写入（仅覆盖本次压缩新增轮次，非累积）

**失败处理**：复用三选项（整轮取消 / 从中断处重试 / 整轮重试）。压缩失败时**不提供"跳过压缩直接用全部原文"的降级选项**——若原文已超上限，跳过压缩会导致 generating prompt 超长，可能触发 LLM 截断或报错。用户可通过"整轮取消"后调整压缩模型或关闭压缩阈值来解决（详见 §6.4）。

### 5.2 记忆层级的职责划分（v0.2.3 修订）

中级模式的"记忆"由四个独立机制承担（v0.2.3 新增分段宏摘要层）：

| 层级 | 机制 | 内容 | 保留策略 |
|------|------|------|---------|
| 短期 | 最近 n 轮对话 | 原文消息 | 超过 n 轮丢弃，token 预算控制兜底；总占用超 `compactionTriggerRatio` 触发压缩 |
| 宏观骨架 | 压缩摘要（累积式） | 主要事件时间线、角色出场、剧情阶段、关键转折 | 稳定前缀（下次压缩前不变），-> 上下文注入 |
| 段落摘要 | 分段宏摘要（分段式，v0.2.3 新增） | 本次压缩新增轮次的剧情段落摘要 | 写入 `experiential_memories`（macro 级别，importance=3），-> 记忆检索 + 记忆查看器 |
| 长期细节 | 经历记忆（微摘要） | 5W1E 事件摘要 | 持久化存储，检索回忆（标注"事件记忆"） |

**不存在的层级**：
- ~~事实层~~（factual_memories 属 v0.3；v0.2 中级模式用 factual_entities + factual_attributes 中间方案 DOC-11）

### 5.3 与 Simple 模式的差异（v2.12 修订）

| 维度 | Simple 模式 | 中级模式 |
|------|------------|---------|
| 长期记忆 | CompactionPoint 摘要 | 压缩摘要（宏观骨架）+ 经历记忆（细节检索） |
| 短期记忆 | maxContextMessages 截断 | ~~maxContextMessages 截断（复用）~~ + 原文区上限/下限（**v0.2.2 阶段 2-F**：故事模式已移除 maxContextMessages 截断，仅由 `recentMinRatio` + `compactionTriggerRatio` 动态控制原文区） |
| token 兜底 | CompactionPoint 触发阈值 | contextBudget 预算分配 + CompactionPoint 触发压缩 |
| 压缩触发 | 自动/手动压缩 | 总占用达 `contextWindow × compactionTriggerRatio`（0.5）自动触发 |
| 宏摘要 | 无（CompactionPoint 摘要即宏摘要） | v0.2.3：压缩摘要与分段宏摘要职责分离（压缩摘要->上下文注入，分段宏摘要->记忆检索+查看器；首次压缩时兼作） |
| UI 压缩入口 | 有（手动压缩按钮） | 无（仅自动触发，UI 展示预算百分比条） |

### 5.4 经历记忆的"压缩"问题

经历记忆本身是 append-only（只增不改）。长期对话后经历记忆会积累很多条，需要考虑：
- 检索时 `RetrievalConfig.topK` 默认 12（v2.12 由 3 扩容至 12，配合 5 类关键词分类与 5 路并行检索，详见 DOC-09A-1 §3.2），不会全部塞进 prompt
- 但 DB 存储会增长，影响检索性能

**v0.2 中级模式暂不做经历记忆归档/清理**（DOC-08 第 5.1 节明确 is_archived/is_summary/archived_event_ids 字段中级模式设为 null/false，v0.3 才用）。如果实际使用中记忆量过大影响性能，v0.2.x 补丁版本可追加归档机制。

**consolidation（宏摘要归并）已废弃**（v2.12 修订；v0.2.3 进一步修订）：
- v2.12 起：废弃独立 macroSummarizing 阶段，压缩摘要兼任宏摘要
- v0.2.3 修订：压缩摘要与分段宏摘要职责分离--压缩摘要（累积式）-> 上下文注入，分段宏摘要（分段式）-> 记忆检索 + 记忆查看器（importance=3，参与语义检索，标注"段落摘要"）
- 原 `consolidation.trigger_threshold = 2.0`（永不触发的阈值）配置保留向后兼容，但 macroSummarizing 阶段不再执行
- 宏摘要语义从"某个事件的摘要"变为"本次压缩新增轮次的剧情段落摘要"（分段式），信息来源从"从经历记忆汇总"变为"从对话原文压缩"
- 若未来 v0.3 启用 consolidation，宏摘要仍用 `summary` 单字段，与 §4.6.1 的 summarizing 5W1E 提取分层共存

## 6. 失败处理状态机

### 6.1 完整状态机（扩展 DOC-09A-1 §1）

> **v2.12 修订（2026-07-30）**：状态机顺序由旧称"drafting→extracting→retrieving→revising→summarizing→persisting"调整为"compacting?(可选)→extracting→retrieving→generating→reviewing?(可选)→summarizing→persisting"（检索前置 + 可选审查 + 引入 CompactionPoint；v0.2.2 阶段名重命名：drafting→generating、revising→reviewing）。reviewing 阶段从"始终执行"改为"可选（默认关闭，`reviewEnabled=false`）"。compacting 阶段为条件触发（原文区达 `recentMaxRatio` 0.5 时触发）。

DOC-09A-1 §1 定义了正常状态（v2.12 后含 compacting 共 7 个主阶段 + idle/failed），失败处理增加重试状态和失败状态：

```
正常流程（v2.12 新顺序）：
  idle → compacting?(条件触发) → extracting → retrieving → generating → reviewing?(可选) → summarizing → persisting → idle
  （compacting 仅在总占用达 contextWindow × compactionTriggerRatio(0.5) 时触发；reviewing 仅在 reviewEnabled=true 时执行，默认关闭）

自动重试（同一工位内）：
  compacting 失败 → compactingRetry → compacting   （最多 2 次重试，E019/E016）
  extracting 失败 → extractingRetry → extracting   （最多 2 次重试，E013/E016）
  retrieving 失败 → retrievingRetry → retrieving   （最多 1 次重试，E012）
  generating 失败 → generatingRetry → generating   （最多 2 次重试，E010/E016）
  reviewing 失败 → reviewingRetry → reviewing      （最多 2 次重试，E014/E016，仅 reviewEnabled=true 时）
  summarizing 失败 → summarizingRetry → summarizing （最多 2 次重试，E017/E016）

整轮失败（自动重试用尽）：
  任一工位重试用尽 → failed

手动处理（用户操作，v2.12 三选项统一）：
  failed → 整轮取消 → idle（回滚所有产物，用户消息回填输入框）
  failed → 从中断处重试 → 从 failedPhase 重新执行（保留失败前产物）
  failed → 整轮重试 → 从第 1 步（含 compacting）重新执行（回滚所有产物）
```

### 6.2 自动重试机制

| 失败工位 | 错误码 | 自动重试次数 | 重试间隔 | 特殊处理 |
|---------|--------|------------|---------|---------|
| compacting（压缩，v2.12 新增） | E019/E016 | 2 次 | 1 秒 | E016 流式中断重新建立 SSE 连接；压缩失败不提供"跳过压缩"降级 |
| extracting（关键词提取） | E013/E016 | 2 次 | 立即(E013)/1秒(E016) | E013 格式错误立即重试 |
| retrieving（检索完全失败） | E012 | 1 次 | 1 秒 | 无；v2.12 后 5 路并行，单路失败降级不算整轮失败 |
| generating（生成正文生成） | E010/E016 | 2 次 | 1 秒 | E016 流式中断重新建立 SSE 连接 |
| reviewing（审查修正生成，可选） | E014/E016 | 2 次 | 1 秒 | E016 流式中断重新建立 SSE 连接；仅 `reviewEnabled=true` 时存在 |
| summarizing（摘要） | E017/E016 | 2 次 | 立即(E017)/1秒(E016) | E017 格式错误立即重试 |
| persisting（持久化） | E018 | 0 次 | - | 事务回滚，直接 failed |

> **V2 错误码变化**：E011（旧称 drafting 格式错误）/E015（旧称 revising 格式错误）在 V2 中不再产生（generating/reviewing 输出纯文本无格式约束）。格式错误现由 E013（extracting）/E017（summarizing）覆盖。E011/E015 仍保留在 `RetryScheduler` 中供向后兼容，但实际不触发。

> **重试次数语义**："自动重试次数" = 失败后**额外**重试次数（不含首次尝试）。如 generating "2 次" = 首次尝试 + 2 次重试 = 共 3 次尝试。与 DOC-09B §10 `*_max_retries` 配置项对齐（非 `*_max_attempts`，避免语义歧义）。

> **实现说明**（2026-07-02）：自动重试已启用。`_fail()` 按错误码查询 `RetryConfig` 最大重试次数，未超限进入 `*Retry` 状态并延迟后重跑同阶段（E013/E017 立即重试，E010/E012/E014/E016 延迟 1 秒，E018 不重试）。`retryCounts` 按阶段计数，成功/手动重试/取消时清零。向量化模型未配置时，关键词向量化恒降级为 `queryVector=null`（FTS5 兜底）。

> **后台中断豁免自动重试**（2026-08-10 新增）：App 切到后台时 `onBackgroundInterrupt()` 调用 `_streamRunner.cancel()`，同步设置 `_isCancelled = true`。`_fail()` 第一行 guard `if (_streamRunner.isCancelled) return;` 直接返回，**不触发 `_scheduleRetry`**。这避免了后台中断后自动重试使用可能不完整的 `_round` 上下文（compacting 修改了 history 但 CompactionPoint 未持久化到数据库）继续生成，导致上下文缺失。回到前台后 `recoverIfStuck()` 干净重置到 idle，用户手动重新发送时从数据库加载完整历史。

**检索失败的细分**（澄清 DOC-08 第 6.2 节"检索失败"）：

| 检索失败类型 | 处理 | 是否整轮失败 |
|------------|------|------------|
| 检索部分失败（单路异常） | 降级用单路结果 | 否，继续 reviewing |
| 检索完全失败（两路都异常） | 自动重试 1 次（E012） | 重试用尽 → 整轮失败 |
| 关键词向量化失败 | Vector 路降级，FTS5 路正常则降级 | 否，继续 reviewing |
| 关键词为合法空（extracting 返回空 `ClassifiedKeywords`） | 跳过检索，返回空列表，reviewing 仍执行（仅润色；compact 降级已于 2026-07-16 移除） | 否，正常情况非失败 |
| 关键词格式错误（extracting 工具调用/JSON 解析失败） | **不进入检索**，触发 E013 重试 | 重试用尽 → 整轮失败 |

> **V2 四步重构修订**（2026-07-10）：关键词格式错误从 E011（旧称 drafting 标记解析失败）改为 E013（extracting 工具调用/JSON 解析失败）。合法空关键词仍触发 compact 模式，语义不变。详见 DOC-09A-1 §3.7 V2 修订说明。

> **Embedding 失败处理增强**（2026-07-21；v2.12 修订 2026-07-30）：
> 原行为：embedding 调用失败时静默降级为 FTS5-only（`fallbackOnFailure=true` 默认）。用户不知道实际已降级。
>
> 新行为：`fallbackOnFailure` 默认值改为 `false`（DOC-09B §10.1），embedding 失败时抛 E104 异常，进入失败状态机。用户在 `FailureBar` 中可选**统一三选项**（v2.12 修订，原"重试/临时降级继续/中止"三选项已废弃）：
> 1. **整轮取消**：用户消息回填输入框，方便修改后重新发送（详见 §6.4）
> 2. **从中断处重试**：走 `continueFromFailed()`，重新尝试 embedding 调用（embedding 服务恢复后自动成功）
> 3. **整轮重试**：从第 1 步（含 compacting）重新执行
>
> **v2.12 修订**：原"临时降级继续"按钮（`continueWithFts5Only()`，跳过 embedding 仅用 FTS5）已移除。理由：用户决策"统一三选项，不增加新选项"。用户可通过"从中断处重试"在 embedding 服务恢复后重试，或通过"整轮取消"后调整嵌入模型配置。
>
> 临时降级（`fallback_on_failure=true` 时）产生的未向量化记忆可通过会话设置 → 记忆管理 → 重建向量索引补全（`IntermediateChatController.rebuildEmbeddings`）。
>
> 高级用户仍可在 `default_config.json` 中将 `fallback_on_failure` 改为 `true` 启用原静默降级行为。

> **2026-07-16 修订**：compact 降级已移除，合法空关键词不再触发 compact 模式，改为 reviewing 仍执行（仅润色，无记忆注入）。reviewing 具有双重功能：按记忆修正生成正文 + 润色文案，即使无记忆也有润色价值。`skipReviseWhenEmptyRetrieval` 配置项保留但不再生效（向后兼容）。

### 6.3 失败时的 UI 保留时序

**核心原则**（DOC-08 第 6.1 节）：数据回滚 ≠ UI 清空。失败时数据层绝不持久化，但 UI 层保留已显示的中间产物。

| 失败工位 | UI 保留内容 | 标记方式 |
|---------|------------|---------|
| generating 失败 | 生成小窗（已显示的部分生成正文文本） | 灰显 + 失败图标 |
| extracting 失败 | 生成小窗 + 提取小窗（无内容，仅状态） | 灰显 + 失败图标 |
| retrieving 失败 | 生成/提取小窗 + 检索小窗（已显示的部分结果，如有的话） | 灰显 + 失败图标 |
| reviewing 失败 | 半截回复 + 已完成的生成/提取/检索小窗 | 全部灰显 + 失败图标 |
| summarizing 失败 | 完整回复 + 生成/提取/检索小窗 + 摘要小窗（无内容） | 全部灰显 + 失败图标 |
| persisting 失败 | 完整回复 + 生成/提取/检索/摘要小窗 | 全部灰显 + "保存失败"提示 |

所有失败情况统一显示：**失败提示文案 + 强化重试按钮**（按钮显著，避免用户找不到）。

**失败时输入框禁用**（v2.12 文案更新）：failed 阶段输入框禁用，占位符改为 `请先重试或整轮取消`（i18n: `inputPlaceholderFailed`），发送按钮 disabled（faint 色）。原实现仅 busy 阶段禁用，failed 阶段输入框可输入但发送被 Controller 静默丢弃（`sendMessage: if (state.phase != idle) return`），用户体验差。修订后 failed 阶段也禁用输入，引导用户先重试或整轮取消。**v2.12 修订**：占位符文案从"清空本轮"改为"整轮取消"（与三选项统一）。

**未持久化的保证**：失败时 UI 上保留的所有中间产物（生成正文、检索结果、半截回复）都是临时内存状态，从未写入数据库。用户点重试或整轮取消后即从 UI 消失。

> **修订说明**：上述"未持久化"保证仅适用于 **persisting 失败之前** 的生成正文/检索/半截回复（这些是当前轮次的临时产物，事务未提交故不持久化）。**persisting 成功后**，生成正文/关键词/检索结果会持久化到 `intermediate_round_artifacts` 表（详见 DOC-09C §1 步骤 6），使历史轮次的小窗在切换会话或重启后仍可见。`state.artifactsByTurnNumber` 字段保存这些历史 artifacts，由 loadHistory 加载填充。

### 6.4 手动处理时序（v2.12 修订：三选项统一）

> **v2.12 修订（2026-07-30）**：失败处理从原"重试按钮（整轮从头来）+ 清空按钮"两选项，统一为**三选项**（整轮取消 / 从中断处重试 / 整轮重试）。核心原则：整轮事务性——无论哪个阶段失败，统一走三选项处理逻辑。

**"整轮"的边界定义**（v2.12 包含以下全部操作，合为一整个事务）：

```
┌─────────────────────────────────────────────────────────┐
│                     整轮事务边界                          │
├─────────────────────────────────────────────────────────┤
│  1. CompactionPoint 压缩（条件触发）                     │
│     - 压缩 LLM 调用                                      │
│     - 压缩摘要写入 chat_messages + compaction_points     │
│  2. extracting 关键词提取（LLM 调用）                    │
│  3. retrieving 记忆检索（本地操作）                       │
│  4. generating 生成正文生成（LLM 调用）                   │
│  5. reviewing 审查修正（LLM 调用，可选）                  │
│  6. summarizing 摘要总结（LLM 调用）                     │
│     - EventSummary 提取                                  │
│     - FactsDelta 提取                                    │
│  7. persisting 持久化入库（本地事务）                    │
│     - 生成正文/审查后正文写入 chat_messages              │
│     - EventSummary 写入 experiential_memories            │
│     - FactsDelta 写入 factual_entities + attributes      │
│     - 分段宏摘要写入 experiential_memories（macro，importance=3）│
└─────────────────────────────────────────────────────────┘
```

**事务性含义**：以上 7 步要么全部成功，要么全部回滚。不存在"生成正文成功了但摘要失败导致半成品入库"的中间状态。

**三选项行为**：

| 选项 | 行为 | 适用场景 | Controller 方法 |
|------|------|---------|----------------|
| **整轮取消** | 丢弃本轮所有中间产物（生成正文/关键词/检索结果/摘要），回到 idle 状态。**用户消息内容回填到消息输入框**，方便用户修改后重新发送 | 用户发现方向错误，想重新组织输入 | `cancelRound()` |
| **从中断处重试** | 保留失败前已成功的阶段输出，仅从失败阶段重新执行 | 网络抖动、LLM 临时不可用等可恢复失败 | `continueFromFailed()`（复用现有方法，行为扩展为支持 7 步事务边界） |
| **整轮重试** | 丢弃本轮所有中间产物，从第 1 步（含压缩）重新执行 | 配置错误修复后、prompt 调整后需要完整重跑 | `retryRound()` |

**各阶段失败的"从中断处重试"行为**（v2.12 新增 compacting 行）：

| 失败阶段 | 已保留的中间产物 | 重试起点 | 备注 |
|---------|----------------|---------|------|
| compacting 压缩 | 无（压缩是第 1 步） | 重新压缩 | 若连续失败，用户可"整轮取消"后调整压缩模型 |
| extracting | 无（压缩失败已回滚） | 重新 extracting | — |
| retrieving | 5 类关键词 | 重新检索 | 关键词已提取成功，无需重调 LLM |
| generating | 关键词 + 检索结果 | 重新 generating | 检索结果可复用，省一次本地检索 |
| reviewing | 关键词 + 检索结果 + 生成正文 | 重新 reviewing | 生成正文已生成，无需重调 generating LLM |
| summarizing | 关键词 + 检索结果 + 最终回复（生成正文或审查后正文） | 重新 summarizing | **重要**：最终回复已流式展示给用户，重试时保持已展示内容不变 |
| persisting | 全部 LLM 产物（回复 + 摘要 + deltas） | 重新写入数据库 | 数据库事务失败自动回滚，重试即重新提交事务 |

**整轮取消的输入框回填**（v2.12 新增）：

用户选择"整轮取消"后，`pendingUserMessage` 的内容回填到消息输入框（`InputBar`），用户可直接编辑后重新发送。这与原 §6.4.1 的"保留用户消息在 UI（用户可编辑后重发）"机制对齐——区别在于原方案保留为消息气泡，v2.12 改为回填到输入框，更符合"重新组织输入"的用户意图。

```
用户点【整轮取消】：
1. 清掉所有已显示的中间产物（生成小窗、检索小窗、半截/完整回复）
2. 回填用户消息内容到消息输入框（不保留为消息气泡）
3. 状态 → idle
4. 不自动重试，等用户编辑后重发
```

**summarizing 失败的特殊处理**（v2.12 与 D16 决策一致）：

summarizing 失败时，最终回复已经流式展示给用户。重试时：
- **不清空已展示的回复内容**（用户体验：回复还在，只是记忆没更新）
- 仅重新调用 summarizing LLM
- 若用户选择"整轮取消"，则连回复一起丢弃（符合事务性原则）

这与 D16 决策（2026-06-30 修订）一致："失败时保留已显示内容（标记失败/灰显）+ 强化重试按钮"。

**CompactionPoint 失败的降级**（v2.12 新增）：

压缩失败时，除了三选项外，**不提供"跳过压缩直接用全部原文"的降级选项**。理由：
- 用户决策：统一三选项，不增加新选项
- 若原文已超上限，跳过压缩会导致 generating prompt 超长，可能触发 LLM 截断或报错
- 用户可通过"整轮取消"后调整压缩模型或关闭压缩阈值来解决

**与现有 `continueFromFailed()` 的关系**：

现有 `continueFromFailed()` 方法已实现"保留已完成阶段输出，从失败点恢复"逻辑。v2.12 新流程下：
- 方法签名不变，行为扩展为支持新的 7 步事务边界
- 失败状态记录中新增 `failedPhase` 字段，标识失败的具体阶段（含 compacting）
- 重试时根据 `failedPhase` 跳转到对应阶段的起点

### 6.4.1 失败/取消后保留用户消息的操作能力

§6.4 提到"保留用户消息在 UI（用户可编辑后重发）"，本节明确该保留消息（`pendingUserMessage`）支持的操作集合。

**触发条件**：phase ∈ {idle, failed} 且 `state.pendingUserMessage != null`。
- `idle`：用户点"整轮取消"后，phase 回到 idle，pendingUserMessage 内容回填到输入框（v2.12 修订：原保留为消息气泡，现回填输入框，详见 §6.4）
- `failed`：生成失败后，pendingUserMessage 保留（用户可选择"从中断处重试"/"整轮重试"保留消息，或"整轮取消"回填输入框）

**可用操作**（消息气泡上的操作按钮，与持久化消息保持一致）：
| 操作 | 行为 | 对应 Controller 方法 |
|------|------|---------------------|
| 复制 | 复制消息内容到剪贴板（不依赖 phase） | UI 层直接处理 |
| 编辑重发 | 弹出编辑对话框 → 用户修改后清空 pendingUserMessage（含临时状态）→ 用新内容走 `sendMessage` | `editPendingUserMessage(newContent)` |
| 删除 | 清空 pendingUserMessage + 临时状态 → 回到干净 idle | `deletePendingUserMessage()` |

**与持久化消息编辑/删除的差异**：
- `editPendingUserMessage` 不调用 `chatRepository` 删除记录（pendingUserMessage 未入库），仅清空 state
- `deletePendingUserMessage` 不调用 `deleteRoundAndDownstream`，仅清空 state

**发送新消息的覆盖确认**：若用户在 pendingUserMessage 存在时发送新消息（非编辑重发），UI 层（`_handleSend`）先弹出确认对话框：

```
┌──────────────────────────────────┐
│ 覆盖未发送的消息？                │
│ 你有上一条未发送成功的消息，       │
│ 发送新消息将覆盖它。是否继续？     │
│        [取消]   [确认]           │
└──────────────────────────────────┘
```

用户确认后才走 `sendMessage`（旧 pendingUserMessage 被新消息覆盖）；用户取消则保留原消息不变。

**actionsEnabled 计算**：pendingUserMessage 渲染时 `actionsEnabled = (phase == idle || phase == failed)`，避免生成中（generating/retrieving/reviewing/persisting）出现操作按钮。`canOperate` 通过 `canOperateOverride: true` 绕过窗口检查（pendingUserMessage 不在 `state.messages` 列表中，无法通过 `_computeTurnNumber` 判断窗口）。

### 6.5 原子事务边界

> **v2.12 修订（2026-07-30）**：事务范围从"从 generating 开始到 persisting 结束"扩展为"从 compacting 开始到 persisting 结束"（含 CompactionPoint 压缩）。压缩摘要的写入与回复写入必须在同一事务内——若压缩成功但后续 generating 失败，用户选择"整轮取消"时，压缩摘要也要回滚（避免出现"压缩了但没用上"的孤儿摘要）。

**事务范围**（v2.12）：从 compacting 开始到 persisting 结束，全程一个逻辑事务。但实际 drift transaction 只包裹持久化阶段（compacting/extracting/retrieving/generating/reviewing/summarizing 阶段无 DB 写入，仅 persisting 阶段有 DB 写入）。压缩摘要的写入在 persisting 阶段事务内执行（与回复/记忆同事务），保证原子性。

**drift transaction 内的写操作**（persisting 阶段，同一 transaction，完整时序见 DOC-09C）：

```dart
database.transaction(() async {
  // 1. 用户消息写入 chat_messages
  await chatRepository.addMessage(userMessage);

  // 2. 助手回复写入 chat_messages
  await chatRepository.addMessage(assistantMessage);  // reply

  // 3. 事件摘要追加 experiential_memories（签名以 DOC-05-5 §4.5 为准）
  //    2026-07-19：5W1E 6 字段传入（what 必填，其余可空）
  //    2026-07-25 叙事时间机制：narrativeTime 传入，持久化到 narrative_time 列
  //    summary 字段保留可选，向后兼容与宏摘要归并使用
  final memory = await experienceRepository.appendExperience(
    sessionId: sessionId,
    what: eventSummary.what,              // 必填：核心事件
    when: eventSummary.when,              // 可选：相对叙事时间（5W1E·何时）
    narrativeTime: eventSummary.narrativeTime, // 可选：绝对叙事时间锚点（v0.2 叙事时间机制，2026-07-25）
    where: eventSummary.where,            // 可选：地点
    who: eventSummary.who,                // 可选：人物
    significance: eventSummary.significance, // 可选：意义
    extra: eventSummary.extra,            // 可选：补充
    summary: eventSummary.summary,        // 可选：旧单字段摘要（向后兼容）
    importance: importance,
    tags: tags,
    turnNumber: turnNumber,
  );
  final memoryId = memory.memoryId;

  // 4. 事件摘要 embedding 写入 experiential_memories.embedding BLOB（如果同步生成成功）
  //    无独立 memory_vectors 表，updateEmbedding 直接 UPDATE experiential_memories
  if (embedding != null) {
    await experienceRepository.updateEmbedding(memoryId, embedding);
  }

  // 5. 事件摘要同步写入 memories_fts（显式插入，非触发器）
  //    2026-07-19：insertFtsIndex 接收 7 字段
  //    （memoryId + 6 个 5W1E 字段，summary 与 what 合并写入 FTS5 content 以保证检索召回）
  await experienceRepository.insertFtsIndex(
    memoryId: memoryId,
    what: eventSummary.what,
    when: eventSummary.when,
    where: eventSummary.where,
    who: eventSummary.who,
    significance: eventSummary.significance,
    extra: eventSummary.extra,
    sessionId: sessionId,
  );

  // 6. 更新 session.lastActiveAt + messageCount
  await chatRepository.updateSessionLastActive(sessionId);

  // 6.5 更新会话级当前叙事时间状态（v0.2 叙事时间机制，2026-07-25 新增）
  //    EventSummary.narrativeTime 非空时，upsert 到 chat_sessions.current_narrative_time
  //    作为下一轮 summarizing 阶段时间线上下文的来源。
  //    narrativeTime 为空时保留原状态（不更新）。
  //    事务内执行：与经历层 persisting 同事务，失败回滚整轮。
  if (eventSummary.narrativeTime != null && eventSummary.narrativeTime!.isNotEmpty) {
    await chatRepository.updateCurrentNarrativeTime(
      sessionId,
      eventSummary.narrativeTime!,
    );
  }

  // 7. APPLY 事实变更 deltas → factual_entities / factual_attributes /
  //    factual_memory_history（DOC-11 v22 新增，仅在 factsDeltas 非空且
  //    factual.enabled=true 时执行）
  //    FactApplier.applyDeltas(sessionId, deltas, turnNumber, config) 在本事务内执行：
  //    - 逐个 delta 应用（createEntity / updateAttr / appendList /
  //      removeFromList / addAlias / archiveEntity）
  //    - 每个 delta 经三重防护 + 5 层健康度防护检查（DOC-11 §7）
  //    - 通过检查的 delta 写入 factual_entities / factual_attributes，
  //      并追加 factual_memory_history 审计日志
  //    - 被防护跳过的 delta 不计入失败（appliedCount 不递增）
  //    - 每个 delta 独立捕获；无效或应用失败的单条 delta 记录日志并跳过
  //    - 只有事实层之外传播到事务边界的基础设施异常才回滚整轮
  if (factsDeltas != null && factsDeltas.isNotEmpty && factualConfig.enabled) {
    await factApplier.applyDeltas(
      sessionId: sessionId,
      deltas: factsDeltas,
      turnNumber: turnNumber,
      config: factualConfig,
    );
  }

  // 8. 若本轮触发了 CompactionPoint 压缩，写入压缩摘要（v2.12 新增）
  //    压缩摘要与回复/记忆同事务写入，保证原子性：
  //    - 若压缩成功但后续 drafting 失败，用户选择"整轮取消"时，压缩摘要也回滚
  //      （避免出现"压缩了但没用上"的孤儿摘要）
  //    - 写入三处：
  //      a) chat_messages（is_summary=true，作为稳定前缀消息）
  //      b) compaction_points 表（压缩点记录，含 boundary 消息 ID）
  //      c) experiential_memories（memory_level='macro'，分段宏摘要，importance=3，参与语义检索）
  if (compactionResult != null && compactionResult!.triggered) {
    // a) 压缩摘要写入 chat_messages
    await chatRepository.addMessage(compactionResult.summaryMessage);
    // b) 压缩点记录写入 compaction_points
    await chatRepository.recordCompactionPoint(
      sessionId: sessionId,
      summaryMessageId: compactionResult.summaryMessage.id,
      boundaryMessageId: compactionResult.boundaryMessageId,
      tokenCount: compactionResult.tokenCount,
    );
    // c) 分段宏摘要写入 experiential_memories（macro 级别，importance=3，参与语义检索）
    //    v0.2.3：首次压缩时压缩摘要兼作分段宏摘要（compactionResult.summaryText 即分段宏摘要）
    //    后续压缩时分段宏摘要独立生成（compactionResult.macroSummaryText）
    final macroSummaryText = compactionResult.macroSummaryText
        ?? compactionResult.summaryText;  // 首次压缩兜底
    await experienceRepository.appendExperience(
      sessionId: sessionId,
      what: macroSummaryText,              // 分段宏摘要用 what 字段存储全文
      memoryLevel: 'macro',                 // 标记为宏级别，参与语义检索
      turnNumber: turnNumber,
      importance: 3,                        // v0.2.3：分段宏摘要 importance=3
    );
  }
});
```

**传播到 transaction 边界的异常 → 整个 transaction 回滚 → 不写入任何数据。** FactApplier 内部的单条 delta 失败已被捕获并跳过，不会传播到事务边界；压缩摘要等其他未捕获异常仍会回滚整轮。

> **压缩摘要写入的原子性**（v2.12 新增）：步骤 8 与步骤 1-7 在**同一 drift transaction** 内执行。若压缩成功（compactionResult.triggered=true）但后续 generating/summarizing 失败，用户选择"整轮取消"时，压缩摘要也回滚——避免出现"压缩了但没用上"的孤儿摘要。这是整轮事务性原则的硬约束。

> **事实层写入边界（2026-08-11 按代码核对）**：步骤 7 位于同一 drift transaction，但 `FactApplier.applyDeltas` 对每个 delta 独立捕获。软防护和单条应用异常都会跳过该 delta 并继续，因此可能出现本轮部分事实变更成功、部分失败，而消息与经历记忆仍提交。只有 FactApplier 之外的事务级异常才回滚整轮。这是“事实数据尽力写入、核心经历链路优先可用”的当前实现。

**embedding 同步生成的位置**（DOC-09A-1 §3.9 已定）：
- embedding 生成在 persisting **之前**（summarizing 流结束后立即调用 embedding API）
- embedding 成功 → 作为参数传入 transaction，步骤 4 写入
- embedding 失败 → 降级标记 `has_embedding=false`，步骤 4 跳过，事务仍提交

**用户消息的处理**（与 Simple 模式的差异）：
- Simple 模式：用户消息在 sendMessage 开头就入库（事务外）
- 中级模式：用户消息在 persisting 阶段事务内入库（保证原子性）
- UI 层：用户输入后立即显示（临时状态 `pendingUserMessage`，未持久化），事务成功后才真正持久化；失败时 UI 保留用户消息显示，数据层不持久化
- `editAndResend`（编辑历史消息重发）遵循同样模式：删除旧轮次后立即创建 `pendingUserMessage` 显示新用户消息气泡，`persisting` 事务内持久化。避免编辑重发期间用户消息消失

### 6.5.1 事实层失败降级链（DOC-11 v22 新增，2026-07-20）

事实层在四步生成的两个不同阶段参与，失败降级分为**检索阶段（retrieving）**和**写入阶段（persisting）**两类，降级链如下：

| 阶段 | 失败类型 | 处理 | 是否整轮失败 | 错误码 |
|------|---------|------|------------|--------|
| **retrieving** | 关键实体加载失败（`getKeyEntities` 异常） | try-catch 全包，返回 `factBlock=''`，不抛异常；经历层检索独立执行不受影响 | 否 | 无（记 warn 日志） |
| **retrieving** | 关键词匹配失败（`findByName` 异常） | 同上 | 否 | 无（记 warn 日志） |
| **retrieving** | 属性加载失败（`getAttributes` 异常） | 同上 | 否 | 无（记 warn 日志） |
| **retrieving** | 整个 `FactContextBuilder.buildFactBlock` 抛异常 | 外层 catch 返回 `FactRetrievalResult(factBlock='', facts=[])` | 否 | 无（记 warn 日志） |
| **retrieving** | 事实层禁用（`factual.enabled=false`） | 直接返回空结果，不进入 try 块 | 否 | 无 |
| **summarizing** | `extract_facts` 工具未调用（LLM 只调 `extract_event_summary`） | `factsDeltas=[]`，步骤 7 跳过，不影响经历层持久化 | 否 | 无 |
| **summarizing** | `extract_facts` 工具调用但参数解析失败 | `factsDeltas=[]`（`_parseFactsSafely` 容错返回空列表），步骤 7 跳过，记 warn 日志 | 否 | 无 |
| **summarizing** | `extract_facts` 工具调用但返回空数组 | `factsDeltas=[]`，步骤 7 跳过（正常情况，无事实变更） | 否 | 无 |
| **summarizing** | LLM 只调用 `extract_facts`（不调 `extract_event_summary`） | `factsDeltas` 保留已解析结果，summary 走 JSON 降级；步骤 7 正常应用事实变更 | 否 | 无（修复 2026-07-20：原代码降级时丢失 factsDeltas） |
| **persisting** | 软防护跳过（三重防护 + 5 层健康度防护） | 跳过该 delta，事务正常提交，`appliedCount` 不递增 | 否 | 无（记 info 日志） |
| **persisting** | 单条 delta 校验/应用失败 | FactApplier 捕获并跳过该 delta，继续处理后续 delta，记录日志 | 否 | 无 |
| **persisting** | FactApplier 之外的事务级异常 | 异常传播到事务边界，回滚整轮 | 是 | E018 |

**降级链核心原则**：

1. **检索阶段"绝不阻塞"**：事实层 retrieving 失败时返回空结果，**经历层检索独立执行不受影响**，reviewing 阶段照常进行（仅【世界设定】区块省略，【相关往事】仍正常注入）。事实层是"锦上添花"，不应成为整轮失败的导火索。

2. **写入阶段“核心链路可用性优先”**：事实 delta 单条容错，失败项不阻塞消息与经历记忆提交。只有事务基础设施或 FactApplier 外部异常才触发整轮回滚。

3. **summarizing 双工具并行的容错**：summarizing 阶段 LLM 调用 `extract_event_summary` + `extract_facts` 两个工具。若 LLM 只调用其中一个或两个都未调用，走"未调用则跳过"的容错路径（不抛异常），最大概率跑通整轮。

4. **软防护 vs 硬错误的边界**：
   - 软防护（三重防护 + 5 层健康度防护）的"跳过"是**预期内行为**：LLM 输出的 delta 可能不符合防护规则（如属性值类型不匹配），属于"事实层智能过滤"的设计意图，不计入失败
   - 单条应用异常由 FactApplier 捕获并记录；事务级异常才是整轮失败，需要用户重试

> **与经历层失败处理的对比**：经历层检索失败走 E012 自动重试（1 次重试用尽 → 整轮失败）；事实层检索失败不重试、不抛异常、不进入失败状态。差异原因：经历层检索是"核心流程"，事实层检索是"增强功能"，二者容错策略不同。

### 6.5.2 全局网络超时作用范围（修复 2026-07-20）

**问题背景**：通用设置 → 高级中的"连接超时"（`network.connect_timeout_ms`）和"响应超时"（`network.receive_timeout_ms`）在故事模式（中级模式）下不生效。原代码所有 9 处 `LlmRequest` 构造点均未传递 timeout 参数，回退到 `HttpClient` 硬编码的 15s/30s 默认值，用户在通用设置中调整的超时值被完全忽略。

**修复方案**：
- `RoundContext` 新增 `connectTimeout` / `readTimeout` 字段（`Duration` 类型），由 `IntermediateChatController._prepareAndRunRound` 从全局配置 `network.connect_timeout_ms` / `network.receive_timeout_ms` 读取并填充
- 4 个 PhaseHandler（generating / extracting / reviewing / summarizing）在 `_buildRequest` / `_buildToolCallRequest` / `_runJsonMode` 中将 `ctx.connectTimeout` / `ctx.readTimeout` 透传到 `LlmRequest`
- `MacroSummaryPhaseHandler` 同步透传

**作用范围**：
| 模式 | timeout 来源 | 生效路径 |
|------|-------------|---------|
| Simple 模式（chat） | 全局 `network.*` | ChatController 直接读全局配置传入 LlmRequest |
| 中级模式（story） | 全局 `network.*` | IntermediateChatController → RoundContext → 4 PhaseHandler → LlmRequest → HttpClient.streamPost |
| Advanced 模式（v0.3） | 全局 `network.*` | 待实施，同中级模式架构 |

**关键约束**：故事模式 9 处 LLM 请求构造点（generating 工具调用+JSON降级、extracting 工具调用+JSON降级、reviewing 纯文本、summarizing 工具调用+JSON降级、宏摘要工具调用+JSON降级）必须全部透传 timeout，不得遗漏。`MacroSummaryPhaseHandler` 也需透传。

> **思考配置作用范围**：通用设置 → 高级中的"思考强度"（`reasoning_effort`）同样对双模式生效。v1.4 起，所有 PhaseHandler 无条件传递 `reasoningEffort` 参数到 `LlmRequest`，由适配器层（`ThinkingParamBuilder` / `AnthropicAdapter` / `GeminiAdapter`）按 modelId 过滤。Simple 模式由 `ChatModeController` 同样无条件传递。

> **v0.2.2 阶段 2-G 明确作用范围**：思考预算（reasoningEffort）仅作用于 generating（生成正文生成）和 reviewing（审查修正）阶段。extracting/summarizing/macroSummarizing 等结构化任务阶段强制禁用（`ReasoningEffort.disabled`），因为这些阶段是工具调用/JSON 模式的结构化输出，不需要思考预算。PhaseHandler 在构造这些结构化任务阶段的 `LlmRequest` 时，将 `reasoningEffort` 置为 `ReasoningEffort.disabled`，覆盖会话级/全局级配置。

### 6.6 与 Simple 模式失败处理的核心差异（v2.12 修订）

| 维度 | Simple 模式 | 中级模式（v2.12） |
|------|------------|---------|
| 事务性 | 无原子事务（user 先入库，assistant 流式完成入库） | 原子事务（user+reply+memory+向量+FTS5+压缩摘要+事实层 同一 transaction） |
| 失败时数据 | 错误持久化到消息 error 字段 | 不持久化任何数据（事务回滚，含压缩摘要） |
| 失败时 UI | 保留半截 + 错误卡片 | 保留所有中间产物（灰显）+ 三选项对话框 |
| 自动重试 | 无（LLM 层面） | 有（compacting 2次、extracting 2次、检索1次、generating 2次、reviewing 2次、summarizing 2次） |
| 手动处理 | regenerate/editAndResend（新分支） | **三选项统一**（整轮取消回填输入框 / 从中断处重试 / 整轮重试） |
| 降级策略 | 无降级 | 失败时无降级质量（不用生成正文充当回复、不静默跳过检索）；结构化输出降级链：工具调用→JSON→提示词约束；压缩失败不提供"跳过压缩"降级（v2.12） |
| 单路检索失败 | N/A | 降级用单路结果（不算整轮失败）；v2.12 后 5 路并行，单路失败降级 |

### 6.8 失败分类器（`StoryFailureClassifier`）

纯 Domain 层工具类，将原始异常自动分流为 `ErrorCategory`，并提供 i18n 通俗提示文案和建议操作文案。位于 `lib/features/story_runtime/domain/services/failure_classifier.dart`（与故事模式共用）。

**三个公开方法**：

| 方法 | 签名 | 职责 |
|------|------|------|
| `classifyError` | `Object → ({ErrorCategory category, int? httpStatus, String? rawError})` | 将异常分流为分类+HTTP状态+原始文本 |
| `resolveFailureMessage` | `(String errorCode, ErrorCategory) → String` | 按 errorCode 返回通俗提示（"发生了什么"） |
| `resolveSuggestion` | `ErrorCategory → String` | 按 category 返回建议操作（"该怎么做"），由 UI 层调用 |

**异常分流规则**（`classifyError`）：

| 异常类型 | 条件 | 分类 |
|---------|------|------|
| `AppHttpException` | statusCode 401/403 | auth |
| `AppHttpException` | statusCode 429 | rateLimit |
| `AppHttpException` | statusCode >= 500 | server |
| `AppHttpException` | statusCode >= 400（其他 4xx） | server |
| `AppHttpException` | code `connection_timeout`/`receive_timeout`/`send_timeout` | timeout |
| `AppHttpException` | code `connection_error` | network |
| `TimeoutException`（dart:async） | — | timeout |
| `AgentLlmException`（导演 agent loop 网关异常） | semantic=contextOverflow / 超限文案 / 模型不可用文案 | contextOverflow / server |
| `AgentLlmException` | code `BAD_REQUEST` 或 statusCode 400（模型不可用除外） | request |
| `AgentLlmException` | code `RATE_LIMIT`/429、`AUTH`/401/403、`SERVER`/5xx、`timeout`、`connection_error` | rateLimit / auth / server / timeout / network |
| `_StreamErrorException`（私有，toString 含 "StreamError"） | — | network |
| 其他 | — | unknown |

> **request 类别**：400 参数/工具 schema 被模型拒绝属确定性错误，重发同一载荷必然再失败；建议文案为「调整模型或会话设置后重试」，导演 EAGENT 失败卡与故事 E016 共用该分类。

> **`rawError`**：异常 `toString()` 截断前 500 字符，供技术用户诊断。非 HTTP 错误 `httpStatus` 为 null。

**Controller 集成**（`_fail` 方法）：

```dart
// _fail 签名：
Future<void> _fail(
  IntermediatePhase phase,
  String errorCode, {
  Object? error,           // 原始异常（传入则由分类器分流）
  ErrorCategory? errorCategory,  // 手动覆盖（优先于分类器结果）
  bool jsonFormat = false,
  IntermediateConfig? config,
})
```

- `error != null`：调用 `classifyError(error)` 获取 (category, httpStatus, rawError)，`errorCategory` 参数可覆盖 category
- `error == null`：category = `errorCategory ?? ErrorCategory.unknown`（如 E013/E017 格式错误无异常对象，手动指定 `format`）
- 通俗提示由 `resolveFailureMessage(errorCode, category)` 解析，存入 `FailureContext.errorMessage`

> **覆盖优先级**：`errorCategory ?? result.category`（手动覆盖优先于分类器推断）。E013/E017 固定 `format`、E018 固定 `persist`；E010/E012/E014/E016 由分类器根据异常动态推断。（V2：E011/E015 不再产生，但分类器仍保留其映射供向后兼容）

### 6.9 结构化输出降级链

**背景**：中级模式部分步骤依赖 LLM 输出结构化数据（关键词、事件摘要）。实践中 LLM 输出格式不稳定是导致对话中断的首要原因，故设计降级链最大化"跑通"概率。

**纯客户端约束**：LMStory 是纯 Flutter 客户端，无法引入 Python Instructor/Outlines 等约束解码库。只能依赖供应商原生工具调用/JSON Mode + 客户端容错。

#### 6.9.0 V2 四步重构后的降级链（2026-07-10）

V2 四步拆分后，文本步骤与结构化步骤分离，降级链大幅简化：

| 步骤 | 输出类型 | 降级链 | 实现 |
|------|---------|--------|------|
| drafting（请求1） | 纯文本 | 无需结构化，无降级 | `StreamRunner.runPlainText` |
| revising（请求3） | 纯文本 | 无需结构化，无降级 | `StreamRunner.runPlainText` |
| extracting（请求2） | 结构化 `{entities, events}` | 工具调用 → JSON 模式 → 提示词约束 | `ExtractPhaseHandler` |
| summarizing（请求4） | 结构化 `{what(必填), when?, where?, who?, significance?, extra?, summary?(可选), tags, importance, event_ended}`（5W1E 多字段，2026-07-19） | 工具调用 → JSON 模式 → 提示词约束 | `SummarizePhaseHandler` |

**结构化步骤降级链**（extracting / summarizing 共用）：

1. **工具调用模式**（默认，`StreamConfig.toolCallingEnabled=true`）：
   - 请求体带 `tools=[kExtractKeywordsToolDefinition]` + `toolChoice=required`
   - `StreamRunner.runWithToolCall` 监听 `LlmToolCallStart` / `LlmToolCallArgs` / `LlmToolCallComplete` 事件，累积参数分片
   - `ToolCallResult.hasToolCall=true` → 解析 `arguments {entities, events}` 为 `ClassifiedKeywords`（即使为空也信任，是 LLM 有意输出）
   - `hasToolCall=false` 但有 `fallbackText` → 尝试解析为 JSON（LLM 未调工具但输出了 JSON 文本）
   - 完全无输出 → 降级到 JSON 模式
   - 工具请求被供应商 400 拒收（报文含 additionalProperties / function_declarations / invalid schema for function）→ 直接降级 JSON 模式，不按 E016 重试（确定性失败，重发同载荷必再失败）

2. **JSON 模式降级**（工具调用不支持/失败）：
   - 不注入 `tools`，纯提示词约束（`kExtractKeywordsToolPrompt` 已要求"输出的第一个字符必须是 `{`"）
   - `response_format` 不注入（降级场景下供应商通常也不支持，且提示词已强约束）
   - LLM 通过 `LlmTextDelta` 输出 JSON，累积为 `fallbackText`
   - 解析 `fallbackText` 为 `ClassifiedKeywords`，失败 → 抛 `ExtractFailedException` → 触发 E013 重试

3. **提示词约束兜底**：与 JSON 模式合并实现——同一提示词（`kExtractKeywordsToolPrompt` / `kExtractSummaryToolPrompt`）兼容工具调用与 JSON 两种输出方式（"若提供工具则调用，否则直接输出 JSON"），客户端 `parseKeywords` 容错解析（剥离 markdown 包裹 + 提取首个 `{` 到末尾 `}`）。

**reasoning_content 捕获与回传**（v2.10 新增，2026-07-24）：

DeepSeek V4 thinking 模式下，工具调用响应会携带 `reasoning_content`（思维链）。多轮工具调用场景下，调用方需将此字段回传给 API（注入到 assistant 消息的 `reasoning_content` 字段），否则 DeepSeek 返回 400 错误（`Upstream request failed`）。

- **捕获**：`StreamRunner.runWithToolCall` 监听 `LlmThinkingDelta` 事件，累积到 `thinkingBuffer`，最终注入 `ToolCallResult.reasoningContent` 字段（为空则 null，对不支持 reasoning 的模型零影响）
- **回传**：`ChatModeController._buildMessagesForApi` 构造带 `tool_calls` 的 assistant 消息时，当 `message.thinkingContent` 非空时注入 `reasoning_content` 字段
- **Intermediate 模式现状**：extracting/summarizing 均为单轮工具调用（发请求→收 tool_calls→解析参数→结束），不涉及多轮回传。但已捕获 `reasoning_content` 存入 `ToolCallResult`，为 v0.3 Agent Loop 多轮工具调用做准备
- **非流式响应**：`LlmRemoteDataSource.chat` 解析 `message.reasoning_content`，注入 `LlmResponse.reasoningContent`（详见 DOC-05-7 §8.6）
- **兼容性**：仅当模型支持 reasoning 时 `reasoningContent` 有值，其他模型为 null，不影响现有工具调用流程

**V2 关键变化**：
- 分隔标记方案（`<<<KEYWORDS>>>` / `<<<EVENT_SUMMARY>>>`）已删除——文本步骤无需结构化，结构化步骤独立请求
- `IncrementalJsonParser` 流式 JSON 显示不再使用——结构化步骤无流式显示（解析完成后一次性更新 state），文本步骤用 `runPlainText` 直接流式显示
- `jsonFallback` / `injectResponseFormat` / `_modeDowngraded` / `_responseFormatDowngraded` 等 V1 降级标志已废弃（旧配置项保留 `@Deprecated` 供 `fromJson` 兼容）
- 错误码迁移：E011（drafting 格式错误）/ E015（revising 格式错误）不再产生；格式错误由 E013（extracting）/ E017（summarizing）覆盖
- `LlmRequest` 新增 `tools` / `toolChoice` 字段；`LlmStreamEvent` 新增 `LlmToolCallStart` / `LlmToolCallArgs` / `LlmToolCallComplete` 事件（详见 DOC-05）

> **V1 历史方案（已废弃）**：下方 §6.9.1–§6.9.6 描述的是 V1 两步生成时代的分隔标记 + JSON 兜底方案（`jsonFallback` / `injectResponseFormat` / `_modeDowngraded` / `_responseFormatDowngraded` / `IncrementalJsonParser` / `stream_marker_parser` 等），V2 四步重构后不再使用。保留供历史参考与向后兼容字段说明。

#### 6.9.1 三层容错架构

| 层级 | 机制 | 覆盖场景 | 实现位置 |
|------|------|---------|---------|
| L1 供应商能力探测 | 按 baseUrl 探测供应商，决定注入哪种 `response_format` | OpenAI → `json_schema` strict；DeepSeek/OpenRouter → `json_object`；未知 → 不注入（纯提示词） | `LlmCapabilities.detectJsonSupport` |
| L2 客户端解析容错 | 字段名漂移修复 + 类型转换 + 列表型字段字符串切分 | `draft_text`→`draft`、`importance:"3"`→`3`、`keywords:"古碑,后山"`→`["古碑","后山"]` | `stream_marker_parser.dart` 的 `_readWithAliases`/`_coerceNonEmptyString`/`_coerceImportance`/`_coerceStringList` |
| L3 重试兜底 | L1+L2 均失败后，带"严格 JSON 输出"提示重新请求 1 次 | LLM 完全输出非 JSON 或关键字段缺失 | §6.2「JSON 解析失败」行 |

#### 6.9.2 字段容错规则

| 字段类型 | 容错策略 | 理由 |
|---------|---------|------|
| 文本型（draft/reply/summary） | 仅接受 String；num/bool/null → null（判失败） | 强转 `123`→`"123"` 对用户无意义，宁可重试也不展示无意义内容 |
| 列表型（keywords/tags） | List 取 String 元素；String 按中英文逗号切分 | LLM 常误写 `"keywords":"古碑,后山"`，切分能挽救已提取的关键词 |
| 数值型（importance） | int/double/String 互转，clamp 到 [1,5] | `"3"`→`3`、`3.5`→`3`，避免类型严格导致重试 |

#### 6.9.3 流式 JSON 显示（IncrementalJsonParser）

**原问题**：JSON 模式下 LLM 把 draft/reply 包在 JSON 字符串值中，客户端必须等完整 JSON 收完才能解析显示，用户看到空白直到完成，体验差。

**解决**：`IncrementalJsonParser.extractStringField` 流式增量提取 JSON 字符串字段值。Controller 在 `_runLlmStream` 中每收到一个 chunk 就提取当前字段值，计算与上次差值作为增量 delta 调用 `onDelta`，实现 JSON 模式下的实时流式显示。

**容错处理**：流式末尾恰是反斜杠时丢弃此次累积（避免误判转义）；不完整 `\uXXXX` 返回已累积部分。

#### 6.9.4 配置开关

`StreamConfig`（`intermediate_config.dart` + `default_config.json`）两个开关，默认均为 `true`：

| 开关 | 默认 | 作用 |
|------|------|------|
| `jsonFallback` | true | 启用 JSON 兜底模式（请求 LLM 输出完整 JSON 而非标记分隔格式） |
| `injectResponseFormat` | true | 启用 L1 供应商能力探测 + response_format 注入 |

> 两个开关独立，可单独关闭。`jsonFallback=false` 时走原标记分隔格式（`<<<KEYWORDS>>>`）；`injectResponseFormat=false` 时不注入 response_format（纯提示词，兼容不支持 JSON Mode 的供应商）。

#### 6.9.5 降级链路完善（2026-07-08）

**原问题**：初版的 400 降级只移除 `response_format` 参数，但提示词仍是 JSON 兜底版（要求纯 JSON 输出）。国产模型/未知供应商在无 `response_format` 约束时几乎必然失败（加 markdown 包裹、说明文字、字段名漂移），导致 JSON 模式"形存实亡"。此外，第二轮起 LLM 输出格式不稳定（即便供应商已知、response_format 正常注入），草稿 JSON 解析失败后仍按原 JSON 模式重试，重试仍大概率失败。

**修复策略**：在 `_runDraftPhase` / `_runRevisePhase` 中，jsonFallback 计算改为：

```dart
final supportLevel = LlmCapabilities.detectJsonSupport(baseUrl: ...);
final useMarkerMode = _modeDowngraded ||
    _responseFormatDowngraded ||
    supportLevel == JsonSupportLevel.none;
final jsonFallback = configJsonFallback && !useMarkerMode;
```

- **400 降级**（`_responseFormatDowngraded=true`）→ 强制分隔标记模式
- **未知供应商**（`supportLevel==none`）→ 强制分隔标记模式
- **格式解析失败降级**（`_modeDowngraded=true`，E011/E015 首次重试触发）→ 强制分隔标记模式
- **已知供应商 + 无格式失败**（OpenAI/DeepSeek/OpenRouter）→ 尊重 `configJsonFallback` 配置

**设计理由**：分隔标记模式（正文+标记+简单 JSON）对国产模型更友好——正文部分不受格式约束，仅 JSON 载荷需要解析。配合 §6.9.6 的提取容错，最大化"跑通"概率。

**E011/E015 分级重试策略**（`_scheduleRetry` 中实现，与 `_jsonFormatRetry` 配合）：

| 重试次数 | 设置字段 | 行为 | 理由 |
|---------|---------|------|------|
| retryCount == 1（首次重试） | `_modeDowngraded=true` | 降级到分隔标记模式 | 对 LLM 格式要求更宽松，最大化跑通概率 |
| retryCount >= 2（二次重试） | `_jsonFormatRetry=true` | 追加严格格式提示 | 分隔标记模式 + 明确格式要求双保险 |

- `_modeDowngraded` 在整轮内保持（`_resetPhaseState` 不清空），降级成功后修正阶段也走分隔标记模式（草稿降级 → 修正降级，保持一致）
- 每轮开始（`_prepareAndRunRound`）重置为 false
- `_strictFormatReminder` 的文案根据 `markerMode` 参数（= useMarkerMode）选择：降级模式下用分隔标记格式提醒，否则用 JSON 格式提醒。避免降级后仍输出 JSON 模式文案误导 LLM

#### 6.9.6 JSON 提取容错增强（2026-07-08）

**新增两个工具函数**（`stream_marker_parser.dart`）：

| 函数 | 作用 | 应用场景 |
|------|------|---------|
| `_preprocessJson` | 剥离 markdown 包裹 + 提取嵌入的 JSON 对象/数组 | 应用到全部 5 个 parse 函数开头，处理 LLM 输出的 ```` ```json {...} ``` ```` 包裹或"以下是结果：{...}"格式 |
| `extractJsonFromMixed` | 从混合文本（正文+JSON）分离正文与 JSON | 分隔标记模式下标记未找到时的兜底，提取最后一个合法 JSON 对象/数组 |

**分隔标记模式兜底流程**（draft / revise compact / revise full 三处分支统一）：

```
1. result.jsonPayload != null → 标记找到，正常解析
2. result.jsonPayload == null → 标记未找到
   → extractJsonFromMixed(result.displayText) 尝试提取
   → 成功：jsonPayload = extracted.json, displayText = extracted.textBefore
   → 失败：E011/E015 格式错误
```

**`_preprocessJson` 处理顺序**（fast path 优先，正常合法 JSON 零额外开销）：
1. trim 后首字符是 `{`/`[` → 尝试直接 jsonDecode（fast path）
2. 剥离 markdown 代码块包裹 → 尝试解析
3. 提取第一个 `{` 到最后一个 `}`（JSON 对象）
4. 提取第一个 `[` 到最后一个 `]`（JSON 数组）
5. 全部失败 → 返回原文本（让调用方的 jsonDecode 抛 FormatException）

### 6.10 keywords 分类结构与提示词优化（2026-07-08；V2 修订 2026-07-10）

**背景**：原 keywords 为扁平字符串数组（如 `["古碑","后山"]`），LLM 倾向提取泛化词（"勇者"、"对话"），检索精准度不足。为此 keywords 改为分类结构 + 深度优化提示词，提升关键词质量和检索精准度。

> **V2 四步重构修订**（2026-07-10）：
> - **产出步骤迁移**：keywords 从 drafting（V1 两步生成时草稿附带关键词）迁移到 **extracting**（V2 独立请求2）。drafting 现仅输出纯文本草稿，关键词由 `ExtractPhaseHandler` 调用 `kExtractKeywordsToolPrompt` 独立提取。
> - **提示词常量迁移**：V1 的 `intermediate_prompts.dart` 6 个常量（`kDraftSuffixPrompt` / `kDraftSuffixPromptJson` / `kReviseSuffixPrompt` / `kReviseSuffixPromptJson` / `kCompactReviseSuffixPrompt` / `kCompactReviseSuffixPromptJson`）标注 `@Deprecated`。V2 改用 `intermediate_prompts_v2.dart`：`kDraftSuffixPromptV2`（纯文本草稿）、`kReviseSuffixPromptV2`（纯文本修正）、`kExtractKeywordsToolPrompt` + `kExtractKeywordsToolDefinition`（关键词工具调用）、`kExtractSummaryToolPrompt` + `kExtractSummaryToolDefinition`（摘要工具调用）。
> - **Schema 迁移**：V1 的 `IntermediateJsonSchemas.draft`（keywords 嵌套对象）被 `kExtractKeywordsToolDefinition`（ToolDefinition，`additionalProperties: false` 满足 OpenAI strict 模式）替代。drafting/revise 不再有 JSON Schema（纯文本输出）。
> - **ClassifiedKeywords 数据结构不变**：仍分 entities/events 两类，层级职责（Domain 用 `ClassifiedKeywords?`、Presentation/Persistence 用 `List<String>` 经 `.flatten()` 转换）保持不变。`parseKeywords` 仍由 `ExtractPhaseHandler` 调用（解析工具调用 fallbackText 或 JSON 模式输出）。
> - **向后兼容不变**：`parseKeywords` / `_coerceClassifiedKeywords` 仍兼容三种输入格式（新对象 / 旧数组 / 字符串切分）。

#### 6.10.1 ClassifiedKeywords 数据结构

新增 `lib/features/story_runtime/domain/entities/classified_keywords.dart`：keywords 分为 entities（人/物/地，稳定世界元素）+ events（动作/情节，动态剧情元素）两类，提供 `flatten()` 扁平化方法、`isEmpty`/`isNotEmpty`/`length` getter。

**层级职责**（关键设计决策）：
- **Domain 层**（`_RoundContext.keywords`）：`ClassifiedKeywords?`，保留分类信息供分路检索
- **Presentation 层**（`state.draftKeywords`）：保持 `List<String>?`，通过 `.flatten()` 转换（UI 仅展示扁平列表）
- **持久化层**（`IntermediateRoundArtifacts.draftKeywords`）：保持 `List<String>`，通过 `.flatten()` 转换（数据库存 JSON 数组）

> ClassifiedKeywords 是 Domain 层检索概念，不泄漏到 Presentation/Persistence 层，避免类型变更波及 UI 和数据库 schema。

#### 6.10.2 JSON Schema 更新

`IntermediateJsonSchemas.draft` 的 keywords 从字符串数组改为嵌套对象：

```json
{"draft":"...","keywords":{"entities":["古碑"],"events":["碑文显现"]}}
```

`revise` / `compactRevise` schema 不变（summary/importance/tags 结构未改）。

**summarizing schema 已改为 5W1E 多字段**（2026-07-19）：
- V2 原始 schema：`{summary, tags, importance, event_ended}`（单字段 summary）
- 方案二新 schema：`{what(必填), when?, where?, who?, significance?, extra?, summary?(可选), tags, importance, event_ended}`
- 由 `kExtractSummaryToolDefinition` 的 `parameters` 定义：
  - `what` 必填（type=string，核心事件动宾短语）
  - `when` / `where` / `who` / `significance` / `extra` / `summary` 可选（type=string，缺失输出 null 或省略字段）
  - `tags` 必填（type=array, items=string）
  - `importance` 必填（type=integer, min=1, max=5）
  - `event_ended` 必填（type=boolean）
  - `required = ['what', 'tags', 'importance', 'event_ended']`（注意 `summary` 不在 required 中，降级为可选）
- `additionalProperties: false`（满足 OpenAI strict 模式）
- 向后兼容：`parseEventSummary` / `_parseSummaryFromArguments` 检测旧格式（仅有 `summary` 无 `what`）时，自动用 `summary` 反填 `what`，旧持久化数据可正常读取

#### 6.10.3 提示词优化要点

`lib/core/config/intermediate_prompts.dart` 6 个常量全部更新：

| 提示词 | 优化点 |
|--------|--------|
| `kDraftSuffixPrompt` / `kDraftSuffixPromptJson` | keywords 改为 `{entities, events}` 分类结构；Few-shot 正反例（entities 用具体名词、events 用动宾短语）；禁止把 keywords 输出为数组 |
| `kReviseSuffixPrompt` / `kReviseSuffixPromptJson` | summary 改为节点式（聚焦"发生了什么变化"，附正反例）；importance 精细化刻度（1=无变化/2=微小推进/3=剧情推进/4=重要发展/5=关键转折，每级附判断标准）；禁止 summary 写成纯描述 |
| `kCompactReviseSuffixPrompt` / `kCompactReviseSuffixPromptJson` | 同上 importance/summary 优化 |

**`kExtractSummaryToolPrompt` / `kExtractSummaryToolDefinition` 5W1E 改造**（2026-07-19，位于 `lib/core/config/intermediate_prompts_v2.dart`）：

| 提示词 / 定义 | 5W1E 改造要点 |
|--------------|--------------|
| `kExtractSummaryToolPrompt` | 重写为 5W1E 多字段提取——(1) 6 字段说明（what/when/where/who/significance/extra 各字段语义与示例）；(2) 通用性原则（5W1E 是结构化记忆载体而非回复正文格式约束，缺失字段宁可省略不硬凑，what 必填保证最小可检索单元）；(3) JSON 输出示例（含 5W1E 字段齐全样例 + 缺字段样例）；(4) 旧 `summary` 字段标记为可选并向后兼容说明 |
| `kExtractSummaryToolDefinition` | `parameters` 改为 5W1E 多字段——`what` 必填、`when`/`where`/`who`/`significance`/`extra`/`summary` 可选；`required = ['what', 'tags', 'importance', 'event_ended']`（`summary` 移出 required，降级为可选）；`additionalProperties: false` 保持 OpenAI strict 模式兼容 |

#### 6.10.4 向后兼容

`parseKeywords` / `_coerceClassifiedKeywords` 兼容三种输入格式：
- 新对象 `{entities, events}` → 直接解析（新格式，strict 模式产出）
- 旧数组 `["古碑"]` → 全部归入 entities（兼容非 strict 模式 / 旧持久化数据）
- 字符串 `"古碑,后山"` → 切分后归入 entities（容错）

**分路检索设计**：检索阶段按分路执行——entities 走 FTS5 加权（精确匹配稳定实体）、events 走 Vector 加权（语义匹配动态情节）。
