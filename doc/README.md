# LMStory 文档地图与维护规则

本文档用于回答两个问题：某份材料描述的是「当前实现」还是「历史过程」，以及出现冲突时应该相信什么。

## 权威顺序

当代码、Wiki 和文档不一致时，按以下顺序判断：

1. 当前可执行代码、数据库 Schema、配置解析逻辑，以及已同步到当前 API 的测试。
2. 日期更近、且明确标为现行的设计决策。
3. 较早的设计文档与实施计划。

代码优先。修正代码后，必须在同一变更中同步维护中的设计文档、术语字典和应用内用户 Wiki。测试若仍引用已经删除或重命名的 API，应先修正测试，不能用过时测试推翻当前实现。

## 目录属性

| 目录 | 属性 | 使用方式 |
|---|---|---|
| `product/` | 项目定位 | 项目的定位、边界与能力现状；对外表述以此为准 |
| `design/` | 维护中的设计与明确归档的旧方案 | 先查看文档顶部状态；现行章节必须与代码一致 |
| `design/vX.Y.Z/` | 按版本号归档的小功能/新功能设计 | 小功能不占全局编号，落入对应版本子目录（如 `design/v0.2.3/`、`design/v0.3.0/`） |
| `glossary/` | 维护中的术语字典 | 用户文案、Wiki、代码命名变更时同步更新 |

根目录的 `README.md`、`README.en.md`、`CLAUDE.md`、贡献与安全文件是仓库入口文档。

## 提交前一致性检查

代码修改完成后，对照以下清单检查受影响文档：

- 模式、阶段、实体类型、配置字段是否使用术语字典中的当前名称。
- 数据表、字段、索引和 `schemaVersion` 是否与 `app_database.dart` 一致。
- 「计划中」「已实现」「已废弃」是否明确区分。
- 每一种宣称支持的语言是否确实有对应翻译资源并可在 UI 中选择。
- 协议/供应商是否有可工作的适配器；枚举占位不能写成已支持。
- 相对链接、文件路径和命令是否仍有效。
- 变更 i18n 后运行 `dart run slang`，并确认 YAML 与生成文件一致。
